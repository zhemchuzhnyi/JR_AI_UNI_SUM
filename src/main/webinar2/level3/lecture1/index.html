От prompting к task spec

Claude Code

3 уровень · 1 лекция
В чате можно говорить «поправь тут» или «сделай поаккуратнее». Claude Code работает с файлами, командами и Git, поэтому расплывчатость здесь стоит дорого: агент добирает недостающие решения сам, и изменение расползается за границы задачи. Task spec превращает просьбу в инженерную постановку.

«Сделай нормально» — это не задача

Фраза «Добавь заметки к возврату» понятна человеку с бизнес-контекстом, но Claude за ней видит пачку недосказанных решений: поле только на форме или ещё в базе? Показывать в карточке? Передавать в событии refund.created? Можно ли «заодно» подправить соседний код?

Это «заодно» — helpful overreach: самодеятельность за границами задачи, которую потом хочется откатить.

Плохо:
Добавь notes к возврату.

Лучше:
Добавь необязательное поле notes в сценарий создания refund-request
в админке. Поле должно сохраняться вместе с возвратом и отображаться
в карточке возврата. Не меняй пороги auto/manual approval.
Покажи изменённые файлы и итоговый diff.

Пример из вебинара для нового проекта: плохо — «сделай калькулятор, кто сколько должен в ресторане»; лучше — «собери страницу „делим счёт“: компания вводит итог чека и число людей, каждый видит свою сумму. Аккаунты, историю чеков и деление по позициям не делай».

Расплывчатый prompt → Claude додумывает → изменение расползается → вы разбираете diff, желая одно поле, а получая мини-реформу модуля возвратов.

Что такое task spec

Task spec (engineering task specification) — короткая спецификация задачи для coding agent. Это не трактат на сорок страниц, а рабочий договор между вами и Claude: что именно меняем, зачем, где проходят границы и какой результат считается правильным.

TASK_SPEC.md — это просто рабочий markdown-файл рядом с задачей, а не отдельная команда или фича Claude Code. Его можно вести в репозитории, в тикете или прямо в сообщении.

Аналогия из лекции: «сделайте мне кухню поуютнее» — пожелание; «заменить столешницу, не трогать проводку, сохранить старую мойку, закончить к пятнице» — инженерная постановка.

CLAUDE.md

Общие правила проекта: команды запуска, стиль, повторяющиеся ограничения, принятые подходы.

TASK_SPEC.md

Правила и границы одной конкретной задачи: что делаем сейчас и чего сейчас не делаем.

Правило «в этом проекте не добавляем зависимости без обсуждения» — в CLAUDE.md. Правило «в этой задаче не трогаем пороги approval» — в task spec. Хороший issue в трекере и хороший task spec похожи: оба отвечают на базовые вопросы, разница только в адресате — issue помогает команде, task spec помогает Claude выполнить задачу без лишних фантазий.

Восемь вопросов, которые держат задачу в рамках

  1. Что меняем? — не даёт задаче остаться формулировкой «сделай лучше».
  2. Зачем меняем? — не даёт оптимизировать не то поведение и не для того пользователя.
  3. Где меняем? — сужает поисковую область и не даёт бесконечно бродить по репозиторию.
  4. Что входит в scope? — ограничивает файлы, модули, сценарии и изменения.
  5. Что не входит? — защищает от helpful overreach и «раз уж я здесь, ещё вот это поправлю».
  6. Какие ограничения действуют? — защищает API, зависимости, чувствительные зоны и размер diff.
  7. Как проверим результат? — не даёт закончить на фразе «вроде готово».
  8. Какой артефакт нужен на выходе? — уточняет, что нужно: анализ, план, код, тесты, документация или готовый diff.

Последний вопрос новички часто забывают. Если артефакт не назван, Claude снова начинает додумывать. Из восьми вопросов собирают компактный каркас: Goal → Current behavior → Desired behavior → Scope → Non-goals → Affected area → Constraints.

Tiny spec и full spec: размер по риску

Tiny spec

Один-два файла, низкий риск, почти нет неясности, обычно без чувствительных зон. Нужно точечное изменение.

Full spec

Несколько файлов или слоёв, средний или высокий риск, скрытые решения, возможны API, БД, события и бизнес-правила.

Tiny spec — не халтура, а компактная постановка для действительно маленькой задачи:

Исправить подпись `Refund requset` на `Refund request`
в заголовке формы возврата в админке.
Ничего кроме текста заголовка не менять.
На выходе нужен небольшой diff в одном файле.

Full spec нужен, когда задача затрагивает несколько мест и легко может зацепить соседнюю логику:

Добавить необязательное поле `notes` в сценарий создания refund-request.
Поле должно быть доступно оператору в админке, сохраняться вместе с возвратом
и отображаться в карточке возврата. Не менять текущие пороги auto/manual approval.
Нужен reviewable diff с изменениями в форме, сохранении данных и связанных тестах.

Tiny spec подходит, когда вы почти не рискуете. Full spec нужен, когда Claude может сделать что-то разумное, но не то: такие ошибки обходятся дороже всего — они выглядят полезными, пока вы не дойдёте до diff.

От raw issue к task spec

Пример из Commerce OS — задача F-03: Add notes field to refund-request:

F-03: Добавить поле notes в refund-request

Операторам нужна свободная заметка при создании refund-request из админки.
Заметка должна быть видна финансовым ревьюерам позже.
Включить заметку в payload события `refund.created`.
Существующие пороги approval должны остаться без изменений.

Для команды issue уже неплохое: понятна бизнес-цель, ожидаемый эффект и одно ограничение. Но coding agent работает буквально — если не назвать зону изменений, границы, формат результата и способ проверки, он снова начнёт додумывать.

В issue уже есть

  • бизнес-смысл задачи;
  • нужное поведение;
  • одно важное ограничение;
  • контекст для команды.

В task spec нужно добавить

  • где именно предполагаются изменения;
  • что входит в scope, а что нет;
  • технические границы и запреты;
  • формат ожидаемого результата для Claude.

Issue отвечает на вопрос «зачем задача нужна бизнесу и команде», task spec — «как Claude должен работать с ней в репозитории». Вы не переписываете issue ради красивого Markdown, а переводите человеческое описание в инженерную форму, пригодную для coding agent.

Первый TASK_SPEC.md draft для Commerce OS

# TASK_SPEC.md

## Что меняем
Добавляем необязательное поле `notes` в сценарий создания `refund-request`
в административной части Commerce OS.

## Зачем
Оператору нужен способ передать контекст по возврату, чтобы финансовый
ревьюер позже видел причину и детали решения прямо в карточке возврата.

## Где меняем
Предположительно затронуты: форма создания возврата в админке, backend-flow
создания возврата, хранение данных возврата, карточка возврата и событие
`refund.created`.

## Что входит в scope
Поле в форме, сохранение значения, отображение в detail view,
передача поля в `refund.created`, обновление связанных тестов.

## Что не входит
Не меняем thresholds для auto/manual approval, не трогаем payment processing,
не делаем refactor соседнего кода «заодно», не меняем unrelated formatting.

## Какие ограничения действуют
Не добавлять новые зависимости без явной необходимости.
Diff должен оставаться небольшим и reviewable.
Если по схеме хранения есть неясность, сначала вернуть краткий план, а не править вслепую.

## Как проверяем
Показать список изменённых файлов.
Подтвердить, что `notes` сохраняется, отображается и попадает в событие.
Запустить связанные тесты и сообщить об оставшихся рисках.

## Какой артефакт ожидаем
Небольшой reviewable diff + обновлённые тесты по затронутому сценарию.

Последние два раздела — скорее пометки, чем полноценные блоки: проверка напоминает, что задача не кончается словом «готово», но слой критериев приёмки здесь ещё не разворачивается; артефакт уточняет формат ответа — план, анализ или reviewable diff.

Тон меняется: нет «сделай хорошо» — есть зона работы, бизнес-смысл, запреты, ожидания и формат результата. Задача не стала простой, но стала управляемой.

Здесь prompt перестаёт быть просто prompt — он становится task spec.

Что запомнить

  • Расплывчатый prompt → Claude додумывает → изменение расползается → дорогой diff.
  • Task spec — короткий рабочий договор: что, зачем, где, scope, non-goals, ограничения, проверка, артефакт.
  • CLAUDE.md — общие правила проекта; TASK_SPEC.md — границы одной задачи.
  • Размер спецификации выбирайте по риску: tiny spec для маленькой задачи, full spec — когда легко зацепить соседнюю логику.
  • Issue отвечает «зачем бизнесу», task spec — «как Claude должен работать в репозитории».

Практика (15–25 минут)

Цель: Превратить расплывчатый запрос в tiny spec и full spec.

Что сделать

  1. Возьмите фразу «улучши экран возвратов» и письменно ответьте на восемь вопросов task spec.
  2. Составьте tiny spec для замены Refund requset на Refund request: один файл, без изменения теста, с командой проверки.
  3. Составьте full spec для добавления поля notes: goal, scope, non-goals, constraints, affected area и проверка.
  4. Отметьте, какие строки защищают от helpful overreach и «раз уж я здесь».

Если Claude Code недоступен: выполните доступную часть шагов вручную в редакторе и терминале; недоступные команды разберите по документации. Критерии проверки те же.

Проверка

  • Tiny spec действительно помещается в один файл и содержит проверку.
  • Full spec явно называет non-goals и constraints.
  • Вы можете объяснить, какой из восьми вопросов защищает от расползания.
Размер спецификации выбирайте по риску задачи: tiny spec для маленькой правки, full spec — когда легко зацепить соседнюю логику. Issue отвечает «зачем бизнесу», task spec — «как Claude должен работать в репозитории».
