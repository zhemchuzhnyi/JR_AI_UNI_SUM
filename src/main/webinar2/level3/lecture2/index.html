Проверяемый целевой результат: Goal

Claude Code

3 уровень · 2 лекция
Task spec держится на блоке Goal. Если цели нет, Current behavior превращается в набор наблюдений, Scope — в список мест, а Constraints — в запреты без ответа «ради чего». Цель нужна не для красоты формулировки, а чтобы результат можно было проверить.

«Сделай лучше» — не цель

Одну и ту же фразу можно понять по-разному: «добавить поле заметки», «переделать экран возвратов», «отрефакторить три компонента». Claude тоже выберет своё.

Слабо: «улучшить refund-request»

Неясно, что считать улучшением. Сильно: разрешить оператору добавлять заметку при создании refund-request.

Слабо: «сделать удобнее возвраты»

Нет наблюдаемого результата. Сильно: показывать заметку оператора в карточке возврата для финансового аудита.

Слабо: «доработать форму»

Непонятно, кто пользователь и что меняется. Сильно: оператор может ввести необязательный комментарий до 1000 символов и сохранить его вместе с возвратом.

Сильные формулировки не длиннее — они делают результат наблюдаемым: глазами, тестом, API-ответом, поведением интерфейса. «Сделать лучше» так не проверить — остаётся только кивать на diff в 47 файлов.

Даже у tiny spec цель проверяема: не «пофиксить текст», а «исправить подпись Refnd на Refund в заголовке карточки возврата; остальное не меняется».

Хороший goal делает результат наблюдаемым, а не описывает намерение «сделать хорошо».

Из чего собирается хороший goal

Четыре элемента:

Кто получает изменение

Оператор, менеджер, администратор, пользователь API, иногда сам разработчик.

Что становится возможным

Какое поведение меняется и что теперь можно сделать или увидеть.

Где виден результат

Форма, карточка, API-ответ, событие, документация.

Что не должно сломаться

Стабилизатор: ещё не non-goals, но уже защита от расползания.

Формула:

Хороший goal = кто получает изменение + какое поведение меняется +
где это проявляется + что не должно случайно измениться

На примере F-03 из Commerce OS:

  • Пользователь: оператор поддержки и финансовый ревьюер.
  • Изменение: можно добавлять и видеть заметку к возврату.
  • Проявление: форма, детали возврата, событие.
  • Стабилизатор: порог ручного/авто-аппрува остаётся прежним.

Пример цели для нового проекта из вебинара: «Компания в ресторане вводит итог чека и число людей — каждый видит свою сумму. Работает в браузере, без установки».

Цель описывает поведение, а не решение. «Создать колонку notes, обновить DTO, сервис и событие» — это реализация. Если цель понятна только знающему архитектуру, описаны внутренности, а не результат.

Goal зависит от типа задачи

Новая функциональность

Новое наблюдаемое поведение: «оператор может добавить заметку к запросу на возврат».

Исправление бага

Дефект исчез и корректное поведение подтверждено: «пагинация больше не возвращает дубли на второй странице».

Рефакторинг

Внешнее поведение сохранено, структура улучшена: «упростить логику валидации возврата без изменения публичного поведения».

Тесты

Появился проверяемый защитный сценарий: regression test для порога ручного подтверждения.

Документация

Точное и запускаемое описание: описание refund.created совпадает с текущим payload.

Исследование

Выводы с доказательствами, а не код: есть ли поддержка заметок в схеме и какие consumers затронуты.

Шаг миграции

Подтверждённая совместимость и проверяемый переход: сборка на целевой версии и smoke-check без регрессии.

Новый проект

Минимальный работающий каркас, который можно запустить и проверить: страница «делим счёт».

Для bugfix плохая цель — «починить заказы»; хорошая — «после перехода на вторую страницу нет дублей, сортировка прежняя». Для investigation код не обещают вовсе. А «добавить», «починить», «отрефакторить» и «обновить README» в одной цели — это несколько задач, которым тесно в одном Goal.

F-03: от идеи к рабочей цели

Самая слабая версия — только идея:

## Цель

Добавить поле notes в refund-request.

Чуть лучше — появились роль и действие, но наблюдаемости мало:

## Цель

Разрешить оператору добавлять поле notes при создании refund-request.

Рабочая версия:

## Цель

Разрешить оператору добавлять необязательное поле `notes` при создании
refund-request в административном интерфейсе. Заметка должна сохраняться
вместе с записью возврата, отображаться в деталях возврата и попадать в
payload события `refund.created`, чтобы финансовый ревьюер видел контекст
решения при последующем аудите. Текущая логика порогов авто- и ручного
подтверждения возврата не меняется.

Теперь это инженерный ориентир: видно, для кого изменение, поле сохраняется, отображается и участвует в событии, понятна бизнес-причина — аудит. Последняя фраза про пороги защищает от расползания: Claude не решит «раз уж мы в refund flow, заодно подчистим бизнес-логику».

Goal vs решение, scope и пожелание

Цель

«Оператор может добавить заметку к возврату» — описывает наблюдаемое поведение.

Scope

«Изменения затрагивают admin UI, refund detail и event payload» — границы поверхности, а не результат.

Ограничение

«Не менять approval thresholds и PSP integration» — правило выполнения, а не цель.

Решение / реализация

«Добавить колонку notes, обновить DTO и сервис» — способ достижения результата.

Пожелание

«Сделать возвраты удобнее» — нет проверяемого поведения.

Правило: goal отвечает на вопрос «что станет true после задачи?» — не «как придём» и не «какие файлы тронем». Если вы представляете код, а не поведение, — перескочили в реализацию.

Проверка: прочитайте Goal тому, кто не открывал репозиторий. Понял, что изменится для пользователя или системы, — цель неплоха. Спрашивает «где, в каком сервисе, что считается успехом?» — формулировка рыхлая.

Заполняем Goal в TASK_SPEC.md

Мини-шаблон:

## Цель

[Кто] должен получить возможность [что сделать / какой результат увидеть].
Изменение должно проявляться в [где именно это видно].
Успех задачи означает, что [2–3 наблюдаемых признака результата].
При этом [что не должно непреднамеренно измениться].

Черновик для Commerce OS:

# TASK_SPEC.md

## Цель

Разрешить оператору добавлять необязательное поле `notes` при создании
refund-request в административном интерфейсе. Заметка должна сохраняться
вместе с записью возврата, отображаться в деталях возврата и попадать в
payload события `refund.created`, чтобы финансовый ревьюер видел контекст
решения при последующем аудите. Текущая логика порогов авто- и ручного
подтверждения возврата не меняется.

По такой цели легко спросить: «Сделано — что я увижу?» Ответ конкретный: поле в форме, заметку в деталях возврата, её же в событии — и не увижу внезапно изменённую логику подтверждения.

Чем точнее цель, тем меньше у Claude пространства импровизировать.

Практика (15–25 минут)

Цель: Написать проверяемые Goal для фичи, багфикса и рефакторинга.

Что сделать

  1. Выберите три задачи: добавить заметку, исправить дубли пагинации, упростить валидацию возврата.
  2. Для каждой напишите Goal из четырёх элементов: кто, какое поведение, где видно, что не должно сломаться.
  3. Для рефакторинга используйте формулировку «упростить … без изменения публичного поведения».
  4. Проверьте каждый Goal вопросом «Сделано — что я увижу?» и уберите технические решения.

Проверка

  • В каждом Goal есть все четыре элемента.
  • Goal для рефакторинга сохраняет внешнее поведение.
  • В Goal нет списка файлов и внутренних деталей реализации.
Goal — проверяемый результат, а не пожелание. Хороший goal: кто + какое поведение + где видно + что не должно сломаться. Цель описывает поведение, а не реализацию.
