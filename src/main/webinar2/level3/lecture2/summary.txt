# Саммари лекции 2

## Проверяемый целевой результат: Goal — Claude Code, 3 уровень

Task spec держится на блоке Goal. Если цели нет, остальное висит в воздухе: Current behavior превращается в набор наблюдений, Scope — в список мест, Constraints — в запреты без ответа «ради чего». Проблема «сделай лучше» не в краткости, а в отсутствии проверяемого результата: непонятно, кто получит улучшение, что изменится, где это проявится и как понять, что готово.

## «Сделай лучше» — не цель

Одну и ту же фразу можно понять по-разному: «добавить поле заметки», «переделать экран возвратов», «отрефакторить три компонента». Claude тоже выберет своё.

| Слабая формулировка | Почему слабая | Сильная формулировка |
|---|---|---|
| Улучшить refund-request | Неясно, что считать улучшением | Разрешить оператору добавлять заметку при создании refund-request |
| Сделать удобнее возвраты | Нет наблюдаемого результата | Показывать заметку оператора в карточке возврата для финансового аудита |
| Доработать форму | Непонятно, кто пользователь и что меняется | Оператор может ввести необязательный комментарий до 1000 символов и сохранить его вместе с возвратом |

Сильные формулировки не длиннее — они делают результат наблюдаемым: глазами, тестом, API-ответом, поведением интерфейса. «Сделать лучше» так не проверить — остаётся только кивать на diff в 47 файлов. Даже у tiny spec цель проверяема: не «пофиксить текст», а «исправить подпись `Refnd` на `Refund` в заголовке карточки возврата; остальное не меняется».

## Из чего собирается хороший goal

Четыре элемента:

1. **Кто получает изменение** — оператор, менеджер, администратор, пользователь API, иногда сам разработчик.
2. **Что становится возможным или иным** — какое поведение меняется.
3. **Где виден результат** — форма, карточка, API-ответ, событие, документация.
4. **Что не должно случайно сломаться** — стабилизатор, ещё не non-goals, но уже защита от расползания.

Формула:

```
Хороший goal = кто получает изменение + какое поведение меняется +
где это проявляется + что не должно случайно измениться
```

Пример F-03 из Commerce OS:

| Компонент цели | Вопрос | Пример для F-03 |
|---|---|---|
| Пользователь изменения | Кто это почувствует? | Оператор поддержки и финансовый ревьюер |
| Изменение поведения | Что становится возможным? | Добавлять и видеть заметку к возврату |
| Точка проявления | Где видно результат? | В форме, в деталях возврата, в событии |
| Стабилизатор | Что не должно сломаться? | Порог ручного/авто-аппрува остаётся прежним |

Пример цели для нового проекта из вебинара: «Компания в ресторане вводит итог чека и число людей — каждый видит свою сумму. Работает в браузере, без установки».

Цель описывает поведение, а не решение. «Создать колонку `notes` в refunds, обновить `RefundRequestDto`, изменить `RefundService` и `RefundCreatedEvent`» — это реализация. Цель читают ревьюер, аналитик, тимлид и вы сами через три дня; если понятно только знающему архитектуру — описаны внутренности, а не результат.

## Goal зависит от типа задачи

| Тип задачи | Что считается хорошей целью | Пример |
|---|---|---|
| Новая функциональность | Новое наблюдаемое поведение | Оператор может добавить заметку к запросу на возврат |
| Исправление бага | Исчезновение дефекта + подтверждение корректного поведения | Пагинация заказов больше не возвращает дубли на второй странице |
| Рефакторинг | Сохранение внешнего поведения при улучшении структуры | Упростить логику валидации возврата без изменения публичного поведения |
| Тесты | Появление проверяемого защитного сценария | Добавить regression test для порога ручного подтверждения возврата |
| Документация | Точное и запускаемое описание поведения | Обновить описание `refund.created` так, чтобы оно совпадало с текущим payload |
| Исследование | Выводы с доказательствами, а не код | Определить, есть ли поддержка заметок в схеме БД и какие consumers затрагивает изменение |
| Шаг миграции | Подтверждённая совместимость и проверяемый переход | Сервис собирается на целевой версии, smoke-check возврата проходит без регрессии |
| Новый проект | Минимальный работающий каркас, который можно запустить и проверить | Страница «делим счёт»: итог чека и число людей, каждый видит свою сумму |

Для bugfix плохая цель — «починить заказы»; хорошая — «после перехода на вторую страницу нет дублей, сортировка прежняя». Для investigation код не обещают вовсе: цель — ответ с доказательствами. А «добавить», «починить», «отрефакторить» и «обновить README» в одной цели — это несколько задач, которым тесно в одном Goal.

## F-03: от идеи к рабочей цели

Самая слабая версия:

```
## Цель

Добавить поле notes в refund-request.
```

Только идея: кто пользуется, где появится, сохраняется ли, чего нельзя сломать — неизвестно.

Чуть лучше:

```
## Цель

Разрешить оператору добавлять поле notes при создании refund-request.
```

Роль и действие появились, но наблюдаемости мало: поле есть в форме, но не сохранилось в базе — фраза формально выполнена; или сохранилось, но невидимо ревьюеру.

Рабочая версия:

```
## Цель

Разрешить оператору добавлять необязательное поле `notes` при создании
refund-request в административном интерфейсе. Заметка должна сохраняться
вместе с записью возврата, отображаться в деталях возврата и попадать в
payload события `refund.created`, чтобы финансовый ревьюер видел контекст
решения при последующем аудите. Текущая логика порогов авто- и ручного
подтверждения возврата не меняется.
```

Теперь это инженерный ориентир: видно, для кого изменение, поле сохраняется, отображается и участвует в событии, понятна бизнес-причина — аудит. Последняя фраза про пороги защищает от расползания: Claude не решит «раз уж мы в refund flow, заодно подчистим бизнес-логику».

## Goal vs решение, scope и пожелание

| Формулировка | Что это на самом деле | Почему |
|---|---|---|
| Оператор может добавить заметку к возврату | Цель | Описывает наблюдаемое поведение |
| Изменения затрагивают admin UI, refund detail и event payload | Scope | Это границы поверхности, а не результат |
| Не менять approval thresholds и PSP integration | Ограничение | Правило выполнения, а не цель |
| Добавить колонку notes в refunds, обновить DTO и сервис | Решение / реализация | Способ достижения результата |
| Сделать возвраты удобнее | Пожелание | Нет проверяемого поведения |

Правило: goal отвечает на вопрос «что станет true после задачи?» — не «как придём» и не «какие файлы тронем». Если вы представляете код, а не поведение, — перескочили в реализацию. Проверка: прочитайте Goal тому, кто не открывал репозиторий. Понял, что изменится для пользователя или системы, — цель неплоха. Спрашивает «где, в каком сервисе, что считается успехом?» — формулировка рыхлая.

## Заполняем Goal в TASK_SPEC.md

Мини-шаблон:

```
## Цель

[Кто] должен получить возможность [что сделать / какой результат увидеть].
Изменение должно проявляться в [где именно это видно].
Успех задачи означает, что [2–3 наблюдаемых признака результата].
При этом [что не должно непреднамеренно измениться].
```

Черновик для Commerce OS:

```
# TASK_SPEC.md

## Цель

Разрешить оператору добавлять необязательное поле `notes` при создании
refund-request в административном интерфейсе. Заметка должна сохраняться
вместе с записью возврата, отображаться в деталях возврата и попадать в
payload события `refund.created`, чтобы финансовый ревьюер видел контекст
решения при последующем аудите. Текущая логика порогов авто- и ручного
подтверждения возврата не меняется.
```

По такой цели легко спросить: «Сделано — что я увижу?» Ответ конкретный: поле в форме, заметку в деталях возврата, её же в событии — и не увижу внезапно изменённую логику подтверждения.

## Что запомнить

- Goal — проверяемый результат, а не пожелание «сделай лучше».
- Хороший goal: кто + какое поведение + где видно + что не должно сломаться.
- Цель описывает поведение, а не реализацию.
- Тип задачи определяет вид цели: фича, багфикс, рефакторинг, тесты, документация, исследование, миграция.
- Goal отвечает «что станет true после задачи?», а не «какие файлы тронем».
- Чем точнее цель, тем меньше пространства для импровизации Claude.

## Практика (15–25 минут)

**Цель:** Написать проверяемые Goal для фичи, багфикса и рефакторинга.

**Что сделать:**
1. Выберите три задачи: добавить заметку, исправить дубли пагинации, упростить валидацию возврата.
2. Для каждой напишите Goal из четырёх элементов: кто, какое поведение, где видно, что не должно сломаться.
3. Для рефакторинга используйте формулировку «упростить … без изменения публичного поведения».
4. Проверьте каждый Goal вопросом «Сделано — что я увижу?» и уберите технические решения.

**Если Claude Code недоступен:** выполните доступную часть шагов вручную в редакторе и терминале; недоступные команды разберите по документации. Критерии проверки те же.

**Проверка:**
- В каждом Goal есть все четыре элемента.
- Goal для рефакторинга сохраняет внешнее поведение.
- В Goal нет списка файлов и внутренних деталей реализации.
