Prompt iteration и анти-паттерны

Claude Code

4 уровень · лекция 5
Рабочая постановка задачи созревает ко второй-третьей версии. Claude interview pattern помогает найти пробелы до кода, а implementation начинается в новой чистой сессии.

Постановка не с первой попытки

Идеальный запрос с первого раза и безупречный diff в ответ — миф. Рабочая постановка задачи созревает ко второй-третьей версии. Это не слабость: значит, задача настоящая, а не учебная загадка на три строки.

В Commerce OS возвраты на сумму больше 100 долларов уходят в автообработку, хотя по бизнес-правилам должны ждать ручного подтверждения оператором.

Плохо:

Сделай нормальную обработку возвратов в Commerce OS.

Чуть лучше:

Исправь сценарий, при котором возвраты свыше 100 долларов
уходят в автообработку без ручного подтверждения.

Второй вариант описывает наблюдаемую проблему, но и он не финал. Дальше вылезают вопросы:

  • порог 100 долларов — жёсткое правило или настройка?
  • кто подтверждает возврат: оператор, менеджер, финансовый администратор?
  • менять только серверную логику или ещё показывать в UI статус «ожидает подтверждения»?
  • что делать с уже созданными возвратами «между мирами»?
  • нужна ли обратная совместимость для API?

Итерация — не бюрократия, а инженерная работа: идея проблемы → сужение → отделение фактов от предположений → ограничения и проверки. На выходе — рабочий контракт между вами, Claude и кодовой базой.

Если задача трогает больше одного файла, меняет заметное поведение или пахнет деньгами, доступами, конфигом — первая формулировка будет черновиком.

Claude interview pattern

Задача не умещается в один прозрачный запрос — не пишите сразу полный TASK_SPEC.md. Используйте Claude interview pattern: вы приносите рабочую заготовку, Claude вопросами вытаскивает недостающие детали. На первом шаге он не пишет код — он технический интервьюер.

Короткое описание проблемы
→ Claude задаёт уточняющие вопросы
→ вы отвечаете и сужаете границы
→ собирается финальный TASK_SPEC.md
→ новая чистая сессия на implementation
ШагЧто происходитЗачем это нужно
1Вы даёте краткое описание задачиЧтобы не писать огромную spec вслепую
2Claude задаёт уточняющие вопросыЧтобы найти пробелы в scope, constraints и verification
3Вы отвечаете фактами, а не ощущениямиЧтобы гипотезы не стали ложными «истинами»
4Из ответов собирается финальная specЧтобы implementation стартовал на понятной базе
5Работа начинается в новой сессииЧтобы не тащить в кодовую фазу черновой шум

Пример:

Вы: В Commerce OS возвраты свыше 100 долларов иногда уходят
в автообработку. Не редактируй код. Сначала задай вопросы,
которых тебе не хватает для task spec.

Claude: 1) Где сейчас проверяется сумма возврата?
2) Порог 100 долларов жёстко задан или приходит из настройки?
3) Нужно ли блокировать только автообработку или и ручное создание тоже?
4) Какой статус должен видеть оператор в UI?
5) Что считается успешной проверкой после фикса?

Claude вытаскивает неочевидное, и не только про код: настройки, UX, границы поведения, верификацию. После ответов spec крепнет: порог лежит в конфиге refund.autoApprovalThreshold, схему базы не трогаем, публичный API не меняем, оператор видит статус «ожидает ручного подтверждения».

Claude помогает сформулировать задачу, но не утверждает её — это делаете вы. Лишний вопрос отбрасываете, недостающий риск добавляете сами.

Признак, что pattern сработал: текста не больше — неопределённости меньше.

Вопросы работают в обе стороны

Спрашивать должен не только Claude, но и вы. Если не знаете подход или сомневаетесь, задайте вопрос прямо в сессии: Claude объяснит незнакомое место, предложит варианты и поможет довести формулировку до рабочей. Не гадайте молча и не откладывайте вопрос до implementation.

Implementation — старт в новой сессии

Раунд вопросов прошёл, контекст тёплый — тянет тут же попросить Claude писать код. Здесь начинается болото. Сборка spec и реализация — две разные фазы, и жить им полезно отдельно.

Пока вы обсуждали задачу, в контексте осели черновые гипотезы, отброшенные варианты, старые допущения. Для вас это мышление. Для модели — рабочий материал, который она продолжает учитывать. Так рождается загрязнённая сессия.

Сессия 1: refund-approval-spec
Результат:
- TASK_SPEC.md
- EVIDENCE_LOG.md

Сессия 2: refund-approval-implementation
Вход:
- финальный TASK_SPEC.md
- подтверждённый пакет доказательств

Три выигрыша:

  1. Implementation стартует на чистом контракте, а не на полутора десятках сообщений.
  2. Сломалось — spec не теряется, живёт отдельным артефактом.
  3. Следующему человеку не нужно перечитывать весь диалог, чтобы отличить финальную мысль от вчерашней догадки.

Перед выходом из сессии, где собирали spec, попросите Claude написать стартовый промпт для новой сессии: цель, путь к спецификации, важные решения и ограничения. Так новая сессия стартует быстрее и получает нужный контекст без мусора обсуждения.

ПризнакЧто это обычно означает
Claude ссылается на старую гипотезу, которую вы уже отбросилиВ контексте осталось слишком много чернового шума
Он предлагает исправлять сразу несколько несвязанных вещейScope начал расплываться
Вы сами уже не уверены, что в этой сессии финальное, а что временноеПора фиксировать spec отдельно
После каждого нового сообщения diff становится только ширеImplementation идёт без опоры на контракт

Новая сессия — не потеря прогресса, а способ сохранить здравый смысл. Длинная беседа без чёткой границы работает против вас.

Анти-паттерны prompting

Анти-паттерн — это не только плохая фраза. Чаще ломается поведение: запрос вежливый, а процесс выстроен так, что задача обречена на хаотичный diff и слабую приёмку. Это повторяющиеся сбои workflow.

Анти-паттернЧто ломаетсяЧем заменить
Fix everything / «почини всё»Claude сам выбирает scope и почти всегда расширяет егоДать одну проблему, границы и non-goals
Нет критериев приёмкиНепонятно, по чему принимать результатОписать наблюдаемое поведение до implementation
Нет плана проверкиПроверка превращается в импровизацию после diffСпроектировать проверки заранее
Feature + refactor в одном diffНельзя понять, что именно сломалось или улучшилосьРазнести на две отдельные задачи
«Claude said it works»Решение принимается по уверенности текста, а не по доказательствамЧитать diff, запускать checks, сверять с готовностью задачи
Продолжение polluted sessionСтарые гипотезы продолжают влиять на implementationЗавершить spec, открыть fresh session

Fix everything для Commerce OS опасен: возвраты, заказы, поддержка и платежи выглядят связанными, и Claude заодно «подчистит» сервис, DTO, UI-статусы и пару тестов в соседнем модуле. Итог — огромный diff.

«Claude said it works» означает одно: модель сформулировала уверенное предложение на естественном языке. Diff себя не прочитал, тесты себя не интерпретировали, границы никто не проверил. Уверенный тон — не доказательство.

Финальный шаблон Task Spec

Теперь у вас есть всё для финального шаблона, который не стыдно отдать Claude, коллеге и себе завтра. Это рабочий контракт, не бумажка для порядка.

Верх шаблона — Цель и желаемый результат, Текущее поведение и желаемое, Границы задачи, Ограничения — был нужен и раньше. Сегодня добавляем фактическую базу, критерии приёмки, план проверки, готовность задачи и ожидаемый workflow:

# TASK_SPEC.md

## Цель и желаемый результат
## Текущее поведение и желаемое
## Границы задачи (scope и non-goals)
## Ограничения и границы изменений
## Пакет доказательств (краткая выжимка + ссылка на EVIDENCE_LOG.md, если он вынесен отдельно)
## Критерии приёмки
## План проверки
## Готовность задачи
## Ожидаемый workflow
## Ожидаемый артефакт

За каждой строкой — работа:

  • верхние секции защищают задачу от расползания и «полезного, но опасного» overreach;
  • пакет доказательств привязывает её к фактам; если полный журнал в EVIDENCE_LOG.md, здесь хватит выжимки и ссылки;
  • критерии приёмки, план проверки и готовность задачи заранее отвечают, по чему принимаете результат;
  • ожидаемый workflow напоминает маршрут для нетривиальной задачи: Explore → Plan → Implement → Verify → Review → Commit/PR;
  • ожидаемый артефакт фиксирует, что хотите на выходе: анализ, diff, tests, документацию или изменение под ревью.

Заполните шаблон под Commerce OS — и абстракция станет рабочей вещью. Открываете его в новой сессии: «Вот утверждённая spec. Работай только в этих границах. Упрёшься в противоречие — остановись и задай вопрос».

Взрослая позиция не в длине документа, а в том, что главные инженерные решения приняты заранее: что меняем, чего не меняем, как проверяем и когда задача готова.

Пример из вебинара: TASK_SPEC для сплита

# TASK_SPEC.md

## Цель и желаемый результат
Компания в ресторане вводит итог чека и число людей -
каждый видит свою сумму. Работает в браузере, без установки.

## Текущее поведение и желаемое
Проекта ещё нет, repo пустой. Нужна первая версия: одна страница.

## Границы задачи (scope и non-goals)
Одна страница, делим итог чека поровну.
Non-goals: аккаунты, история чеков, деление по позициям заказа.

## Ограничения и границы изменений
Без бэкенда и без фреймворков: один HTML-файл.

## Пакет доказательств
Контрольный чек: итог 1000, компания из трёх человек.

## Критерии приёмки
Сумма долей равна итогу чека - копейка в копейку.
Чаевые задаются процентом и входят в делёж.
Лишняя копейка округления достаётся первой доле, это видно на странице.
Пустые поля или ноль человек - расчёта нет, есть подсказка.

## План проверки
Прогнать контрольный чек: 1000 на троих, с чаевыми и без.
Проверить пустые поля и компанию из одного человека.

## Готовность задачи
Страница открывается двойным кликом, суммы сходятся,
diff прочитан до merge.

## Ожидаемый workflow
Сначала план, после подтверждения - реализация по шагам.

## Ожидаемый артефакт
Один HTML-файл и короткое описание, как проверить.

Что запомнить

  • Первая формулировка задачи — черновик; рабочая spec рождается после вопросов и уточнений.
  • Claude interview pattern: сначала вопросы без кода, потом финальный TASK_SPEC.md.
  • Implementation запускается в новой чистой сессии, а не в загрязнённой обсуждением.
  • Анти-паттерны — это сбои процесса: «почини всё», отсутствие критериев и плана проверки, смешение feature и refactor, доверие «Claude said it works», продолжение polluted session.
  • Задача прошла вопросы и сбор spec — значит, заслуживает чистого старта на реализации.
  • Финальный TASK_SPEC.md — рабочий контракт: цель, текущее/желаемое, границы, ограничения, evidence, критерии, проверка, готовность, workflow, артефакт.

Практика (15–25 минут)

Цель: провести Claude interview и собрать черновик TASK_SPEC.md для задачи с возвратами.

Что сделать

  1. Возьмите короткую постановку: «Возвраты свыше 100 долларов уходят в автообработку без ручного подтверждения». Не пишите полный spec сразу.
  2. Попросите Claude: «Не редактируй код. Задай вопросы, которых тебе не хватает для task spec».
  3. Ответьте фактами: где проверяется сумма, откуда берётся порог, кто подтверждает, какой статус видит оператор, что считать успешной проверкой. Используйте только вымышленные данные.
  4. Соберите черновик TASK_SPEC.md по финальному шаблону из лекции.
  5. Найдите в своей формулировке хотя бы один анти-паттерн из таблицы и перепишите его.
  6. Сформулируйте стартовый промпт для новой сессии implementation: путь к spec, границы, запрет выходить за них, остановка при противоречии.

Проверка

  • Claude задавал вопросы, а не сразу писал код.
  • В spec есть цель, границы, ограничения, критерии приёмки, план проверки и готовность.
  • Указан хотя бы один анти-паттерн и его замена.
  • Есть отдельный стартовый промпт для новой сессии.
  • Вы можете объяснить, почему implementation нельзя продолжать в сессии обсуждения.
