От skill к plugin

Claude Code

10 уровень · лекция 1
Plugin — не «skill на максималках». Skill отвечает за процедуру, plugin — за её доставку, версионирование и установку. Сначала workflow должен доказать пользу локально, и только потом его стоит упаковывать.

1. Plugin стоит в конце лестницы, а не в начале

После skills легко решить, что plugin — следующий обязательный уровень. На практике он появляется позже: когда workflow стал стабильным и его нужно передавать другим.

СлойНа какой вопрос отвечаетКогда нужен
PromptЧто сделать прямо сейчас?Разовая задача
CLAUDE.md / rulesКак принято работать в проекте?Постоянные правила
SkillКак повторять процедуру без импровизации?Повторяющийся workflow
PluginКак доставить workflow другим?Команда или несколько репозиториев

Skill — единица поведения: одна процедура, SKILL.md, при необходимости scripts и references. Plugin — упаковка вокруг умений: манифест, версия, namespace и содержимое.

Plugin не делает skill умнее. Он делает workflow доставляемым, устанавливаемым и версионируемым.

Если рецепт ещё меняется каждый день, упаковывать его рано: красивый ящик не исправит хаос внутри.

2. Когда .claude/ достаточно

Внутри одного репозитория .claude/ часто закрывает задачу целиком. Это нормальное решение, пока workflow нужен только вам, завязан на структуру проекта и активно меняется.

Например, issue-analysis для Commerce OS может спокойно жить в .claude/skills/: он превращает issue в TASK_SPEC.md и не претендует на универсальность. Если его используете только вы и никто не просит «скинь это по-человечески», plugin добавит только версии, README и namespace.

Преждевременная упаковка выглядит как зрелость, но добавляет вторую задачу — распространение — до того, как решена первая — польза.

3. Сигналы, что workflow дорос до plugin

Смотреть нужно не на ощущение продвинутости, а на конкретные признаки:

  • один и тот же набор нужен в нескольких репозиториях;
  • skill нужен не только автору;
  • важна точная версия workflow;
  • появляются конфликты имён между наборами;
  • изменения нужно документировать и передавать;
  • skills, agents, hooks или MCP нужно поставлять вместе.

Живой сценарий: issue-analysis жил в Commerce OS, потом его захотели в CashFlow Dashboard, потом в третьем репозитории. Сначала каталог копировали руками. Через неделю версии разошлись: в одном месте новая формулировка проверки, в другом старая, в третьем локальная правка.

Plugin нужен не потому, что «мы стали взрослыми», а потому, что одну процедуру нужно доставлять в несколько мест без ручного копирования. Ещё один сигнал — вам приходится объяснять коллеге, куда что скопировать. Если установка требует созвона и ручных правок, у workflow уже есть скрытая стоимость распространения.

4. Skill, plugin и namespace

Разница короткая: skill — единица поведения, plugin — единица распространения.

Skill из plugin вызывается полным именем:

/team-kit:git-commit

team-kit — имя плагина из манифеста, git-commit — имя skill. Короткое /git-commit может сработать, если его никто не занял, но полное имя надёжнее. Два разных плагина могут принести skill commit, и namespace не даст им столкнуться.

Плагин платит длинным именем за то, что его skills не смешиваются с чужими. Это дешёвая профилактика конфликтов.

5. Экосистема плагинов

Полезно понимать классы задач, а не запоминать каталог:

  • code intelligence — LSP-плагины для навигации и ошибок типов;
  • внешние интеграции — GitHub, трекеры, дизайн через MCP;
  • code review и testing — ревью PR, помощники по тестам;
  • security — проверка изменений на типовые уязвимости;
  • dev workflows — commit, PR, создание собственных плагинов.

Официальный marketplace claude-plugins-official доступен сразу. Community-каталог добавляют отдельно:

/plugin marketplace add anthropics/claude-plugins-community
/plugin install <plugin>@claude-community

Точный состав каталогов меняется. Актуальный список открывается через /plugin, вкладку Discover, или на claude.com/plugins.

Marketplace — это каталог, а не установка. Сначала добавляете источник, потом ставите конкретный плагин. Источником может быть GitHub-репозиторий, git-URL, локальный путь или URL на marketplace.json.

Сторонние установщики иногда предлагают symlink или копию. Symlink обычно удобнее для нескольких агентов: все смотрят на один файл, обновление каталога подхватывается сразу. Копия даёт независимый снимок, но версии со временем расходятся. На Windows symlink может требовать режим разработчика или права администратора — тогда копия проще.

6. Install scopes: кому достанется плагин

У плагина те же уровни, что у настроек проекта:

ScopeКому доступенГде живёт
UserВам во всех проектахПользовательская конфигурация
ProjectВсей команде репозитория.claude/settings.json, едет в Git
LocalТолько вам в этом репозиторииЛокальные настройки
ManagedЗадаёт администраторУправляемая конфигурация

/plugin install name@marketplace открывает карточку и позволяет выбрать scope. В терминале можно указать явно:

claude plugin install name@marketplace --scope project

Без --scope установка обычно идёт в user scope. Ставьте в самый узкий подходящий scope: меньше прав и меньше неожиданностей для коллег.

7. Жизненный цикл и цена контекста

Вся работа с плагинами живёт вокруг /plugin:

  • Discover — искать плагины в подключённых marketplace;
  • Installed — включать, выключать и удалять;
  • Marketplaces — добавлять и обновлять каталоги;
  • Errors — смотреть ошибки загрузки;
  • Stats — цена skills в контексте и частота использования.

Команды: /plugin install, /plugin disable, /plugin enable, /plugin uninstall. Установка активирует плагин без рестарта; изменения из меню применяются после закрытия. Если плагин меняется вне меню, нужен /reload-plugins; при предупреждении о пересчёте контекста — /reload-plugins --force.

Плагин стоит не только денег, но и контекста:

  • каждый включённый плагин с самого старта добавляет объявления компонентов;
  • работа плагина добавляет токены на ответы, тело skill и вывод инструментов;
  • внешние сервисы и команды добавляют время;
  • /plugin показывает context cost ещё до установки, а /context — фактическое состояние.

«Поставил всё и не выключаю» — плохая стратегия. Держите активным нужное, остальное выключайте. Плагин, который давно не используется, — это занятое место в окне и лишняя стоимость каждого запроса.

8. Безопасность: плагин выполняет код с вашими правами

Плагин — не безобидная тема оформления. Он может содержать skills, agents, hooks, MCP и команды, которые выполняются на вашей машине с вашими правами.

Сначала смотрите на источник:

  • claude-plugins-official курирует Anthropic;
  • community-каталог проходит автоматическую проверку, но это не гарантия;
  • произвольный git-URL или локальный marketplace не проверяется: смотрите, кто автор и что внутри.

До установки /plugin показывает, что будет установлено и сколько примерно займёт контекст:

Will install:  skills: 12   agents: 2   hooks: 1   MCP servers: 0
Context cost:  ~1.8k tokens

Смотрите не на звёзды, а на состав, источник, контекстную цену и нужность именно вам. Если плагин приносит hooks, MCP, фоновые команды или сетевые действия, проверяйте его внимательнее. Обновление — почти новый install: состав может измениться, поэтому перед важным обновлением стоит снова просмотреть детали.

Практическое правило: узкий scope, проверенный источник и отключение плагина при странном поведении. /plugin disable и вкладка Errors помогают быстро проверить, не новый ли плагин виноват.

9. Структура плагина

Плагин — обычная папка с manifest и компонентами. Манифест лежит строго в .claude-plugin/plugin.json, а skills/, agents/, hooks/ и другие компоненты — в корне плагина.

team-kit/
  .claude-plugin/
    plugin.json
  skills/
    git-commit/
      SKILL.md
    prompt-improve/
      SKILL.md
  README.md

Типичная ошибка — положить skills/ внутрь .claude-plugin/. Плагин может загрузиться, но skills молча не найдутся. Второй источник путаницы — короткое имя: если старый standalone /git-commit остался в .claude/skills/, короткое имя попадёт в него, а не в плагин. Проверяйте полным /team-kit:git-commit.

10. Манифест plugin.json

Манифест задаёт личность плагина. Технически Claude может работать и без него, но для командного артефакта manifest обязателен: именно он стабильно задаёт имя, версию и namespace.

{
  "name": "team-kit",
  "description": "Team git-commit and prompt-improve skills",
  "version": "1.0.0",
  "author": { "name": "Platform team" }
}
  • name — идентификатор плагина и namespace его skills;
  • version — состояние артефакта; без версии непонятно, у кого какая копия. При раздаче через git забытая версия означает, что каждый коммит может считаться новой версией;
  • description — что увидят в менеджере плагинов;
  • author — атрибуция.

Полная схема может включать homepage, repository и license; набор полей зависит от версии Claude Code. Важнее не выучить все поля, а понять: упаковка должна иметь паспорт.

11. Локальная проверка и раздача

Публиковать плагин, чтобы попробовать, не нужно. Его можно загрузить прямо из папки:

claude --plugin-dir ./team-kit

Дальше проверяйте результат, а не факт загрузки: вызовите skill под namespace, посмотрите, что он отработал, и убедитесь, что действие не произошло само.

/team-kit:git-commit
# > created commit a1b2c3d  feat(api): add health endpoint

Если меняли SKILL.md, подхватите изменения через /reload-plugins. Перед раздачей полезен разовый чек:

claude plugin validate ./team-kit

Для команды рядом с плагином заводят собственный marketplace — репозиторий-каталог с .claude-plugin/marketplace.json. Коллега добавляет каталог и ставит плагин:

/plugin marketplace add ваш-логин/team-tools
/plugin install team-kit@team-tools

Здесь легко перепутать имена: слева — имя плагина, справа — имя marketplace из его name, а не имя репозитория.

Можно вообще не диктовать команды, а прописать каталог и плагин в .claude/settings.json проекта:

{
  "extraKnownMarketplaces": {
    "team-tools": {
      "source": { "source": "github", "repo": "ваш-логин/team-tools" }
    }
  },
  "enabledPlugins": {
    "team-kit@team-tools": true
  }
}

Эти поля уходят в Git, поэтому команда получает каталог и подсказку, что установить, после доверия репозиторию. Плагины из внешних источников каждый ставит себе сам.

12. Сквозной пример team-kit

В Workflow Kit уже есть два полезных skill: /git-commit и /prompt-improve. По отдельности они живут в .claude/, но команде нужны в нескольких репозиториях. Пора упаковать их в team-kit.

  1. Создаём папку team-kit/.
  2. Кладём .claude-plugin/plugin.json с именем, версией и описанием.
  3. Переносим оба skill в skills/ без изменения поведения.
  4. Добавляем README: что внутри, как поставить, как вызывать, какие границы.
  5. Проверяем локально через --plugin-dir, /reload-plugins и validate.
  6. При необходимости заводим marketplace team-tools и прописываем его в настройках проекта.

git-commit остаётся action-skill с disable-model-invocation: true: Claude не должен коммитить сам по совпадению описания. Упаковка в plugin это поведение сохраняет. prompt-improve остаётся текстовым skill и не получает лишних прав.

13. Когда плагин мешает

Плагин — не обязанность. Если после установки появились конфликты, ошибки загрузки или странное поведение сессии:

  1. Отключите свежий плагин через /plugin disable.
  2. Посмотрите Errors в /plugin.
  3. Если не нужен — /plugin uninstall.
  4. В крайнем случае проверьте кэш ~/.claude/plugins/cache и переустановите.

Сломался плагин — это рабочая ситуация. Хуже держать его включённым «на всякий случай», платить контекстом и гадать, откуда странности.

Что запомнить

  • Plugin — упаковка и доставка, а не «skill на максималках».
  • Сначала workflow должен доказать пользу локально; упаковывать хаос рано.
  • Сигналы к plugin: несколько репозиториев, другие люди, версии, конфликты имён, marketplace.
  • Namespace /plugin-name:skill-name защищает от конфликтов; имя плагина задаёт манифест.
  • Install scopes: user, project, local, managed.
  • Плагин выполняет код с вашими правами: проверяйте источник, состав и context cost.
  • Каждый активный плагин занимает контекст и время; лишнее выключайте.
  • Манифест лежит в .claude-plugin/plugin.json, компоненты — в корне плагина.
  • Локальная проверка: --plugin-dir, вызов под namespace, /reload-plugins, claude plugin validate.
  • Для команды — marketplace и extraKnownMarketplaces / enabledPlugins в настройках проекта.

Практика (15–25 минут)

Цель: собрать минимальный plugin-контейнер team-kit из двух учебных skills, проверить структуру и локальный вызов под namespace.

Что сделать

  1. В вымышленном Workflow Kit создайте папку team-kit и два крошечных skill: skills/git-commit/SKILL.md и skills/prompt-improve/SKILL.md. В каждом опишите только цель и один шаг; используйте фейковые данные.
  2. Добавьте .claude-plugin/plugin.json с name: team-kit, версией 0.1.0, коротким description и автором. Убедитесь, что skills/ лежит в корне плагина, а не внутри .claude-plugin/.
  3. Добавьте README.md: что внутри, как поставить локально, как вызвать оба skill и какие у них границы.
  4. Если Claude Code доступен, выполните claude plugin validate ./team-kit, затем claude --plugin-dir ./team-kit и вызовите /team-kit:git-commit. Если CLI недоступен, проверьте JSON, дерево папок и полное имя вызова вручную.
  5. Зафиксируйте в PLUGIN_REVIEW.md одну строку: что упаковано, каким scope вы бы поделились с командой и почему. Не добавляйте реальные ключи, секреты и боевые команды.

Если Claude Code недоступен: выполните доступную часть шагов вручную в редакторе, проверьте JSON и структуру папок; недоступные команды разберите по документации. Критерии проверки те же.

Проверка

  • plugin.json лежит в .claude-plugin/, а skills — в корне плагина.
  • В манифесте есть имя, версия и описание.
  • Оба skill вызываются под namespace /team-kit:....
  • README объясняет установку и границы без устной экскурсии.
  • Полный вызов не путается со старым standalone skill.
  • В практике только фейковые данные и нет реальных секретов.
  • Вы можете объяснить, почему этот набор пока не обязан быть публичным плагином.
