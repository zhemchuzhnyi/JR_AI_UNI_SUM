Уровень 10 — контрольные вопросы

Контрольный блок по 5 лекциям уровня 10 и практике вебинара 6: 25 открытых вопросов с короткими ответами и ссылками на конспекты. Вопросы синхронизированы с презентацией: plugin как упаковка, экосистема, scope и lifecycle, проверка перед установкой и team-ready prototype.

Лекция 1 — от skill к plugin

  1. Чем skill принципиально отличается от plugin?
    Skill — единица процедуры: одна повторяемая инструкция с входом, действиями и результатом. Plugin — единица распространения: упаковка, которая делает набор skills устанавливаемым, версионируемым и понятным другим. Plugin не добавляет поведение сам по себе.
    → Лекция 1
  2. Как выглядит лестница зрелости prompt → CLAUDE.md → skill → plugin?
    Prompt отвечает «что сделать сейчас», CLAUDE.md/rules — «как принято в проекте», skill — «как повторять процедуру», plugin — «как доставить workflow другим людям и в другие репозитории».
    → Лекция 1
  3. Когда .claude/ достаточно и не нужно упаковывать skill в plugin?
    Когда workflow нужен только вам, живёт в одном проекте, завязан на его структуру и ещё активно меняется. Если нет задачи делиться, версионировать и поддерживать пакет для других, plugin добавляет лишнюю работу.
    → Лекция 1
  4. Какие сигналы говорят, что workflow дорос до plugin?
    Набор нужен в нескольких репозиториях; skill нужен не только автору; важна версия; появляются конфликты имён; изменения нужно документировать; skills, agents, hooks или MCP нужно поставлять вместе.
    → Лекция 1
  5. Зачем plugin нужен namespace и откуда берётся его префикс?
    Namespace разводит skills из разных plugins по именам и показывает происхождение компонента. Префикс берётся из name в manifest: team-kit даёт /team-kit:git-commit. Короткое имя может сработать, если свободно, но полное надёжнее.
    → Лекция 1

Лекция 2 — экосистема и выбор

  1. Чем отличаются категория, plugin и capability surface?
    Категория — класс инженерной боли, plugin — конкретный installable package, capability surface — реальные действия, на которые plugin способен: чтение, запись, shell, hooks, сеть, credentials.
    → Лекция 2
  2. С чего лекция советует начинать выбор plugin?
    С workflow-боли, а не с названия, топа или звёзд. Сначала понять, какую работу нужно сократить, затем определить категорию, потом смотреть capability surface конкретных кандидатов.
    → Лекция 2
  3. Какие категории plugins существуют, кроме «написания кода»?
    Документация и справка, навигация по коду, память проекта и первичная настройка, развитие артефактов Workflow Kit; среди AI-инструментов — review, testing/browser, frontend/UI, refactoring, security; отдельно Git/PR, infra/delivery и командный workflow.
    → Лекция 2
  4. Какие официальные plugins лекция приводит как примеры и для каких категорий?
    Code Review — review кода; Code Simplifier — рефакторинг; frontend-design — frontend/UI; Skill Creator — мета-инструменты для skills; Superpowers — упакованная методология. Это снимок marketplace, а не обязательный набор.
    → Лекция 2
  5. Почему популярность — плохой первый фильтр при выборе plugin?
    Популярность — социальный сигнал, а не инженерный. Она не знает вашу задачу, стек, команду и ограничения, может подтолкнуть к лишнему контексту и дублированию. Популярность — довесок при равенстве, а не стартовая эвристика.
    → Лекция 2

Лекция 3 — scope и lifecycle

  1. За что отвечают permissions и scope?
    Permissions — что plugin может делать. Scope — где и для кого он существует: только у вас, в одном repo, у команды проекта или на уровне организации.
    → Лекция 3
  2. Чем отличаются user, local, project и managed scopes?
    user — только вы, во всех проектах; local — только вы в одном repo; project — командный workflow конкретного repo; managed — централизованная политика организации. Имена могут меняться между версиями.
    → Лекция 3
  3. Почему project scope — уже не личная настройка?
    Plugin привязан к repo и влияет на всех, кто работает по его workflow. Это кусок инфраструктуры команды, поэтому нужны понятный baseline, владелец, способ раскатки и отключения. Для сырого эксперимента лучше local или user.
    → Лекция 3
  4. Какие шаги входят в жизненный цикл plugin и почему update — почти новый install?
    install → activate → use → update → disable → uninstall. Update может изменить состав, поведение, права и нагрузку на контекст, поэтому перед обновлением нужно снова прочитать release notes и проверить изменения.
    → Лекция 3
  5. Чем disable отличается от uninstall и какую цену создаёт активный plugin?
    disable временно выключает plugin, но оставляет его установленным; uninstall убирает полностью. Активный plugin занимает контекст и увеличивает сложность среды, поэтому неиспользуемые пакеты лучше отключать или удалять.
    → Лекция 3

Лекция 4 — проверка перед установкой

  1. Какие три блока входят в review plugin перед установкой?
    Авторство и поддержка; capability surface; поддерживаемость — версия, changelog, owner, update и путь отката.
    → Лекция 4
  2. Почему известный автор не отменяет проверку plugin и почему внутренний plugin не безопасен по умолчанию?
    Даже у известного автора внутри могут быть hooks, shell, сеть, credentials и write-действия. Внутренние plugins часто документированы хуже внешних: README откладывают, changelog не ведут, автор может уйти. Проверять нужно сам пакет.
    → Лекция 4
  3. Что такое capability surface и какие признаки для review-плагина тревожны?
    Capability surface — реальные действия plugin, а не обещания README. Для review-workflow тревожны shell, сеть, credentials, write-действия и hooks без необходимости; обычно достаточно skills с read-only доступом к diff.
    → Лекция 4
  4. Что проверять в совместимости plugin с проектом, кроме технической установки?
    Scope, namespace и конфликты имён, оболочку и окружение, структуру repo и команды, а также дублирование с существующими skills/workflow. Хороший plugin может просто не подойти вашей команде.
    → Лекция 4
  5. Что делает plugin поддерживаемым и зачем фиксировать решение?
    Версия и changelog, понятный owner, update и disable/uninstall. Решение «ставим / не ставим», причина, ограничения и путь отката фиксируются в заметке, чтобы через месяц оно не стало легендой.
    → Лекция 4

Лекция 5 — team-ready prototype

  1. Из чего состоит минимальный team-ready plugin?
    Metadata/manifest, skills/, README, examples, CHANGELOG, compatibility notes и install instructions. В первой версии не нужны agents, hooks, MCP и shell-скрипты.
    → Лекция 5
  2. Какие три skills входят в учебный team-review-kit и какой workflow они образуют?
    issue-analysis, pr-review и project-setup: принять issue, проверить базовое состояние проекта и сделать локальный review diff перед PR.
    → Лекция 5
  3. Почему первый прототип начинают с версии 0.1.0 и зачем нужен CHANGELOG.md?
    0.1.0 честно говорит, что пакет уже можно ставить, но он ещё растёт. CHANGELOG фиксирует, что вошло в версию, и делает разговор об обновлении конкретным.
    → Лекция 5
  4. Почему README — часть архитектуры и что в него входит?
    Для коллеги plugin начинается с ответов: что это, как поставить, как вызвать и где границы. README описывает состав, установку, namespaced skills, безопасность/capability surface и ограничения. Без него пакет не готов для команды.
    → Лекция 5
  5. Как проверить, что plugin действительно team-ready, и что сознательно не кладут в первый прототип?
    Другой разработчик должен без личной экскурсии понять пакет, поставить его и использовать. В первый прототип не кладут hooks, agents, MCP и shell-скрипты: они расширяют риск и требуют отдельного разговора о правах и lifecycle.
    → Лекция 5
