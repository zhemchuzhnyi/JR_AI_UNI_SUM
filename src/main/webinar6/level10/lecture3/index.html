Установка plugin

Claude Code

10 уровень · лекция 3
Установка plugin — не кнопка, а выбор радиуса действия. Permissions отвечают за то, что plugin может делать; scope — за то, где и для кого он существует.

1. Установка — выбор радиуса действия

На словах установка почти невинна: нажали команду — получили инструмент. В workflow это решение: где plugin будет жить, кто его почувствует и как его потом выключить.

Permissions — что plugin может делать. Scope — где и для кого он существует.

Умение поставить plugin не оправдывает установку первого попавшегося пакета. Сначала категория и capability surface, потом решение о scope.

«Установлен» и «уже участвует в текущей сессии» — не всегда одно и то же. Пакет может лежать в системе, но подхватиться только после обновления списка, перезапуска сессии или повторного открытия проекта.

2. Scope: где plugin живёт и кого касается

Один и тот же team-review-kit в разных scope означает разный круг влияния.

ScopeНа кого влияетКогда уместенЧто помнить
userТолько на вас, во всех проектахЛичный workflow нужен регулярно в разных репозиторияхPlugin будет всплывать везде
localТолько на вас и только в одном repoЭксперимент или временная настройкаХорошо для проб, но не общий стандарт
projectНа конкретный repo и работающих по его workflowPlugin — часть общего workflow командыПривязка к repo; механизм хранения зависит от версии
managedНа организацию или её частьЦентрализованная политикаОбычно вы не выбираете его сами

Имена scope между версиями могут отличаться — user где-то называется personal, — но логика та же.

Самая частая путаница — user и local. Оба означают «только я», но:

  • user — инструмент в рюкзаке: носите по всем проектам;
  • local — инструмент на одном верстаке: в соседнем репозитории его нет.

Тестируете review-plugin только для Commerce OS — local разумнее user.

3. Project scope — уже не личная настройка

С project начинается взрослая жизнь. Пока plugin стоял только у вас, это было личное удобство. Как только он привязан к repo, это решение о проектном workflow и кусок общей инфраструктуры.

Команда Commerce OS решила пользоваться единым review workflow. project говорит: plugin относится к этому repo, а не ко всем вашим проектам. Где именно живёт привязка — в конфиге проекта или в состоянии менеджера plugins — зависит от реализации. Перед раскаткой проверьте справку и договоритесь, как команда будет его распространять и отключать.

Полезно зафиксировать решение:

## Plugin baseline

Плагин: team-review-kit
Scope: project
Зачем: единый review workflow для Commerce OS
Кого касается: тех, кто работает по общему plugin baseline этого repo
Как отключить: временно disable; полностью убрать project-level привязку способом, который поддерживает текущая установка

Это не бюрократия, а способ не забыть, зачем у проекта появился plugin. Иначе через месяц половина команды считает его обязательным стандартом, вторая — чьим-то экспериментом, а автор уже не помнит, с чего всё началось.

Если plugin сырой, живёт один день и нужен только вам — не спешите с project. Сначала докажите, что он нужен команде.

4. Namespace: зачем плагину «фамилия»

Пока в группе один Дима, можно просто «Дима». Появляется второй — и фамилия перестаёт быть бюрократией. С plugin так же: один review-плагин — имя review удобно; появляется второй с похожим смыслом — начинается организационный хаос.

Без namespace:

review
review

Непонятно, какой именно review вызвался, откуда он пришёл и почему вместо проверки PR вы получили советы по README.

С namespace:

review-kit:pr-review
docs-kit:review

Точный формат зависит от реализации, но идея одна: namespace добавляет skill или команде «фамилию». Конфликт имён становится заметен не тогда, когда вы пишете plugin, а когда в одном окружении живут несколько plugins.

Новичку namespace кажется избыточным: «у нас пока один plugin». Это логика «я пока один Дима, фамилия мне не нужна». Среда растёт, коллеги приносят свои инструменты, и без namespace приходится устраивать болезненную миграцию имён.

Хороший namespace не обязан звучать как название стартапа. team-review-kit, commerce-tools, docs-kit работают лучше, чем абстрактное super-ai-pro.

5. Жизненный цикл: install → use → update → uninstall

Люди часто думают только про установку, а с неё всё только начинается. Без жизненного цикла в голове копится кладбище полумёртвых расширений: что-то ставили, что-то выключали, что-то обновляли, а что активно сейчас — непонятно.

install → activate → use → update → disable → uninstall
ШагЧто значит на практике
installpackage появился в окружении
activateplugin подхватился проектом или сессией
useвы убедились, что он работает там, где ожидали
updateперешли на новую версию и заново проверили изменения
disableвременно выключили без удаления
uninstallубрали полностью

disable и uninstall путают постоянно. disable нужен, когда вы отлаживаете конфликт, сравниваете поведение «с plugin и без» или временно выключаете эксперимент. Это как вынуть батарейки из пульта, но не выбрасывать пульт. uninstall — уже «нам это больше не нужно».

Самый недооценённый шаг — update. Обновление plugin — почти новый install: может измениться состав, поведение, подсказки и нагрузка на контекст. Обновлять «автоматом, потому что цифра версии стала больше» — плохая привычка. Здоровее относиться к update как к новой версии договора: ещё раз проверить, что именно вы принимаете в workflow.

6. Practical walkthrough: реальный plugin из claude-plugins-official

Синтетический team-review-kit удобен для объяснения, но полезно пройти цикл на реальном плагине.

claude-plugins-official — поддерживаемый Anthropic каталог, доступный в Claude Code по умолчанию. Если вы ничего не настраивали, источник уже подключён.

Сначала полезно посмотреть, какие marketplace активны и что в них есть:

# Концептуально: точные команды и вывод зависят от версии Claude Code
/plugin marketplace list
/plugin marketplace add anthropics/claude-plugins-official

В большинстве случаев официальный marketplace уже в списке. Второй шаг нужен только в нестандартном setup.

Дальше — установка конкретного плагина. Возьмём code-review: категория узнаваемая, capability surface проверяемый.

# Концептуально: имена и флаги могут отличаться
/plugin install code-review --scope user
/plugin list
/plugin details code-review

details особенно ценен до запуска: видно, какие slash-команды, агенты, hooks и требования к окружению принёс пакет. Это и есть capability surface: пакет, его состав, его права.

После установки проверяем на реальной задаче. У code-review сценарий простой: переключиться на ветку с готовым PR и запустить команду.

# На ветке с готовым PR, концептуально
/code-review
/code-review --comment

Первая команда — чтение и анализ, ничего не пишется наружу. Вторая — внешнее действие, публикация комментария в PR, и требует осознанного решения. Начинать стоит с «спокойного» режима, где результат остаётся локальным.

И самое важное для дисциплины — уметь так же спокойно откатывать:

# Концептуально, последовательность отката
/plugin disable code-review
/plugin enable code-review
/plugin uninstall code-review

Это полный цикл install → activate → use → disable → uninstall. Когда вы прошли его на реальном плагине, следующий пакет перестаёт быть загадочным жителем системы.

Полезно записать короткий trial log:

## Plugin trial log

Плагин: code-review (claude-plugins-official)
Зачем пробовал: self-review перед PR
Scope: user (только мой workflow)
Результат: помог поймать пропущенную проверку null; шум на простых diff
Решение: оставляю в user scope, переводить в project пока не буду
Как откатить: /plugin disable, далее /plugin uninstall

Через две недели вы не вспомните, почему plugin установлен, в каком scope и что вы тогда решили. Маленький log избавляет от амнезии.

Команды, флаги и формат вывода могут меняться. Не запоминайте форму команды как заклинание. Запоминайте логику: marketplace → каталог → категория и capability surface → узкий scope → безопасный режим → disable/uninstall при необходимости.

7. Невидимая цена: context overhead и лишние plugins

Самое коварное в plugins то, что вред редко выглядит драматично. Компьютер не падает, экран не мигает. Чаще plugins просто понемногу засоряют среду.

Один лишний plugin — мелочь. Когда их пять, появляются странные подсказки, конфликтующие названия, более шумный контекст и ощущение, что среда стала тяжелее.

Установленный plugin — не просто файл на диске. Его описание, названия компонентов, а иногда инструкции и метаданные становятся частью рабочей среды Claude Code. У Claude нет пыльной полки «когда-нибудь пригодится»: активный plugin увеличивает сложность общей картины.

Аналогия с рюкзаком: один предмет почти не чувствуется, но если бросать туда «вдруг пригодится» и не разбирать, рюкзак становится тяжелее, а нужную вещь искать дольше.

Гигиена простая:

  • plugin больше не помогает — убирайте;
  • эксперимент закончился — не оставляйте его выключенным навсегда «на память»;
  • несколько похожих инструментов одной категории — спросите, дополняют ли они друг друга или вы коллекционируете инструменты из инженерной жадности.

Настройка набора инструментов иногда увлекает больше, чем сама работа. Plugins этим прекрасно пользуются.

8. Сквозной пример: team-review-kit в Commerce OS

У Workflow Kit есть issue-analysis и pr-review. Вы упаковали их в team-review-kit. Теперь нужно подключить plugin к Commerce OS так, чтобы он помогал, а не создавал путаницу.

СитуацияРазумный scopeПочему
Вы один тестируете pluginlocalНе засоряете другие проекты и не трогаете команду
Plugin нужен почти во всех ваших репозиторияхuserЛичный стабильный набор везде под рукой
Команда договорилась о едином review workflowprojectPlugin привязан к repo; раскатка зависит от версии
Компания централизованно раскатывает approved toolingmanagedРешение на уровне организации

Типичная история: сначала team-review-kit идёт в local Commerce OS — пару дней проверяете, помогает ли pr-review перед PR. Потом подключается второй разработчик, workflow повторяется — теперь решение можно переводить в project, фиксировать в plugin baseline и отдельно проверять, как текущая версия Claude Code хранит такой уровень и делится им.

На install-команду вы смотрите уже не как на волшебную строчку, а как на инженерное решение с тремя вопросами:

  1. Где будет жить plugin?
  2. Кто его почувствует?
  3. Как я его выключу или удалю, если эксперимент не удастся?

Если умеете честно ответить на них до запуска команды — вы перестали «просто ставить плагины» и начали работать с ними как с артефактами команды.

Что запомнить

  • Permissions отвечают за «что можно», scope — за «где и для кого».
  • user — во всех ваших проектах; local — только в одном repo; project — командный workflow repo; managed — политика организации.
  • project — уже не личная настройка, а кусок инфраструктуры команды.
  • Namespace защищает от конфликтов имён; называйте plugin понятно и стабильно.
  • Жизненный цикл: install → activate → use → update → disable → uninstall.
  • update — почти новый install: состав и поведение могут измениться.
  • Начинайте с безопасного режима без внешних действий; публикация PR-комментария — отдельное решение.
  • Каждый активный plugin занимает контекст и увеличивает сложность среды.
  • disable — временно выключить, uninstall — убрать полностью.
  • Команды и флаги меняются; логика выбора scope и lifecycle остаётся.

Практика (15–25 минут)

Цель: выбрать scope для четырёх сценариев и провести учебный plugin через полный жизненный цикл без влияния на реальный проект.

Что сделать

  1. Для вымышленного team-review-kit в Commerce OS разберите четыре ситуации: (а) вы тестируете plugin один, (б) он нужен во всех ваших репозиториях, (в) команда договорилась о едином review workflow, (г) компания централизованно раскатывает approved tooling. Запишите scope и одну причину для каждого.
  2. Создайте PLUGIN_LIFECYCLE_PLAN.md: plugin, выбранный scope, кто ощутит установку, как проверить активацию, какой безопасный режим использовать первым, как обновлять и как откатить.
  3. Если Claude Code доступен, выполните /plugin marketplace list, /plugin details code-review и установите code-review в local или user scope на учебной машине. Если нет — разберите README и manifest кандидата вручную.
  4. Пройдите или опишите цепочку install → use → disable → uninstall. Для use возьмите только безопасный режим без публикации комментария; --comment не запускайте.
  5. Добавьте Plugin trial log: зачем пробовали, scope, результат, решение и команду отката. Не используйте реальные PR, ключи и секреты.

Если Claude Code недоступен: выполните доступную часть шагов вручную в редакторе, проверьте README и manifest кандидата; недоступные команды разберите по документации. Критерии проверки те же.

Проверка

  • Для каждого из четырёх сценариев scope выбран осознанно.
  • В плане разделены «установлен» и «активирован».
  • Первый запуск не выполняет внешних действий.
  • Есть понятный путь disable и uninstall.
  • Trial log фиксирует решение и причину, а не только факт установки.
  • В практике нет реальных ключей, PR и секретов.
