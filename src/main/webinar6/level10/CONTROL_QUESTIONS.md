# Уровень 10 — контрольные вопросы

Контрольный блок по 5 лекциям уровня 10 и практике вебинара 6: 25 открытых вопросов с короткими ответами и ссылками на конспекты. Вопросы синхронизированы с презентацией: plugin как упаковка, экосистема, scope и lifecycle, проверка перед установкой и team-ready prototype.

## Лекция 1 — от skill к plugin

1. **Чем skill принципиально отличается от plugin?**<br>
   Skill — единица процедуры: одна повторяемая инструкция с входом, действиями и результатом. Plugin — единица распространения: упаковка, которая делает набор skills устанавливаемым, версионируемым и понятным другим. Plugin не добавляет поведение сам по себе.<br>
   → [Лекция 1](lecture1/index.html)

2. **Как выглядит лестница зрелости prompt → CLAUDE.md → skill → plugin?**<br>
   Prompt отвечает «что сделать сейчас», `CLAUDE.md`/rules — «как принято в проекте», skill — «как повторять процедуру», plugin — «как доставить workflow другим людям и в другие репозитории».<br>
   → [Лекция 1](lecture1/index.html)

3. **Когда `.claude/` достаточно и не нужно упаковывать skill в plugin?**<br>
   Когда workflow нужен только вам, живёт в одном проекте, завязан на его структуру и ещё активно меняется. Если нет задачи делиться, версионировать и поддерживать пакет для других, plugin добавляет лишнюю работу.<br>
   → [Лекция 1](lecture1/index.html)

4. **Какие сигналы говорят, что workflow дорос до plugin?**<br>
   Набор нужен в нескольких репозиториях; skill нужен не только автору; важна версия; появляются конфликты имён; изменения нужно документировать; skills, agents, hooks или MCP нужно поставлять вместе.<br>
   → [Лекция 1](lecture1/index.html)

5. **Зачем plugin нужен namespace и откуда берётся его префикс?**<br>
   Namespace разводит skills из разных plugins по именам и показывает происхождение компонента. Префикс берётся из `name` в manifest: `team-kit` даёт `/team-kit:git-commit`. Короткое имя может сработать, если свободно, но полное надёжнее.<br>
   → [Лекция 1](lecture1/index.html)

## Лекция 2 — экосистема и выбор

6. **Чем отличаются категория, plugin и capability surface?**<br>
   Категория — класс инженерной боли, plugin — конкретный installable package, capability surface — реальные действия, на которые plugin способен: чтение, запись, shell, hooks, сеть, credentials.<br>
   → [Лекция 2](lecture2/index.html)

7. **С чего лекция советует начинать выбор plugin?**<br>
   С workflow-боли, а не с названия, топа или звёзд. Сначала понять, какую работу нужно сократить, затем определить категорию, потом смотреть capability surface конкретных кандидатов.<br>
   → [Лекция 2](lecture2/index.html)

8. **Какие категории plugins существуют, кроме «написания кода»?**<br>
   Документация и справка, навигация по коду, память проекта и первичная настройка, развитие артефактов Workflow Kit; среди AI-инструментов — review, testing/browser, frontend/UI, refactoring, security; отдельно Git/PR, infra/delivery и командный workflow.<br>
   → [Лекция 2](lecture2/index.html)

9. **Какие официальные plugins лекция приводит как примеры и для каких категорий?**<br>
   Code Review — review кода; Code Simplifier — рефакторинг; frontend-design — frontend/UI; Skill Creator — мета-инструменты для skills; Superpowers — упакованная методология. Это снимок marketplace, а не обязательный набор.<br>
   → [Лекция 2](lecture2/index.html)

10. **Почему популярность — плохой первый фильтр при выборе plugin?**<br>
    Популярность — социальный сигнал, а не инженерный. Она не знает вашу задачу, стек, команду и ограничения, может подтолкнуть к лишнему контексту и дублированию. Популярность — довесок при равенстве, а не стартовая эвристика.<br>
    → [Лекция 2](lecture2/index.html)

## Лекция 3 — scope и lifecycle

11. **За что отвечают permissions и scope?**<br>
    Permissions — что plugin может делать. Scope — где и для кого он существует: только у вас, в одном repo, у команды проекта или на уровне организации.<br>
    → [Лекция 3](lecture3/index.html)

12. **Чем отличаются user, local, project и managed scopes?**<br>
    `user` — только вы, во всех проектах; `local` — только вы в одном repo; `project` — командный workflow конкретного repo; `managed` — централизованная политика организации. Имена могут меняться между версиями.<br>
    → [Лекция 3](lecture3/index.html)

13. **Почему project scope — уже не личная настройка?**<br>
    Plugin привязан к repo и влияет на всех, кто работает по его workflow. Это кусок инфраструктуры команды, поэтому нужны понятный baseline, владелец, способ раскатки и отключения. Для сырого эксперимента лучше `local` или `user`.<br>
    → [Лекция 3](lecture3/index.html)

14. **Какие шаги входят в жизненный цикл plugin и почему update — почти новый install?**<br>
    `install → activate → use → update → disable → uninstall`. Update может изменить состав, поведение, права и нагрузку на контекст, поэтому перед обновлением нужно снова прочитать release notes и проверить изменения.<br>
    → [Лекция 3](lecture3/index.html)

15. **Чем disable отличается от uninstall и какую цену создаёт активный plugin?**<br>
    `disable` временно выключает plugin, но оставляет его установленным; `uninstall` убирает полностью. Активный plugin занимает контекст и увеличивает сложность среды, поэтому неиспользуемые пакеты лучше отключать или удалять.<br>
    → [Лекция 3](lecture3/index.html)

## Лекция 4 — проверка перед установкой

16. **Какие три блока входят в review plugin перед установкой?**<br>
    Авторство и поддержка; capability surface; поддерживаемость — версия, changelog, owner, update и путь отката.<br>
    → [Лекция 4](lecture4/index.html)

17. **Почему известный автор не отменяет проверку plugin и почему внутренний plugin не безопасен по умолчанию?**<br>
    Даже у известного автора внутри могут быть hooks, shell, сеть, credentials и write-действия. Внутренние plugins часто документированы хуже внешних: README откладывают, changelog не ведут, автор может уйти. Проверять нужно сам пакет.<br>
    → [Лекция 4](lecture4/index.html)

18. **Что такое capability surface и какие признаки для review-плагина тревожны?**<br>
    Capability surface — реальные действия plugin, а не обещания README. Для review-workflow тревожны shell, сеть, credentials, write-действия и hooks без необходимости; обычно достаточно skills с read-only доступом к diff.<br>
    → [Лекция 4](lecture4/index.html)

19. **Что проверять в совместимости plugin с проектом, кроме технической установки?**<br>
    Scope, namespace и конфликты имён, оболочку и окружение, структуру repo и команды, а также дублирование с существующими skills/workflow. Хороший plugin может просто не подойти вашей команде.<br>
    → [Лекция 4](lecture4/index.html)

20. **Что делает plugin поддерживаемым и зачем фиксировать решение?**<br>
    Версия и changelog, понятный owner, update и disable/uninstall. Решение «ставим / не ставим», причина, ограничения и путь отката фиксируются в заметке, чтобы через месяц оно не стало легендой.<br>
    → [Лекция 4](lecture4/index.html)

## Лекция 5 — team-ready prototype

21. **Из чего состоит минимальный team-ready plugin?**<br>
    Metadata/manifest, `skills/`, README, examples, CHANGELOG, compatibility notes и install instructions. В первой версии не нужны agents, hooks, MCP и shell-скрипты.<br>
    → [Лекция 5](lecture5/index.html)

22. **Какие три skills входят в учебный team-review-kit и какой workflow они образуют?**<br>
    `issue-analysis`, `pr-review` и `project-setup`: принять issue, проверить базовое состояние проекта и сделать локальный review diff перед PR.<br>
    → [Лекция 5](lecture5/index.html)

23. **Почему первый прототип начинают с версии 0.1.0 и зачем нужен CHANGELOG.md?**<br>
    `0.1.0` честно говорит, что пакет уже можно ставить, но он ещё растёт. CHANGELOG фиксирует, что вошло в версию, и делает разговор об обновлении конкретным.<br>
    → [Лекция 5](lecture5/index.html)

24. **Почему README — часть архитектуры и что в него входит?**<br>
    Для коллеги plugin начинается с ответов: что это, как поставить, как вызвать и где границы. README описывает состав, установку, namespaced skills, безопасность/capability surface и ограничения. Без него пакет не готов для команды.<br>
    → [Лекция 5](lecture5/index.html)

25. **Как проверить, что plugin действительно team-ready, и что сознательно не кладут в первый прототип?**<br>
    Другой разработчик должен без личной экскурсии понять пакет, поставить его и использовать. В первый прототип не кладут hooks, agents, MCP и shell-скрипты: они расширяют риск и требуют отдельного разговора о правах и lifecycle.<br>
    → [Лекция 5](lecture5/index.html)
