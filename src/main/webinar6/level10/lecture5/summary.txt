# Саммари лекции 5

## Custom plugin: team-ready prototype — Claude Code, 10 уровень

## 1. Момент, когда папка становится пакетом

Пока plugin живёт только у автора, многое держится на памяти и привычке. Отдаёте его команде — этого мало: другой разработчик должен без созвона понять, что внутри, как поставить, где границы и что делать после обновления.

Skill — одна повторяемая процедура. Plugin — пакет, который делает набор таких процедур переносимым и понятным другим. Сегодня вопрос не «как написать skill», а «что должно появиться, когда workflow выходит из личной папки и становится командным артефактом».

Если коллега открывает репозиторий и не понимает, что перед ним, у вас не plugin, а аккуратно названная папка, которую все боятся трогать. Для Workflow Kit это особенно важно: мы собираем инженерный набор для подключения к проектам, а не прячем фичу внутри Commerce OS. Пакету нужны паспорт, структура и минимальный состав, проверяемый глазами.

## 2. Из чего собран минимальный team-ready plugin

После лекций про расширяемость легко переусердствовать: пять слоёв абстракции, загадочная папка core и «на будущее» ещё десять компонентов. Не надо. Минимальный plugin — небольшой читаемый пакет.

| Компонент | Простыми словами | Зачем в первой версии |
|---|---|---|
| Plugin metadata | Паспорт: имя, версия, описание, совместимость | Опознать, обновить и не перепутать с соседом |
| `skills/` | Основная полезная начинка | Ради них plugin и существует |
| `README.md` | Инструкция для людей | Что внутри, как поставить и использовать |
| `examples/` | Маленькие примеры | Понять, в каком контексте skill уместен |
| `CHANGELOG.md` | Журнал изменений | Версия — история, а не число для красоты |
| Compatibility notes | Заметки о совместимости | Не ловить сюрпризы после обновления |
| Install instructions | Короткий путь запуска | Чтобы не спрашивали: «А это куда класть?» |

В первой версии нет agents, hooks, MCP и shell-скриптов. Не потому, что они плохие, а потому, что мы собираем минимальный пакет на понятном наборе знаний, который можно проверить глазами. Первый plugin должен помогать команде, а не впечатлять соседний отдел.

Типовая структура:

```text
team-review-kit/
├── plugin.json
├── README.md
├── CHANGELOG.md
├── skills/
│   ├── issue-analysis/
│   │   └── SKILL.md
│   ├── pr-review/
│   │   └── SKILL.md
│   └── project-setup/
│       └── SKILL.md
└── examples/
    ├── issue-analysis-example.md
    └── pr-review-example.md
```

Структуру нужно уметь открыть и понять за минуту, а не за вечер. Если plugin выглядит как шкаф из мебельного магазина без инструкции — это ещё не пакет для команды.

## 3. Собираем team-review-kit из трёх знакомых skills

`team-review-kit` покрывает участок «от входящего issue до аккуратной подготовки PR»:

- `issue-analysis` — превращает сырое issue в структурированный task spec;
- `pr-review` — проверяет diff перед PR и возвращает риски с evidence;
- `project-setup` — проверяет базовое состояние Git, наличие `CLAUDE.md` и соглашения проекта.

Набор логически замкнут: не случайные skills из трёх миров, а один workflow. Manifest может выглядеть так:

```json
{
  "name": "team-review-kit",
  "version": "0.1.0",
  "description": "Командный набор skills для анализа issue и подготовки PR.",
  "namespace": "review-kit",
  "components": [
    "skills/issue-analysis",
    "skills/pr-review",
    "skills/project-setup"
  ]
}
```

Точное имя и набор полей зависят от версии Claude Code; это ориентир, а не священная табличка. Важны два поля: `name` и `namespace`. Имя `team-review-kit` сразу отсылает к командному review workflow, а namespace не даёт skills столкнуться с чужими.

Skill внутри plugin не меняет природу: у него те же назначение, ограничения и результат. Просто теперь он живёт в распространяемом наборе, поэтому описание должно быть особенно ясным.

```markdown
---
name: pr-review
description: Проверяет diff перед PR и возвращает риски с evidence.
when_to_use: Когда изменения уже сделаны и нужен локальный self-review.
allowed-tools: Read
---

Верни список рисков, спорные места в diff, недостающие проверки
и короткий итог, который можно использовать в описании PR.
```

Хороший plugin не изобретает новую физику. Он собирает рабочие куски в пакет, который легко поставить и поддерживать.

## 4. Версия, совместимость и CHANGELOG.md

Как только plugin живёт за пределами вашего ноутбука, появляется версионирование. Скучное до момента, когда один говорит «у меня работает», второй — «у меня нет», и выясняется, что у вас разные версии.

Не нужно сразу писать `1.0.0`. Молодой прототип честнее начинать с `0.1.0`: ставить уже можно, но пакет ещё растёт. Это инженерная скромность, а не слабость.

CHANGELOG.md — не хроника со времён динозавров, а короткая запись изменений:

```text
## 0.1.0

- упакованы skills issue-analysis, pr-review и project-setup
- добавлены примеры использования
- зафиксированы namespace и базовая совместимость
```

Совместимость лучше описывать честно: на каком наборе команд и менеджере plugins проверяли, что входит, чего не обещаем.

| Что фиксируем | Как записываем |
|---|---|
| Версия plugin | `0.1.0` |
| Что входит | Только skills, без agents, hooks и MCP |
| Совместимость | Проверяйте по текущей справке Claude Code |
| Ограничения | Пакет рассчитан на review workflow команды |

Заметка о совместимости — не тщеславие, а снижение удивления. Коллега видит, что plugin не обещает лишнего, и реже ждёт чудес.

## 5. README — часть архитектуры

README — не декоративный салатик сверху. Без него plugin не готов для команды даже с отличными skills: для коллеги пакет начинается не с JSON, а с ответов на три вопроса — что это, как поставить и чем оно мне грозит.

Фрагмент для первой версии:

```text
# team-review-kit

Набор skills для командного workflow: анализ issue, проверка проекта
перед началом работы и локальный review diff перед PR.

## Что входит
review-kit:issue-analysis
review-kit:pr-review
review-kit:project-setup

## Безопасность
В этой версии нет hooks, agents, MCP и shell-скриптов.
Пакет ограничен skills и рассчитан на project/user scope.
```

Здесь уже есть всё основное: что пакет делает, из чего состоит и каков capability surface. Нет hooks, внешних подключений и скриптов — хорошая новость, напишите её прямо.

Блок установки должен быть практичным, без ложной вечности: «устанавливается через текущий менеджер plugins в user или project scope; после установки доступны такие-то namespaced skills». Точные команды меняются, логика остаётся.

Простой тест: если коллега не может поставить и использовать plugin без личного сообщения в мессенджер, README ещё не готов. Не драма — повод дописать два абзаца и пример.

## 6. Что сознательно не входит в первый прототип

После лекций про расширяемость трудно удержаться и не положить в plugin «ещё чуть-чуть полезного». Потом ещё. И ещё. В прототипе появляется hook, полуготовый агент, внешний сервис и скрипт, который автор «потом почистит». Спойлер: не почистит.

| Здоровый первый plugin | Переусердствовавший вариант |
|---|---|
| 2–3 понятных skills | 9 разнородных компонентов «на будущее» |
| Ясный README | «Ну там по коду всё понятно» |
| Честная версия `0.1.0` | Сразу гордое `1.0.0` |
| Нет скрытых automation-слоёв | Внезапные hooks и shell-скрипты |
| Один понятный workflow | Попытка решить полжизни команды сразу |

Agents, hooks и внешние инструменты расширяют поверхность риска и требуют отдельного разговора о правах, событиях, изоляции контекста и lifecycle. Включите их раньше, чем команда готова, — и аккуратный пакет станет тревожным. Тревожный plugin ставят один раз, а потом тихо обходят.

Готовый для команды не значит готовый для всех. Первый пакет не обязан решать проблемы всех команд и репозиториев. Хороший старт — узкий понятный пакет под один workflow; здесь это review и подготовка issue-to-PR.

## 7. Секунда, когда plugin становится командным

Самый честный тест прототипа — встреча с другим разработчиком, который не сидел рядом и не слышал пояснений.

Сценарий: коллега открывает Workflow Kit, видит `team-review-kit`, читает README и за пару минут понимает три вещи:

1. пакет анализирует issue, проверяет базовое состояние проекта и делает локальный review diff;
2. в первой версии он безопасен и ограничен skills;
3. у него внятная версия и короткая история изменений.

Дальше коллега ставит plugin в подходящий scope, вызывает namespaced skill, получает результат — и не спрашивает, что означает половина файлов. В эту секунду plugin перестаёт быть личной магией и становится командным инструментом.

Но до раскатки он проходит тот же взрослый фильтр, что внешний кандидат: владелец, capability surface, README, версия, путь отключения и осознанный scope. То, что вы собрали plugin сами, не делает его автоматически безопасным или подходящим для `project`.

Архитектура здесь не для доклада на конференции, а для того, чтобы другой человек взял артефакт и работал без лишнего трения. Минимальный прототип удался не потому, что в нём много всего, а потому, что в нём ровно столько, сколько нужно.

## 8. Чеклист team-ready прототипа

Перед передачей пакета команде проверьте:

- имя и namespace понятны без расшифровки;
- в manifest есть версия, описание и состав;
- skills лежат в `skills/`, а не внутри `.claude-plugin/`;
- README отвечает: что это, как поставить, как вызвать, где границы;
- есть 2–3 примера использования;
- CHANGELOG объясняет, что вошло в версию;
- compatibility notes честно говорят, что проверено;
- в первой версии нет лишних hooks, agents, MCP и shell-скриптов;
- есть владелец и путь disable/uninstall;
- коллега может пройти путь без личной переписки с автором.

## Что запомнить

- Plugin — пакет для передачи workflow, а не личная папка с красивым именем.
- Минимальный team-ready набор: metadata, skills, README, examples, CHANGELOG, compatibility notes, install instructions.
- `team-review-kit` собирает три знакомых skill в один workflow: issue → setup → PR review.
- Manifest задаёт имя, версию, описание, namespace и состав.
- Начинайте с `0.1.0`: версия — история, а не украшение.
- README — часть архитектуры; без него пакет не готов для команды.
- Не кладите в первый прототип hooks, agents, MCP и shell-скрипты без отдельной причины.
- Узкий пакет под один workflow лучше «plugin обо всём».
- Проверка team-ready — другой разработчик понял, поставил и использовал без личной экскурсии.
- Свой plugin тоже проходит проверку capability surface, scope и пути отката.

## Практика (15–25 минут)

**Цель:** собрать минимальный team-ready manifest и документацию для `team-review-kit`, не добавляя лишних компонентов.

**Что сделать:**
1. В вымышленном Workflow Kit создайте `team-review-kit/` с тремя учебными skill: `issue-analysis`, `pr-review`, `project-setup`. В каждом `SKILL.md` опишите только цель, вход и результат; используйте фейковые данные.
2. Добавьте `plugin.json` с именем, версией `0.1.0`, описанием, namespace `review-kit` и списком трёх components.
3. Добавьте `README.md` с блоками «что входит», «как поставить», «безопасность» и «границы». Укажите, что hooks, agents, MCP и shell-скриптов нет.
4. Добавьте `CHANGELOG.md` на одну запись и `examples/` с двумя короткими примерами использования namespaced skills.
5. Проверьте пакет глазами коллеги: структура, manifest, README, примеры, версия и отсутствие лишних компонентов. Если Claude Code доступен, проверьте JSON и структуру командой валидации; если нет — вручную.

**Проверка:**
- В manifest есть имя, версия, описание, namespace и components.
- Skills лежат в `skills/`, а не внутри `.claude-plugin/`.
- README объясняет установку, использование, границы и отсутствие опасных компонентов.
- Есть CHANGELOG и минимум два примера.
- В первой версии нет hooks, agents, MCP и shell-скриптов.
- Коллега может понять пакет без личной экскурсии.
- В практике нет реальных ключей, секретов и боевых репозиториев.
