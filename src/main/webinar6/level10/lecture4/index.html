Проверка plugin

Claude Code

10 уровень · лекция 4
Plugin — чемодан возможностей, а не безобидная заметка. Перед установкой проверяем три блока: кто автор, что plugin реально может и что будет с ним через месяц.

1. Plugin — это чемодан, а не заметка

После первого plugin легко расслабиться: «Это же просто подсказки для Claude, что тут может пойти не так?» Много чего. Plugin почти никогда не бывает просто текстом: снаружи красиво подписан, внутри может лежать аккуратная отвёртка — или бензопила.

Установка — не жест симпатии, а решение пустить в рабочий процесс новый пакет возможностей. В прошлой лекции была механика: install, update, scope, lifecycle. Она не отвечает на главный вопрос: нужно ли ставить этот пакет вообще.

БлокГлавный вопросЧто проверяем
АвторствоКто это сделал?Доверие к источнику и поддержке
ВозможностиЧто plugin реально умеет?Capability surface и необходимые права
ПоддерживаемостьЧто будет потом?Обновление, отключение, откат, судьба после ухода автора

Схема не зависит от версии Claude Code. Команды, имена полей и метаданные могут меняться, а логика остаётся: сначала источник, потом границы возможностей, потом жизнь после установки.

Нужен новый plugin
  → проверить источник и автора
  → проверить возможности и права
  → проверить совместимость с проектом
  → проверить обновление и путь отката
  → риск оправдан? да → установить в нужный scope
                      нет → не устанавливать

2. Кто отвечает за plugin завтра утром

На этом шаге легко удариться в одну из крайностей: доверять всему, что лежит в marketplace, или подозревать каждый plugin в краже ноутбука. Нужна не наивность и не страх, а спокойная проверка происхождения.

Первый вопрос: если plugin сломается завтра утром, вы понимаете, кто за него отвечает? Для внутреннего plugin ответ конкретен: репозиторий, владелец из tooling-команды, канал поддержки. Для внешнего хочется видеть репозиторий, автора, лицензию, историю релизов и признаки живого проекта.

Минимум метаданных выглядит примерно так:

{
  "name": "team-review-kit",
  "version": "0.1.0",
  "author": "internal-tooling-team",
  "license": "MIT",
  "namespace": "review-kit"
}

Имя, версия, автор, лицензия, namespace — уже признаки оформленного артефакта, а не «папки с чем-то полезным на моей машине». Качество это не доказывает, но даёт опору для проверки.

Известный автор снижает риск происхождения, но не отменяет проверку самого plugin. Даже у уважаемого автора внутри могут быть hooks, shell-скрипты, сетевые вызовы и широкие права. Имя на обложке — повод читать внимательнее, а не переставать читать.

Внутренние plugins не безопасны по умолчанию. Внутреннее часто документировано хуже внешнего: README отложили, changelog не завели, автор ушёл в отпуск или на другой проект. Получается полезная, но загадочная коробка без инструкции.

3. Capability surface: не что обещает, а что может

Самая важная часть review. Capability surface — суммарный набор действий, на которые plugin способен в вашем проекте. Не то, что он обещает, а то, что реально может сделать после установки.

Два skill-компонента как структурированные подсказки без автодействий — один риск. Hooks, shell-скрипты, доступ к внешним данным, сетевые запросы, credentials и write-действия — совсем другой разговор.

Что внутри pluginЧто это означает для риска
Только skillsОбычно низкий риск, если они не тянут лишние инструменты
Shell-скриптыНужно понимать, что запускается и в какой оболочке
HooksPlugin может реагировать автоматически, а не только по команде
Доступ к сетиВопрос: куда он ходит и зачем
Credentials / токеныНужно проверить объём прав и место хранения
Write-capable действияPlugin может менять состояние проекта

Хороший безопасный README не прячет capability surface, а делает его коротким и понятным:

## Сводка capability

Плагин добавляет два skills: issue-analysis и pr-review.
Автоматических hooks нет.
Сетевых запросов нет.
Токены и внешние credentials не требуются.
Shell-скрипты не используются.

После такого фрагмента границы понятны: два skill — и всё. Скрытого второго этажа нет.

Тревожный пример выглядит иначе:

{
  "name": "generic-automation-suite",
  "permissions": ["shell", "network", "write"],
  "requiresCredentials": true,
  "hooks": 4
}

Даже если пример условный, он заставляет задать правильные вопросы. Зачем review-workflow нужен shell? Почему network? Какие write-операции? Почему четыре hooks? «Наверное, для удобства» — человеческая ошибка. Инженерный ответ другой: если задаче нужен review diff, а plugin просит половину кухни, это не удобство, а нарушение least privilege.

Даже skill-only plugin грузит контекст описанием, namespace и командами. Поэтому «нужен ли он вообще» — часть capability surface, а не отдельная придирка.

4. Хороший plugin — и всё равно не ваш

Можно найти аккуратный plugin: автор понятен, возможности безопасны, README написан не кровью. И всё равно его можно не ставить: он должен подойти проекту, команде и среде.

Сначала scope:

  • user рискует личным набором инструментов во всех проектах;
  • local держит эксперимент в одном repo;
  • project связывает plugin с командным workflow, и цена ошибки выше;
  • managed — централизованное решение организации.

Для экспериментов почти всегда разумнее начинать с user или local. К project переходите, когда ясно, что workflow нужен команде и понятно, как его раскатывать.

Вторая часть — namespace и пересечения имён. Если у вас уже есть review plugin, а новый тоже приносит skill pr-review, без namespace начинается лотерея: кто сработает, как отобразится, что увидит команда. Здоровее так:

review-kit:issue-analysis
review-kit:pr-review

Сразу видно, откуда пришёл компонент, и меньше риск конфликтов.

Совместимость — не только имена. На какую оболочку и среду рассчитан plugin? Bash-скрипты при команде на PowerShell — уже проблема, хотя сам plugin «хороший». То же со структурой репозитория, ожидаемыми командами и соглашениями по каталогам. Plugin, идеальный в одном mono-repo, в другом может быть бесполезен.

И дублирование: plugin может ничего не ломать, но дублировать существующий skill, workflow или вторую команду для той же задачи. Это организационная несовместимость. Слишком много почти одинаковых инструментов ведёт к вопросу «какой правильный?», после которого не пользуются никаким.

5. Где дверь, если что-то пойдёт не так

Установка — начало отношений. Полезно заранее знать, где дверь, если что-то пойдёт не так. Поддерживаемость отвечает на вопрос: что будет с расширением через месяц, после обновления, с новым участником команды и в день, когда оно начнёт мешать.

Первое, что хочется видеть, — версия и changelog. Даже 0.1.0 лучше, чем «актуальная папка на сегодня»: можно конкретно сказать, что у команды 0.2.0, а в 0.3.0 появились hooks, поэтому обновление отложено. Версия — язык разговора об обновлении и откате.

Второе — понятный путь update и отката. Обновление нельзя считать нейтральной мелочью: новая версия может добавить возможности, изменить поведение, расширить права и начать конфликтовать с workflow. Поэтому update — почти новый install. Changelog «many improvements» — повод читать внимательнее.

Хороший README объясняет жизнь после установки:

## Обновление

Перед update проверьте release notes.
Если новая версия меняет hooks, permissions или список credentials,
обновляйте только после повторного review.

## Отключение

Плагин можно отключить через менеджер plugins
или убрать project-level привязку способом, который поддерживает ваша версия Claude Code.

Третье — владелец. У plugin должен быть человек или команда, кому можно задать вопрос. Иначе получается артефакт-сирота: все пользуются, никто не отвечает, обновлять страшно, удалять ещё страшнее. Внутри команды это особенно заметно: полезный plugin стоит, а автор «кажется, Паша, который теперь на другом проекте».

6. Ставим или отказываемся

Сравним два воображаемых, но жизненных варианта. team-review-kit команда хочет для issue analysis и PR review. generic-automation-suite выглядит эффектно, но вызывает вопросы.

Критерийteam-review-kitgeneric-automation-suite
АвторВнутренняя tooling-командаНеочевидный внешний источник
Компоненты2 skills для reviewSkills, hooks, shell, сеть
CredentialsНе нужныНужен токен с широкими правами
NamespaceПонятный, не конфликтуетНеясный или общий
README / changelogЕсть и читается быстроНеполный, capabilities описаны расплывчато
Путь отключенияПонятенПочти не описан

Для первого решение спокойное: возможности ограничены задачей, поддержка понятна, project scope оправдан.

Решение: устанавливаем в project scope.

Причина: plugin закрывает командный workflow issue-analysis и pr-review.
Capability surface ограничен двумя skills, токены не нужны, namespace не конфликтует.
Есть понятный owner, версия и путь отключения.

Для второго отказ — не перестраховка, а нормальный инженерный вердикт. Не обязаны давать слабо документированному plugin с hooks, shell, сетью и широкими credentials шанс «просто посмотреть на практике».

Решение: не устанавливаем.

Причина: plugin требует больше возможностей, чем нужно для нашего review workflow.
Есть hooks, shell-скрипты и сетевой доступ без достаточной документации.
Путь отключения и последствия update не описаны.

В обоих случаях язык спокойный. Без «ужасный» и «идеальный». Только соответствие задаче, границы возможностей и качество сопровождения.

7. Запишите решение, пока оно не стало легендой

Если решение не зафиксировано, оно быстро превращается в легенду: через месяц никто не помнит, почему plugin стоит, кто одобрил и на каких условиях. Поэтому полезно сделать маленькую заметку в README команды, tooling-документе или описании PR.

Plugin: team-review-kit v0.2.0
Scope: project
Решение: устанавливаем

Зачем:
единый workflow для issue-analysis и pr-review

Что умеет:
только skills, без hooks, сети и credentials

Ограничения:
используем только для review-задач

Путь отката:
отключить через менеджер plugins или убрать project-level привязку
способом, который поддерживает текущая установка

Отрицательное решение записывают почти так же коротко. Важен не бюрократический ритуал, а умение объяснить выбор инженерным языком. Когда заметка за минуту отвечает, зачем plugin нужен, что умеет, где границы и как от него отказаться, вы мыслите не как коллекционер расширений, а как человек, отвечающий за рабочую среду команды.

8. Мини-чеклист перед установкой

  1. Источник: кто автор, есть ли репозиторий, лицензия, поддержка.
  2. Capability surface: только skills или ещё hooks, shell, сеть, credentials, write.
  3. Совместимость: scope, namespace, оболочка, структура проекта, дублирование.
  4. Поддерживаемость: версия, changelog, owner, update, disable/uninstall.
  5. Решение: записать причину «ставим» или «не ставим» и путь отката.

Этот чеклист полезен и для чужого plugin, и для своего. Внутренний автор — не индульгенция: у собственного пакета тоже должны быть владелец, версия, описание прав и понятное удаление.

Что запомнить

  • Plugin — чемодан возможностей, а не безобидная заметка.
  • Проверяйте три блока: авторство, capability surface, поддерживаемость.
  • Известный автор не отменяет проверку hooks, shell, сети и credentials.
  • Capability surface — что plugin может, а не что обещает README.
  • Даже skill-only plugin занимает контекст; нужность — часть оценки.
  • Хороший plugin может не подойти проекту: scope, namespace, среда, дублирование.
  • Update — почти новый install; версия и changelog нужны для разговора об изменениях.
  • У plugin должен быть владелец и понятный путь disable/uninstall.
  • Решение «не ставить» так же нормально, как «ставить».
  • Фиксируйте решение и причину, пока оно не стало легендой.

Практика (15–25 минут)

Цель: провести структурированный review двух plugin-кандидатов и записать решение по каждому.

Что сделать

  1. Возьмите два вымышленных кандидата: team-review-kit (два skill для review) и generic-automation-suite (skills, hooks, shell, сеть, credentials). Для каждого придумайте автора, версию, namespace и краткое описание.
  2. Заполните PLUGIN_REVIEW.md по трём блокам: авторство и поддержка; capability surface; совместимость и поддерживаемость. Для capability перечислите skills, hooks, shell, сеть, credentials и write-действия.
  3. Проверьте совместимость: какой scope нужен, конфликтует ли namespace с существующим pr-review, рассчитан ли plugin на вашу оболочку и не дублирует ли он текущий workflow.
  4. Примите решение по каждому кандидату и запишите его в PLUGIN_DECISION.md: «ставим / не ставим», причина, ограничения и путь отката. Для безопасного кандидата укажите проверку в режиме без внешних действий.
  5. Если Claude Code и marketplace доступны, проверьте метаданные и README реального кандидата; если нет — работайте с вымышленными карточками. Не устанавливайте plugin с hooks, shell и credentials и не используйте реальные токены.

Если Claude Code недоступен: выполните доступную часть шагов вручную в редакторе, проверьте README и метаданные кандидата; недоступные команды разберите по документации. Критерии проверки те же.

Проверка

  • Для каждого кандидата заполнены авторство, capability surface и поддерживаемость.
  • Capability перечислены конкретно, а не «полезные функции».
  • Проверены scope, namespace, среда и дублирование.
  • Решение записано спокойным инженерным языком.
  • Для «ставим» есть безопасный первый запуск и путь отката.
  • Для «не ставим» причина конкретна, а не «не понравилось».
  • В практике нет реальных ключей, секретов и установок опасных plugins.
