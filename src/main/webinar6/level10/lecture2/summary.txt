# Саммари лекции 2

## Plugin ecosystem: категории и выбор — Claude Code, 10 уровень

## 1. Топ недели ничего не знает про вашу задачу

Когда workflow уже упакован в plugin, хочется выбирать следующий по принципу «что сейчас в топе». Это понятное желание, но плохой первый фильтр: чужой рейтинг почти никогда не совпадает с вашей задачей.

Аналогия проста. Если вы пришли в строительный магазин без вопроса «мне нужна дрель, отвёртка или уровень?», полка «самые популярные инструменты месяца» уведёт куда угодно. С plugin так же: сначала нужна категория задачи, а не громкое имя.

| Подход | Как мыслит разработчик | Чем заканчивается |
|---|---|---|
| Сначала имя | «Этот plugin у всех на слуху» | Набор случайных расширений |
| Сначала категория | «Нужен plugin для ревью кода» | 1–2 осмысленных кандидата |
| Сначала workflow-боль | «Мы тратим много времени на PR summaries» | Понятный критерий «ставить / не ставить» |

Имена и топы меняются быстрее, чем живёт лекция, а категории задач — медленно. Разбираться в проекте, смотреть diff и вести PR никуда не денется. Категория делает выбор менее зависимым от маркетинговой витрины.

## 2. Категория, plugin и capability surface — разные уровни

Начинающие смешивают три вещи: категорию, конкретный plugin и его реальные возможности. Из-за этого разговор становится странным: «нам нужен plugin» — хотя нужна категория «ревью кода»; «этот plugin безопасный» — хотя проверена страница в marketplace, а не capability surface.

| Уровень | Что это | Пример |
|---|---|---|
| Категория | Класс инженерной боли | «Нужно быстрее и аккуратнее делать ревью кода» |
| Plugin | Упакованный installable package | `team-review-kit` |
| Capability surface | Что plugin реально умеет и на что влияет | читает diff, пишет PR summary, запускает hooks, shell или сеть |

У Workflow Kit уже есть skill `pr-review` для self-review. Из этого не следует, что нужен любой plugin с надписью «AI review suite». Сначала называем категорию — «ревью кода». Потом решаем: брать чужой plugin или упаковать собственный `pr-review`. И только потом смотрим на capability surface: он только читает diff — или заодно тянет hooks, сеть, shell и половину интернета.

С командой это работает так же. «Давайте поставим популярный plugin» — фраза ни о чём. «Нам нужен plugin категории ревью кода с минимальными правами, без браузерной автоматизации, чтобы сократить self-review перед PR» — уже инженерное требование.

## 3. Самый ценный plugin часто не пишет код

Не все plugins существуют ради генерации кода. Большая часть полезной работы происходит раньше: на входе в проект, в поиске контекста и понимании, где живёт нужная логика.

| Категория | Какую боль снимает | Пример в Commerce OS / Workflow Kit |
|---|---|---|
| Документация и справка | Быстро находят актуальные команды и примеры | Понять, как запускать Commerce OS локально |
| Навигация по коду | Помогают искать определения, связи и использования | Быстрее найти логику refund |
| Память проекта и первичная настройка | Подсказывают соглашения, команды и правила | Быстрее ввести нового участника в контекст |
| Развитие артефактов Workflow Kit | Поддерживают шаблоны, примеры и структуру пакета | Проверить `SKILL.md`, шаблоны и README |

Новичку кажется, что самый крутой plugin — тот, который сразу меняет код. Выигрыш часто раньше: если вы каждый раз заново вспоминаете команды запуска и имя модуля, plugin для памяти проекта окупится быстрее ещё одного модного рефакторщика.

Отдельная мета-категория — плагины для развития самих артефактов Workflow Kit. Они не пишут бизнес-код, зато не дают шаблонам, примерам и README расползаться.

## 4. «AI помогает программировать» — это пять разных инструментов

Внутри этой фразы полезно видеть разные классы задач:

| Категория | Что закрывает | Пример |
|---|---|---|
| Ревью кода | self-review, проверка diff, пропущенные тесты, расползание scope | Ревью PR по refund-логике |
| Тестирование и браузерная проверка | smoke-проверки, UI-проходы, воспроизведение сценариев | Проверить форму возврата после изменения |
| Frontend/UI | компоненты, layout, мелкие UX-проверки | Карточки заказов и статусы |
| Рефакторинг и упрощение | безопасные улучшения структуры, уменьшение шума | Упростить сервис без переписывания модуля |
| Security/static scanning | явные риски и подозрительные зоны | Не пропустить опасное изменение в payments |

Категория полезна, только когда совпадает с текущей задачей. Если вы чините backend-ошибку в API, а ставите plugin для браузерной автоматизации только потому, что он популярный, — это палатка в лифте: снаряжение есть, к походу отношения не имеет.

## 5. Скучный командный plugin окупается быстрее эффектного

После того как код понят, изменён и проверен, остаётся командный процесс. Здесь plugins часто выглядят невзрачно, но окупаются быстрее:

| Категория | Что поддерживает | Пример |
|---|---|---|
| Git / GitHub / PR | summary по diff, PR description, связка issue → PR | `pr-review` и PR notes |
| Инфраструктура и delivery | build, release notes, простые ритуалы | Release summary без ручного копирования |
| Командный workflow | общие соглашения, ввод в проект, единые процедуры | Один пакет review-практик для команды |

Командный workflow обычно недооценивают. Плагины воспринимают как личные ускорители, но выигрыш команды в другом: новый человек быстрее понимает проект, PR выглядят одинаково, правила review и setup не приходится объяснять по кругу. Plugin переносит рабочую привычку из головы автора в воспроизводимую форму.

## 6. Категория на каждую категорию — перегруз

Когда вы начинаете мыслить категориями, появляется новая ловушка: поставить по plugin на каждую категорию и стать «максимально эффективным». На практике это перегруз.

Категории пересекаются: один plugin закрывает ревью, PR workflow и часть командного tooling; другой — тестирование, браузерные проверки и frontend. Пересечение не беда. Беда — считать каждую категорию обязательной установкой.

Помогает короткая заметка до установки:

```text
# team-review-kit

Главная боль: review diff перед PR
Нужные категории: ревью кода, Git/PR workflow
Не включаем: browser automation, infra
Причина: первая версия решает одну боль — качественный review.
```

Такая заметка заставляет спрашивать не «что мне нравится», а «какую работу должен сократить пакет». Половина красивых идей быстро оказывается любопытством, а не болью.

Типичный многоплагинный героизм: один plugin комментирует PR, второй собирает summary, третий подкидывает checklist. Через полчаса команды дублируются, названия похожи, а понять, кто за что отвечает, сложнее, чем написать PR руками. Если две установки в одной зоне решают одну боль — сравните capability surface и оставьте одну.

## 7. Звёзды не знают, что вы чините refund

Популярность — социальный сигнал, а не инженерный. Plugin много обсуждали, часто ставили и хорошо продвигали, но про ваши задачи, стек, команду и ограничения это почти ничего не говорит.

| Выглядит убедительно | Важно сначала |
|---|---|
| Много звёзд и обзоров | Совпадение с реальной болью |
| Красивая страница marketplace | Понятный capability surface |
| «У всех стоит» | Отсутствие дублирования с тем, что уже есть |
| Громкое имя автора | Ограничения и адекватные permissions |
| Большой набор фич | Поддержка, README и понятный путь удаления |

Хороший порядок мыслей другой: нужна ли вообще эта категория → что plugin реально делает → не дублирует ли Workflow Kit → и только потом популярность. Если два plugin одинаково подходят по категории и capability surface, разумно взять тот, у кого лучше README, активнее поддержка и понятнее репозиторий. Популярность — довесок при равенстве, а не стартовая эвристика.

Популярный plugin для браузерной автоматизации не станет полезнее от лайков, если весь спринт про review backend-изменений. Наоборот, он займёт место в голове и подтолкнёт тянуть тяжёлый инструмент туда, где хватило бы спокойного read-only review.

## 8. Конкретные плагины официального marketplace

Категории полезно приземлять на примеры. `claude-plugins-official` — официальный marketplace, поддерживаемый Anthropic; по умолчанию он подключён к Claude Code. Это не единственный правильный источник, но аккуратная стартовая точка: у плагинов есть владелец, обозримая поддержка и понятный путь установки.

Ниже — пять примеров на разные категории. Это снимок состояния, а не обязательный набор и не источник истины.

### Code Review — ревью кода

Официальный Anthropic-verified plugin. Внутри — несколько reviewer-агентов, которые параллельно смотрят разные срезы изменения: правила из `CLAUDE.md`, потенциальные баги, контекст git-истории, прошлые комментарии к PR, осмысленность комментариев. Каждое замечание получает confidence-оценку; по умолчанию отсекается то, что ниже порога.

Запуск — на ветке с готовым PR, результат в терминал; публикация комментариев к PR — отдельное осознанное действие. Capability surface показательный: в простом режиме плагин читает diff и историю, но ничего не пишет.

### Code Simplifier — рефакторинг

Официальный плагин, который ищет, что безопасно упростить в недавно изменённом коде: уменьшить вложенность, заменить запутанные тернарные конструкции, привести имена в порядок, убрать дублирование. «Недавно изменённый» принципиально: он не переделывает половину репозитория.

Побочный эффект — гигиена кодовой базы: упрощённый код занимает меньше токенов и читается быстрее. Plugin бывает не только фичей под задачу, но и инструментом гигиены.

### frontend-design — frontend/UI

Официальный skill, который помогает Claude не скатываться в статистическое среднее при генерации интерфейсов: бледный градиент, Inter, одинаковые кнопки. Вместо «универсальной красоты» он подталкивает к осознанным aesthetic-решениям — brutalist, maximalist, retro-futuristic, luxury, playful — под задачу.

Capability surface другой: это не reviewer, а co-creator. Он помогает создавать визуальный код, а не оценивать существующий.

### Skill Creator — мета-инструменты для skills

Официальный plugin для создания skills. Закрывает осязаемую боль: самописный `SKILL.md` часто страдает расплывчатым описанием и не срабатывает в нужный момент. У Skill Creator есть режимы Create, Eval, Improve, Benchmark и специализированные агенты: прогон против тестовых промптов, оценка результата, A/B-сравнение версий, точечные улучшения.

Для Workflow Kit это эталонный подход: разработка skills превращается из «написал markdown и надеемся» в eval-driven цикл с измеримым качеством.

### Superpowers — методология как plugin

Не один маленький инструмент, а целый framework методологии, упакованный как plugin. Внутри — около дюжины composable skills: брейншторминг, test-driven development по циклу red-green-refactor, subagent-driven development, structured code review и инструменты для проектирования skills.

Технически это плагин третьей стороны, но он попал в официальный marketplace — хороший сигнал. Сила в том, что работа с ИИ становится умнее: появляются фазы, контроль качества и разделение ролей. Методология не привязана к одному инструменту: тот же набор skills работает в Cursor, Codex, Copilot CLI, Gemini и OpenCode.

### Version-resilience

Все пять плагинов — снимок маркетплейса на момент лекции. Команды, имена опций, версии и состав агентов могут меняться. Не меняется механика: открыть marketplace, отфильтровать по категории, прочитать capability surface и решить, добавляет ли плагин что-то к тому, что уже есть в Workflow Kit.

## 9. Экосистема как карта, а не витрина

Соберём всё в контексте Workflow Kit. У нас есть skills вроде `issue-analysis` и `pr-review`. В первой лекции уровня мы решили, что некоторые из них созрели для упаковки. Сегодня добавляем недостающий слой: прежде чем выбирать из экосистемы, нужно понять категорию будущего plugin.

Для первой версии пакета мышление трезвое: мы не строим «plugin обо всём». Есть одна командная боль — PR нужно смотреть структурно и единообразно. Базовая категория — ревью кода. Рядом почти неизбежно Git/PR workflow: review живёт не в вакууме, а в diff, summary и PR notes.

```text
# Решение по plugin-package

Пакет: team-review-kit
Базовая категория: ревью кода
Соседняя категория: Git/PR workflow
Вне первой версии: browser testing, infra, project memory
Цель: сократить время self-review и сделать PR более ровными.
```

Совпадение по категории только сужает поиск. Дальше — источник, capability surface, совместимость, permissions и лишь потом решение ставить или нет.

После такой записи экосистема становится спокойнее. Список «лучших плагинов мира» не нужен — нужна маленькая часть про ревью кода и Git/PR workflow с аккуратным capability surface. Любой marketplace и совет коллеги превращаются в источник кандидатов для короткого списка.

Читаете экосистему именами и топами — она бесконечна. Читаете категориями — сворачивается до нескольких классов боли, из которых вашей задаче отвечают один-два. Сначала категория, потом capability surface, и только потом имя и звёзды.

## Что запомнить

- Начинайте с workflow-боли и категории, а не с названия и топа недели.
- Категория — класс боли; plugin — упаковка; capability surface — что он реально умеет.
- Самые полезные плагины часто помогают до написания кода: навигация, память проекта, документация, развитие Workflow Kit.
- «AI помогает программировать» — это ревью, тестирование, frontend, рефакторинг и security, а не один общий мешок.
- Командные плагины для Git/PR и workflow окупаются буднично и быстро.
- Не ставьте plugin на каждую категорию: пересечения дублируют работу и путают ответственность.
- Популярность — довесок при равенстве, а не первый фильтр.
- Сначала категория и capability surface; потом источник, permissions, README, поддержка и только потом звёзды.
- Конкретные имена и состав плагинов меняются; механика выбора остаётся.

## Практика (15–25 минут)

**Цель:** собрать category-first shortlist для одной workflow-боли и принять решение по plugin, не поддаваясь популярности.

**Что сделать:**
1. Возьмите вымышленную боль команды Commerce OS: «PR по refund-логике долго и неодинаково проходят self-review». Сформулируйте одну фразу, какую работу должен сократить plugin.
2. Заведите `PLUGIN_CATEGORY_PLAN.md`: главная боль, базовая категория, соседняя категория, что не входит в первую версию и почему.
3. Соберите 2–3 кандидата из `claude-plugins-official` или локального каталога. Для каждого запишите источник, что он читает и что пишет, есть ли hooks/MCP/сеть, сколько примерно стоит контекст и не дублирует ли он `pr-review` из Workflow Kit.
4. Выберите одного кандидата или решение «не ставить». Назовите одну конкретную задачу, на которой проверите эффект до/после; если marketplace недоступен, разберите кандидатов по README и capability surface вручную.
5. Добавьте в план строку про удаление: `/plugin disable` или `/plugin uninstall`, если польза не подтвердилась. Не используйте реальные ключи и секреты.

**Проверка:**
- Боль сформулирована как работа, а не как «хотим модный plugin».
- В плане есть категория, границы и исключённые категории.
- У кандидатов описан capability surface, а не только название.
- Проверено дублирование с существующими skills.
- Выбрана одна проверяемая задача до/после.
- Есть критерий отказа и способ удаления.
- В плане нет секретов и реальных данных.
