# Саммари лекции 5

## Dynamic context и supporting files — Claude Code, 9 уровень

## 1. Skill живёт не только в тексте

Даже аккуратный `SKILL.md` легко начать воспринимать слишком упрощённо: будто это просто prompt, который переехал в файл. Снаружи выглядит прилично, но по сути вы всё так же зависите: удачно ли сформулировали задачу, приложили ли файлы, не забыли ли половину контекста. Такой skill — бумажка на мониторе «не забудь проверить тесты». Полезно, но не инженерная система.

Обычный prompt почти всегда статичен: работает с тем, что вы вложили в сообщение вручную. Забыли приложить issue, пример `TASK_SPEC.md`, план проверки — модель импровизирует. А импровизация в инженерной работе романтична только до первого странного diff.

Skill сильнее не потому, что он «длиннее», а потому, что у него появляется структура. Prompt говорит: «сделай что-нибудь похожее на правильное». Skill: «вот процедура, вот шаблон, вот примеры, вот ограничения, вот ожидаемый артефакт». Разница как между «свари что-нибудь вкусное» и «вот рецепт, вот продукты, вот форма подачи, и, пожалуйста, не взрывайте кухню».

| Ситуация | Обычный prompt | Skill |
|---|---|---|
| Нужно один раз быстро набросать идею | Подходит | Часто избыточен |
| Нужно стабильно получать один и тот же артефакт | Хрупко | Надёжно |
| Нужны шаблоны и примеры рядом | Неудобно | Естественно |
| Нужен review и versioning | Почти никак | Нормальная практика |
| Нужно опираться на актуальные данные проекта | Всё вручную | Это встраивается в workflow |

В Workflow Kit это особенно заметно на `issue-analysis`. Пока он живёт только как текст внутри `SKILL.md`, он слабый: запутается, когда issue поменяется, проект подрастёт, придёт новый разработчик — или когда через две недели вы сами глянете и подумаете: «а что я имел в виду под “собери evidence”?» Поэтому хороший skill почти никогда не замыкается на одном файле. Он живёт как маленькая система: короткая инструкция плюс источники правды рядом.

## 2. Dynamic context: skill работает по сигналам

**Dynamic context** — это контекст, который skill берёт из текущей задачи и состояния проекта, а не из «фонового знания» модели. Текст issue, список файлов, фрагмент кода, результат `grep`, текущий diff, вывод тестов, шаблон артефакта. Не «вспомни, как обычно бывает», а «посмотри, что происходит прямо сейчас».

Это важный переход. Когда skill работает только по инструкции, он остаётся красивым, но глухим. Когда он работает по динамическим сигналам — становится адаптивным. Поэтому один и тот же `issue-analysis` применим и к багу с сортировкой refund-запросов, и к дублирующейся пагинации, и к локальному refactor: меняется вход и evidence, не процедура. Skill — не заготовленный ответ, а способ задавать правильные вопросы к текущей задаче.

Пример из Commerce OS: в поддержку прилетает проблема — запросы на возврат в inbox идут в неправильном порядке. На голом prompt «прочитай issue и напиши task spec» модель выдумает половину деталей. А skill берёт issue как аргумент, смотрит на шаблон `TASK_SPEC.template.md`, через поиск по проекту вытаскивает пару релевантных файлов — и у него появляется опора.

```text
Текст issue
  → аргументы skill
  → поиск релевантных файлов
  → сбор evidence
  → шаблон TASK_SPEC
  → готовый TASK_SPEC.md
```

В живом skill это может быть зафиксировано коротко:

```text
## Вход
- issue: $ARGUMENTS

## Действия
1. Прочитай issue.
2. Найди 2–5 наиболее релевантных файлов.
3. Заполни templates/TASK_SPEC.template.md.
4. Отдели facts от assumptions.
5. Верни TASK_SPEC.md без начала implementation.
```

Важна не конкретная служебная переменная — её имя в зависимости от версии может отличаться. Важен принцип: skill не висит в воздухе, а получает явный вход.

Допустим, он дополнительно запускает поиск по коду:

```text
$ grep -R "refund" support/ orders/
support/inbox/RefundRequestSorter.java
support/inbox/RefundQueueService.java
orders/api/RefundController.java
```

Это и есть dynamic context в хорошем смысле: не «модель знает, что refund обычно рядом с orders», а «мы увидели конкретные файлы, вероятно относящиеся к проблеме». Дальше skill либо ссылается на них в артефакте, либо помечает как candidate files для проверки.

Для `/git-commit` dynamic context — это живое состояние Git: текущая ветка, `git status --short`, `git diff --cached`, список изменённых файлов и последние коммиты. Skill не «помнит», что было в прошлый раз, а читает состояние перед каждым запуском. Если в skill есть `` !`команда` `` для такого контекста, помните: она выполнится автоматически при вызове, поэтому команда должна быть безопасной и не содержать секретов.

Dynamic context не означает «засунем в skill весь репозиторий на всякий случай». Лишний контекст не делает модель мудрее — он быстрее её утомляет. Вся codebase на старте, логи за неделю, три старых обсуждения из чата — не dynamic context, а контекстная каша. Хороший skill поднимает только сигнал, нужный сейчас: для `issue-analysis` это обычно issue, 2–5 файлов, шаблон и, может, один похожий example.

## 3. Supporting files и плохой SKILL.md

У многих возникает соблазн: раз skill должен быть умным — запихнём в `SKILL.md` всё. Шаблон, два примера, справочные заметки, пояснение архитектуры, пол-энциклопедии по проекту. И файл превращается в роман, который страшно открывать без перекуса. Это не сила, а сигнал: skill спроектирован неаккуратно.

**Supporting files** нужны ровно для того, чтобы отделить процедуру от материалов. Сам `SKILL.md` короткий: когда использовать, что подать на вход, что делать, что выдать, чего не делать. Остальное — рядом:

```text
workflow-kit/.claude/skills/issue-analysis/
  SKILL.md
  templates/
    TASK_SPEC.template.md
    EVIDENCE_LOG.template.md
  examples/
    refund-sorting-bugfix.md
    pagination-duplicates.md
  references/
    commerce-risk-notes.md
```

Такая папка хороша по трём причинам. Во-первых, её легко ревьюить: сразу видно, где инструкция, где шаблоны, где примеры. Во-вторых, ею удобно пользоваться повторно. В-третьих, вы обновите шаблон или пример, не трогая процедуру.

Шаблон `TASK_SPEC` может быть совсем коротким:

```markdown
# TASK SPEC

## Цель
...

## Область изменений
...

## Не-цели
...

## Критерии приёмки
...

## Проверка
...
```

Держать его в теле skill огромным блоком не нужно: сошлитесь на вспомогательный файл и заполните по месту. `SKILL.md` остаётся инструкцией, шаблон — шаблоном. Это простое разделение ролей сильно улучшает читаемость.

Примеры тоже полезнее держать рядом. Один показывает хороший bugfix-спек для refund sorting, второй — как оформить issue про дубли в пагинации. Skill перестаёт быть абстрактным: он не говорит «делай хорошо», он показывает «вот так выглядит хороший выходной артефакт в нашей команде».

Если нужен дополнительный сбор сигнала, добавьте небольшой вспомогательный скрипт: например, он собирает кандидатов на файлы по ключевому слову issue. Но не заигрывайтесь: если supporting files разрослись так, что без археолога и лупы skill не открыть, — вы снова ушли в избыточность. Раздувшийся `SKILL.md` редко значит, что skill поумнел. Обычно — что материалы не разложены по местам.

## 4. Как усилить issue-analysis для Commerce OS

Возьмём минимальный `issue-analysis`: он уже умеет принять issue, собрать `TASK_SPEC.md` и не лезть в реализацию. Этого достаточно, чтобы навык заработал. Но в живом проекте быстро выясняется: одной инструкции мало — без шаблона, примеров и явных сигналов skill снова импровизирует.

Поэтому усиливается не название и не frontmatter, а опорная система вокруг: аргументы, поиск по релевантным файлам, шаблон, примеры, явное разделение фактов и предположений. Внутри `SKILL.md` это компактно:

```text
Используй templates/TASK_SPEC.template.md.
Возьми issue из аргументов.
Найди только релевантные файлы, а не весь проект.
Ссылайся на evidence, а assumptions помечай явно.
Верни заполненный TASK_SPEC.md и список открытых вопросов.
```

Сила не из лишнего текста, а из того, что навык знает: где лежит шаблон, какие файлы проверить, как не перепутать факт с догадкой. Сегодня issue про `RefundRequestSorter` — подтянется один набор кандидатов. Завтра дубли в пагинации orders — другой. Процедура та же, меняется контекст. Этим reusable workflow и отличается от длинного красивого prompt: prompt держит слишком многое у вас в голове, skill фиксирует это рядом с собой.

Помните про версионную устойчивость: поля и формат вызова меняются, но устройство skill остаётся — аргументы, вспомогательные файлы, dynamic context, контракт результата и ограничения. Опора в этом, а не в имени YAML-ключа.

## 5. Skill quality: рабочий артефакт

Как понять, что skill действительно хороший? Написать уверенный `SKILL.md` быстро, но хороший skill определяется не интонацией, а тем, насколько он повторяемый, понятный и экономный по контексту. На качество полезно смотреть как на инженерный review: не «красиво ли написано», а «получит ли другой человек и другая сессия предсказуемый результат».

| Вопрос | Что должно быть правдой |
|---|---|
| Понятно, когда использовать skill? | `description` и `when_to_use` не расплывчаты |
| Ясен вход? | Есть аргументы или понятный источник dynamic context |
| Ясен выход? | Назван артефакт и его формат |
| Есть evidence-first поведение? | Skill не подменяет факты догадками |
| Ограничены инструменты? | Нет лишних прав «на всякий случай» |
| `SKILL.md` не раздут? | Шаблоны и примеры вынесены во вспомогательные файлы |
| Контекст экономный? | Загружается только нужный сигнал |
| Результат можно ревьюить? | Есть повторяемый контракт результата |

Каждый пункт ловит конкретную проблему. Если непонятно, когда использовать skill, он быстро превращается в универсального «помощника на все случаи жизни», то есть ни на один случай толком. Если не ясен вход, skill требует телепатии. Если не ясен выход, он выдаёт то краткое резюме, то полупустой markdown, то ещё что-нибудь «вдохновляющее». Если не ограничены инструменты, даже невинный аналитический skill внезапно получает возможность редактировать файлы.

Частая ошибка — перепутать «богатый skill» с «раздутым skill». Богатый skill короток в инструкции, но силён опорной системой вокруг. Раздутый — когда всё свалено в один файл, а потом автор говорит, что он «самодостаточный». Самодостаточность хороша до момента, пока второй человек не попробует это ревьюить.

Хороший тест: если вернуться к skill через месяц, поймёте ли за минуту, что он делает, откуда берёт данные и что обязан вернуть? Если «ну, примерно» — skill ещё сырой. Если «да, вот вход, вот шаблон, вот примеры, вот ожидаемый результат» — это поддерживаемый артефакт.

В этот момент skill перестаёт быть красивым именованным prompt и становится частью Workflow Kit по-настоящему. Он живёт за счёт структуры, актуального контекста и аккуратно разложенных вспомогательных файлов. А когда такой skill перестаёт быть локальной штукой одного человека или репозитория, следующий вопрос — упаковка, версионирование и распространение.

## Практика (15–25 минут)

**Цель:** разгрузить раздутый `SKILL.md`, вынести шаблон и пример в supporting files и применить skill с аргументами и dynamic context.

**Что сделать:**
1. Возьмите вымышленный Workflow Kit и `issue-analysis/SKILL.md`, в котором шаблон `TASK_SPEC` и пример разбора лежат прямо в теле. Создайте фейковый issue про сортировку refund-запросов; используйте только вымышленные данные.
2. Вынесите шаблон в `templates/TASK_SPEC.template.md`, пример — в `examples/refund-sorting.md`, а `SKILL.md` сократите до процедуры: когда использовать, вход, действия, результат и запреты.
3. Добавьте dynamic context: issue из аргументов (или эквивалент для текущей версии), поиск 2–5 релевантных файлов, ссылку на шаблон и требование отделять facts от assumptions. Не загружайте весь репозиторий.
4. Прогоните skill на фейковом issue через Claude CLI или вручную. Получите `TASK_SPEC.md` с целью, scope, non-goals, критериями приёмки и открытыми вопросами; убедитесь, что skill не меняет код.
5. Проверьте папку и diff по quality-чеклисту: короткий `SKILL.md`, шаблоны и примеры рядом, контекст экономный, права минимальные, результат воспроизводим.

**Проверка:**
- `SKILL.md` не содержит огромный шаблон и примеры в теле.
- Supporting files лежат в `templates/`, `examples/` или `references/`.
- У skill есть явный вход и 2–5 релевантных источников контекста.
- Факты и assumptions разделены.
- Skill возвращает конкретный `TASK_SPEC.md`, а не «полезный анализ».
- Инструменты ограничены чтением/поиском; код не изменяется.
- Контекст не раздут: нет всей кодовой базы и старых логов «на всякий случай».
- В практике только фейковые данные, без секретов и реальных issue.
