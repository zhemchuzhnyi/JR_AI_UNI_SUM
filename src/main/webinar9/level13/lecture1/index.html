MCP как внешний слой

Claude Code

13 уровень · лекция 1
Код — важная часть истории, но не вся. MCP добавляет Claude Code контролируемый доступ к внешнему контексту: трекеру, monitoring, read-only базе, документации и PR-комментариям.

1. Одного репозитория уже недостаточно

В реальной работе задача редко выглядит как «открой один файл и поправь строчку». Обычно всё начинается снаружи: кто-то завёл тикет в трекере, monitoring прислал алерт, менеджер приложил дизайн, аналитик попросил свериться с отчётом, а поддержка прислала номер заказа. Код — важная часть истории, но не вся.

Без внешнего доступа Claude Code похож на очень сильного коллегу, которого позвали расследовать баг, но забыли выдать доступ к трекеру, monitoring и документации: гениальный — и работающий в режиме «пришлите ещё скриншот, ещё лог, ещё кусок текста». Для разовой задачи терпимо, для повторяющегося workflow уже нет. Начинается офисное кардио: браузер, скопировать issue, вставить в Claude, снова браузер за комментариями, снова вставить.

Где живёт информацияЧто это такоеКак вы работали до сих пор
Внутри репозиториякод, тесты, конфиги, CODEBASE_INVENTORY.md, API_MAP.mdClaude читает это напрямую
Снаружи репозиторияissue tracker, monitoring, read-only БД, документация, дизайн, PR-комментариивы приносите это в чат вручную

Важно не перепутать две вещи. Когда мы говорим про внутренние артефакты вроде CODEBASE_INVENTORY.md, мы описываем сам проект. Когда говорим про MCP — мы описываем мост во внешний мир команды: не новый способ читать код, а контролируемый доступ к тому, что раньше вы таскали в сессию вручную.

2. MCP простыми словами

Слово protocol в названии Model Context Protocol звучит так, будто сейчас начнётся лекция про сетевые пакеты. На деле протокол здесь — договорённость, как Claude Code узнаёт, какие внешние инструменты доступны, как их вызывать и в каком виде получать ответ.

MCP — это внешний слой возможностей для Claude Code. Он не делает модель магической и не открывает модели весь интернет. Он добавляет ограниченные «окошки» во внешние системы: через них Claude читает данные, выполняет действия или получает узкоспециализированный контекст.

Три роли:

  • клиент — кто хочет спросить или вызвать; у нас это Claude Code;
  • сервер — кто даёт доступ к возможностям внешней системы;
  • инструмент — отдельное действие с именем: list_issues, get_issue, search_docs.
Задача пользователя
  → Claude Code
  → MCP-клиент внутри Claude Code
  → MCP-сервер
  → внешняя система: трекер / мониторинг / база / docs

Аналогия: Claude Code — инженер, MCP-сервер — стойка доступа в здании, инструменты — пропуска. Один пропуск даёт посмотреть задачу, другой — найти документацию, третий — прочитать схему базы. Стойка не обязана выдавать мастер-ключ от всего здания.

Для учебного Workflow Kit пока можно записать простую модель ролей и доступа:

{
  "server": "issue-tracker",
  "tools": ["list_issues", "get_issue", "search_issues"],
  "access": "read-only"
}

Это не канонический формат боевого конфига, а умственная модель: внешний сервер issue-tracker даёт три инструмента в безопасном режиме, только чтение.

3. От какой рабочей боли MCP нас спасает

Проблема не в том, что Claude Code «недостаточно умный», а в том, что часть инженерного контекста живёт вне репозитория, а таскать его руками долго и ненадёжно.

Ситуация в Commerce OS. В трекере появилась карточка COM-481: возвраты заказов в определённом статусе отображаются в неправильном порядке. Без MCP вы вручную переносите её в Claude Code и просите найти затронутые файлы. Через десять минут в карточке новый комментарий — а у Claude его нет. Снова копипаст.

С MCP сценарий меняется по сути: Claude Code не ждёт копирования — через get_issue читает актуальную задачу и сопоставляет её с CODEBASE_INVENTORY.md и кодовой базой Commerce OS. Репозиторий остаётся внутренним источником истины о коде, трекер — внешним источником истины о постановке задачи.

СценарийБез MCPС MCP
Разобрать issue из трекеравы копируете текст задачи вручнуюClaude читает задачу через внешний инструмент
Проверить свежий алертвы вставляете кусок лога вручнуюClaude получает актуальные данные из monitoring
Свериться со схемой БДвы копируете SQL-результаты или скриншотыClaude читает схему через read-only доступ
Найти актуальную документациювы ищете и вставляете фрагменты самиClaude запрашивает нужный справочный контекст

MCP не заменяет вашу голову — он убирает рутину переноса данных в сессию.

4. Возможности MCP для Claude Code

Полезнее мыслить не конкретными продуктами, а классами возможностей. Их три:

  1. Доступ к внешним данным — issue из трекера, список PR, график ошибки из monitoring, схема таблицы из read-only базы. Это действие «понять мир», и на старте нужен именно он.
  2. Внешние действия — оставить комментарий в PR, создать тикет, изменить статус задачи, запустить операцию. Технически MCP это умеет, но наличие действия не значит, что его надо сразу разрешать.
  3. Узкоспециализированный контекст от внешнего инструмента — например, документация: без MCP вы сами ищете актуальный раздел, а с инструментом Claude Code получает именно тот фрагмент справки, который нужен.

Различайте три вопроса:

  • данные — «что происходит снаружи?»;
  • действия — «что я могу изменить снаружи?»;
  • контекст — «что мне нужно знать снаружи, чтобы понять задачу?».
Так MCP перестаёт быть абстрактной платформенной магией: это данные, действия и контекст с внешней стороны.

5. MCP встраивается в уже знакомый workflow

Появление MCP не ломает workflow из предыдущих модулей. Он не отменяет task spec, не заменяет plan mode, не убирает diff и не делает тесты необязательными. Он лишь добавляет источник входных данных до планирования.

Задача: разобраться с COM-481
Внешний источник: issue tracker
Внутренние артефакты: CODEBASE_INVENTORY.md, API_MAP.md
Результат: список затронутых модулей и план проверки
Код не менять

Решение всё равно принимается по знакомой схеме: задача → контекст → план → проверка. MCP — слой под уже знакомым процессом; всё из модулей про task specification, context hygiene и evidence-based discovery остаётся в силе.

6. MCP не заменяет другие артефакты

Когда появляется новый сильный механизм, рука тянется использовать его как замену всему подряд. Лучше затормозить и развести роли.

Что вам уже знакомоДля чего это нужноПочему MCP это не заменяет
CLAUDE.mdпостоянные правила проектаMCP даёт внешние возможности, а не память проекта
Skillповторяемая процедураMCP даёт доступ к внешней системе, но не описывает workflow
Subagentотдельная роль и изолированный контекстMCP — это возможность, а не роль
CODEBASE_INVENTORY.mdкарта внутреннего устройства проектаMCP работает с внешними системами, а не с картой кода
API_MAP.mdкарта внутренних API и интеграций проектаMCP не описывает внутренние маршруты приложения

Skill — рецепт. Subagent — роль. CLAUDE.md — правила. CODEBASE_INVENTORY.md — карта внутренней местности. MCP — пропуск к внешней системе.

Иногда кажется: раз Claude прочитает задачу из трекера, значит TASK_SPEC.md не нужен. Нет. Issue в трекере — сырой внешний сигнал, task spec — инженерная постановка работы именно в вашем контексте. MCP приносит сигнал, но не оформляет за вас задачу.

7. Сквозной пример: Workflow Kit и Commerce OS

Основной проект уровня — Claude Workflow Kit for Team, второй контекст — Commerce OS. Workflow Kit отвечает за то, как команда работает с Claude Code, Commerce OS — реальная кодовая база с багами, фичами и интеграционными вопросами.

Команда Commerce OS регулярно берёт задачи из внешнего трекера, и без MCP каждый приносит их вручную — вход у всех разного качества. Workflow Kit стабилизирует сам вход:

# Внешний источник для issue-analysis
Система: issue tracker Commerce OS
Режим: только чтение
Инструменты: list_issues, get_issue, search_issues
Назначение: забирать актуальные задачи без ручного копирования

Никакого «распределённого AI-платформенного поколения» — команда увидела повторяющуюся боль и оформила внешний доступ как инженерный артефакт.

Главный сдвиг лекции: раньше репозиторий был единственным, что Claude Code видел напрямую, а всё остальное вы приносили руками. Теперь у картины два источника: внутренняя карта проекта (код, тесты, CODEBASE_INVENTORY.md) и внешний источник задач через MCP-мост. Claude Code работает с обоими, а COM-481 перестаёт жить в браузере отдельно от кода.

Что запомнить

  • MCP — внешний слой возможностей Claude Code, а не «весь интернет» и не замена коду.
  • MCP-клиент — Claude Code, MCP-сервер — доступ к внешней системе, инструмент — отдельное действие.
  • MCP закрывает разрыв между кодом в репозитории и внешним контекстом: трекер, monitoring, БД, docs, дизайн, PR-комментарии.
  • Три класса возможностей: внешние данные, внешние действия, специализированный контекст.
  • На старте нужнее read-only данные, а не write-действия.
  • MCP не отменяет task spec, plan mode, diff, тесты и evidence-based discovery.
  • MCP не заменяет CLAUDE.md, skill, subagent, CODEBASE_INVENTORY.md и API_MAP.md.
  • Issue из трекера — сырой сигнал; task spec — инженерная постановка задачи.
  • Для Workflow Kit разумный первый шаг — read-only issue tracker с list_issues, get_issue, search_issues.
  • MCP добавляет второй источник истины: внутреннюю карту проекта и внешний контекст задачи.

Практика (15–25 минут)

Цель: спроектировать первый read-only MCP-контур для Workflow Kit, развести MCP и уже знакомые артефакты и проверить сценарий COM-481 без реальных внешних подключений.

Что сделать

  1. В вымышленном Workflow Kit создайте MCP_CAPABILITY_MAP.md. Опишите MCP-клиент, сервер issue-tracker и три инструмента list_issues, get_issue, search_issues; зафиксируйте режим read-only.
  2. Заполните таблицу «внутреннее vs внешнее»: код, тесты, CODEBASE_INVENTORY.md, API_MAP.md — внутри; issue tracker, monitoring, docs — снаружи. Для каждого внешнего источника укажите, нужен ли он роли и почему.
  3. Разведите артефакты: CLAUDE.md, skill, subagent, CODEBASE_INVENTORY.md, API_MAP.md и MCP. Для каждого напишите, что он делает и почему MCP его не заменяет.
  4. Разберите сценарий COM-481: какой инструмент читает issue, с какими внутренними артефактами сопоставляется, какой результат нужен и почему код не меняется. Добавьте отдельный TASK_SPEC.md, чтобы показать разницу между сырым issue и инженерной постановкой.
  5. Проверьте карту по вопросам: есть ли внешние write-actions? есть ли секреты? не пытается ли MCP заменить task spec или карту проекта? Если Claude Code доступен, сымитируйте чтение issue и сверку с inventory; если нет — выполните вручную. Запишите вывод в MCP_CAPABILITY_MAP.md.

Если Claude Code или MCP недоступны: выполните карту и сценарий вручную в редакторе, без реальных подключений и токенов; критерии проверки те же.

Проверка

  • В MCP_CAPABILITY_MAP.md есть клиент, сервер и минимум три read-only инструмента.
  • Внешние источники отделены от внутренних артефактов.
  • MCP не заменяет CLAUDE.md, skill, subagent, CODEBASE_INVENTORY.md и API_MAP.md.
  • Для COM-481 указано, какой инструмент читает issue и с чем он сопоставляется.
  • Есть TASK_SPEC.md, и объяснено отличие issue от task spec.
  • Нет внешних write-actions, реальных токенов и секретов.
  • Сценарий не меняет код на этапе discovery.
  • Если Claude Code или MCP недоступны, карта и сценарий выполнены вручную по тем же критериям.
