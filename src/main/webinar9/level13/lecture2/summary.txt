# Саммари лекции 2

## Правило «сначала вручную» для MCP — Claude Code, 13 уровень

## 1. Здесь легко переборщить

Когда вы впервые узнаёте про MCP, он легко выглядит идеальным решением почти любой боли. Копировать issue руками? MCP. Открыть документацию? MCP. Есть лог ошибки? Тоже MCP. Тут очень легко начать относиться к нему как к универсальной отвёртке, которой заодно можно варить кофе. А дальше — лишние настройки, лишние токены, лишние риски и ноль пользы.

Проблема не в самом MCP, а в ложном ощущении зрелости процесса: будто сам факт подключения внешнего сервера делает workflow «профессиональным». Наоборот. Профессиональный workflow начинается с вопроса: какую конкретную боль я убираю?

Сквозной контекст: команда работает над Commerce OS, в Workflow Kit есть skill `issue-analysis` — он превращает входящую задачу в task spec. Пока разработчик руками открывает issue в трекере, копирует заголовок, описание, иногда комментарии, вставляет в Claude и просит собрать черновик `TASK_SPEC.md`. Раз в месяц — не проблема. Десять раз в день — повторяющаяся точка трения.

Именно в таких местах стоит думать про MCP. Не «куда бы ещё прикрутить технологию», а «где повторяется ручной шаг, что съедает время и плодит ошибки».

## 2. Формула «сначала вручную»

Правило звучит слишком просто, поэтому новички часто недооценивают его силу. Кажется, что «сначала вручную» — шаг назад, капитуляция перед автоматизацией. На деле это нормальная инженерная дисциплина: пока вы не сделали действие руками несколько раз, вы не понимаете, что автоматизируете, где настоящая боль и где её границы.

Формула курса:

> Сначала вручную. Автоматизировать внешний доступ стоит только тогда, когда он повторяется, приносит реальную пользу и остаётся управляемым.

Слово «управляемым» здесь важнее, чем кажется. Иногда разработчики видят повторяемую задачу и сразу бегут строить интеграцию. Но если у интеграции нет понятного scope, нет доверия к серверу, нет безопасной работы с credentials и нет способа проверить, что данные пришли корректно, вы не автоматизировали работу — вы автоматизировали риск.

Сравните два сценария. В первом у вас один короткий stack trace, который вы просто вставили в Claude и за две минуты получили гипотезы. Во втором — постоянная работа с живыми issue из трекера, где важны статус, метки, комментарии и актуальное описание задачи. В первом случае MCP избыточен. Во втором он вполне может оказаться разумным.

```text
Нужны внешние данные?
  → нет → работаем без MCP
  → да → это повторяется регулярно?
      → нет → работаем без MCP
      → да → можно ограничить scope и проверить результат?
          → нет → работаем без MCP
          → да → рассматриваем read-only MCP
```

Схема заканчивается не на «срочно подключаем всё», а скромно: рассматриваем read-only MCP. Даже положительный ответ — не карт-бланш, а обоснованный следующий шаг.

## 3. Три вопроса, которые решают почти всё

Чтобы решение было инженерным, а не интуитивным, прогоняйте ситуацию через три измерения: ценность, повторяемость, управляемость. Если хотя бы одно проваливается, с MCP лучше не спешить.

| Измерение | Что вы спрашиваете | MCP скорее нужен | MCP скорее не нужен |
|---|---|---|---|
| Ценность | Какую боль мы убираем? | ручной шаг медленный, ошибочный, постоянный | экономия символическая, боль надумана |
| Повторяемость | Как часто это происходит? | каждый день или каждую неделю | один раз по особому случаю |
| Управляемость | Можем ли ограничить и проверить интеграцию? | read-only, понятный scope, доверенный сервер, проверяемый результат | непонятные права, сомнительный сервер, результат нельзя быстро проверить |

Ценность — не «было бы прикольно», а конкретная боль. «Каждый день руками копируем пять полей из issue tracker, забываем комментарии, теряем контекст» — хорошее описание. «Хотим современную архитектуру» — плохое: архитектура не самоцель.

Повторяемость отвечает на вопрос: вы точно будете делать это ещё много раз? Заглянуть в одну ошибку дешевле руками. MCP окупается, когда действие стало частью цикла.

Управляемость — фильтр от неприятностей: доступ только на чтение, ограниченный список tools, понятный источник для сверки. Нет ясного ответа — интеграция сырая.

## 4. Кейс Workflow Kit: MCP для issue tracker

В Workflow Kit есть skill `issue-analysis`. Команда думает: добавить ли `mcp/issue-tracker.json`, чтобы не копировать вручную данные из задач Commerce OS?

Смотрим по трём вопросам:

- **Ценность зелёная.** Поля живые: заголовок, описание, статус, метки, иногда комментарии. Ручное копирование хрупкое — забыл комментарий, вставил старую формулировку, утащил не тот номер задачи.
- **Повторяемость зелёная.** Это не разовый сценарий, а рабочий ритм команды.
- **Управляемость зелёная**, если начать с чтения. Менять статус, писать комментарии и закрывать задачи сейчас не нужно.

Минимум: `list_issues`, `get_issue`, `search_issues`.

```text
## Решение по MCP
Источник: issue tracker Commerce OS
Нужен ли MCP: да
Режим: read-only
Причина: задачи приходят регулярно, данные живые, ручной copy-paste повторяется
Проверка: сверять id и заголовок issue с источником
```

Здесь нет ни слова про «автоматически обновлять workflow всей компании». Очень локальное и трезвое решение: да, read-only issue tracker MCP полезен.

## 5. Иногда лучше остаться без MCP

Взрослая часть темы — уметь сказать не только «да», но и спокойно, без чувства вины, «нет». Это профессиональный навык: он экономит время, деньги и нервные клетки.

Один лог ошибки из локального запуска. Вы в терминале, проект открыт, ошибка перед глазами. Поднимать ради этого MCP к monitoring-системе — как вызывать грузовой кран, чтобы переставить табуретку. То же с разовым обращением к документации: нужен фрагмент из changelog — проще вставить кусок в сессию, чем поднимать внешний слой. Правило «сначала вручную» именно поэтому и работает.

Есть и более жёсткие случаи. Сервер сомнительный, credentials не ограничить, output огромный и засоряет контекст, результат не проверить быстро. Тут MCP не лишний — вредный: красивая схема и непрозрачное поведение.

| Ситуация | Разумный путь |
|---|---|
| Один stack trace из локального запуска | вставить в чат вручную |
| Один скриншот или маленький лог | вставить вручную |
| Регулярный анализ живых issue | read-only MCP оправдан |
| Автоматическое закрытие issue после merge | слишком рано, нужен отдельный разбор и согласование |
| Доступ к чувствительным данным без ясного scope | не подключать |

Паттерн простой: MCP хорош там, где есть регулярность и границы. Где разовость и неопределённость — мешает.

## 6. Read-only почти всегда первый шаг

Часто разработчик рассуждает так: «Раз подключаем issue tracker, давайте сразу и статусы менять, и комментарии писать». Звучит естественным продолжением, а на деле это уже другой класс риска, и здесь многие команды случайно делают слишком большой шаг.

Даже один и тот же сервис живёт в двух принципиально разных режимах. Аналитический: прочитать список задач, открыть карточку, найти issue по фильтру. Меняющий внешний мир: закрыть задачу, перевести статус, оставить комментарий, назначить исполнителя. Формально «тот же трекер», по риску — две разные планеты.

Поэтому курс предлагает почти всегда начинать с read-only. Сначала докажите, что интеграция полезна и результат проверяем, а write-операции решайте позже.

В Commerce OS: `get_issue` нужен, `search_issues` тоже. А «перевести COM-481 в Done после merge» — уже другая история: появляется side effect, и учебный вопрос превращается в организационную политику. Не продолжение того же шага, а отдельное инженерное решение.

## 7. Фиксируем решение в артефактах проекта

Одна из частых слабостей — хорошие решения принимаются «в голове» и через два дня исчезают. Вчера вы твёрдо понимали, зачем нужен MCP и где границы, а сегодня открыли проект — и не помните, почему трекер подключать можно, а комментарии писать нельзя. Поэтому решения стоит фиксировать письменно — в task spec или в заметках рядом со skill’ом.

```text
## Внешний контекст
Нужен доступ к issue COM-481 из трекера.
Использовать только read-only MCP issue-tracker.
Не менять статус issue и не писать комментарии.
Если MCP недоступен, взять текст issue вручную.
```

Хороший инженерный стиль по трём причинам:

- решение прозрачно для любого, кто откроет задачу позже;
- есть fallback: MCP не работает — процесс не встаёт намертво;
- сразу видна граница интеграции.

Можно фиксировать это и рядом со skill’ом Workflow Kit. В описании `issue-analysis` указать: при read-only MCP skill берёт оттуда поля issue, но не меняет внешнее состояние. Это уже не молчаливое знание автора, а часть поддерживаемого процесса.

## 8. Решение на трёх ситуациях из Commerce OS

Чтобы правило закрепилось, прогоним его на земных сценариях:

```text
## Решения команды
Issue intake из трекера — да, через read-only MCP.
Разовый локальный лог — нет, вручную.
Изменение статуса issue — нет, отдельный approval.
```

Главная мысль лекции: решение «подключать MCP или нет» — не про моду и не про то, как выглядит workflow со стороны. Это три честных вопроса подряд:

1. убираю ли я реальную боль;
2. повторяется ли она;
3. могу ли я ограничить и проверить интеграцию.

Прошли все три — вручную вы уже наигрались, пора автоматизировать. Провалился хоть один — оставайтесь на копипасте без чувства вины. Так Workflow Kit для Commerce OS набирает не модные интеграции, а только те, что заслужили место.

## Что запомнить

- MCP легко переоценить: подключение сервера само по себе не делает workflow зрелым.
- Правило курса: сначала вручную, автоматизировать внешний доступ только при повторяемости, пользе и управляемости.
- Три измерения: ценность, повторяемость, управляемость.
- Ценность — конкретная боль, а не «современная архитектура».
- Повторяемость — действие стало частью цикла, а не разовый случай.
- Управляемость — read-only, понятный scope, доверенный сервер, проверяемый результат.
- Read-only MCP — почти всегда первый шаг; write-операции — отдельное решение.
- Регулярный issue intake оправдывает read-only MCP; разовый лог или скриншот — нет.
- Решение по MCP фиксируется в task spec или рядом со skill’ом, вместе с fallback и границами.
- Не подключайте MCP к чувствительным данным без ясного scope.

## Практика (15–25 минут)

**Цель:** применить правило «сначала вручную» к трём сценариям Commerce OS, обосновать решения по MCP и зафиксировать границы read-only интеграции в task spec.

**Что сделать:**
1. В вымышленном Workflow Kit создайте `MCP_DECISION.md` и разберите три ситуации: регулярный issue intake из трекера; один локальный stack trace; автоматическое закрытие issue после merge.
2. Для каждой ситуации ответьте на три вопроса: ценность, повторяемость, управляемость. Запишите решение `MCP нужен / не нужен / нужен позже` и причину.
3. Для issue intake опишите read-only контур: сервер `issue-tracker`, tools `list_issues`, `get_issue`, `search_issues`, что именно читается и что запрещено.
4. Добавьте в `TASK_SPEC.md` блок «Внешний контекст»: какой issue читаем, read-only режим, запрет менять статус и писать комментарии, fallback при недоступном MCP.
5. Проверьте, что в решении нет write-actions, реальных токенов и секретов. Если Claude Code или MCP недоступны, выполните разбор вручную; критерии те же.

**Проверка:**
- В `MCP_DECISION.md` разобраны три ситуации.
- Для каждой есть ответы по ценности, повторяемости и управляемости.
- Issue intake получил read-only MCP с тремя инструментами.
- Локальный лог и изменение статуса не получили MCP-автоматизации.
- В `TASK_SPEC.md` есть внешний контекст, границы и fallback.
- Нет write-actions, секретов и реальных внешних подключений.
- Решение объясняет, какую боль убирает MCP, а не «так современнее».
- Если Claude Code или MCP недоступны, разбор выполнен вручную по тем же критериям.
