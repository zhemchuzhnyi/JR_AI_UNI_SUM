# Уровень 13 — контрольные вопросы

Контрольный блок по 5 лекциям уровня 13: 25 открытых вопросов с короткими ответами и ссылками на конспекты. Вопросы покрывают MCP как внешний слой, правило «сначала вручную», категории возможностей, конфиг MCP и четыре зоны риска.

## Лекция 1 — MCP как внешний слой

1. **Что такое MCP применительно к Claude Code?**<br>
   MCP — внешний слой возможностей Claude Code: договорённость, как Claude узнаёт о внешних инструментах, вызывает их и получает ответ. Он не открывает весь интернет, а добавляет контролируемые «окошки» во внешние системы: трекер, monitoring, read-only БД, документацию, PR-комментарии.<br>
   → [Лекция 1](lecture1/index.html)

2. **Какие три роли выделяются в концептуальной модели MCP?**<br>
   Клиент — Claude Code; сервер — доступ к возможностям внешней системы; инструмент — отдельное действие вроде `list_issues`, `get_issue`, `search_docs`. Схема: задача → Claude Code → MCP-клиент → MCP-сервер → внешняя система.<br>
   → [Лекция 1](lecture1/index.html)

3. **Какие три класса возможностей даёт MCP?**<br>
   Доступ к внешним данным («что происходит снаружи?»), внешние действия («что можно изменить снаружи?») и узкоспециализированный контекст («что нужно знать снаружи, чтобы понять задачу?»). На старте обычно нужнее данные, а не write-действия. Кроме tools сервер может отдавать resources (через `@`-упоминание) и prompts (через slash-команду).<br>
   → [Лекция 1](lecture1/index.html)

4. **Что MCP не заменяет и чем issue отличается от task spec?**<br>
   MCP не заменяет `CLAUDE.md`, skill, subagent, `CODEBASE_INVENTORY.md`, `API_MAP.md` и `TASK_SPEC.md`. Issue в трекере — сырой внешний сигнал, а task spec — инженерная постановка задачи в контексте проекта. MCP приносит сигнал, но не оформляет задачу.<br>
   → [Лекция 1](lecture1/index.html)

5. **Почему для Workflow Kit разумен read-only issue-tracker с `list_issues`, `get_issue`, `search_issues`?**<br>
   Он закрывает повторяющуюся боль с ручным копированием issue, даёт живые данные для `issue-analysis` и при этом не меняет внешнее состояние. Репозиторий остаётся источником истины о коде, трекер — о постановке задачи.<br>
   → [Лекция 1](lecture1/index.html)

## Лекция 2 — правило «сначала вручную»

6. **В чём формула «сначала вручную» для MCP?**<br>
   Автоматизировать внешний доступ стоит только тогда, когда он повторяется, приносит реальную пользу и остаётся управляемым. Сначала действие выполняется руками; это показывает настоящую боль, её границы и то, что вообще имеет смысл автоматизировать.<br>
   → [Лекция 2](lecture2/index.html)

7. **Через какие три измерения курса советует прогонять идею MCP?**<br>
   Ценность (какую конкретную боль убираем), повторяемость (как часто это происходит) и управляемость (можно ли ограничить scope, использовать read-only и проверить результат). Если хотя бы одно измерение проваливается, с MCP лучше не спешить.<br>
   → [Лекция 2](lecture2/index.html)

8. **Когда MCP скорее не нужен?**<br>
   Для разового локального stack trace, одного скриншота, маленького лога или однократного обращения к документации. Также если сервер сомнительный, credentials не ограничить, output огромный или результат нельзя быстро проверить.<br>
   → [Лекция 2](lecture2/index.html)

9. **Почему read-only MCP почти всегда первый шаг?**<br>
   Он даёт качественный внешний контекст при минимальном blast radius и не меняет внешнее состояние. Сначала доказываем пользу и проверяемость интеграции, а write-операции рассматриваем отдельно, с подтверждениями и согласованием.<br>
   → [Лекция 2](lecture2/index.html)

10. **Где фиксируется решение по MCP и что в нём должно быть?**<br>
    В `TASK_SPEC.md` или рядом со skill’ом: какой источник используется, read-only режим, какие действия запрещены, что делать при недоступном MCP. Нужен fallback: если MCP не работает, текст issue берётся вручную.<br>
    → [Лекция 2](lecture2/index.html)

## Лекция 3 — категории MCP-возможностей

11. **Почему запоминать названия MCP-серверов бесполезно и что важнее?**<br>
    Названия и продукты меняются, а типы рабочих болей стабильны. Важнее три вопроса к категории: какой внешний сигнал она даёт, Claude только читает или уже меняет, куда это встраивается в процесс — task spec, план, diff, tests, review.<br>
    → [Лекция 3](lecture3/index.html)

12. **Какие основные категории MCP-возможностей перечисляет лекция?**<br>
    Issue tracker, PR/source control, monitoring/incidents, docs lookup, read-only DB, browser/design, communications, platform/deployment. У каждой категории есть read-only режим и потенциальные write-actions.<br>
    → [Лекция 3](lecture3/index.html)

13. **Какую пару категорий лекция называет хорошим стартом для Commerce OS?**<br>
    Issue tracker и PR/source control: трекер отвечает «что хотели изменить?», diff — «что реально изменили?». С read-only Claude получает живое описание issue и комментарии ревью, не меняя внешнее состояние.<br>
    → [Лекция 3](lecture3/index.html)

14. **Чем monitoring отличается от docs lookup и какую проблему закрывает Context7?**<br>
    Monitoring даёт фактический сигнал: alert, stack trace, метрику, лог. Docs lookup даёт нормативный контекст: как это должно работать по официальной версии. Context7 подтягивает актуальную version-specific документацию библиотек, чтобы Claude не опирался на устаревшие знания из обучения.<br>
    → [Лекция 3](lecture3/index.html)

15. **Почему один и тот же MCP-сервер может быть и безопасным, и опасным?**<br>
    Риск определяют конкретные tools, а не название категории. `get_issue` и `search_issues` — read-only, а `update_issue` и `transition_issue` уже меняют внешний мир. Поэтому нужен минимально достаточный набор tools и read-only по умолчанию.<br>
    → [Лекция 3](lecture3/index.html)

## Лекция 4 — конфиг MCP

16. **Почему MCP-конфиг называют инженерным артефактом?**<br>
    Его читают, кладут в репозиторий, обсуждают в diff, версионируют и при необходимости отключают. По конфигу должно быть понятно, куда Claude идёт, от чьего имени и кто ещё видит подключение.<br>
    → [Лекция 4](lecture4/index.html)

17. **На какой вопрос отвечает `transport` и какие варианты рассматриваются?**<br>
    Transport отвечает, как Claude добирается до MCP-сервера. Локальный `stdio` — процесс рядом с Claude (`command`/`args`); удалённый HTTP-подобный — подключение к уже работающему серверу по сети (`type: http`/`url`). В project-scope это обычно карта `mcpServers` в `.mcp.json`.<br>
    → [Лекция 4](lecture4/index.html)

18. **Чем scope конфига отличается от auth-scope и какой scope нужен Workflow Kit?**<br>
    Scope конфига — где живёт файл и кому доступен: `user`, `local`, `project`, `plugin`. Auth-scope — права токена/OAuth, например `read:issues`. Для командного MCP нужен `project` scope: запись живёт в `.mcp.json`, видна команде и проходит review; при первом запуске чужого `.mcp.json` Claude Code спрашивает подтверждение.<br>
    → [Лекция 4](lecture4/index.html)

19. **Как правильно обращаться с токеном MCP?**<br>
    Не хранить токен в конфиге или репозитории. Секреты — в переменных окружения/`.env`, реальные файлы в `.gitignore`, в Git только `.env.example`. В конфиге ссылка `${ISSUE_TRACKER_URL}`, auth-scope `read:issues`, плюс ротация и отзыв токена. Второй путь — OAuth через `/mcp` или `claude mcp login`: токены хранит Claude Code, в конфиге их нет.<br>
    → [Лекция 4](lecture4/index.html)

20. **Зачем нужна `/mcp` и какие действия она обычно поддерживает?**<br>
    Чтобы проверить подключение, а не верить на слово. `list` показывает серверы, `get` — детали конкретного подключения, `status` — состояние и ошибки, `debug` — подробную диагностику. Из терминала доступны `claude mcp list/get/remove`, а временно выключить сервер можно через `/mcp disable`. Если инструмент не работает, сначала проверяют `/mcp`, а не переписывают workflow.<br>
    → [Лекция 4](lecture4/index.html)

## Лекция 5 — четыре зоны риска

21. **Какие четыре зоны риска MCP выделяет лекция?**<br>
    Credentials (секреты и scope), prompt injection (внешний текст как инструкции), избыточный объём данных (засорение контекста) и side effects (write-действия и другие изменения снаружи). Каждой зоне соответствует своя политика.<br>
    → [Лекция 5](lecture5/index.html)

22. **Как защищаться от prompt injection через issue или документ?**<br>
    Считать любой внешний текст данными, а не инструкциями. Извлекать симптомы, ограничения и риски, но не выполнять команды внутри issue. Помнить, что injection не всегда атака — это может быть обычный хаос в тексте.<br>
    → [Лекция 5](lecture5/index.html)

23. **Как ограничивать объём данных, который MCP возвращает в контекст?**<br>
    Использовать `filter`, `limit`, `fields` и `summarize`: выбирать только нужные объекты и поля, сначала делать обзорную выборку, потом точечно читать полный issue. Не просить «дай всё» без конкретной задачи. Claude Code предупреждает при выводе больше ~10 тысяч токенов, стандартный потолок — около 25 тысяч; `MAX_MCP_OUTPUT_TOKENS` меняет лимит, но узкий запрос всё равно лучше.<br>
    → [Лекция 5](lecture5/index.html)

24. **Какая политика предлагается для side effects и MCP из плагина?**<br>
    Read-only по умолчанию; write-actions только по явному сценарию, с подтверждением на каждый вызов. Правила задаются как `mcp__server__tool`: например, `mcp__github__get_diff` — allow, `mcp__github__comment_on_pr` — ask. `close_issue` выключен, `deploy_release` вне учебного baseline. MCP из плагина проверяется дважды: сначала плагин, затем сам сервер, его tools, scopes и credentials. Долгий вызов уходит в `/tasks`.<br>
    → [Лекция 5](lecture5/index.html)

25. **Как выглядит риск-модель issue-tracker для Workflow Kit?**<br>
    Credentials — только env vars; permissions — `read:issues`; prompt injection — текст issue считается данными; output — не больше 20 тикетов, fields-only; freshness — критичные статусы перепроверяются; revocation — токены отзываются. Write-действия отсутствуют.<br>
    → [Лекция 5](lecture5/index.html)
