Конфиг MCP

Claude Code

13 уровень · лекция 4
MCP-конфиг — инженерный артефакт, а не туманная магия. Он отвечает на четыре вопроса: как Claude добирается до сервера, где живёт файл, от чьего имени идёт запрос и чем вы проверяете подключение.

1. MCP-конфиг как инженерный артефакт

Когда дело доходит до реального подключения MCP, легко представить туманную магию: где-то что-то прописали, Claude внезапно увидел issue tracker, все счастливы. В реальной работе так лучше не делать. MCP без понятного конфига — как удлинитель без вилки: выглядит технически, а пользы мало.

Конфиг превращает подключение в артефакт: его читают, кладут в репозиторий, обсуждают в diff, при нужде отключают. Такие вы уже знаете — CLAUDE.md, SKILL.md, файл агента. MCP-конфиг фиксирует, к какому серверу Claude подключается, как до него добирается, где живёт и как проходит авторизация.

workflow-kit/
  .claude/
    mcp/
      issue-tracker.json
mcp/issue-tracker.json
  → transport: как Claude добирается до сервера
  → scope конфига: где живёт файл и кому доступен
  → auth: как проходит авторизация
  → MCP server → issue tracker
Часть конфигаНа какой вопрос отвечает
nameчто это за подключение

Точные ключи, формат файла и даже названия transport’ов могут немного отличаться от версии к версии. Важнее логика. Если вы открыли mcp/issue-tracker.json, вы должны быстро понять три вещи: куда Claude идёт, от чьего имени он туда идёт и кто ещё в команде видит этот конфиг.

Если вы когда-нибудь увидите токен прямо внутри такого файла, это уже не «удобство». Это крик о помощи.

2. Transport: дорога Claude к MCP-серверу

Transport — ответ на вопрос, каким способом Claude Code разговаривает с MCP-сервером. Не что сервер умеет, а как до него добраться. Аналогия: transport — это дорога. Можно идти в соседнюю комнату пешком, а можно звонить в другой офис по сети.

В MCP «внешний» означает внешний по отношению к встроенному контексту репозитория: возможность приходит не из того, что Claude и так читает внутри проекта. Но физически она может жить как в локальном процессе на вашей машине, так и в удалённом сервисе по сети.

ВариантЧто это значит по-человеческиКогда обычно подходит
Локальный stdioClaude запускает процесс рядом с собой и обменивается данными через стандартные потокилокальный скрипт, утилита, эксперимент на вашей машине
Удалённый HTTP-подобный transportClaude подключается к уже работающему серверу по сетиобщая командная система: issue tracker, docs lookup, monitoring

Локальный вариант удобен для быстрых экспериментов:

{
  "name": "docs-local",
  "transport": "stdio",
  "command": "python",
  "args": ["scripts/docs_server.py"]
}

Минус очевиден: пока сервер живёт только на вашей машине, для команды это не актив, а личная игрушка.

Для Workflow Kit и issue-tracker логичнее удалённый сервер. Issue tracker — не программа «только у Пети под столом», а общая внешняя система команды:

{
  "name": "issue-tracker",
  "transport": "http",
  "endpoint": "${ISSUE_TRACKER_URL}"
}

Важен не сам ключ http, а идея: сервер уже существует отдельно, а Claude лишь подключается к нему по адресу. Если возможность нужна только вам и живёт в локальном скрипте — берите локальный процесс; если система общая и должна работать одинаково у всей команды — чаще выигрывает удалённый endpoint.

3. Scope: где живёт конфиг и кому он принадлежит

После transport студенты чаще всего путаются в scope. И это нормально, потому что слово одно, а в практике рядом живут два разных смысла. Scope конфига — где лежит файл и кому доступен. Auth-scope — права токена или OAuth, например read:issues.

Scope конфига отвечает: это моя личная настройка, локальная настройка проекта, командный артефакт в репозитории или часть установленного плагина?

scope конфигаГде живётКому виденКогда обычно выбирать
userв ваших пользовательских настройкахтолько вамодин и тот же сервер нужен вам в разных проектах
localлокально в конкретном проекте, без коммитатолько вам в этом репозиториивы тестируете интеграцию и ещё не готовы делиться
projectв репозитории проектавсей командеMCP — часть общего workflow
pluginприезжает вместе с плагиномвсем, кто поставил plugincapability распространяется на несколько репозиториев

Самый важный для нас случай — project. mcp/issue-tracker.json в Workflow Kit — не личная заметка на холодильнике, а командный артефакт: раз issue-analysis рассчитывает на read-only доступ к issue tracker, подключение должно быть видно команде, лежать в Git и проходить review как код.

Local scope отлично подходит для проб и ошибок: проверяете новый docs lookup сервер, не уверены в формате, не хотите засорять репозиторий — делаете локально, а как только capability реально помогает, повышаете до project. С plugin scope логика похожая, только масштаб больше: подключение приезжает частью plugin-пакета — и ревьюить его нужно так же внимательно.

4. Auth: доступ без выставки токенов

На этом месте у новичков появляется опасное желание: «Ну давайте просто быстро впишем токен прямо в JSON, чтобы уже заработало». Желание человеческое. И очень вредное. Хороший MCP-конфиг всегда разводит две вещи: описание способа авторизации и секретное значение, которое реально даёт доступ.

Конфиг может говорить: «я использую OAuth» или «мне нужен endpoint из переменной окружения». Но сам токен, секрет, пароль или ключ в Git не кладётся. Никогда. Даже если это «только для учебного проекта».

# .env.example
ISSUE_TRACKER_URL=
ISSUE_TRACKER_TOKEN=
# .gitignore
.env
.env.local
*.token
mcp/*.local.json

Конфиг ссылается на эти значения, а не хранит их внутри:

{
  "name": "issue-tracker",
  "transport": "http",
  "endpoint": "${ISSUE_TRACKER_URL}",
  "auth": "oauth"
}

Синтаксис подстановки переменных может отличаться от версии и инструмента. Где-то это ${VAR}, где-то другой формат. Важен принцип: секреты живут вне репозитория, а конфиг только знает, что они существуют.

Auth-scope — не scope конфига, а права самой авторизации. Issue tracker может разрешать токену только read:issues. Именно это нужно для учебного Workflow Kit. Не admin:*, не «полный доступ ко всему», а узкое право на чтение issue. Чем уже auth-scope, тем меньше радиус поражения.

Auth отвечает на вопрос «как пройти в здание», а auth-scope — «в какие комнаты вас после этого пустят». Обычно нужен не мастер-ключ директора, а гостевой пропуск.

5. /mcp: панель проверки подключения

Допустим, вы аккуратно написали конфиг, убрали секреты из репозитория и положили файл туда, куда нужно. Следующий шаг простой и очень недооценённый: не верить на слово, что всё подключилось правильно. Для этого существует служебный интерфейс вроде команды /mcp или её аналога. Точное имя и набор подкоманд могут меняться, но модель обычно одна: list, get, status, debug.

/mcp list            # показать все подключённые MCP-серверы
/mcp get issue-tracker  # открыть детали конкретного подключения
/mcp status          # состояние и последние ошибки
/mcp debug           # более подробная диагностика

Не держитесь за эти названия как за заповеди в камне — в вашей версии формулировки могут отличаться. Логика полезна в любой версии.

  • list — видит ли система ваш MCP-сервер вообще;
  • get — что за transport, endpoint и описание у конкретного подключения;
  • status — когда «вроде настроили, но ничего не работает»;
  • debug — когда нужна подробная диагностика и логи.

Полезное профессиональное правило: если get_issue не работает, не начинайте с переписывания половины workflow. Сначала проверьте /mcp. Часто проблема скучная и бытовая: неправильный endpoint, не тот scope, забытая переменная окружения, просроченный токен. Лучше чинить на уровне подключения, а не городить новые слои хаоса.

Для Workflow Kit это особенно важно. Если issue-analysis внезапно перестал «видеть» задачу Commerce OS, не нужно сразу обвинять skill. Возможно, issue-tracker не поднялся или не прошёл auth. Диагностика через /mcp экономит время и драматические монологи в терминал.

6. Собираем mcp/issue-tracker.json для Workflow Kit

Теперь соберём в один артефакт read-only issue-tracker, который уже оправдали для issue-analysis. Нужен project-scoped MCP-конфиг в Workflow Kit. Задача — перестать копировать описание issue руками и дать Claude читать задачи из внешней системы контролируемым способом.

{
  "name": "issue-tracker",
  "transport": "http",
  "endpoint": "${ISSUE_TRACKER_URL}",
  "auth": "oauth",
  "authScopes": ["read:issues"],
  "tools": [
    { "name": "list_issues", "permissions": "read-only" },
    { "name": "get_issue", "permissions": "read-only" },
    { "name": "search_issues", "permissions": "read-only" }
  ],
  "notes": "Read-only access for Commerce OS issue analysis."
}

Точные имена полей могут отличаться — где-то tools подтягиваются с сервера сами, где-то authScopes оформлены иначе. Но как учебная модель чтения конфиг идеален: удалённый сервер, OAuth, суженный до чтения, три read-only tool без единой write-операции. notes объясняет, зачем подключение существует, чтобы через месяц никто не гадал про ещё один JSON-файл.

Если положить файл в workflow-kit/.claude/mcp/issue-tracker.json, закоммитить без секретов и проверить через /mcp, вместо разговорной идеи «надо подключить issue tracker» появится инженерный актив команды: его можно ревьюить, обсуждать, улучшать, переиспользовать. А skill issue-analysis перестанет зависеть от копирования из браузера и обопрётся на читаемый, прозрачный, ограниченный слой возможностей.

Главный результат лекции: туманная магия «где-то что-то прописали» раскладывается на четыре читаемых решения в одном файле:

  1. transport — как Claude добирается до сервера;
  2. scope конфига — где файл живёт и кто его видит;
  3. auth со ссылкой на env — от чьего имени и с какими правами идёт запрос;
  4. /mcp — чем вы это проверяете, когда «вроде настроили, а не работает».

Открыли issue-tracker.json, прочитали эти четыре ответа за минуту — значит, конфиг написан по-инженерному, а не скопирован из случайного JSON в интернете.

Что запомнить

  • MCP-конфиг — инженерный артефакт, который читают, ревьюят и версионируют.
  • Конфиг отвечает: куда Claude идёт, от чьего имени и кто ещё видит подключение.
  • Transport — способ добраться до сервера: локальный stdio или удалённый HTTP-подобный.
  • Scope конфига — где живёт файл и кому доступен: user, local, project, plugin.
  • Для командного Workflow Kit обычно нужен project scope.
  • Auth описывает способ авторизации, но секреты хранятся вне репозитория.
  • Auth-scope сужает права токена, например read:issues.
  • Секреты — в .env/переменных окружения; в Git только .env.example.
  • /mcp помогает проверить list, get, status и debug подключения.
  • Если инструмент не работает, сначала проверьте /mcp, а не переписывайте workflow.
  • Read-only issue tracker: list_issues, get_issue, search_issues, без write-операций.
  • Четыре ответа читаемого конфига: transport, scope, auth, проверка через /mcp.

Практика (15–25 минут)

Цель: собрать project-scoped read-only MCP-конфиг для issue tracker, спрятать секреты и проверить подключение через /mcp или ручной аудит.

Что сделать

  1. В вымышленном Workflow Kit создайте mcp/issue-tracker.json с transport: http, ${ISSUE_TRACKER_URL}, auth: oauth, authScopes: ["read:issues"] и read-only tools list_issues, get_issue, search_issues.
  2. Создайте .env.example с пустыми ISSUE_TRACKER_URL и ISSUE_TRACKER_TOKEN; добавьте .env, .env.local, *.token и mcp/*.local.json в .gitignore.
  3. Заполните MCP_CONFIG_REVIEW.md: transport и почему он подходит; scope конфига и кто видит файл; auth-scope; какие tools read-only, какие write-actions запрещены; как проверить через /mcp.
  4. Проверьте конфиг на секреты: токенов, реальных URL и паролей внутри JSON быть не должно. Если Claude Code доступен, выполните /mcp list и /mcp get issue-tracker; если нет — проведите ручной аудит по тем же полям.
  5. Зафиксируйте в MCP_CONFIG_REVIEW.md fallback: если MCP недоступен, issue читается вручную и кладётся в TASK_SPEC.md. Не подключайте реальные внешние сервисы.

Если Claude Code или MCP недоступны: выполните конфиг и аудит вручную в редакторе, без реальных подключений; критерии проверки те же.

Проверка

  • Конфиг лежит в mcp/issue-tracker.json и использует project scope.
  • transport, endpoint, auth и auth-scope явно указаны.
  • В конфиге только read-only tools; write-actions отсутствуют.
  • Секретов в JSON нет; .env.example и .gitignore настроены.
  • В MCP_CONFIG_REVIEW.md объяснены все четыре решения: transport, scope, auth, /mcp.
  • Есть fallback при недоступном MCP.
  • Нет реальных токенов, URL и внешних подключений.
  • Если Claude Code недоступен, аудит выполнен вручную по тем же критериям.
