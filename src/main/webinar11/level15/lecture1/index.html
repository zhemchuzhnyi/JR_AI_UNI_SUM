Parallelism levels

Claude Code

15 уровень · лекция 1
По умолчанию достаточно одной сессии Claude. Subagent, worktree, background и agent team — не фичи «на всякий случай», а design decision, который оправдывается структурой задачи и ценой координации.

1. Один Claude часто лучше маленькой «AI-команды»

Когда люди впервые доходят до темы multi-agent, их почти всегда тянет переусложнить даже простую задачу. Это нормальная стадия: инструменты уже под рукой, и рука сама тянется собрать AI-оркестр там, где хватило бы одного исполнителя. Поэтому вопрос стоит сместить: не «что включить», а «когда это оправдано».

По умолчанию достаточно одной основной сессии Claude. Всё остальное нужно оправдать задачей.

Один Claude уже читает код, работает в plan mode, вносит изменения, запускает проверки и показывает diff. Если задача небольшая, последовательная и находится в одном месте проекта, subagent, отдельная сессия или worktree её не ускорят — они лишь добавят движущихся частей.

Полезно прогонять задачу через признаки:

Признак задачиЧто спрашиваем
РазмерЭто небольшое изменение или длинная многошаговая работа?
Независимость частейМожно ли и правда разделить работу на куски, которые не мешают друг другу?
OwnershipМожно ли честно сказать, кто отвечает за какие файлы, модули или слои?
РискЭто простой UI-текст или sensitive area вроде payments, auth, migrations?
VerificationЕсть ли tests, checks и понятный способ доказать, что всё работает?
Merge-conflict riskНе полезут ли разные роли в один и тот же файл?
Human attentionЕсть ли у вас ресурс проверять промежуточные результаты?

Parallelism — это не «фича», а design decision. Его принимают до старта работы, а не «по ходу, потому что стало интересно».

Пример из Commerce OS: issue «исправить подпись в сообщении об ошибке в корзине» — а вы запускаете planner, reviewer и background agent. Всё равно что вызвать строительную бригаду поправить криво висящую картину.

2. Меню уровней: от сессии до agent team

Варианты параллельности — не хаос возможностей, а ограниченное меню: выбираете не «что моднее», а «что дешевле по координации и достаточно для задачи». Есть два измерения: уровень координации и режимы, которые меняют способ исследования, изоляции или исполнения.

Уровень / режимКогда подходитЧто даёт
Одна основная сессияНебольшая и понятная задачаМинимум координации
Отдельная роль: subagent или fresh / separate sessionНужно изолированное investigation или независимый reviewОтдельный context window без full team
Agent teamЕсть несколько независимых workstreams и явная точка координацииКоординация нескольких ролей
plan modeНужна разведка без editsОграничение текущей сессии, а не новый worker
worktreeНужны параллельные или рискованные editsFile/Git isolation; часто идёт вместе с выбранным уровнем
Background sessionРабота действительно независима и её можно вести асинхронноAdvanced operational mode; нужен явный status tracking

То есть plan mode и worktree — не ещё два «следующих агента в списке», а модификаторы выбранного уровня. Конкретный surface background-сессий и agent team может отличаться по версии Claude Code, но принцип выбора остаётся.

Чтобы это почувствовать, полезно вести короткий decision record рядом с AGENT_HANDOFF_CONTRACT.md:

# Решение по параллелизму — COM-482
Задача: вынести refund-валидацию из OrderService в отдельный helper.
Размер: небольшой
Независимые части: нет
Риск: средний, payment-adjacent
Тесты: есть 2 целевых теста
Выбор: одна сессия + plan mode
Отвергнуто:
- subagent: отдельная роль не нужна
- worktree: параллельных edits нет
- agent team: независимых workstreams нет

Важно не только то, что выбрали, но и то, от чего осознанно отказались. Именно так решение становится проверяемым артефактом, а не «ощущением».

3. Coordination cost важнее количества агентов

Когда говорят «давайте распараллелим», обычно думают только о выигрыше по времени. Но у параллельности есть цена, и не только в токенах. Самое дорогое часто человеческое: внимание, контроль, синхронизация промежуточных решений.

Компонент стоимостиЧто это значит на практике
КонтекстЗадачу нужно объяснить нескольким ролям, а не одной
Время на handoffКаждый результат надо передать дальше и правильно прочитать
Git-стоимостьПоявляются merge conflicts, отдельные ветки, worktree
Review-нагрузкаПроверять нужно не один diff, а несколько промежуточных результатов
Token-costБольше сессий = больше чтений, сводок и перепроверок
Cognitive loadНужно помнить, кто что делает и на каком этапе застрял

Формула курса:

More agents create coordination cost;
use them only when parallelism is real and verification is clear.

Если задача не распадается на куски, вы получаете не «команду», а несколько источников бардака. Представьте, что вы чините баг в Commerce OS: дублируется заказ в pagination на /api/orders. Один Claude в plan mode — одна нить рассуждения. А если поднять исследовательскую сессию, отдельного executor и ещё reviewer — вы платите за три контекста, три handoff-а и три точки, где теряется исходная гипотеза. Быстрее баг не чинится. Он просто наблюдает за вашим организационным талантом.

4. Decision tree для выбора уровня без гадания

Соберём простую шпаргалку, которую держат в Workflow Kit как внутренний документ.

Шаг 1. Базовый уровень

Есть задача
  → Маленькая и последовательная?
      → да: одна сессия
      → нет: нужна разведка без edits?
          → да: plan mode
          → нет: нужна отдельная роль?
              → да: fresh session или subagent
              → нет: одна сессия + уточнить task spec

«Отдельная роль» — это investigation или review, которые лучше отделить от основной работы.

Шаг 2. Что добавить поверх выбранного уровня

Несколько независимых workstreams?
  → нет: выбранного уровня достаточно
  → да:
      будут параллельные edits?
        → да: добавить worktree
        → нет: обойтись без file isolation
      нужна async execution или team-координация?
        → да: background execution или agent team
        → нет: выбранного уровня достаточно

Эти схемы учат главному: сначала вопросы о задаче, потом инструмент.

Три коротких примера:

ЗадачаВыборПочему
Исправить текст кнопки “Refund accpeted” → “Refund accepted”Одна сессияОдин файл, нулевой риск параллельности, verification очевиден
Понять, где собирается response для /api/dashboard/metricsplan modeСначала исследование, edits пока не нужны
Получить свежий взгляд на diff по orders APIОсновная сессия + fresh reviewer sessionНужен новый контекст без writer bias

Рост сложности начинается не с «добавим ещё агентов», а с вопроса «какая у задачи реальная структура?».

5. plan mode против subagent

У многих возникает честный вопрос: если plan mode тоже ничего не редактирует и умеет исследовать проект, зачем тогда subagent? Всё дело в границе между режимом работы и отдельной ролью.

plan mode — это всё ещё ваша основная сессия: одна нить разговора с ограничением «сначала исследуем, без edits». Берите его, когда задача одна и отдельный worker не нужен.

Subagent имеет смысл, когда investigation или review идут в отдельном context window и не засоряют main session: основная держит task spec и implementation context, а subagent собирает evidence по tests или проходит по API map и возвращает сжатый вывод.

ВариантЧто получает main sessionКогда брать
plan modeПолную нить исследования внутри той же сессииОдна задача, один поток
subagentКороткую summary с findings и evidenceОтдельная investigation/review роль
Fresh sessionПолностью новый взглядНужна независимая интерпретация

Пример для Commerce OS:

  • понять, почему metrics endpoint иногда медленный, и код ещё не исследован — достаточно plan mode;
  • основная сессия уже занята implementation другой части, а длинное исследование SQL и logs не хочется тащить внутрь — логичен subagent;
  • implementation уже сделан и нужен независимый reviewer — fresh session.

Без этого различия subagent быстро превращается в «умный синоним любой разведки», а это уже лишняя координация.

6. worktree идёт рядом с параллельными edits

Как только речь заходит о параллельных изменениях файлов, разговор упирается в worktree. Не потому, что Git хочет вас воспитывать, а потому что файловая система не любит, когда несколько потоков разом считают себя хозяевами одних файлов.

Если у вас одна сессия, один diff, одна ветка — драмы нет. А захотите два изменяющих потока (один правит backend, второй проверяет альтернативную реализацию) — без worktree быстро придёте к «а кто это поменял файл, и почему у меня теперь всё смешалось?».

Context isolation и file isolation — не одно и то же:

ИзоляцияЧто защищает
Отдельная сессияИсторию рассуждений и контекст
SubagentMain session от лишнего investigation
worktreeФайлы, ветку и Git-состояние

Формула:

Если параллельность касается рассуждений — может хватить отдельной сессии.
Если параллельность касается edits — почти всегда нужен worktree.

Пример decision note:

Задача: сравнить две реализации фильтрации orders.
Вариант A: main session + одна ветка
Проблема: обе реализации будут менять те же файлы
Решение: завести отдельный worktree для альтернативной реализации
Почему: нужен безопасный параллельный diff без смешивания изменений

Worktree создаёт лишнюю работу, но это честная цена за изоляцию файлов. Куда хуже сэкономить на нём, а потом играть в Git-археолога.

7. Agent management surface против «зомби-сессий»

Как только появляется больше одного параллельного workstream, проблема становится операционной: как помнить, кто ещё жив, кто ждёт решения, кто закончил, а кто тихо ушёл в лес и утащил с собой контекст?

Для этого в современных версиях Claude Code появляется agent management surface — claude agents, agent view или похожий экран; имя и интерфейс могут меняться. Есть он у вас — используйте его. Нет — тот же эффект даёт короткий status note в Workflow Kit, issue note или task list. Важен принцип: единый экран статусов — какие сессии активны, сколько работают, кто их owner, где нужны human decisions.

С момента второго параллельного workstream нужен не обязательно отдельный экран, но обязательно явный способ видеть status, owner и pending decisions.

Без этого появляются классические «зомби-процессы»:

  • вы забыли, что где-то ещё живёт background session;
  • один subagent завершился, но его findings никто не прочитал;
  • одна из сессий уже двадцать минут ждёт решения, а вы ушли в другой поток;
  • вы больше не помните, кто из параллельных workers работает с какой веткой или каталогом.
2+ параллельных workstreams
  → нужен единый экран статусов
      → видно ownership
      → видно elapsed time
      → видны pending decisions
      → меньше зомби-сессий

Профессиональная привычка выглядит просто: прежде чем запускать второй параллельный поток, договоритесь, где именно вы будете видеть status, owner и pending decisions.

8. Шаблон parallelism decision record

Чтобы всё это не осталось красивой теорией, первый рабочий артефакт — запись о том, нужна ли вообще параллельность. Она лежит в Workflow Kit как parallelism-decision.template.md. Шаблон короткий — и это хорошо: чем меньше церемонии, тем выше шанс, что его будут применять.

## Задача
<id / короткое описание>
## Размер

## Независимые рабочие потоки

- ...

Пример для реального issue:

# Решение по параллелизму
## Задача
COM-538 — исправить сортировку refund inbox
## Размер
medium
## Независимые рабочие потоки
no
## Распределение ответственности
none
## Риск
medium
## Доступная проверка
unit tests + smoke
## Выбранный уровень
one session + plan mode
## Отклонённые варианты
- subagent: отдельная роль не нужна
- worktree: нет параллельных edits
- agent team: нет независимых workstreams
## Обоснование
Нужно сначала локализовать причину бага и сделать маленький diff.
Параллельность не даст выигрыша, а только увеличит review cost.

Если verdict говорит «параллельность не нужна» — вопрос закрыт. Если «нужна», следующий вопрос жёстче: это отдельный reviewer/investigator или уже более тяжёлая координация. Сначала фиксируется verdict, и только потом обсуждаются роли, pipeline и handoff.

Один из самых недооценённых навыков в AI-assisted разработке — не запустить пять агентов, а не запустить их, когда очень хочется, и при этом быть правым.

Что запомнить

  • По умолчанию достаточно одной основной сессии Claude.
  • Parallelism — design decision, а не фича; его принимают до старта.
  • Признаки: размер, независимость частей, ownership, риск, verification, merge-conflict risk, human attention.
  • Уровни: одна сессия → отдельная роль (subagent/fresh session) → agent team.
  • plan mode и worktree — модификаторы уровня, а не «ещё два агента».
  • Coordination cost: контекст, handoff, Git, review, tokens, cognitive load.
  • Если параллельность касается рассуждений, может хватить отдельной сессии; если edits — почти всегда нужен worktree.
  • С двумя и более workstreams нужен явный status: owner, время, pending decisions.
  • Первый артефакт — parallelism-decision.template.md.
  • Важно фиксировать не только выбранный уровень, но и отклонённые варианты с причиной.
  • Не запустить лишних агентов, когда очень хочется, — профессиональный навык.

Практика (15–25 минут)

Цель: принять и обосновать решение о параллельности для трёх задач, а не выбирать инструмент «по ощущению».

Что сделать

  1. В вымышленном Workflow Kit создайте PARALLELISM_DECISION.md и скопируйте шаблон из лекции.
  2. Заполните запись для трёх задач: исправление опечатки в одном компоненте; исследование медленного /api/dashboard/metrics без edits; две независимые задачи с параллельными правками backend и frontend.
  3. Для каждой задачи пройдите decision tree: базовый уровень → нужна ли отдельная роль → нужны ли worktree/background/agent team. Запишите выбранный уровень и отклонённые варианты с причиной.
  4. Для задачи с двумя workstreams добавьте status surface: где видны owner, active/pending, elapsed time и решения, которые ждут человека.
  5. Проверьте записи: нет ли параллельности там, где не нужна; есть ли verification; не конфликтуют ли edits. Если Claude Code недоступен, выполните решение вручную по тем же критериям.

Если Claude Code недоступен: выполните решения и проверку вручную в редакторе; критерии те же.

Проверка

  • В PARALLELISM_DECISION.md есть три заполненные записи.
  • Для простой задачи выбран один session, а не agent team.
  • Для investigation выбран plan mode или subagent с обоснованием.
  • Для двух workstreams указан worktree или другой способ file isolation.
  • У каждой записи есть отклонённые варианты и причина.
  • Для параллельной работы описан status surface.
  • Нет выдуманных гарантий и реальных опасных действий.
  • Если Claude Code недоступен, решения и проверка выполнены вручную.
