# Саммари лекции 1

## Карта API и интеграций проекта — Claude Code, 8 уровень

## 1. Общего понимания проекта мало — нужна карта

Откройте Commerce OS — впечатление обманчиво простое: заказы, платежи, поддержка, отчёты. Хватает до первого вопроса: «где ломается возврат?», «какой маршрут вызывает платёжный сервис?» В этот момент «вроде понятно» превращается в блуждание по папкам.

`CODEBASE_INVENTORY.md` отвечает на вопрос «что в проекте есть». `API_MAP.md` — на вопрос «куда идёт запрос»: через какой маршрут он входит, где уходит в сервисы, когда упирается в базу, когда дёргает платёжного провайдера. Один сценарий тянет за собой HTTP-маршрут, бизнес-логику, клиента внешнего сервиса, очередь событий, конфиг и тесты. Без карты каждое расследование начинается с нуля.

Это рабочий документ: куда входит запрос, куда идёт дальше, чем подтверждается.

## 2. Интеграция — это любой важный стык, не только внешний

«Интеграция» звучит так, будто речь про платёжный шлюз, CRM и вебхуки. В учебном смысле это **любой важный стык между частями системы, влияющий на поведение**: и внешние сервисы, и внутренние точки соединения. Смотрите на них через таблицу:

| Что мы видим в проекте | Пример в Commerce OS | Почему это попадает в карту |
|---|---|---|
| HTTP-эндпоинт | `POST /api/orders` | Это входная точка пользовательского сценария |
| Обработчик или контроллер | `OrderController` | Здесь начинается серверный маршрут |
| Внутренний клиент | `StripeClient` | Он связывает проект с внешним сервисом |
| База данных | таблицы заказов и возвратов | Без неё многие маршруты просто не имеют смысла |
| Очередь или событие | `order-events` | Это асинхронное продолжение сценария |
| Граница авторизации | customer session, operator role | Показывает, кто вообще имеет право вызвать маршрут |
| Конфигурация окружения | `STRIPE_API_KEY`, `QUEUE_URL` | Маршрут зависит не только от кода, но и от настроек |
| Тесты | `OrderControllerTest` | Они подтверждают контракт и ожидаемое поведение |

Ловушка: не путайте карту интеграций проекта с подключением Claude Code к внешним инструментам. Здесь мы описываем то, что уже живёт внутри кодовой базы, а не настраиваем новые подключения для самого Claude. MCP — способ подключать к Claude внешние инструменты, например читать задачи из трекера — это другая тема.

Граница авторизации — это ответ на вопрос, кто может дойти до этого маршрута: аннотация на методе, фильтр, правила в конфиге безопасности, тест.

## 3. Доказательства берём из кода, а не из догадок

Частая ошибка звучит мило и опасно одновременно: «Ну он же правдоподобно объяснил». Правдоподобно — не значит проверяемо. Источник истины один: код, конфиги, тесты, при нужде команды сборки.

| Источник в проекте | Что он обычно доказывает |
|---|---|
| Контроллер, маршрут, обработчик | Что эндпоинт реально существует |
| Сервис или клиент | Куда маршрут идёт дальше |
| Конфигурация | Какие переменные окружения и внешние зависимости нужны |
| Тест | Какой контракт или сценарий проект считает нормальным |
| Файл сборки | Что внешняя библиотека вообще подключена |
| Комментарий в коде | Иногда помогает, но сам по себе не является достаточным доказательством |

Упрощённый фрагмент контроллера:

```java
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/orders")
class OrderController { // фрагмент класса
    @PostMapping
    OrderResponse create(@RequestBody CreateOrderRequest request) {
        return orderService.createOrder(request); // дальше маршрут уходит в сервис
    }
}
```

Этот кусок подтверждает несколько вещей. Маршрут `POST /api/orders` существует. Точка входа находится в `OrderController`. Контроллер сам почти ничего не делает, а передаёт выполнение в `OrderService`. Значит, расследование не заканчивается.

Конфигурация:

```yaml
payments:
  stripe:
    api-key: ${STRIPE_API_KEY}
queues:
  order-events-url: ${QUEUE_URL}
```

Конфиг не доказывает, что вызов точно произойдёт, но показывает важные зависимости маршрута от окружения. Если в карте написано «создание заказа использует Stripe и очередь событий», а в конфиге нет следов этих настроек, стоит насторожиться: возможно, перепутан сервис или найден старый мёртвый код.

Тест подтверждает не только существование маршрута, но и ожидания проекта:

```java
@Test
void create_returns400_forEmptyCart() throws Exception {
    mockMvc.perform(post("/api/orders").content("{}"))
           .andExpect(status().isBadRequest()); // пустая корзина недопустима
}
```

Такой тест — доказательство контракта API. Он добавляет важное условие: пустая корзина должна давать ошибку `400`, а не молча создавать пустой заказ. Карта перестаёт быть сухим списком URL и фиксирует реальное поведение системы.

## 4. Хороший API_MAP.md — короткий и проверяемый

Когда студенты впервые делают такой артефакт, они бросаются в одну из двух крайностей: пишут две строчки «у нас есть заказы и платежи» или пытаются сделать энциклопедию на сорок экранов. Обе крайности не очень полезны. Хорошая карта должна быть короткой, рабочей и проверяемой.

Для Commerce OS достаточно начать с простой структуры:

```markdown
# API_MAP.md

## Customer API
## Support API
## Dashboard API
## Внешние интеграции
## Открытые вопросы
```

Внутри секций удобно использовать таблицу:

| Поле | Зачем оно нужно |
|---|---|
| Метод и путь | Быстро найти входную точку |
| Обработчик | Понять, где начинается кодовый маршрут |
| Авторизация | Увидеть, кто имеет доступ |
| Интеграции | Зафиксировать базу, очередь, внешние клиенты |
| Конфиг | Понять, от чего маршрут зависит в окружении |
| Тесты | Подтвердить контракт и поведение |
| Evidence / статус | `file:line`, тест, вывод команды или честное «не проверено» |
| Открытые вопросы | Не выдумывать отсутствующие факты |

Колонка **Evidence / статус** дисциплинирует лучше любого пафосного лозунга: в ней должно быть либо конкретное доказательство, либо честное «не проверено». Если не найден мобильный клиент, который использует маршрут, не нужно писать «используется мобильным приложением» только потому, что так было бы логично. Это остаётся открытым вопросом, а не фактом.

Полезно относиться к `API_MAP.md` как к живому файлу в репозитории, а не как к красивому ответу в окне чата. Ответ Claude Code может помочь собрать черновик, но рабочим артефактом карта становится только тогда, когда лежит рядом с проектом, проходит через diff и обновляется после изменений.

## 5. Разбор маршрута на примере создания заказа

Теперь соберём один маршрут целиком, чтобы увидеть, как из кода рождается нормальная запись в `API_MAP.md`. Возьмём Commerce OS и типичный сценарий создания заказа.

Сначала полезно увидеть маршрут в виде схемы:

```text
Веб-клиент
  ↓
POST /api/orders
  ↓
OrderController
  ↓
OrderService
  ├─→ StripeClient        // внешний провайдер оплаты
  ├─→ OrderEventPublisher // событие в очередь
  └─→ PostgreSQL          // сохранение заказа
```

Сервисный слой:

```java
import org.springframework.stereotype.Service;

@Service
class OrderService { // фрагмент класса
    OrderResponse createOrder(CreateOrderRequest request) {
        paymentClient.charge(request.payment()); // внешний платёжный сервис
        orderEventPublisher.publishCreated(request); // асинхронное событие
        return OrderResponse.created();
    }
}
```

Если контроллер доказал вход в маршрут, то сервис доказывает, что сценарий идёт как минимум в две стороны: к платёжному клиенту и к издателю событий. Если рядом есть сохранение заказа в репозиторий, в карте стоит упомянуть и базу данных.

Запись в `API_MAP.md`:

```markdown
## Customer API

| Метод | Путь | Обработчик | Авторизация | Интеграции | Конфиг | Тесты | Evidence / статус | Открытые вопросы |
|---|---|---|---|---|---|---|---|---|
| POST | /api/orders | OrderController#create | customer session | PostgreSQL `orders`, `StripeClient`, `order-events` queue | `STRIPE_API_KEY`, `QUEUE_URL` | `OrderControllerTest#create_returns400_forEmptyCart` | `OrderController.java:41-67`; `OrderService.java:132-154`; `application.yml:54-61` | mobile-клиент — не проверено |
```

Заметьте, как мы пришли к этой строке. Не «Claude красиво резюмировал», а буквально собрали её из наблюдаемых деталей: контроллера, сервиса, конфига и теста. Если научиться делать так хотя бы для трёх-четырёх ключевых маршрутов проекта, дальше работать станет спокойнее. Уже не нужно каждый раз заново вспоминать, где у проекта платежи, где события, а где только HTTP-обёртка.

И да, это ровно тот момент, когда видно, почему карта API — это не просто список эндпоинтов. Если бы вы зафиксировали только `POST /api/orders`, вы бы потеряли почти всё интересное.

## 6. Просим у Claude Code карту, а не выдумки

Здесь соблазн особенно велик. Очень хочется написать: «Посмотри проект и расскажи, какие тут API и интеграции». Claude Code, как вежливый собеседник, постарается помочь. Иногда даже слишком старательно: расскажет не только то, что нашёл, но и то, что просто звучит правдоподобно. Нам такое не подходит.

Слабый запрос:

```text
Расскажи, какие API есть в проекте.
```

После такого запроса вы почти гарантированно получите красивый, но рыхлый текст. Нормальный запрос должен заставить модель работать как аккуратного помощника по исследованию, а не как экскурсовода-импровизатора. Например:

```text
Построй черновик файла API_MAP.md для этого репозитория.

Для каждой записи укажи:
- метод и путь;
- файл обработчика;
- связанную бизнес-логику или клиент;
- границу авторизации, если она видна;
- конфиг или переменные окружения, от которых зависит маршрут;
- связанные тесты;
- что не удалось проверить.

Не придумывай недостающие факты.
Если доказательства нет, помечай это как открытый вопрос.
```

У такого запроса несколько плюсов. Вы просите именно черновик, а не истину в последней инстанции. Вы задаёте структуру ответа. Вы прямо запрещаете модели додумывать недостающие факты.

Если Claude пишет «проект использует Stripe», хороший следующий вопрос простой: покажи, чем это подтверждается. Файл клиента, зависимость в сборке, ключ в конфиге, тест, использование в сервисе — что угодно из этого превращает догадку в проверяемое утверждение. Фраза без опоры должна либо получить доказательство, либо отправиться в колонку «открытые вопросы».

## 7. Карта живёт в репозитории, а не в истории чата

Очень легко один раз собрать информацию, порадоваться и оставить её в чате, где она утонет через пару дней в новых обсуждениях. Артефакт начинает работать только тогда, когда лежит рядом с кодом и меняется вместе с кодом.

Практическое правило: вы не обязаны описать весь проект за один присест. Полезнее начать с нескольких критичных маршрутов — например, заказы, возвраты, поддержка — а потом дополнять карту по мере расследований. Нашли новый webhook — добавили строку. Обнаружили, что маршрут зависит ещё от одной переменной окружения, — обновили запись. Появился тест, подтверждающий контракт, — дописали его в карту.

Хорошая карта обычно немного неполная, но честная. Плохая — очень полная, очень красивая и местами выдуманная. Для инженерной работы почти всегда лучше первый вариант. Особенно если вы работаете с Claude Code и хотите, чтобы он использовал этот файл как надёжный контекст, а не как сборник легенд о проекте.

Для Commerce OS цель понятна: начать `API_MAP.md` с нескольких проверенных маршрутов, фиксировать рядом обработчик, авторизацию, интеграции, конфиг и тесты, а всё непроверенное честно складывать в открытые вопросы. В этот момент проект перестаёт быть тёмным лесом с табличкой «тут где-то есть платежи» и начинает превращаться в систему, по которой можно ходить не на ощупь, а по карте.

## Практика (15–25 минут)

**Цель:** собрать короткую evidence-based карту API для одного-двух маршрутов учебного проекта и оформить её как рабочий артефакт.

**Что сделать:**
1. Возьмите небольшой учебный репозиторий или создайте фейковый `commerce-os-mini` с `OrderController`, `OrderService`, `StripeClient`, очередью событий, конфигом и тестами. Сделайте baseline-коммит и используйте только вымышленные данные.
2. Проведите фокусную CLI-сессию по одному маршруту, например `POST /api/orders`. Попросите Claude собрать короткую route note: метод, путь, обработчик, авторизация, интеграции, конфиг, тесты и открытые вопросы. Запретите правки файлов.
3. Проверьте запись по коду: откройте контроллер, сервис, конфиг и тест. Убедитесь, что `StripeClient`, очередь и база действительно участвуют в сценарии, а не просто упомянуты в ответе.
4. Добавьте в `API_MAP.md` секцию для заказов и заполните таблицу по шаблону из лекции. Для второго маршрута, например возврата, добавьте ещё одну строку или отметьте его как открытый вопрос, если evidence пока нет.
5. Проверьте diff и честность карты: все важные утверждения имеют источник, непроверенное лежит в «Открытых вопросах», а код проекта не изменён.

**Проверка:**
- В карте есть метод, путь, обработчик, авторизация, интеграции, конфиг и тесты.
- Каждая важная строка подтверждена файлом, тестом, конфигом или командой.
- Указаны минимум две интеграции: например, внешний клиент и очередь/база.
- Открытые вопросы не заменены правдоподобными догадками.
- Карта короткая и рабочая, а не энциклопедия на сорок экранов.
- `API_MAP.md` сохранён в репозитории и просматривается через diff.
- В практике только фейковые данные, без секретов и реального платёжного ключа.
