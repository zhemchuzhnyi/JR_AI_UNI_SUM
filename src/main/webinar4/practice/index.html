Haiku 50

Аудит чужого проекта · API-контракт · backend · frontend · проверка
Сквозная практика вебинара 4: сначала разбираем чужой проект как исследователи, потом принимаем инженерное решение и доводим генератор хайку до контракта. Это отдельное capstone-задание, оно не заменяет практики в конце лекций.

Что собираем

Веб-приложение генерирует хайку через OpenAI API. Хайку — короткое японское стихотворение из трёх строк: момент, образ, настроение, краткость и поэтичность. Строгий счётчик слогов 5-7-5 здесь не нужен.

Пользователь вводит 3–7 ключевых слов или коротких фраз через запятую, выбирает язык генерации и нажимает «Сгенерировать хайку». Доступны 12 языков и две модели OpenAI:

  • gpt-5-nano-2025-08-07;
  • gpt-5.6-luna.

Две особенности делают проект собой:

  • кнопка «50 васаби» с иконкой васаби поднимает уровень остроты от 0 до 6 — от спокойной классики до острого, почти абсурдного текста;
  • история хранит последние 100 генераций локально в браузере.

Интерфейс минималистичный, желательно в стиле Bento Grid. Базы данных, авторизации, регистрации и мобильного приложения не нужно.

Проект достаётся не с нуля

Кот дизайнера собрал симпатичный UI и backend на Node.js. На первый взгляд всё живое: сервер стартует, хайку генерируются, история сохраняется. Но «выглядит как приложение» не значит «выполняет ТЗ».

В архиве есть HTML/CSS/JS-макет, server.js и readme.txt в духе «лапки мешают». Задача — разобраться с чужим кодом и довести приложение до состояния, когда оно честно выполняет требования. Сначала inventory и runtime flow, потом решение: чинить точечно или переписать по контракту. Запрещён только один вариант — «перепишу всё не глядя», без аудита.

Ключ OpenAI — это деньги на счёте. Если он утечёт в публичный репозиторий, его автоматически заблокируют, обычно в пределах 20 минут. Кот уже наступил на эти грабли — ключ нужно найти во время аудита и убрать из кода, репозитория и переписки с агентом.

Главное правило: сначала аудит

До первой правки соберите HANDOFF_REVIEW.md: что уже работает, что только выглядит готовым, какие требования не закрыты и чем это подтверждается в файлах.

Это не отчёт для отчётности, а рабочий контракт с самим собой. После него проще давать агенту маленькие задачи и проверять, что именно он поменял.

Каждый gap фиксируйте с evidence: файл, строка, вывод команды или запрос в Network. Без evidence это не находка, а догадка.

Этап 2. Контракт API и решение

После аудита зафиксируйте целевой контракт. Кошачий server.js уже объявляет endpoint, но нужно проверить, что он реально принимает и возвращает, а не что должен по контракту.

POST /generate-haiku

request:
  words: string[]        // 3–7 ключевых слов или коротких фраз
  language: string       // один из 12 языков
  wasabiLevel: number    // 0–6

response:
  haiku: string          // ровно 3 строки

Фронтенд проверяет ввод, хранит историю и показывает ошибки. Backend держит API-ключ, название модели и промпт. OpenAI API только генерирует хайку.

Решение «чинить или переписать» принимайте по evidence. Если большая часть контракта не совпадает с кодом, переписывание backend может быть дешевле точечных заплаток. Если UI и структура нормальные, сохраните их и замените проблемные слои.

Этап 3. Backend и промпты

Минимальные требования к backend:

  • ключ OpenAI берётся из переменной окружения, а .env добавлен в .gitignore;
  • в репозитории и фронтенде нет настоящего ключа;
  • имя модели вынесено в одно место;
  • тексты промптов лежат отдельно от кода — в отдельном файле или константах;
  • валидация 3–7 слов и пустого языка дублируется на сервере, а не только в браузере;
  • ошибки «меньше 3 слов», «больше 7 слов», «пустой язык», «сервер недоступен», «OpenAI недоступен» обрабатываются понятными сообщениями;
  • ответ нормализуется: убираются markdown-обёртки и вступления вроде «Вот ваше хайку», после чего проверяется, что осталось ровно 3 строки;
  • если после нормализации строк не три, возвращается понятная ошибка или выполняется ограниченная попытка исправления формата.
# .env.example
OPENAI_API_KEY=your_key_here

Настоящий .env не коммитится и не показывается агенту. Для проверки используйте только тестовый ключ с ограниченным бюджетом или mock-ответ, но mock не должен незаметно подменять реальную ошибку в production-сценарии.

Промпт делится на два слоя:

  • базовый: три строки, выбранный язык, слова пользователя, краткость, поэтичность, без объяснений после текста;
  • острота: уровень 0–6 — от спокойной классики до острого, сюрреалистичного, но безопасного результата.

Отдельно задайте безопасность: без мата, агрессии и запрещённого контента. В запрос передавайте отдельные поля language, words и wasabiLevel, а не одну склеенную строку — так проще проверять и менять поведение.

Для моделей gpt-5 можно использовать reasoning_effort со значением low или medium: для хайку глубокое рассуждение не нужно. verbosity: low даёт короткий ответ без лишней прозы. Точные параметры и их доступность зависят от версии API — сверяйтесь с документацией.

Этап 4. Frontend и сценарии

Сохраните Bento Grid и общий дизайн, но проверьте поведение:

  • поле ключевых слов не очищается после генерации; для очистки есть отдельная кнопка;
  • выбранный язык уходит в запрос и промпт;
  • кнопка «50 васаби» с иконкой повышает уровень остроты от 0 до 6;
  • история хранит последние 100 генераций в localStorage и не требует базы данных;
  • серверное in-memory-хранилище допустимо только как дополнительная опция, но не как основное;
  • ошибки показываются рядом с формой и не выглядят как успешная генерация;
  • при недоступном сервере или OpenAI пользователь видит понятное сообщение, а не пустой экран.

Идти лучше слоями: сначала целевая картинка без кода — API-контракт, обработка ошибок и что из кошачьего кода оставляем. Потом отдельными шагами backend, связка фронт-бекенд и проверка сценариев. Не смешивайте рефакторинг, изменение дизайна и исправление ошибок в один diff.

Этап 5. Проверка

Пройдите сценарии вручную или тестами:

  1. 3 слова, 7 слов — успешная генерация; 2 и 8 слов — понятная ошибка.
  2. Пустой язык — ошибка; каждый из 12 языков реально передаётся в запрос.
  3. «50 васаби» на 0 и на 6 даёт заметно разную остроту, но не нарушает safety-правила.
  4. Ответ модели в markdown-обёртке нормализуется до трёх строк.
  5. Ошибка OpenAI и недоступный сервер показываются пользователю.
  6. После генерации поле слов не очищается; отдельная кнопка очищает его.
  7. История хранит не больше 100 записей и переживает перезагрузку страницы.
  8. В собранном фронтенде и репозитории нет ключа; ключ читается только на backend.
  9. Модель выбирается в одном месте; промпты не размазаны по обработчикам.

Критерии готовности

  • HANDOFF_REVIEW.md содержит список gap'ов с evidence, а не общие впечатления.
  • Приложение выполняет все требования ТЗ, а не только выглядит как демо.
  • API-ключ не попадает во фронтенд, Git и чат.
  • Валидация и ошибки работают на сервере, а не только в браузере.
  • История — последние 100 генераций в браузере.
  • Дизайн сохраняет Bento Grid и не переписан без причины.
  • Есть проверяемые сценарии для 3–7 слов, языков, остроты, ошибок и формата ответа.
  • В практике используются только вымышленные данные и тестовые ключи без реального бюджета.
