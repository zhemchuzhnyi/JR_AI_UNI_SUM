Уровень 12 — контрольные вопросы

Контрольный блок по 5 лекциям уровня 12 и практике вебинара 8: 25 открытых вопросов с короткими ответами и ссылками на конспекты. Вопросы синхронизированы с презентацией: tools и least privilege, scoped skills/MCP/memory, context и worktree isolation, output contract, lifecycle и evaluation.

Лекция 1 — tools и permissions

  1. На какой вопрос отвечает поле tools во frontmatter subagent’а?
    На вопрос «что именно агент имеет право делать руками»: какие инструменты и действия ему технически разрешены. Роль отвечает, зачем агент существует, а tools задаёт техническую границу его действий.
    → Лекция 1
  2. Как соотносятся L1 — права сессии и L2 — tools агента?
    L1 — общий потолок действий сессии, L2 — allow-list конкретного агента. L2 может только сузить L1, но не расширить его. Фактически возможности агента — это L1 ∩ L2: в read-only сессии Edit в tools не даст права писать.
    → Лекция 1
  3. Что произойдёт, если tools не указать вообще? Что такое disallowedTools?
    Без tools агент наследует почти все инструменты сессии, включая Edit, Write и MCP, кроме нескольких служебных. disallowedTools — подход «всё, кроме»; при нём агент может унаследовать и Agent, поэтому узкой роли нужно добавить Agent в запрет.
    → Лекция 1
  4. Какой набор tools рекомендуется reviewer и чем отличается tester?
    Reviewer: Read, Glob, Grep, Bash, без Edit/Write. Tester: те же инструменты плюс Edit и Write, но правки ограничены test-каталогами (src/test/, tests/), а production-код менять нельзя. Edit tester’у нужен ради тестов, reviewer’у — не нужен вовсе.
    → Лекция 1
  5. Почему Edit/Write считаются самым высоким риском выхода за роль?
    Они напрямую меняют файлы. Reviewer с Edit становится не проверяющим, а соавтором diff; tester без границ начинает «чинить» production-код под видом зелёных тестов. Поэтому write-права выдаются только под конкретный результат и с границами каталогов.
    → Лекция 1

Лекция 2 — scoped skills, MCP и memory

  1. На какие четыре слоя capability удобно делить возможности агента?
    Tools — что можно делать руками; skills — по какой процедуре работать; MCP — к каким внешним данным есть доступ; memory — что переносится между запусками. Least privilege применяется ко всем четырём слоям, а не только к tools.
    → Лекция 2
  2. Что делает scoped skill и даёт ли он новые права?
    Scoped skill подключает агенту конкретную процедуру под роль: reviewer — pr-review, tester — test-strategy, migration assistant — migration-plan. Новых прав skill не даёт: он описывает, как думать, а tools определяют, что можно делать руками. Reviewer с pr-review, но без Edit, остаётся read-only.
    → Лекция 2
  3. Какому агенту Workflow Kit разумнее подключить read-only MCP docs-lookup и почему?
    Migration assistant: ему нужно сверяться с официальными changelog’ами и migration notes. Reviewer и tester обычно не нуждаются во внешнем MCP — им хватает diff, файлов, тестов и локальных проверок. Подключается один конкретный read-only источник, без БД и write-actions.
    → Лекция 2
  4. Почему по умолчанию лучше обходиться без MCP, а если он нужен — выбирать read-only?
    Лишний MCP создаёт шум в контексте и дополнительную поверхность риска. Read-only источник может принести лишние данные, но не меняет внешнее состояние; write-capable уже может изменить систему. Принцип: можно обойтись — обходимся; нельзя — сначала думаем о read-only.
    → Лекция 2
  5. Что стоит и что не стоит класть в memory агента?
    Стоит: расположение test-пакетов, устойчивые naming conventions, проверенные правила команды, стабильные ограничения роли. Не стоит: разовые гипотезы, временные stack trace, «эти тесты всегда падают, игнорируй», секреты и чувствительные данные. Memory не обязательна; её отсутствие — дисциплина, а не недонастройка.
    → Лекция 2

Лекция 3 — context и worktree isolation

  1. От какой боли защищает context isolation?
    От засорения основной сессии промежуточным исследованием: десятками прочитанных файлов, grep-выводом, stack trace и ложными гипотезами. Подзадача уходит в отдельное окно контекста, а обратно возвращается короткая сводка с evidence.
    → Лекция 3
  2. От чего защищает worktree isolation?
    От смешивания экспериментальных или параллельных правок с основным checkout. Агент получает отдельную рабочую директорию, ветку и собственный diff; неудачный эксперимент можно удалить, не трогая основной Git state.
    → Лекция 3
  3. Какая Git-команда используется для создания отдельного рабочего дерева под эксперимент?
    git worktree add ../commerce-os-refund-lab -b exp/refund-rules, затем cd в эту директорию и запуск отдельной сессии. В свежих версиях Claude Code также доступен claude --worktree refund-lab, который создаёт worktree в .claude/worktrees/.
    → Лекция 3
  4. Что делает isolation: worktree и какие детали worktree важно помнить?
    Агент получает временную копию репозитория; worktree удаляется сам, если правок не было. Worktree — свежий checkout без незакоммиченных правок; по умолчанию ветвится от default-ветки. Для старта от локального HEAD нужен worktree.baseRef: "head", для копирования .env — .worktreeinclude, а .claude/worktrees/ стоит добавить в .gitignore.
    → Лекция 3
  5. Когда изоляция не нужна и почему форк /subtask не считается context isolation?
    Для задачи на один-два файла без экспериментов изоляция может стоить дороже пользы. Форк /subtask видит весь текущий разговор: у него не изолирован вход, изолирован только результат. Для context isolation нужен именно свежий subagent, а не форк.
    → Лекция 3

Лекция 4 — output contract

  1. Чем output contract отличается от Session Handoff Note?
    Handoff Note передаёт состояние задачи дальше — другой сессии или человеку: решения, открытые вопросы, следующий шаг. Output contract принимает результат роли назад и отвечает, можно ли его принять: формат, evidence, scope, uncertainty, stop conditions.
    → Лекция 4
  2. Из каких секций состоит хороший output contract?
    Summary, findings, evidence, tests/checks run, uncertainty, changed files, next step и stop conditions. Для reviewer changed files должен быть none; для tester — только tests/**.
    → Лекция 4
  3. Чем «жёсткие» поля output contract отличаются от «мягких»?
    Жёсткие проверяются почти механически: file:line, команда, exit code, changed files: none, diff, лог. Мягкие требуют человеческого суждения: severity, риск, recommendation. Нужны оба слоя: только мягкие дают уверенного комментатора, только жёсткие — сухой протокол без смысла.
    → Лекция 4
  4. Какие три решения возможны при приёмке результата?
    Принять — evidence есть, scope и границы роли соблюдены, следующий шаг понятен. Вернуть на уточнение — идея полезная, но не хватает evidence или маркировки гипотез. Отклонить — были неожиданные edits, нарушены stop conditions или границы роли.
    → Лекция 4
  5. Как правильно подавать неопределённость в output агента?
    Явно маркировать гипотезы [hypothesis], выносить их в блок uncertainty и указывать evidence, причину подозрения и нужную проверку. Нельзя выдавать догадку за установленный факт вроде «refund flow ломается из-за stale cache» без доказательств.
    → Лекция 4

Лекция 5 — lifecycle и evaluation

  1. По каким критериям лекция предлагает оценивать полезность агента?
    Correctness, source anchoring, scope discipline, useful severity, false positives, missed issues, no unwanted edits и human time saved. Главный практический критерий — human time saved: если человек дольше разбирает output, чем сделал бы сам, агент не окупается.
    → Лекция 5
  2. Какие failure modes агента считаются типовыми и как они лечатся?
    Hallucinated findings — жёстче evidence; over-permissioned agent — сузить tools и убрать write; stale instructions — обновить файл и версию; memory pollution — почистить memory; plugin/config conflicts — упростить конфигурацию; lost context — уточнить description и входной контекст. Лечение — правка конфигурации, а не просьба «быть внимательнее».
    → Лекция 5
  3. Как выглядит жизненный цикл агента?
    Создали → прогнали на маленьких кейсах → разобрали сбои → сузили tools и contract → подняли версию → поделились с командой → собрали feedback → обновили или пометили deprecated → удалили, если агент вреднее, чем полезнее.
    → Лекция 5
  4. Зачем нужны маленькие кейсы и CHANGELOG.md?
    Маленькие кейсы (3–5) с заранее известным ожиданием показывают нарушение границ без эксперимента над живым проектом. CHANGELOG.md фиксирует, что изменилось в поведении агента и почему, помогает сравнить версии и откатиться.
    → Лекция 5
  5. Когда агента стоит упростить или отправить в deprecation?
    Когда он шумит больше, чем помогает, экономит меньше времени, чем отнимает на разбор output, или дублируется другой ролью. Можно сузить роль до tester-lite, оставить для конкретных зон или честно пометить deprecated и удалить. Это нормальная инженерная развилка, а не поражение.
    → Лекция 5
