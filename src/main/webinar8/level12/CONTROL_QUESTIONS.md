# Уровень 12 — контрольные вопросы

Контрольный блок по 5 лекциям уровня 12 и практике вебинара 8: 25 открытых вопросов с короткими ответами и ссылками на конспекты. Вопросы синхронизированы с презентацией: tools и least privilege, scoped skills/MCP/memory, context и worktree isolation, output contract, lifecycle и evaluation.

## Лекция 1 — tools и permissions

1. **На какой вопрос отвечает поле `tools` во frontmatter subagent’а?**<br>
   На вопрос «что именно агент имеет право делать руками»: какие инструменты и действия ему технически разрешены. Роль отвечает, зачем агент существует, а `tools` задаёт техническую границу его действий.<br>
   → [Лекция 1](lecture1/index.html)

2. **Как соотносятся L1 — права сессии и L2 — tools агента?**<br>
   L1 — общий потолок действий сессии, L2 — allow-list конкретного агента. L2 может только сузить L1, но не расширить его. Фактически возможности агента — это `L1 ∩ L2`: в read-only сессии `Edit` в tools не даст права писать.<br>
   → [Лекция 1](lecture1/index.html)

3. **Что произойдёт, если `tools` не указать вообще? Что такое `disallowedTools`?**<br>
   Без `tools` агент наследует почти все инструменты сессии, включая `Edit`, `Write` и MCP, кроме нескольких служебных. `disallowedTools` — подход «всё, кроме»; при нём агент может унаследовать и `Agent`, поэтому узкой роли нужно добавить `Agent` в запрет.<br>
   → [Лекция 1](lecture1/index.html)

4. **Какой набор tools рекомендуется reviewer и чем отличается tester?**<br>
   Reviewer: `Read`, `Glob`, `Grep`, `Bash`, без `Edit`/`Write`. Tester: те же инструменты плюс `Edit` и `Write`, но правки ограничены test-каталогами (`src/test/`, `tests/`), а production-код менять нельзя. `Edit` tester’у нужен ради тестов, reviewer’у — не нужен вовсе.<br>
   → [Лекция 1](lecture1/index.html)

5. **Почему `Edit`/`Write` считаются самым высоким риском выхода за роль?**<br>
   Они напрямую меняют файлы. Reviewer с `Edit` становится не проверяющим, а соавтором diff; tester без границ начинает «чинить» production-код под видом зелёных тестов. Поэтому write-права выдаются только под конкретный результат и с границами каталогов.<br>
   → [Лекция 1](lecture1/index.html)

## Лекция 2 — scoped skills, MCP и memory

6. **На какие четыре слоя capability удобно делить возможности агента?**<br>
   Tools — что можно делать руками; skills — по какой процедуре работать; MCP — к каким внешним данным есть доступ; memory — что переносится между запусками. Least privilege применяется ко всем четырём слоям, а не только к tools.<br>
   → [Лекция 2](lecture2/index.html)

7. **Что делает scoped skill и даёт ли он новые права?**<br>
   Scoped skill подключает агенту конкретную процедуру под роль: reviewer — `pr-review`, tester — `test-strategy`, migration assistant — `migration-plan`. Новых прав skill не даёт: он описывает, как думать, а tools определяют, что можно делать руками. Reviewer с `pr-review`, но без `Edit`, остаётся read-only.<br>
   → [Лекция 2](lecture2/index.html)

8. **Какому агенту Workflow Kit разумнее подключить read-only MCP `docs-lookup` и почему?**<br>
   Migration assistant: ему нужно сверяться с официальными changelog’ами и migration notes. Reviewer и tester обычно не нуждаются во внешнем MCP — им хватает diff, файлов, тестов и локальных проверок. Подключается один конкретный read-only источник, без БД и write-actions.<br>
   → [Лекция 2](lecture2/index.html)

9. **Почему по умолчанию лучше обходиться без MCP, а если он нужен — выбирать read-only?**<br>
   Лишний MCP создаёт шум в контексте и дополнительную поверхность риска. Read-only источник может принести лишние данные, но не меняет внешнее состояние; write-capable уже может изменить систему. Принцип: можно обойтись — обходимся; нельзя — сначала думаем о read-only.<br>
   → [Лекция 2](lecture2/index.html)

10. **Что стоит и что не стоит класть в memory агента?**<br>
    Стоит: расположение test-пакетов, устойчивые naming conventions, проверенные правила команды, стабильные ограничения роли. Не стоит: разовые гипотезы, временные stack trace, «эти тесты всегда падают, игнорируй», секреты и чувствительные данные. Memory не обязательна; её отсутствие — дисциплина, а не недонастройка.<br>
    → [Лекция 2](lecture2/index.html)

## Лекция 3 — context и worktree isolation

11. **От какой боли защищает context isolation?**<br>
    От засорения основной сессии промежуточным исследованием: десятками прочитанных файлов, grep-выводом, stack trace и ложными гипотезами. Подзадача уходит в отдельное окно контекста, а обратно возвращается короткая сводка с evidence.<br>
    → [Лекция 3](lecture3/index.html)

12. **От чего защищает worktree isolation?**<br>
    От смешивания экспериментальных или параллельных правок с основным checkout. Агент получает отдельную рабочую директорию, ветку и собственный diff; неудачный эксперимент можно удалить, не трогая основной Git state.<br>
    → [Лекция 3](lecture3/index.html)

13. **Какая Git-команда используется для создания отдельного рабочего дерева под эксперимент?**<br>
    `git worktree add ../commerce-os-refund-lab -b exp/refund-rules`, затем `cd` в эту директорию и запуск отдельной сессии. В свежих версиях Claude Code также доступен `claude --worktree refund-lab`, который создаёт worktree в `.claude/worktrees/`.<br>
    → [Лекция 3](lecture3/index.html)

14. **Что делает `isolation: worktree` и какие детали worktree важно помнить?**<br>
    Агент получает временную копию репозитория; worktree удаляется сам, если правок не было. Worktree — свежий checkout без незакоммиченных правок; по умолчанию ветвится от default-ветки. Для старта от локального HEAD нужен `worktree.baseRef: "head"`, для копирования `.env` — `.worktreeinclude`, а `.claude/worktrees/` стоит добавить в `.gitignore`.<br>
    → [Лекция 3](lecture3/index.html)

15. **Когда изоляция не нужна и почему форк `/subtask` не считается context isolation?**<br>
    Для задачи на один-два файла без экспериментов изоляция может стоить дороже пользы. Форк `/subtask` видит весь текущий разговор: у него не изолирован вход, изолирован только результат. Для context isolation нужен именно свежий subagent, а не форк.<br>
    → [Лекция 3](lecture3/index.html)

## Лекция 4 — output contract

16. **Чем output contract отличается от Session Handoff Note?**<br>
    Handoff Note передаёт состояние задачи дальше — другой сессии или человеку: решения, открытые вопросы, следующий шаг. Output contract принимает результат роли назад и отвечает, можно ли его принять: формат, evidence, scope, uncertainty, stop conditions.<br>
    → [Лекция 4](lecture4/index.html)

17. **Из каких секций состоит хороший output contract?**<br>
    Summary, findings, evidence, tests/checks run, uncertainty, changed files, next step и stop conditions. Для reviewer `changed files` должен быть `none`; для tester — только `tests/**`.<br>
    → [Лекция 4](lecture4/index.html)

18. **Чем «жёсткие» поля output contract отличаются от «мягких»?**<br>
    Жёсткие проверяются почти механически: `file:line`, команда, `exit code`, `changed files: none`, diff, лог. Мягкие требуют человеческого суждения: severity, риск, recommendation. Нужны оба слоя: только мягкие дают уверенного комментатора, только жёсткие — сухой протокол без смысла.<br>
    → [Лекция 4](lecture4/index.html)

19. **Какие три решения возможны при приёмке результата?**<br>
    Принять — evidence есть, scope и границы роли соблюдены, следующий шаг понятен. Вернуть на уточнение — идея полезная, но не хватает evidence или маркировки гипотез. Отклонить — были неожиданные edits, нарушены stop conditions или границы роли.<br>
    → [Лекция 4](lecture4/index.html)

20. **Как правильно подавать неопределённость в output агента?**<br>
    Явно маркировать гипотезы `[hypothesis]`, выносить их в блок `uncertainty` и указывать evidence, причину подозрения и нужную проверку. Нельзя выдавать догадку за установленный факт вроде «refund flow ломается из-за stale cache» без доказательств.<br>
    → [Лекция 4](lecture4/index.html)

## Лекция 5 — lifecycle и evaluation

21. **По каким критериям лекция предлагает оценивать полезность агента?**<br>
    Correctness, source anchoring, scope discipline, useful severity, false positives, missed issues, no unwanted edits и human time saved. Главный практический критерий — human time saved: если человек дольше разбирает output, чем сделал бы сам, агент не окупается.<br>
    → [Лекция 5](lecture5/index.html)

22. **Какие failure modes агента считаются типовыми и как они лечатся?**<br>
    Hallucinated findings — жёстче evidence; over-permissioned agent — сузить tools и убрать write; stale instructions — обновить файл и версию; memory pollution — почистить memory; plugin/config conflicts — упростить конфигурацию; lost context — уточнить description и входной контекст. Лечение — правка конфигурации, а не просьба «быть внимательнее».<br>
    → [Лекция 5](lecture5/index.html)

23. **Как выглядит жизненный цикл агента?**<br>
    Создали → прогнали на маленьких кейсах → разобрали сбои → сузили tools и contract → подняли версию → поделились с командой → собрали feedback → обновили или пометили deprecated → удалили, если агент вреднее, чем полезнее.<br>
    → [Лекция 5](lecture5/index.html)

24. **Зачем нужны маленькие кейсы и `CHANGELOG.md`?**<br>
    Маленькие кейсы (3–5) с заранее известным ожиданием показывают нарушение границ без эксперимента над живым проектом. `CHANGELOG.md` фиксирует, что изменилось в поведении агента и почему, помогает сравнить версии и откатиться.<br>
    → [Лекция 5](lecture5/index.html)

25. **Когда агента стоит упростить или отправить в deprecation?**<br>
    Когда он шумит больше, чем помогает, экономит меньше времени, чем отнимает на разбор output, или дублируется другой ролью. Можно сузить роль до tester-lite, оставить для конкретных зон или честно пометить deprecated и удалить. Это нормальная инженерная развилка, а не поражение.<br>
    → [Лекция 5](lecture5/index.html)
