Tools и permissions

Claude Code

12 уровень · лекция 1
Инструкция без технической границы — табличка «не входить» на двери без замка. Роль отвечает, зачем агент существует, а tools — что он имеет право делать руками.

1. Инструкция без замка

Когда вы впервые проектируете агента, очень легко влюбиться в красивую инструкцию: «ты tester, проверяешь тесты и не трогаешь production-код» — и кажется, что дальше всё сложится само. Это как повесить табличку «не входить» на дверь без замка и удивляться, почему кто-то всё-таки вошёл.

Представьте ситуацию из Commerce OS. Вы починили баг в refund flow — один сценарий возврата обрабатывался неверно — и хотите поручить tester-агенту написать regression test. Если у него есть всё подряд — чтение, поиск, команды, полное редактирование проекта, — он может решить, что быстрее «помочь» правкой боевого кода, а не тестом. Проблема формально исчезнет. А у вас вместо tester — очень инициативный соавтор, которого никто не просил.

Вот здесь и появляется ключевой принцип. Роль отвечает на вопрос «зачем агент существует». Набор инструментов — на вопрос «что именно он имеет право делать руками». Оставите только первое — агент выйдет свободным. А свободный агент — это лишний diff, лишние риски и тот момент, когда вы открываете изменения: «Я же просил проверить тесты, а не переставить мебель во всей квартире».

У роли должна быть не только инструкция, но и техническая граница. tools — это не декоративное поле во frontmatter, а граница ответственности роли.

2. Два слоя прав: L1 и L2

Чтобы не путаться в терминах, полезно разложить модель прав по слоям. Права складываются и вкладываются друг в друга: сессия задаёт потолок, агент сужает его под роль.

L1: права текущей сессии
  → L2: tools конкретного агента
  → что агент реально может сделать

Если говорить просто, L1 — режим сессии, в котором вы работаете вместе с Claude. L2 — права конкретного subagent внутри неё. Важнейшее правило: L2 не может сделать агента сильнее, чем позволяет L1. Только сузить, не расширить.

СлойКто задаётЧто ограничиваетПример
L1 — права сессиивы, как автор текущей сессииобщий потолок действийсессия в режиме только чтения
L2 — права агентаконфиг агентавозможности конкретной ролиtester может править только тесты
L3 — командные правилапроект или командаобщие политики и защищённые зонызапрет правок payments/

Агент работает внутри permission-контекста сессии: deny-правила и protected paths действуют и на него. Спорное действие фонового агента приходит в сессию как permission prompt или решается классификатором в auto mode.

Сегодня нас интересует именно L2. Полезно посмотреть на практические комбинации:

Права сессии (L1)tools агента (L2)Что получится
только чтение / plan modeRead, Grep, Bash, Editагент всё равно не сможет править файлы
обычная рабочая сессияRead, Grep, Bashагент читает код и запускает проверки, но не пишет
обычная рабочая сессияRead, Grep, Bash, Editагент потенциально может писать, но только если это соответствует его роли и инструкции

Из этого следует практический вывод. Хотите агента безопаснее — не надейтесь на «будь осторожен» в инструкции. Сначала спросите: нужен ли этой роли такой инструмент? Не нужен — не выдавайте. Самая сильная защита от лишнего редактирования — отсутствие Edit, а не просьба «не редактируй ничего лишнего».

Некоторые поля могут дать агенту больше, чем есть у сессии. permissionMode (например, acceptEdits в Manual-сессии снимает запросы на правки) и mcpServers (подключает серверы, которых в сессии нет) — это уже не сужение, а расширение. Для первого tester их не трогаем.

3. tools как инженерный договор

Теперь можно смотреть на поле tools не как на мелочь, а как на инженерный договор: допустимый радиус действий роли. Как хороший API-контракт: границы ясны — поведение предсказуемо; границ нет — догадки, расширение scope и хаос с уверенным лицом.

Обычно инструменты делятся на естественные группы:

ГруппаЗачем обычно нужнаГде начинается риск
Read, Grep и другие инструменты чтения и поискачитать код, искать по проекту, собирать evidenceриск невысокий, но контекст легко раздуть
Bash или выполнение командзапускать тесты, сборку, git diff, диагностикуодин и тот же инструмент умеет и полезное, и опасное
Edit / write-инструментывносить изменения в файлысамый высокий риск выхода за роль

С Read и Grep всё относительно спокойно — это естественная база почти для любого аналитического или ревью-агента. А Bash — инструмент взрослый: им можно запустить ./gradlew test, а можно выполнить совсем не ту команду, после которой вы внезапно полюбите резервные копии. Поэтому Bash почти никогда не живёт один: рядом нужны текстовые ограничения и понятные stop conditions.

Ещё важнее история с Edit. Частая ловушка новичка: кажется, лучше выдать чуть больше прав — вдруг пригодится. На практике это превращается в «вдруг он решил помочь сильнее, чем мы просили». Reviewer с Edit — уже не reviewer, а автор правок. Tester с Edit без каталоговых границ начнёт «чинить» production-код под видом борьбы за зелёные тесты.

Если инструмент не нужен роли для получения её результата, этого инструмента не должно быть в tools.

Важно: если tools не указать вообще, агент наследует почти все инструменты сессии, включая Edit, Write и MCP, кроме нескольких служебных. Явный список — это allow-list, а не пожелание. Обратный способ — disallowedTools: «всё, кроме». Он удобен, когда проще назвать запретное, но при таком подходе агент унаследует и Agent, то есть сможет нанимать своих субагентов. Для узкой роли добавьте Agent в запрет.

У агента есть и другие поля тюнинга — permissionMode, maxTurns, effort. Это для специальных случаев; первому tester они не нужны.

Точные имена инструментов и способ их объявления могут немного отличаться между версиями Claude Code. Суть не меняется: нужен явный allow-list, а не надежда на здравый смысл модели.

4. Least-privilege на живых ролях Workflow Kit

Теперь перенесём принцип least privilege в живые роли Workflow Kit. Разница видна не на «агенте вообще», а на нескольких ролях рядом — тогда сразу ясно, почему «одинаковый набор tools всем подряд» — плохая идея.

РольКакой результат она должна датьБазовый набор toolsЧто лучше не выдавать
reviewerзамечания по diff, риски, evidenceRead, Glob, Grep, BashEdit, Write
testerтесты, результаты прогонов, пробелы в проверкеRead, Glob, Grep, Bash, Edit, Writeредактирование production-файлов
documenterобновлённые docs и поясненияRead, Glob, Grep, Edit, Writeширокие code edits, Bash «про запас»
debuggerroot cause с evidenceRead, Glob, Grep, Bashобычно ничего не пишет

С reviewer всё проще всего: прочитать diff, посмотреть связанные файлы, запустить безопасные проверки, вернуть findings. Как только reviewer получает Edit, идея ревью размывается — уже не взгляд со стороны, а второй автор, который ломает трассируемость: где закончился review и началось авторство.

С tester ситуация тоньше. Ему действительно часто нужен Edit и Write: работа не только запускать тесты, но и писать test-файлы. Но даже здесь least privilege не исчезает, а становится точнее: редактирование разрешено только внутри test-каталогов. Агент работает в src/test/, tests/ и аналогичных зонах, но если для проверок нужно менять production-код — обязан остановиться и вернуть объяснение человеку.

Documenter — ещё один показательный случай. Edit ему нужен для документации, а Bash часто вообще не нужен: не выдавайте команды «про запас». Лишний Bash — лишний соблазн и лишняя поверхность риска.

Сноска про платформы: на macOS, Linux и WSL Claude Code ищет файлы через Bash, поэтому у ролей с Bash отдельные Glob и Grep могут не появиться. Нужен поиск без Bash — перечислите Glob и Grep без Bash, как у documenter.

Когда вы начинаете так смотреть на роли, принцип least privilege становится почти очевидным. Вопрос больше не «что умеет Claude», а: какой минимальный набор действий нужен этой роли ради этого результата.

Быстрый тест конфига: сможет ли агент случайно улучшить то, что вы не просили улучшать? Ответ «да» — набор инструментов всё ещё широкий.

5. Собираем agents/tester.md для Workflow Kit

Теперь превратим теорию в рабочий артефакт. Представим, что в репозитории Workflow Kit вы открываете workflow-kit/.claude/agents/tester.md. Задача — не «самый умный tester в мире», а первый безопасный вариант, который работает с Commerce OS и не расползётся по проекту.

Точный синтаксис frontmatter и имена инструментов могут отличаться в вашей версии Claude Code — воспринимайте пример как инженерный шаблон, а не как священный YAML.

---
name: tester
description: Проверяет текущий diff Commerce OS, запускает тесты и пишет или обновляет тестовые файлы. Production-код не меняет.
tools: Read, Glob, Grep, Bash, Edit, Write
model: inherit
---

Тело агента:

Ты tester-агент.
Работай только в каталогах src/test/, tests/ и аналогичных test-папках.
Не меняй production-файлы.
Если для прохождения тестов нужен фикс в боевом коде,
остановись и верни explanation человеку.
После работы обязательно сообщи:
какие тесты добавлены или обновлены,
какие команды запущены,
какие проверки не удалось подтвердить.

В таком виде конфигурация намеренно узкая: минимальный набор действий, но ещё не весь контур знаний роли.

Поле description задаёт рамку: production-код уже не зона агента. Edit и Write в tools — только потому, что tester действительно пишет тесты. Собирали бы reviewer — этих прав не было бы вовсе.

Но одних tools здесь всё равно недостаточно. Поэтому ниже идёт жёсткое текстовое сужение: редактирование дано не как «право редактировать всё», а ради одного класса файлов. Это контракт поведения, а не технический замок: tools не умеют ограничивать запись одним каталогом. Поэтому после прогона смотрим changed files: production-файл в списке — результат не принимаем, даже если тесты зелёные.

Для контраста полезно посмотреть на reviewer:

---
name: reviewer
description: Проводит локальный review diff перед PR. Только чтение.
tools: Read, Glob, Grep, Bash
model: inherit
---
Ты reviewer-агент.
Не редактируй файлы.
Проверь diff, связанные тесты и команды проверки.
Верни findings с evidence и уровнем серьёзности.

Разница принципиальная. Оба смотрят на один и тот же refund bugfix в Commerce OS, но у одного Edit нет вовсе, у второго он связан границами каталогов. Вот это и есть least privilege в живом виде, а не лозунг на стене.

Если вы хотите быстро понять, хорошо ли собран agents/tester.md, задайте один вопрос: сможет ли этот агент случайно улучшить то, что вы не просили улучшать? Ответ «да» — набор инструментов всё ещё широкий.

6. Собирай от результата, а не от прав

Когда вы проектируете нового агента, очень хочется начать с tools: что бы выдать? Но надёжнее двигаться наоборот — от результата к минимальным действиям. Иначе выйдет типичный инженерный фокус: «сначала выдали права, потом придумали, зачем».

Работайте по простой последовательности из четырёх шагов:

  1. Начните с результата. Что именно агент должен вернуть — findings по diff, набор тестов, документацию? Пока этого нет, поле tools — угадайка.
  2. Для каждого результата выпишите минимальные действия. Review findings — чтение кода, поиск и, возможно, запуск проверок. Написать тесты — появляется редактирование, но не раньше.
  3. Для каждого инструмента задайте неприятный вопрос: что плохого случится, если агент использует его неидеально? С Read вред ограничен. С Bash можно устроить приключение. С Edit — полноценный выход за роль.
  4. Уберите всё, без чего роль всё ещё справляется. Documenter не запускает команды — убирайте Bash. Reviewer не должен править код — убирайте Edit. Tester пишет только тесты — сужайте редактирование до test-каталогов.

Эта последовательность хорошо работает на agents/tester.md. Начали с результата — дописать тесты и показать, что проверено, — и из этого выросли Read, Glob, Grep, Bash, Edit и Write. Не больше. Не «на всякий случай». Не «вдруг пригодится».

Когда вы в следующий раз откроете файл, в поле tools полезно видеть не список возможностей, а договор: что этой роли позволено ради результата — и что ей не позволено, даже если очень хочется помочь.

Что запомнить

  • Инструкция без технической границы — табличка «не входить» на двери без замка.
  • L1 — права сессии, L2 — tools агента, L3 — командные правила и защищённые зоны.
  • L2 может сузить L1, но не расширить её.
  • permissionMode и mcpServers могут дать больше, чем есть у сессии; для первого tester их не трогаем.
  • Если tools не указать, агент наследует почти все инструменты, включая Edit, Write и MCP.
  • disallowedTools — подход «всё, кроме»; при нём агент может унаследовать Agent, поэтому узкой роли добавьте Agent в запрет.
  • Reviewer: Read, Glob, Grep, Bash, без Edit/Write.
  • Tester: Read, Glob, Grep, Bash, Edit, Write, но редактирует только test-каталоги.
  • Edit/Write — не «на всякий случай», а под конкретный результат.
  • Текстовые границы каталогов не являются техническим замком; проверяйте changed files.
  • Проектируйте права от результата: результат → минимальные действия → риск неидеального использования → удаление лишнего.

Практика (15–25 минут)

Цель: собрать безопасные tester.md и reviewer.md, разложить их права по L1/L2 и проверить, не может ли агент выйти за границы роли.

Что сделать

  1. В вымышленном Workflow Kit создайте .claude/agents/tester.md: description с запретом менять production-код, tools: Read, Glob, Grep, Bash, Edit, Write, model: inherit. В теле разрешите правки только в src/test/ и tests/, а при необходимости production-фикса требуйте остановиться и вернуть объяснение.
  2. Создайте .claude/agents/reviewer.md с tools: Read, Glob, Grep, Bash без Edit/Write; тело должно требовать findings с severity, file:line и evidence.
  3. Заполните PERMISSIONS_AUDIT.md: для ролей reviewer, tester, documenter и debugger укажите результат, минимальные tools, что не выдано и что случится при неидеальном использовании инструмента.
  4. Придумайте учебный diff в Commerce OS с тестовым файлом и production-файлом. Если Claude Code доступен, вызовите @agent-tester на фейковой задаче; если нет — вручную сымитируйте результат. Проверьте changed files: production-файл в списке означает отказ, даже если тесты зелёные.
  5. Проверьте конфиги по вопросу «сможет ли агент случайно улучшить то, что я не просил?» и запишите вывод в PERMISSIONS_AUDIT.md. Не меняйте реальный код проекта.

Если Claude Code недоступен: выполните конфиги и аудит вручную в редакторе, а результат tester сымитируйте по фейковому diff; недоступные команды разберите по документации. Критерии проверки те же.

Проверка

  • У reviewer нет Edit и Write.
  • У tester есть Edit/Write, но в инструкции явно ограничены test-каталоги.
  • В description tester зафиксировано, что production-код не меняется.
  • Есть stop condition для случая «нужен production-фикс».
  • В PERMISSIONS_AUDIT.md разобраны четыре роли и их риски.
  • L1/L2/L3 не перепутаны: tools агента не выходят за права сессии.
  • Проверены changed files, а не только зелёный статус тестов.
  • В практике только фейковые данные, без секретов и реальных репозиториев.
  • Если Claude Code недоступен, аудит и симуляция выполнены вручную по тем же критериям.
