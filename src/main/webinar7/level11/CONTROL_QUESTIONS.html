Уровень 11 — контрольные вопросы

Контрольный блок по 5 лекциям уровня 11 и практике вебинара 7: 25 открытых вопросов с короткими ответами и ссылками на конспекты. Вопросы синхронизированы с презентацией: субагенты и пять механизмов, встроенные роли, конфигурация агента, engineering contract, роли reviewer/tester/debugger/documenter и трёхслойная модель review.

Лекция 1 — терминология агентов

  1. Что такое subagent и из чего состоит его рабочая формула?
    Subagent — специализированный помощник внутри текущего workflow: работает в собственном окне контекста и возвращает в основную сессию короткую сводку. Формула: role + isolated context + tools + output contract. Его сила — в специализации и изоляции, а не в автономности; это не «второй Claude рядом».
    → Лекция 1
  2. Какие пять механизмов прячутся за словом «agent» и по каким трём осям их различать?
    subagent, separate session, background agent, worktree-backed session и agent team. Оси: где живёт контекст, возвращается ли результат автоматически и нужна ли отдельная файловая поверхность — ветка или worktree.
    → Лекция 1
  3. Чем worktree-backed session отличается от обычного subagent и когда она уместна?
    Subagent изолирует контекст и обычно не даёт файловой изоляции; worktree-backed session даёт отдельную рабочую директорию, branch и собственный diff. Она нужна для рискованных реальных правок, параллельной работы без конфликтов и сравнения вариантов. Для исследования «где лежит код» достаточно subagent.
    → Лекция 1
  4. Чем background agent отличается от subagent?
    Background agent — отдельная фоновая сессия: задача выполняется асинхронно, результат возвращается позже, а перед правками у неё есть свой worktree. Subagent обычно быстро возвращает summary в текущий разговор. Фон нужен для долгой работы без постоянного диалога; для плотного интерактива он мешает.
    → Лекция 1
  5. Что такое fork (/subtask) и почему его нельзя путать с «чистым» subagent?
    Fork — subagent, который получает весь текущий разговор. Ему не нужно переобъяснять контекст, но у него нет «чистого взгляда»: он наследует гипотезы и тупики основной сессии. Это вариант subagent с унаследованным контекстом, а не шестая сущность из таблицы пяти механизмов.
    → Лекция 1

Лекция 2 — встроенные subagents и делегирование

  1. Каких встроенных subagents приводит лекция и для чего они нужны?
    Explore — read-only разведка по коду: файлы, точки входа, цепочки вызовов. Plan — research в plan mode, собирает материал для плана до правок. general-purpose — многошаговые подзадачи, где нужно и искать, и действовать. Имена меняются от версии к версии; важнее тип поведения.
    → Лекция 2
  2. Почему изолированный контекст полезен и что возвращается в основную сессию?
    Он не заваливает основную сессию десятками прочитанных файлов, поисками и ложными гипотезами; исследование становится дешевле для контекста. В основную сессию возвращается короткая сводка, а не весь транскрипт. Посмотреть транскрипт работающего агента можно через /tasks, но проверять нужно именно сводку.
    → Лекция 2
  3. Какой признак отличает сильную returned summary от слабой?
    Сильная сводка проверяема: в ней есть файлы и, желательно, строки, связанные тесты, evidence и честный блок «не проверено». Слабая — общий вывод вроде «похоже, проблема в support-модуле», который нечем проверить. Сводка — папка со следами, а не приговор.
    → Лекция 2
  4. Когда делегирование subagent оправдано, а когда лучше справиться самому?
    Если задача маленькая, вы знаете точный файл и хотите понять короткую функцию — читайте сами. Если исследование расползается на слои, тесты, конфиги и точки входа и может захламить основной разговор — делегируйте. Критерий один: насколько расследование загрязнит основную сессию.
    → Лекция 2
  5. В каких двух случаях subagent скорее навредит?
    В конвейере reproduce → debug → fix, где шаги зависят от находок друг друга и на стыках теряется информация, и при прогоне тестов ради результата: агент вернёт «tests failed» без полного вывода, нужного для дебага. Такие задачи держите в основной сессии.
    → Лекция 2

Лекция 3 — кастомный subagent

  1. Где живёт project-scope агент и кто его видит?
    В .claude/agents/ внутри репозитория. Он виден всей команде, попадает в Git и проходит через diff и review как обычный артефакт. Personal-агент лежит в ~/.claude/agents/ и доступен только вам.
    → Лекция 3
  2. Как создать агента в свежих версиях Claude Code и что случилось с командой /agents?
    Есть два пути: попросить Claude сгенерировать черновик по описанию или вручную добавить markdown-файл в .claude/agents/. В свежих версиях /agents удалена: при вводе Claude Code подсказывает замену — попросить Claude создать агента или отредактировать папку агентов.
    → Лекция 3
  3. Какие четыре поля минимальны для стартового агента и какое пятое поле полезно добавить?
    name, description, tools и тело инструкции. Пятое полезное поле — model: inherit (как в основной сессии), быстрая Haiku для лёгкого поиска или Opus для сложного анализа.
    → Лекция 3
  4. Почему description называют решающим полем?
    По нему Claude выбирает, когда делегировать задачу, и по нему же главная сессия составляет задание агенту. Конкретное описание даёт конкретный промпт; use proactively подталкивает звать агента чаще, а примеры сценариев чинят «не подхватывается, когда должен». Без name или description файл молча пропускается.
    → Лекция 3
  5. Какие tools нужны reviewer и что произойдёт, если не указать tools вообще?
    Для reviewer достаточно Read, Glob, Grep и Bash — читать diff, искать evidence и запускать безопасные read-only проверки. Edit и Write ему не нужны. Если tools не указаны, агент наследует почти все инструменты сессии, включая Edit, Write и MCP, — это не безопасный минимум.
    → Лекция 3

Лекция 4 — engineering contract

  1. Из каких четырёх элементов состоит engineering contract в инструкции агента?
    Роль; когда использовать; разрешённые действия и формат результата; условия остановки. Формула: инструкция = роль + триггер + действия/формат + стоп-условия.
    → Лекция 4
  2. Какая инструкция считается плохой и почему?
    «Ты очень опытный code reviewer. Думай как senior engineer, проверяй код глубоко и внимательно, находи всё важное». Она описывает характер, а не контракт: непонятно, когда запускать, что вернуть, где остановиться и что запрещено. Агент-«эксперт» тоже не добавляет способностей — ценность в границах и формате.
    → Лекция 4
  3. Чем description отличается от раздела «Когда использовать»?
    description — короткая вывеска для выбора агента снаружи. Раздел «Когда использовать» — рабочая дисциплина изнутри: конкретные триггеры, контекст и условия «не использовать». Полезно указывать не только «когда да», но и «когда нет».
    → Лекция 4
  4. Что обязательно включить в формат результата reviewer?
    Краткое summary; findings с severity, file:line, evidence и suggested action; отдельно open questions. Гипотезы без доказательств помечаются [hypothesis] и не выдаются за факт. Формат одновременно служит встроенным стопом: заполнил секции — работа готова.
    → Лекция 4
  5. Какие условия остановки нужны reviewer?
    Большой diff — попросить сузить scope; чувствительные зоны (auth, payments, migrations) — не делать сильных выводов без evidence; нехватка данных — вернуть open questions; после findings передать решение человеку. Reviewer готовит материал, а не выносит финальный приговор.
    → Лекция 4

Лекция 5 — роли и review

  1. Какие четыре базовые роли агентов и что каждая пишет?
    reviewer — ничего; tester — только тестовые файлы, если разрешено; debugger — обычно ничего; documenter — только документацию. Оси роли: read, run, write, stop. Пустая ось write у reviewer принципиальна: иначе он становится тихим соавтором diff.
    → Лекция 5
  2. Что делает каждый из трёх слоёв review?
    Layer 1 — локальный review до push/PR: автор и reviewer-агент читают diff, ловят явные риски и проверяют scope. Layer 2 — технический gate: CI и автоматические проверки. Layer 3 — team approval и решение владельца зоны на чувствительных изменениях. Это учебная карта, а не термин Claude Code.
    → Лекция 5
  3. Чем review отличается от verification?
    Verification отвечает, что проверяем и как доказываем: тесты, build, lint, smoke, логи, скриншоты. Review отвечает, кто и когда решает, что можно идти дальше: локальный review, gate, team approval. Мнемоника: L + число — verification, Layer + число — review.
    → Лекция 5
  4. Почему reviewer должен оставаться read-only и чем опасен write-доступ?
    С write-доступом он начинает не проверять, а исправлять: сегодня опечатка, завтра форматирование, послезавтра «слегка улучшил» бизнес-логику. Review смешивается с реализацией, а findings подменяются тихим соавторством в diff. Поэтому reviewer пишет nothing, а tester — только тесты.
    → Лекция 5
  5. Почему специализации reviewer — не зоопарк агентов и что делает /code-review?
    Security, performance, test quality, architecture, DB и frontend — фокусы одного шаблона reviewer; разница в description и инструкции. Заводят их по реальной боли, а не «шесть ревьюеров на старте». Встроенный /code-review проверяет diff в фоновом контексте, /code-review ultra запускает глубокое облачное ревью; свой reviewer нужен ради правил и формата команды.
    → Лекция 5
