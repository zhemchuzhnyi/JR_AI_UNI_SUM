# Саммари лекции 3

## Кастомный subagent: устройство — Claude Code, 11 уровень

## 1. Свой агент команды vs встроенные

Изолированное расследование решило одну проблему: основная сессия перестаёт тонуть в промежуточном шуме. Но когда одна и та же узкая подзадача повторяется по правилам команды, встроенного поведения быстро становится мало. Тот же subagent-паттерн меняет форму: из одноразового делегирования становится версионируемым артефактом репозитория.

Встроенные агенты хороши для общих задач: поиск по коду, исследование файлов, планирование, сбор сведений. Но если команде нужен предсказуемый ритуал — смотреть готовый diff, не трогать файлы, возвращать замечания в одном формате и не превращать ревью в ремонт всего проекта — нужен custom subagent.

В Workflow Kit это выглядит приземлённо:

```text
workflow-kit/
  .claude/
    skills/
      issue-analysis/
    agents/
      reviewer.md
```

Кастомный агент — не «ещё один Claude внутри Claude», а аккуратно оформленный переиспользуемый файл с понятной задачей. Чем меньше магии, тем легче поддерживать.

## 2. Область видимости агента

Перед созданием важно понять не только «что он делает», но и «где живёт». Иначе reviewer готов, всё работает, а коллега открывает репозиторий и ничего не видит: агент остался в личной папке.

| Область | Где обычно лежит | Кто видит | Когда использовать |
|---|---|---|---|
| personal | `~/.claude/agents/` | только вы | личные эксперименты |
| project | `.claude/agents/` в корне repo | вся команда репозитория | общие проектные агенты |
| plugin-provided | приходит с plugin | все, кто поставил plugin | агент как часть пакета |
| managed | управляется организацией | команда или компания | централизованная политика |

`~` означает домашнюю папку. Personal — личный ящик стола, project — шкафчик на кухне команды. Для Workflow Kit ключевой вариант — `project`: `agents/reviewer.md` должен одинаково работать у всех, кто ведёт изменения в Commerce OS. В personal он заработает только у вас.

## 3. Четыре поля стартового агента

Для первого рабочего агента достаточно четырёх вещей: имени, описания, списка инструментов и тела инструкции. Остальное — тюнинг.

| Поле | Что означает | Зачем нужно |
|---|---|---|
| `name` | имя агента | ссылаться и отличать от других |
| `description` | когда и зачем использовать | чтобы Claude правильно делегировал задачу |
| `tools` | разрешённые инструменты | чтобы агент не выходил за роль |
| instruction body | текст инструкции | чтобы агент понимал, что делать после вызова |

Минимальный каркас:

```markdown
---
name: reviewer
description: Проверяет готовый diff и возвращает замечания без правки кода.
tools:
  - Read
  - Grep
---

Проверь изменённые файлы и верни краткие замечания по найденным проблемам.
```

Точные идентификаторы инструментов и формат интерфейса зависят от версии Claude Code; заполняя tools через `/agents`, ориентируйтесь на актуальные варианты. Тело — обычный markdown под frontmatter, его можно открыть в IDE и закоммитить.

## 4. description: решающее поле

Многие думают, что главное — «умная» инструкция внизу. На практике первое критическое поле — `description`: это правило выбора. Решая, делегировать ли задачу custom subagent, Claude смотрит на описанную область применения. Расплывчатое описание даёт плохую маршрутизацию.

```text
description: Reviewer для всего.
```

```text
description: Read-only reviewer для готового diff. Использовать после того,
как изменения собраны и нужен второй взгляд перед merge.
```

Второй вариант отвечает на скрытые вопросы: кто это, когда использовать, в каком режиме. У Claude появляется не имя роли, а понятный триггер.

Хорошее description даёт три опоры:

- что агент делает;
- в какой момент workflow он нужен;
- где проходит его граница.

Для reviewer в Workflow Kit укажите: проверяет готовый diff, не редактирует код, нужен перед merge или локальным принятием изменений.

## 5. tools: граница полномочий

Начинающие любят мысль «дам всё, а там он сам разберётся». Агент с лишними tools не становится умнее — он получает больше способов сделать что-то неожиданное.

Для reviewer логика простая: читать изменения и возвращать замечания. Права на редактирование, широкий доступ к командам и режим «вдруг сам поправит» не нужны.

```text
tools:
  - Read
  - Grep
```

Вместо:

```text
tools:
  - Read
  - Grep
  - Edit
  - Bash
```

Во втором варианте агент может начать редактировать код только потому, что «уже здесь». Смешивать review и реализацию — плохая привычка даже у людей, а у AI она возникает быстрее.

Агент живёт внутри рамки разрешений сессии и не вырастет в сверхсущество. Но tools всё равно важны: сужают его сильнее и делают поведение понятным. Сначала минимум; расширяйте осознанно, если реально не хватает read-only способа собрать evidence.

## 6. Создание agents/reviewer.md через /agents

Агент создаётся через интерфейс управления агентами — обычно `/agents` или близкую панель. Название может отличаться; сверьтесь с `/help`, важен workflow.

```text
/agents
  → выбор scope
  → 4 поля: name, description, tools, body
  → сохранение
  → файл в .claude/agents/
  → проверка через Git diff
```

| Шаг | Что делаете | На что смотрите |
|---|---|---|
| 1 | Открываете `/agents` | Есть ли режим создания агента |
| 2 | Выбираете scope | Для командного артефакта — project |
| 3 | Заполняете 4 поля | Имя, описание, инструменты, инструкция |
| 4 | Сохраняете | Где именно появился файл |
| 5 | Проверяете diff | Агент должен быть виден в Git |

После сохранения в project файл обычно оказывается здесь:

```text
.claude/
  agents/
    reviewer.md
```

Если файл в проекте, вы видите его в IDE и Git diff: можно прочитать, поправить, обсудить в PR. Создали в personal — Git промолчит, и команда не узнает про помощника.

## 7. Агент как файл репозитория

Последняя привычка связана не с созданием, а с отношением к результату. Легко настроить агента и забыть про него как про бытовую магию IDE. Но если reviewer полезен проекту, он должен читаться, обсуждаться, меняться и проходить через Git наравне с инженерными файлами.

Через пару недель в Commerce OS меняются правила, появляются новые каталоги, иначе называются зоны риска, уточняется стиль review. Агент в репозитории — меняете description или инструкцию, смотрите diff, коммитите. Агент «где-то локально» — команда живёт со старой версией, вы с новой, и поведение одного инструмента различается у разных людей.

Хороший финальный жест прозаичен: сделайте `git status` после сохранения. Файл `agents/reviewer.md` виден в diff, лежит в project-области, поедет к команде вместе с кодом — значит scope выбран верно. Git промолчал — reviewer застрял в `~/.claude/`, и коллеги про него не узнают.

## 8. Чеклист первого reviewer-агента

- scope — `project`, если агент нужен команде;
- `name` короткий и понятный;
- `description` объясняет, что делает, когда запускать и где граница;
- `tools` минимальны: для review достаточно `Read` и `Grep`;
- тело инструкции короткое: роль, порядок, формат findings, запрет на правки;
- файл лежит в `.claude/agents/`, виден в Git;
- после сохранения проверен `git diff`;
- агент не пытается чинить код вместо review;
- при изменении правил команды файл обновляется через обычный PR.

## Что запомнить

- Custom subagent нужен, когда узкая подзадача повторяется по правилам команды.
- Scope определяет, кто увидит агента: personal, project, plugin-provided, managed.
- Для командного артефакта обычно нужен `project`, а не personal.
- Стартовые поля: `name`, `description`, `tools`, instruction body.
- `description` — правило выбора и маршрутизации, а не подпись.
- `tools` — граница полномочий; для reviewer достаточно read-only.
- `/agents` создаёт файл в `.claude/agents/`; проверяйте его в Git.
- Агент — файл репозитория, который меняется через diff и review.
- Git промолчал — агент остался личным и не стал командным.
- Сначала минимальные права; расширяйте только по реальной необходимости.

## Практика (15–25 минут)

**Цель:** создать project-scope reviewer-агента с четырьмя полями, минимальными tools и проверкой файла в Git.

**Что сделать:**
1. В вымышленном Workflow Kit создайте `.claude/agents/reviewer.md`. Используйте только фейковые данные.
2. Заполните frontmatter: `name: reviewer`, `description` с триггером «готовый diff, read-only, перед merge», `tools: [Read, Grep]`.
3. Добавьте тело: проверить только изменённые файлы, вернуть findings по рискам, пропущенным тестам и scope, не менять код, перечислить open questions.
4. Если Claude Code доступен, создайте агента через `/agents` в project scope и сравните файл с ручным вариантом; если нет — проверьте структуру вручную.
5. Выполните `git status` и `git diff`: файл должен быть виден как проектный артефакт. Запишите в `AGENT_REVIEW.md`, почему выбран project scope и какие tools сознательно не выданы.

**Проверка:**
- Файл лежит в `.claude/agents/reviewer.md`.
- Есть `name`, `description`, `tools` и тело инструкции.
- `description` объясняет, когда запускать и где граница.
- В tools только `Read` и `Grep`, без Edit/Bash.
- Тело запрещает менять код и требует findings/open questions.
- `git status`/`git diff` показывают файл.
- В практике только фейковые данные и нет реальных секретов.
