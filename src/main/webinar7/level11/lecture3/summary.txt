# Саммари лекции 3

## Кастомный subagent: устройство — Claude Code, 11 уровень

## 1. Свой агент команды vs встроенные

Изолированное расследование решает одну проблему: основная сессия перестаёт тонуть в промежуточном шуме. Но когда одна и та же узкая подзадача повторяется по правилам команды, встроенного поведения быстро становится мало. Тот же subagent-паттерн меняет форму: из одноразового делегирования становится версионируемым артефактом репозитория.

Встроенные агенты хороши для общих задач: Explore ищет по коду, Plan собирает материал для плана, general-purpose берёт многошаговые подзадачи. Но если команде нужен предсказуемый ритуал — смотреть готовый diff, не трогать файлы, возвращать замечания в одном формате и не превращать review в ремонт всего проекта — нужен custom subagent.

В Workflow Kit это выглядит приземлённо:

```text
workflow-kit/
  .claude/
    skills/
      issue-analysis/
    agents/
      reviewer.md
```

Кастомный агент — не «ещё один Claude внутри Claude», а аккуратно оформленный переиспользуемый файл с понятной задачей. Чем меньше магии, тем легче поддерживать.

## 2. Область видимости агента

Перед созданием важно понять не только «что он делает», но и «где живёт». Иначе reviewer готов, всё работает, а коллега открывает репозиторий и ничего не видит: агент остался в личной папке.

| Область | Где обычно лежит | Кто видит | Когда использовать |
|---|---|---|---|
| personal | `~/.claude/agents/` | только вы | личные эксперименты |
| project | `.claude/agents/` в корне repo | вся команда репозитория | общие проектные агенты |
| plugin-provided | приходит с plugin | все, кто поставил plugin | агент как часть пакета |
| managed | управляется организацией | команда или компания | централизованная политика |

`~` означает домашнюю папку. Personal — личный ящик стола, project — шкафчик на кухне команды. Для Workflow Kit ключевой вариант — `project`: `agents/reviewer.md` должен одинаково работать у всех, кто ведёт изменения в Commerce OS. В personal он заработает только у вас.

## 3. Четыре поля стартового агента

Для первого рабочего агента достаточно четырёх вещей: имени, описания, списка инструментов и тела инструкции. Остальное — тюнинг. Практически сразу полезно добавить пятое поле — `model`: оно выбирает движок под задачу.

| Поле | Что означает | Зачем нужно |
|---|---|---|
| `name` | имя агента | ссылаться и отличать от других |
| `description` | когда и зачем использовать | чтобы Claude правильно делегировал задачу |
| `tools` | разрешённые инструменты | чтобы агент не выходил за роль |
| instruction body | текст инструкции | чтобы агент понимал, что делать после вызова |
| `model` | `inherit`, Haiku или Opus | чтобы у лёгкого поиска и сложного анализа был подходящий движок |

Минимальный каркас:

```markdown
---
name: reviewer
description: Read-only review готового diff перед merge
tools: Read, Glob, Grep, Bash
model: inherit
---

Проверь изменённые файлы и верни краткие замечания.
```

`model: inherit` означает «та же модель, что в основной сессии». Для лёгкого поиска можно выбрать быструю Haiku, для сложного анализа — Opus. На какой модели агент реально работает, показывает `/tasks`: модель подписана в строке субагента.

Тело — обычный markdown под frontmatter. Его можно открыть в IDE, обсудить в PR и закоммитить.

## 4. description: решающее поле

Многие думают, что главное — «умная» инструкция внизу. На практике первое критическое поле — `description`: это правило выбора. Решая, делегировать ли задачу custom subagent, Claude смотрит на описанную область применения. Расплывчатое описание даёт плохую маршрутизацию.

У `description` две роли:

- по нему главная сессия выбирает агента;
- по нему же она составляет задание для агента, поэтому конкретное описание даёт конкретный промпт.

```text
description: Reviewer для всего.
```

```text
description: Read-only reviewer готового diff. Запускать для локального
review перед merge, когда тесты прогнаны. Use proactively после сборки diff.
```

Второй вариант отвечает на скрытые вопросы: кто это, когда использовать, в каком режиме. Фраза `use proactively` подталкивает Claude звать агента чаще, а примеры сценариев чинят ситуацию «не подхватывается, когда должен».

Хорошее description даёт три опоры:

- что агент делает;
- в какой момент workflow он нужен;
- где проходит его граница.

Если в frontmatter нет `name` или `description`, Claude Code пропускает файл, ничего не сообщая в сессии. Поэтому после создания проверьте, что агент появился в `@`-списке.

## 5. tools: граница полномочий

Начинающие любят мысль «дам всё, а там он сам разберётся». Агент с лишними tools не становится умнее — он получает больше способов сделать что-то неожиданное.

Для reviewer логика простая: читать изменения, искать evidence и запускать безопасные read-only проверки. Права на редактирование ему не нужны.

```text
tools: Read, Glob, Grep, Bash
```

Вместо:

```text
tools: Read, Glob, Grep, Bash, Edit, Write
```

`Read` читает файл, `Bash` запускает команды. `Glob` и `Grep` ищут файлы по маске и по содержимому; на Windows они нужны отдельно, а на macOS, Linux и WSL Claude ищет через `find` и `grep` в Bash. `Bash` reviewer'у нужен ради `git diff` и безопасных read-only проверок. `Edit` и `Write` — право менять файлы — ему ни к чему.

Важная ловушка: **если `tools` не указаны вообще, агент наследует почти все инструменты сессии**, включая `Edit`, `Write` и MCP, кроме нескольких служебных. Поэтому «не указал tools» не означает «безопасный минимум».

Минимум прав — это «под работу», а не «как можно меньше». Сначала выдайте необходимое, расширяйте только когда реально упёрлись.

## 6. Создание agents/reviewer.md

Субагент — это markdown-файл в папке `.claude/agents/`. В свежих версиях Claude Code есть два пути:

```text
Что должен делать агент
  → попросить Claude сгенерировать черновик
  → или добавить файл вручную
  → .claude/agents/reviewer.md
```

Лучший путь тот же, что со skill: опишите словами — «read-only reviewer, проверяет готовый diff, возвращает findings» — и Claude сам сгенерирует `name`, `description` и инструкцию. Вам останется отревьюить черновик. Второй путь — создать файл вручную и заполнить frontmatter.

В старых гайдах встречается команда `/agents`. В свежих версиях она удалена: при вводе Claude Code сам подсказывает замену — попросить Claude создать агента или отредактировать `.claude/agents/`. Если в вашей версии команда ещё есть, интерфейс может отличаться, но артефакт всё равно один — markdown-файл в папке агентов.

Почему не skill? Skill работает inline в вашем контексте, агент — в отдельном окне. Нужна изоляция и автономная работа — агент; повторяемая процедура без шума — skill.

## 7. Агент как файл репозитория

После создания агент лежит в `.claude/agents/reviewer.md`. Внутри — frontmatter и тело инструкции:

```markdown
---
name: reviewer
description: Read-only review готового diff перед merge
tools: Read, Glob, Grep, Bash
model: inherit
---

Проверь изменённые файлы и верни краткие замечания.
```

Вызвать агента можно точечно: наберите `@` и выберите из списка или напишите `@agent-reviewer` вручную.

Добавили или поправили файл на диске — Claude Code замечает изменение за несколько секунд, без перезапуска. Restart нужен только один раз: если папка `agents/` создана впервые уже после старта сессии.

Если агент не появился в `@`-списке, первым делом проверьте frontmatter. Битый YAML найдёт `claude plugin validate .claude/agents`, а пропущенный `name` эта проверка не ловит — его нужно смотреть глазами.

Хороший финальный жест прозаичен: сделайте `git status` после сохранения. Файл `agents/reviewer.md` виден в diff, лежит в project-области, поедет к команде вместе с кодом — значит scope выбран верно. Git промолчал — reviewer застрял в `~/.claude/`, и коллеги про него не узнают.

## 8. Чеклист первого reviewer-агента

- scope — `project`, если агент нужен команде;
- `name` короткий и понятный;
- `description` объясняет, что делает, когда запускать и где граница; при необходимости — `use proactively` и примеры;
- `tools` минимальны: для review достаточно `Read`, `Glob`, `Grep`, `Bash`, без `Edit` и `Write`;
- `model` выбран осознанно: `inherit`, быстрая Haiku или Opus для сложного анализа;
- тело инструкции короткое: роль, порядок, формат findings, запрет на правки;
- файл лежит в `.claude/agents/`, виден в Git;
- после сохранения проверен `git status`/`git diff`;
- агент вызывается через `@agent-reviewer`;
- при изменении правил команды файл обновляется через обычный PR.

## Что запомнить

- Custom subagent нужен, когда узкая подзадача повторяется по правилам команды.
- Scope определяет, кто увидит агента: personal, project, plugin-provided, managed.
- Для командного артефакта обычно нужен `project`, а не personal.
- Стартовые поля: `name`, `description`, `tools`, instruction body; `model` — практичное дополнение.
- `description` — правило выбора и маршрутизации, а не подпись; по нему же строится задание агенту.
- `tools` — граница полномочий; для reviewer достаточно `Read`, `Glob`, `Grep`, `Bash`, без `Edit`/`Write`.
- Если `tools` не указаны, агент наследует почти все инструменты сессии.
- В свежих версиях `/agents` удалена: агента создают через Claude или вручную в `.claude/agents/`.
- Агент вызывается через `@agent-reviewer`; правки файла подхватываются без перезапуска.
- Агент — файл репозитория, который меняется через diff и review.
- Git промолчал — агент остался личным и не стал командным.

## Практика (15–25 минут)

**Цель:** создать project-scope reviewer-агента с четырьмя полями, `model` и безопасными tools, затем проверить его в Git.

**Что сделать:**
1. В вымышленном Workflow Kit создайте `.claude/agents/reviewer.md`. Используйте только фейковые данные.
2. Заполните frontmatter: `name: reviewer`, `description` с триггером «готовый diff, read-only, перед merge», `tools: Read, Glob, Grep, Bash`, `model: inherit`.
3. Добавьте тело: проверить только изменённые файлы, вернуть findings по рискам, пропущенным тестам и scope, не менять код, перечислить open questions. Явно запретите `Edit` и `Write`.
4. Если Claude Code доступен, создайте агента через Claude или вручную и вызовите `@agent-reviewer`; проверьте, что правка файла подхватилась без перезапуска. Если папка `agents/` создана впервые после старта сессии, один раз перезапустите Claude Code. Если Claude Code недоступен — проверьте структуру вручную.
5. Выполните `git status` и `git diff`: файл должен быть виден как проектный артефакт. Запишите в `AGENT_REVIEW.md`, почему выбран project scope, какие tools выданы и какие сознательно запрещены.

**Проверка:**
- Файл лежит в `.claude/agents/reviewer.md`.
- Есть `name`, `description`, `tools`, `model` и тело инструкции.
- `description` объясняет, когда запускать и где граница.
- В tools есть `Read`, `Glob`, `Grep`, `Bash`, но нет `Edit`/`Write`; `Bash` разрешён только для read-only проверок.
- Тело запрещает менять код и требует findings/open questions.
- Агент вызывается через `@agent-reviewer` или виден в `@`-списке.
- `git status`/`git diff` показывают файл.
- В практике только фейковые данные и нет реальных секретов.
