# Саммари лекции 1

## Терминология агентов в Claude Code — Claude Code, 11 уровень

## 1. Путаница вокруг слова agent

Когда продукт быстро растёт, удобные слова начинают обозначать сразу несколько сущностей. С agent происходит именно это: «запустим агента», «пусть агент проверит код», «нужен ещё один агент» звучат красиво, но инженерно это туман.

За одним словом прячутся разные механики:

- помощник внутри текущей сессии;
- отдельный разговор Claude со своей историей;
- фоновая задача, которую запустили и пошли заниматься другим;
- рабочая единица с отдельной файловой изоляцией;
- координация нескольких исполнителей.

Если называть всё одним словом, обсуждение в команде превращается в «принеси вон ту штуку из того места». Точность здесь не бюрократия, а условие нормальной работы.

Полезно сразу задавать три вопроса:

1. Где живёт контекст этой рабочей единицы?
2. Возвращается ли результат в текущий разговор автоматически?
3. Нужна ли отдельная файловая изоляция — ветка или worktree?

Три вопроса — и туман рассеивается.

> Если фраза «запусти ещё одного агента» звучит достаточно точно, значит разговор пока недостаточно точный.

## 2. Agent — зонтичный термин

В обычной речи agent удобен как зонтик: любой AI-исполнитель внутри Claude Code. Для общей картины годится, для точной команды — слабо.

«У нас есть agent» — примерно то же, что «у нас есть специалист». Какой? Аналитик, ревьюер, тестировщик? С доступом только на чтение или с правом менять код? Пока не уточнили — это лишь категория.

Agent уместен в двух случаях:

- архитектурный разговор верхнего уровня: «агентные механизмы в системе есть»;
- тип ещё не определён.

Дошло до реальной задачи в Workflow Kit или Commerce OS — переходите к точным словам.

```text
Неточно:
«Давайте запустим ещё одного агента на auth-модуль».

Точнее:
«Нужен read-only subagent для исследования auth-модуля
и короткого summary в текущую сессию».
```

Во втором варианте уже понятно: это не отдельная ветка с правками, не фоновый процесс и не команда нескольких исполнителей, а конкретная рабочая единица с конкретной функцией.

## 3. Subagent: рабочий термин уровня

Если agent — шапка категории, то **subagent** — рабочее определение, на котором можно строить инженерный артефакт. Центральный термин уровня. `agent` — разговорное название, `subagent` — техническое: тот же файл, но запущенный под вашей сессией.

Рабочая формула:

```text
subagent = role
         + isolated context
         + tools
         + output contract
```

- **role** — кто он по функции: reviewer, исследователь, документатор;
- **isolated context** — работает в собственном окне: читает много файлов и не заваливает основную сессию шумом;
- **tools** — граница возможностей: читать, искать, запускать команды или ничего лишнего;
- **output contract** — форма результата: summary, findings, ссылки на файлы, открытые вопросы.

На старте subagent получает два входа: system prompt из файла конфигурации — роль и правила поведения — и описание задачи, которое главная сессия составляет по вашему запросу. Дальше он работает сам, а в основную сессию возвращается только сводка.

Из формулы следуют два свойства. Subagent — не «второй Claude рядом»: он встроен в текущий workflow и обычно возвращает результат в текущий разговор. Его сила не в автономности, а в специализации и изоляции контекста.

Пока subagent работает — и ещё примерно полминуты после завершения — его транскрипт можно открыть через `/tasks`. Но в основную сессию возвращается только сводка, поэтому проверять нужно её, а не рассчитывать, что весь ход рассуждений останется перед глазами.

Рядом с subagent есть **fork** (`/subtask`) — subagent, который получает весь текущий разговор. Ему не нужно переобъяснять контекст, но и «чистого взгляда» у него нет: он наследует ваши гипотезы и тупики. Это вариант subagent с унаследованным контекстом, а не шестая сущность из таблицы пяти механизмов.

Если вы открываете артефакт `agents/reviewer.md` в Workflow Kit, читайте его не как «какого-то агента», а как конкретный subagent с ролью ревьюера, отдельным контекстом и понятным форматом вывода. Файл перестаёт быть магическим свитком и становится инженерной конструкцией.

Subagent удобно держать рабочим вариантом по умолчанию. Остальные сущности не конкурируют с ним, а показывают, когда нужна другая форма изоляции.

## 4. Separate session: отдельный разговор

Separate session легко спутать с subagent: там и там будто появляется «ещё один Claude». Различие принципиальное: это не помощник внутри текущего workflow, а отдельный разговор со своей историей. Результат обратно автоматически не приносится: вы сами решаете, что перенести дальше.

Аналогия:

- **subagent** — специалист, которому дали узкую подзадачу и попросили вернуться с короткой запиской;
- **separate session** — другой блокнот, где вы ведёте параллельную линию мысли.

Separate session уместна, когда задача стала самостоятельной:

- продумать альтернативный план модуля, не смешивая с текущим разговором;
- пересобрать понимание проблемы с нуля, потому что старая сессия обросла гипотезами и неудачными ходами;
- начать чистую линию работы с новым контекстом.

У subagent встроена идея возврата результата в текущий поток. У отдельной сессии — идея самостоятельности. Это разные рабочие жесты, даже если со стороны оба выглядят как «открыли ещё одного помощника».

## 5. Background agent: работа в фоне

Иногда задаче нужен не диалог, а время: сканировать проект, собрать крупный отчёт, не блокировать текущую работу. Тогда agent может означать фоновую рабочую единицу, которую отправляют выполнять задачу асинхронно.

В свежих версиях это отдельная фоновая сессия (`claude agents`): она получает результат позже, а перед правками — свой worktree. Точные названия и наличие такой возможности зависят от версии Claude Code, но паттерн важнее кнопки.

Background agent хорош, когда:

- вы не хотите сидеть с ним в постоянном диалоге;
- задача понятна и имеет ожидаемый артефакт;
- можно вернуться за результатом позже.

Если задача требует плотного интерактива — «посмотри это, нет, лучше так, а теперь уточни ещё одно место» — фон мешает. Логичнее обычный subagent или текущая сессия.

```text
Нужен быстрый возврат summary в текущий разговор → subagent.
Нужен результат позже, без постоянного диалога → background agent.
```

## 6. Worktree-backed session: изоляция файлов

До этого речь шла в основном об изоляции контекста: кто где думает и куда возвращает ответ. Но есть ещё файловый уровень: правки должны физически идти в другой Git-ветке и другой рабочей директории.

**Worktree-backed session** — сессия, привязанная к отдельной Git worktree: собственная файловая поверхность для правок, свой branch, свой diff.

Разница с subagent:

- исследовательская задача — найти точки входа в payments или разобрать auth: worktree не нужна;
- рискованная реализация, которую не хочется делать в основном working tree: worktree оправдана;
- сравнение двух вариантов без конфликтов по файлам: worktree удобна.

У subagent файловой изоляции по умолчанию нет, но её можно запросить через `isolation: worktree`, если агенту действительно нужно менять файлы в отдельной поверхности. Для обычного read-only исследования это лишняя тяжесть.

```text
Нужно только изолировать исследование → subagent.
Нужно изолировать реальные правки и Git-history → worktree-backed session.
```

Зрелость терминологии — не одно слово agent на всё, а форма изоляции под реальную инженерную потребность.

## 7. Agent team: координация, а не замена дизайну

Когда люди слышат про несколько агентов, хочется сразу вообразить AI-команду: один планирует, второй пишет код, третий тестирует, четвёртый делает кофе. Звучит бодро, поэтому agent team полезно сразу поставить на место: это карта возможной координации, а не режим по умолчанию.

Agent team предполагает несколько исполнителей или сессий с общим планом и координацией. В теории полезно. Но на базовом уровне важнее не разгонять оркестр, а различать одиночные сущности. Очень часто «мне нужен agent team» переводится как «мне нужен один нормально спроектированный subagent».

В программировании легко переусложнить: систему можно собрать из одного понятного механизма, а мы тянем туда хор, оркестр и дым-машину. Agent team — тот случай, когда красивый термин создаёт ложное ощущение зрелости. Профессиональнее обратное: не множить сущности без необходимости.

На текущем этапе достаточно помнить: agent team — не синоним subagent и не «прокачанный Claude». Термин знать полезно, строить на нём базовый workflow пока рано.

## 8. Сравнительная таблица терминов

| Сущность | Где живёт контекст | Как возвращается результат | Файловая изоляция | Когда уместна |
|---|---|---|---|---|
| agent | Зависит от типа | Зависит от типа | Зависит от типа | Общий зонтичный термин |
| subagent | Отдельное окно внутри текущего workflow | Обычно summary в основную сессию | Нет по умолчанию; `isolation: worktree` — по желанию | Узкая специализированная подзадача |
| separate session | Полностью отдельная сессия | Переносите вручную | Не обязательно | Самостоятельная линия работы |
| background agent | Отдельная фоновая сессия (`claude agents`) | Позже, когда завершится | Да, свой worktree перед правками | Долгая работа без диалога |
| worktree-backed session | Отдельная сессия | С собственным diff | Да, worktree/branch | Параллельные или рискованные правки |
| agent team | Несколько координируемых контекстов | Через общую координацию | Может быть, но не обязательна | Сложная координация нескольких единиц |

Таблица полезна для артефакта `agents/reviewer.md`. Через неё видно: это именно subagent. Не отдельная сессия — работает внутри текущего workflow. Не worktree-backed session — не его дело разводить правки по веткам. Не agent team — для локального review это декоративно.

Точная формулировка:

```text
Нужен read-only subagent reviewer для локальной проверки diff.
Ему не нужна отдельная worktree и не нужна самостоятельная session.
```

Расплывчатый вариант:

```text
Давайте заведём ещё одного агента на ревью.
```

Самое ценное — не список модных слов, а привычка уточнять форму рабочей единицы. Когда в следующий раз вы услышите «запусти агента», включайте переводчик: subagent, отдельная сессия, фон, worktree-сессия или координация нескольких штук?

## 9. Практический алгоритм выбора

1. Нужно много прочитать и вернуть короткий результат в текущий разговор — **subagent**.
2. Нужна полностью самостоятельная линия мысли с новым контекстом — **separate session**.
3. Нужна долгая работа без постоянного диалога — **background agent**, если версия поддерживает.
4. Нужно изолировать реальные правки и Git-history — **worktree-backed session**.
5. Нужна координация нескольких исполнителей с общим планом — **agent team**, но только если без неё действительно нельзя.

Перед запуском сформулируйте роль, границы, ожидаемый артефакт и способ проверки. Если формулировка всё ещё звучит как «пусть агент разберётся», вы не выбрали рабочую единицу — вы выбрали надежду.

## Что запомнить

- «Agent» — зонтичный термин, а не конкретная механика.
- Subagent = role + isolated context + tools + output contract.
- Subagent обычно возвращает summary в текущую сессию; separate session — самостоятельная линия.
- Транскрипт работающего subagent доступен через `/tasks`, но проверять нужно сводку.
- Fork (`/subtask`) получает весь текущий разговор и не даёт «чистого взгляда».
- Background agent нужен для асинхронной работы без постоянного диалога; в свежих версиях это отдельная фоновая сессия со своим worktree.
- Worktree-backed session изолирует реальные правки и Git-history; subagent может запросить `isolation: worktree`, но по умолчанию её не имеет.
- Agent team — координация нескольких единиц, а не режим по умолчанию.
- Перед запуском уточняйте: где контекст, куда вернётся результат и нужна ли файловая изоляция.
- `agents/reviewer.md` в Workflow Kit — это subagent, если он работает внутри текущего workflow и возвращает summary.
- Если «agent team» можно заменить одним нормально спроектированным subagent — замените.
- Точная формулировка рабочей единицы дешевле, чем разбор последствий тумана.

## Практика (15–25 минут)

**Цель:** научиться переводить расплывчатое «запусти агента» в конкретную рабочую единицу и фиксировать выбор термина.

**Что сделать:**
1. Возьмите пять вымышленных задач для Commerce OS: (а) прочитать auth-модуль и вернуть summary, (б) продумать альтернативный план рефакторинга с чистого листа, (в) просканировать большой проект и вернуть отчёт позже, (г) рискованно изменить payments в отдельной ветке, (д) координировать review, тесты и документацию.
2. Для каждой задачи ответьте на три вопроса: где живёт контекст, возвращается ли результат автоматически и нужна ли файловая изоляция.
3. Заполните `AGENT_TERMS.md`: задача → термин (`subagent`, `separate session`, `background agent`, `worktree-backed session`, `agent team`) → роль → инструменты → output contract → почему не подошли соседние варианты.
4. Для одной задачи сформулируйте точную команду или brief без слова «агент»: роль, границы, ожидаемый артефакт и проверка. Используйте только фейковые данные.
5. Проверьте таблицу: нет ли задач, где вы выбрали agent team или worktree только из желания усложнить. Если можно обойтись subagent — упростите.

**Проверка:**
- Для каждой задачи выбран один термин и объяснена причина.
- Различаются контекст, возврат результата и файловая изоляция.
- У выбранной рабочей единицы есть роль, инструменты и output contract.
- Нет лишнего agent team или worktree без инженерной необходимости.
- Формулировка задачи понятна без личной экскурсии.
- В практике только фейковые данные и нет реальных ключей.
