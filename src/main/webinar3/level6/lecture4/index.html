Параллельные сессии и worktree

Claude Code

6 уровень · лекция 4
Ветка хранит историю, сессия — контекст разговора, worktree — отдельную рабочую папку. Это три разных слоя. Если нужно параллельно вести большой рефакторинг и срочный hotfix, недостаточно открыть вторую сессию в той же папке.

Три разных слоя одной работы

«Ветка», «сессия» и «worktree» — это не три названия одного переключения, а три разных слоя. Спутаете их — быстро упрётесь в вопрос: «А я сейчас вообще где?».

СущностьГде живётЗа что отвечаетЧто не заменяет
Ветка (branch)В GitИсторию измененийСессию Claude и папку на диске
Сессия (session)В Claude CodeКонтекст разговора и решения по задачеGit-ветку и файловую изоляцию
WorktreeВ файловой системе и GitОтдельную рабочую папку того же репозиторияНовую историю проекта; сам по себе не даёт новую «память» Claude

Если сказать по-человечески:

  • ветка отвечает на вопрос, в какую линию истории я сейчас пишу изменения;
  • сессия отвечает на вопрос, в каком разговоре Claude сейчас думает об этой задаче;
  • worktree отвечает на вопрос, в какой физической папке на диске открыта эта работа.

Представьте большой архив документов, два рабочих стола и два разговора с коллегой. Архив — это Git. Рабочие столы — worktree. Разговоры — сессии Claude. Если смешать архив, стол и разговор в одно понятие, начнётся классическая разработческая комедия: «Подождите, а я сейчас где именно?»

Ветка хранит историю, сессия хранит контекст, worktree хранит отдельное рабочее место.

Из этой формулы сразу следует важный вывод. Можно создать новую ветку и вообще не открывать Claude. Можно открыть новую сессию Claude и не создавать новую ветку. Можно создать второй worktree и работать там руками без AI. Эти сущности связаны, но не равны друг другу.

Ветка хранит историю, сессия хранит контекст

Ветка — чисто Git-объект. Её можно создать без всякого Claude, и Git будет совершенно счастлив.

git switch -c refund-refactor
git branch --show-current   # refund-refactor
git status                  # On branch refund-refactor

Переход в новую линию истории проекта уже произошёл. Но никакой новой сессии Claude вы ещё не создали. Если сейчас открыть Claude Code, он просто увидит текущую папку и текущую ветку. Не больше и не меньше.

Сессия устроена наоборот. Это разговор, а не история. У одной и той же ветки может быть несколько разных сессий. Например, утром вы открыли сессию и попросили Claude исследовать, как в AI Commerce Growth OS устроен refund-flow. Вечером открыли уже другую сессию, в той же ветке, но с чистым контекстом, и попросили только проверить diff и тесты.

И тут появляется важный практический нюанс. Если открыть две редактирующие сессии Claude в одной и той же папке, они будут смотреть на один и тот же набор файлов. Это уже не две независимые комнаты, а два человека, которые одновременно пишут на одной доске. Формально Git от этого не ломается, но когнитивно становится очень весело. Один Claude уже переписал сервис, второй ещё думает на основе старого чтения файлов, а вы сидите между ними и чувствуете себя диспетчером маленького хаоса.

Одна активная редактирующая сессия — один рабочий поток. Нужен только другой контекст — открывайте сессию. Нужна файловая изоляция — нужен worktree.

Точные команды переименования или возобновления сессий могут меняться от версии Claude Code. Но привычка не меняется: называйте сессии по задаче, а не по настроению. refund-refactor-review всегда лучше, чем «новая сессия 7». Иначе через пару дней у вас будет музей артефактов под названием «потом разберусь».

Worktree: вторая рабочая папка без clone

Worktree — это вторая физическая папка того же репозитория, чтобы держать ещё одну задачу открытой одновременно, не переключая основную папку туда-сюда.

git worktree add -b hotfix/refund-amount-typo ../commerce-os-hotfix main
cd ../commerce-os-hotfix
git branch --show-current   # hotfix/refund-amount-typo
pwd                         # /projects/commerce-os-hotfix

Git создал рядом новую папку, завёл для неё новую ветку от main и выдал второй рабочий каталог. Это не полный новый clone репозитория. История Git у worktree общая с основным проектом, поэтому операция быстрая и обычно не раздувает диск так, как второй полноценный клон.

/projects/
├── commerce-os/          # ветка refund-refactor, своя сессия Claude
└── commerce-os-hotfix/   # ветка hotfix/refund-amount-typo, своя сессия Claude

У вас теперь не одна папка, которую приходится мучить stash, switch, switch back, «ой, а где мои незакоммиченные изменения», а две отдельные поверхности. В одной продолжается длинный рефакторинг. В другой спокойно делается срочный hotfix.

У каждой папки свои локальные build-артефакты, свои незакоммиченные изменения, свои открытые вкладки IDE, свои терминалы. Для Commerce OS, где есть и Java-часть, и Next.js-часть, это особенно удобно.

В Claude Code worktree можно создать и без ручного git worktree add: команда claude -w locales-ui создаст worktree в .claude/worktrees/locales-ui и откроет сессию в нём. Если в одном TASK_SPEC есть независимые куски — backend, UI, тесты, миграции — основной агент, отдельные сессии или субагенты могут вести их параллельно в разных worktree, не перетирая файлы.

Git пытается вас защитить. Одну и ту же ветку он обычно не даст держать в двух worktree одновременно:

git worktree add ../commerce-os-copy refund-refactor
# fatal: 'refund-refactor' is already checked out at '/projects/commerce-os'

Это не вредность Git, а заборчик, который не даёт запустить две независимые физические папки на одной ветке и потом удивляться, почему всё странно.

Уместность worktree и риск лишнего шума

Worktree полезен ровно в тот момент, когда он убирает переключение и снижает риск. Если он нужен «потому что так делают серьёзные люди», он начинает мешать. Для большинства повседневных задач обычной ветки достаточно.

СитуацияЧто обычно лучше
Одна задача, одна активная папка, всё спокойноОбычная ветка
Нужно быстро посмотреть другую ветку, рабочее дерево чистоеОбычное переключение ветки
Идёт большой рефакторинг, а параллельно прилетел срочный hotfixWorktree
Хотите сравнить две альтернативные реализации бок о бокWorktree
Две Claude-сессии хотят редактировать один и тот же checkoutПочти всегда лучше развести по worktree

Если рабочее дерево чистое, а вторая задача короткая и займёт десять минут, worktree может быть избыточен. Проще переключиться на другую ветку, сделать правку, закоммитить и вернуться. Не нужно доставать строительный кран, чтобы передвинуть табуретку.

Но если уже идёт длинная задача, есть незавершённые изменения и срочно требуется ещё одна работа, начинается старый Git-цирк: stash, переключение, возврат, конфликты, попытка вспомнить, что было в буфере. Вот именно в этот момент worktree и показывает характер. Он не делает ничего магического. Он просто убирает ненужный цирк.

Отдельно про параллельные Claude-сессии без worktree. Это выглядит заманчиво: открыл два окна, в одном просишь «проанализируй», в другом «параллельно поправь». Но если обе сессии смотрят в одну папку, физического разделения нет. В какой-то момент одна сессия читает уже изменённые файлы, вторая всё ещё рассуждает по старым данным, и вы оказываетесь в домашней версии распределённой системы без координации.

Если задачам нужно одновременно иметь своё локальное состояние на диске, им нужен worktree. Если разница только в разговоре и фокусе анализа, достаточно отдельных сессий.

Сценарий Commerce OS: refactor + hotfix

В AI Commerce Growth OS вы уже второй день ведёте рефакторинг refund-flow. Есть ветка refund-refactor, часть логики вынесена, тесты зелёные только на одном milestone, но работа ещё не закончена.

И вот прилетает срочная мелочь: в админке неправильно отображается сумма возврата, поддержка просит hotfix прямо сейчас. Если делать всё в одной папке, нужно либо коммитить недоделанный рефакторинг, либо прятать его в stash, потом переключаться на main, делать hotfix, коммитить, возвращаться, поднимать stash обратно и надеяться, что ничего не перекосилось.

С worktree последовательность спокойнее.

# в основной папке продолжается большой refactor
git branch --show-current   # refund-refactor

# рядом создаём отдельную папку под hotfix от main
git worktree add -b hotfix/refund-amount-typo ../commerce-os-hotfix main
cd ../commerce-os-hotfix
git status                  # On branch hotfix/refund-amount-typo

Проверяем, что Git видит обе рабочие папки:

git worktree list
# /projects/commerce-os         a1b2c3d [refund-refactor]
# /projects/commerce-os-hotfix  e4f5a6b [hotfix/refund-amount-typo]

В основной папке остаётся длинный рефакторинг и та сессия Claude, где накоплен контекст по refund-flow. В папке commerce-os-hotfix/ вы открываете второй терминал, вторую IDE-вкладку или вторую сессию Claude и работаете только с hotfix. Никакого stash, никакого «подождите, а это сейчас уже main или всё ещё refactor?»

./gradlew test --tests "*Refund*"
# BUILD SUCCESSFUL

Дальше живёте обычной жизнью: commit, PR, merge. А большая задача даже не вздрогнула. Она всё ещё лежит в первой папке ровно в том состоянии, в каком вы её оставили.

Worktree не ускоряет hotfix магически. Он просто не заставляет платить дополнительный налог вниманием за то, что задач стало две.

Дисциплина параллельной работы и уборка

Когда у вас больше одной рабочей папки, самое важное — не растерять простые привычки. Worktree не наказывает за сложность сам по себе, но очень быстро усиливает любую небрежность. В одной папке вы ещё можете случайно понять, где находитесь, а в двух папках случайность перестаёт быть стратегией.

Хорошая микропривычка — первые три секунды в любом терминале тратить на короткую проверку:

pwd                       # /projects/commerce-os-hotfix
git branch --show-current # hotfix/refund-amount-typo
git status -sb            # ## hotfix/refund-amount-typo

Это выглядит почти смешно по простоте, но именно такие три команды спасают от очень глупых ошибок. Открыли терминал, посмотрели папку, посмотрели ветку, посмотрели статус. Вы уже не редактируете вслепую.

Очень помогает нормальное именование. Папка ../commerce-os-hotfix лучше, чем ../temp2. Ветка hotfix/refund-amount-typo лучше, чем fix1. Сессия Claude по смыслу hotfix тоже должна называться как hotfix, а не «новая».

Worktree — это временный рабочий ресурс, а не коллекция вечных папок. После merge его нужно закрывать так же аккуратно, как вы его открывали. Не стоит просто удалять папку мышкой или rm -rf, будто ничего не произошло. Git хранит список worktree, и лучше дать именно Git корректно убрать запись.

cd ../commerce-os
git worktree remove ../commerce-os-hotfix
git branch -d hotfix/refund-amount-typo   # после merge
git worktree list                         # убеждаемся, что всё чисто

Если хранить старые worktree «на всякий случай», проект через пару недель превращается в шкаф с коробками без подписей. Самая неприятная инженерная уборка — это уборка старого контекста, который вы сами когда-то не закрыли.

Worktree — не медаль «теперь вы senior». Это просто инструмент файловой изоляции. Если без него проще — не используйте его. Если он спасает от stash-цирка, случайных переключений и двух задач в одной папке — используйте без чувства вины.

Практика (15–25 минут)

Цель: создать worktree, изолировать hotfix-правку от основной ветки и корректно убрать рабочую папку после проверки.

Что сделать

  1. В отдельной учебной папке создайте Git-репозиторий с фейковым проектом Commerce OS: message.txt, README.md и один baseline commit. Создайте долгую ветку refactor/refund-flow и оставьте в ней незакоммиченную «работу».
  2. Вернитесь на main и создайте worktree: git worktree add -b hotfix/refund-message ../commerce-os-hotfix main. Перейдите в новую папку, проверьте pwd, git branch --show-current и git status -sb.
  3. Только в hotfix-worktree измените message.txt и сделайте commit. Вернитесь в основную папку и убедитесь, что её message.txt и незакоммиченная работа не изменились.
  4. Выполните git worktree list и зафиксируйте обе папки. Затем корректно уберите worktree через git worktree remove ../commerce-os-hotfix и удалите временную ветку после merge.
  5. Напишите WORKTREE_NOTE.md: пути, ветки, команда создания, результат изоляции и команда уборки. Если worktree недоступен, опишите эквивалентный сценарий через обычную ветку и объясните ограничение.

Проверка

  • Worktree создан отдельной командой Git, а не копированием папки.
  • В hotfix-worktree своя ветка и своя рабочая поверхность.
  • Изменение message.txt не появилось в основной папке.
  • git worktree list показывает обе рабочие папки.
  • Уборка выполнена через git worktree remove, а не rm -rf.
  • В WORKTREE_NOTE.md объяснено, когда worktree уместен, а когда достаточно ветки.
  • В практике только фейковые данные; реальные репозитории и сервисы не затрагиваются.
