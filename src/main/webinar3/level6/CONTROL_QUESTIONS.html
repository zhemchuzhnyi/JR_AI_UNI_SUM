Уровень 6 — контрольные вопросы

Лекция 1 — длинные задачи, milestones и context rot

  1. Чем по сути является длинная AI-assisted задача?
    Не одним большим prompt, а маленьким инженерным процессом: task spec, milestones, именованная сессия, stop points, summary/decision log и маленькие коммиты. Процесс делает задачу управляемой, проверяемой и передаваемой. → Лекция 1
  2. Какие три вопроса задают каркас длинной задачи и как он превращается в milestones?
    Что делаем, чего не делаем и где останавливаемся проверять состояние. Task spec делится на этапы с проверяемым финишем; например, новый проект: M1 — backend API и тесты, M2 — UI со списком, M3 — поиск и фильтр. Если форма продукта неясна, первым может быть M0 — разведка или прототип. → Лекция 1
  3. Что должно быть хорошим stop point?
    Конец осмысленного куска или milestone, а не момент усталости. В этой точке есть проверки, короткий summary, зафиксированные решения, маленький commit и один конкретный следующий шаг. Задачу можно безопасно передать другому человеку или себе будущему. → Лекция 1
  4. Что такое context rot и когда выбирают goal-driven режим?
    Context rot — загрязнение на длинной дистанции: контекст стареет, и Claude тащит старые гипотезы и отвергнутые идеи как актуальные. Лечение — summary, фиксация решений и чистый контекст. Goal-driven выбирают, когда финиш проверяется машиной: например, /goal <условие>, тесты или build зелёные. /goal clear снимает цель; при субъективной проверке безопаснее пошаговый режим. → Лекция 1

Лекция 2 — checkpoints и /rewind

  1. Чем checkpoint в Claude Code отличается от Git-коммита?
    Checkpoint живёт внутри сессии Claude и позволяет вернуться к точке через /rewind; откатывается ветка разговора и часто связанные правки файлов. Git-коммит живёт в истории проекта, переживает сессию, может быть опубликован и не откатывается через /rewind. Checkpoint — session-level recovery, а не замена version control. → Лекция 2
  2. Что именно откатывает /rewind и как работает checkpoint?
    Только состояние текущей сессии: ветку разговора, гипотезы, решения и часто правки, сделанные инструментами Claude. В поддерживающих версиях checkpoint создаётся автоматически на каждый промпт; меню открывается через /rewind или двойной Esc, где можно вернуть код, разговор или оба, либо выбрать Summarize from here / Summarize up to here. Детали проверяйте через /help. После случайного /clear можно вернуть предыдущую сессию, пока Claude Code не закрыт. → Лекция 2
  3. Что /rewind точно не откатит?
    Уже созданные Git-коммиты, особенно в shared-истории; внешние эффекты — миграции БД, деплой, письма, платежи, запросы во внешние сервисы; ручные правки в IDE; изменения через shell-команды вроде rm, mv, cp и скрипты. Для этих слоёв нужны Git, миграции/бэкапы или системный rollback. → Лекция 2
  4. Когда пора нажимать /rewind и что означает «третий /rewind к одной развилке»?
    Пора, если Claude возвращается к отвергнутой гипотезе, diff расползается, появляются латки на латках или вам уже не хочется читать diff. Третий откат к одной и той же развилке — не стратегия, а диагноз: проблема в task spec, evidence или слишком расплывчатом scope. Нужно переписать постановку, сузить границы или открыть fresh session. → Лекция 2

Лекция 3 — Git-first recovery

  1. Какой первый шаг рекомендует лекция после неудачной AI-итерации, тронувшей лишние файлы?
    Остановиться и не просить «исправить всё» поверх хаоса. Сначала посмотреть на факты: git status, затем git diff по конкретным подозрительным файлам. Только после этого выбирать минимальный rollback. → Лекция 3
  2. Как выбрать между git restore, git revert, git reset и новой веткой?
    git restore — лишние правки в файлах, коммита ещё нет. git revert — плохой коммит уже есть, особенно в shared-истории. git reset — только локальный коммит, который никто не видел; на общей истории опасен. Новая ветка — текущая попытка слишком грязная и дорогая в спасении. → Лекция 3
  3. Что делать с плохим коммитом в shared-истории?
    Предпочесть git revert: он создаёт новый коммит, отменяющий изменения плохого, и не переписывает историю. git reset в такой ситуации опасен, потому что меняет ветку и историю, которую уже могли получить другие. → Лекция 3
  4. Почему маленькие milestone-коммиты делают rollback дешёвым?
    Гигантский коммит «refactor + cleanup + tests» нельзя откатить частично. Маленькие коммиты на границах этапов позволяют отменить только неудачный шаг, не трогая полезные предыдущие. Milestone задаёт смысл шага, commit фиксирует состояние файлов. → Лекция 3

Лекция 4 — параллельные сессии и worktree

  1. Что отвечает каждая из сущностей: ветка, сессия, worktree?
    Ветка хранит историю изменений в Git. Сессия хранит контекст разговора и решения по задаче в Claude Code. Worktree — отдельная физическая рабочая папка того же репозитория. Они связаны, но не заменяют друг друга. → Лекция 4
  2. В каком сценарии worktree оправдан сильнее всего?
    Когда идёт длинный рефакторинг с незакоммиченными изменениями, а параллельно нужен срочный hotfix. Worktree даёт отдельную папку и ветку, убирая stash-цирк. Также полезен для сравнения альтернатив бок о бок и для двух редактирующих Claude-сессий с разным файловым состоянием. → Лекция 4
  3. Как создать worktree и проверить, что вы в нужном месте?
    Например: git worktree add -b hotfix/refund-amount-typo ../commerce-os-hotfix main, затем cd ../commerce-os-hotfix. В Claude Code можно использовать claude -w locales-ui — worktree появится в .claude/worktrees/locales-ui. Проверка: pwd, git branch --show-current, git status -sb; список — git worktree list. → Лекция 4
  4. Как правильно убрать worktree после merge?
    Из основной папки: git worktree remove ../commerce-os-hotfix, затем git branch -d hotfix/refund-amount-typo и git worktree list. Не удалять папку вручную через rm -rf: Git хранит список worktree. При незакоммиченных изменениях сначала проверить, можно ли их потерять, и только потом использовать --force. → Лекция 4

Лекция 5 — handoff и fresh reviewer

  1. Что такое handoff и когда нужен HANDOFF_NOTE.md?
    Компактный пакет смысла для продолжения или проверки задачи: HANDOFF_NOTE.md, TASK_SPEC.md, актуальный diff и результаты проверок. Для маленькой правки можно использовать сокращённый чек-лист из пяти пунктов в PR или issue; полный HANDOFF_NOTE.md содержит девять полей. Отдельный файл нужен, когда задача переживает сессию, день работы или передачу другому человеку. → Лекция 5
  2. Какие поля должны быть в HANDOFF_NOTE.md?
    Goal, Task spec, Changed files, Decisions, Assumptions, Evidence, Tests/checks, Known failures / Risks и Next step. Формулировки должны быть конкретными: не «тесты зелёные», а команда и результат; не «продолжить работу», а один следующий шаг. → Лекция 5
  3. Что такое fresh reviewer pattern и что он проверяет?
    Это проверка задачи в свежем контексте — новой сессией Claude или человеком — по компактному пакету: TASK_SPEC, HANDOFF_NOTE, diff и checks. Reviewer смотрит не как автор и ищет пропущенные edge cases, выход за scope и недоказанные утверждения. Всю переписку ему давать не нужно, иначе он заразится старыми гипотезами. → Лекция 5
  4. Чем HANDOFF_NOTE.md отличается от PR description, commit message и changelog?
    Handoff написан для следующей сессии или человека, который продолжит/проверит незавершённую задачу. PR description — для reviewer’а готового изменения перед merge. Commit message — для истории Git. Changelog — для пользователя или команды релиза. Смешивать их роли нельзя. → Лекция 5

Дополнительные сценарии — выбор recovery action

  1. Claude сделал неудачные правки в файлах, коммита ещё нет. Что проверить и когда выбрать /rewind, а когда Git?
    Сначала git status и git diff: понять, какие файлы изменены и есть ли среди них лишние. Если правки сделаны внутри текущей сессии и ещё не закоммичены, можно вернуться через /rewind; если нужно выборочно убрать файлы, надёжнее Git (restore, stash -u, clean -nd перед удалением). Коммиты, внешние эффекты и ручные правки вне сессии /rewind не отменяет. → Лекция 2
  2. Плохой коммит уже отправлен в общую ветку. Какой откат выбрать?
    git revert <hash>: он создаёт новый commit-отмену и не переписывает общую историю. git reset и /rewind здесь не подходят: они не должны менять опубликованную историю или состояние сессии вместо Git. После revert запустите проверки и зафиксируйте результат. → Лекция 3
