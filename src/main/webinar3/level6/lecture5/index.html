Handoff Note и Fresh Reviewer Pattern

Claude Code

6 уровень · лекция 5
«Вроде готово» — не handoff. Следующему человеку нужен компактный пакет: задача, изменённые файлы, решения, доказательства, риски и один следующий шаг. А свежий reviewer должен смотреть на этот пакет без авторской памяти.

«Вроде готово» — это не handoff

Длинная задача ломается не при написании кода, а позже — когда нужно понять, что уже сделано, какие решения приняты, что проверено. Handoff не бюрократия, а способ сохранить смысл задачи, пока он не испарился.

Представьте: второй день чините refund-flow в AI Commerce Growth OS. Вчера вынесли логику из RefundController в RefundService, сегодня добавили тесты, заметили странный кейс с возвратом больше 1000 долларов, переключились на другой баг. Остановитесь на «логика почти вынесена, остался спорный момент» — и следующий человек заново построит всё дерево решений у себя в голове. Знание приклеилось к авторской сессии: пока диалог открыт, всё очевидно, закрыли вкладку — и половина важного была только в вашей голове. А голова не поддерживает git show.

«Вроде готово» не отвечает ни на один инженерный вопрос. Что готово? Какие файлы менялись? Что проверили? Где риск? Что дальше? Нет ответов — handoff не состоялся.

Writer session
  ├── HANDOFF_NOTE.md
  ├── git diff
  └── лог тестов
        ↓
Fresh session / человек-ревьюер
        ↓
Продолжение задачи / проверка и замечания

Handoff — не один файл в вакууме, а компактный пакет смысла: HANDOFF_NOTE.md, рядом TASK_SPEC.md, актуальный diff и результаты проверок. Есть этот набор — следующий человек продолжает задачу. Есть только ваша уверенность — он начинает расследование.

Для маленькой правки handoff может быть не отдельным файлом, а сокращённым чек-листом из пяти пунктов в PR или issue: Goal, Changed files, Tests/checks, Known failures / Risks, Next step. Если заводите HANDOFF_NOTE.md, используйте полный контракт из девяти полей. Отдельный файл нужен, когда задача переживает сессию, день работы или передачу другому человеку.

Структура HANDOFF_NOTE.md

Записка должна быть структурированной: предсказуемый артефакт, где нужное лежит на ожидаемых местах, иначе чтение превращается в квест, только теперь в markdown. И пишется она не с нуля в последний момент, а собирается из накопленного по ходу — milestone summary, decision log, checks, риски, следующий шаг.

ПолеЧто в нём писатьЗачем это нужно
GoalОдной фразой, какой результат должен получитьсяЧтобы reader сразу понял, про какую задачу идёт речь
Task specСсылка на TASK_SPEC.md или короткое резюме scopeЧтобы не вытаскивать границы задачи из памяти автора
Changed filesКакие файлы уже тронутыЧтобы быстро открыть нужные места и увидеть реальный объём работы
DecisionsКакие решения уже приняты и почемуЧтобы не спорить заново с уже решёнными вещами
AssumptionsЧто пока считается верным, но не доказано полностьюЧтобы не путать факты и рабочие гипотезы
EvidenceКакие команды, логи, результаты подтверждают состояниеЧтобы handoff опирался на доказательства, а не на тон автора
Tests/checksЧто запускали и с каким результатомЧтобы следующий reader не гадал, насколько изменение проверено
Known failures / RisksЧто ещё не покрыто, что тревожит, где тонкое местоЧтобы незавершённость была явной
Next stepОдин конкретный следующий шагЧтобы handoff заканчивался направлением движения, а не туманом

Принцип: handoff разделяет факты, решения, гипотезы и следующий шаг. Слиты в один абзац — читатель тратит силы на восстановление структуры, а не на работу.

Пример для refund-flow:

# HANDOFF_NOTE.md

## Goal
Вынести refund decision logic из RefundController в RefundService без изменения API.

## Task spec
См. TASK_SPEC.md: scope = refund-flow only, не трогать payment provider integration.

## Changed files
- src/main/java/com/acme/commerce/refund/RefundController.java
- src/main/java/com/acme/commerce/refund/RefundService.java
- src/test/java/com/acme/commerce/refund/RefundControllerTest.java

## Decisions
- threshold > $100 оставлен как property, не hardcode
- controller стал тоньше, правила перенесены в service

## Assumptions
- threshold приходит из существующей конфигурации и не меняется в этой задаче
- других вызовов RefundController с изменённой семантикой нет

## Evidence
- git diff --stat: 3 files changed, 48 insertions(+), 19 deletions(-)
- ./gradlew test --tests "*Refund*": 8 tests passed

## Tests/checks
- ./gradlew test --tests "*Refund*"  # 8 tests passed

## Known failures / Risks
- кейс refund > $1000 без approval пока не покрыт тестом

## Next step
Добавить тест на > $1000 и проверить, нужен ли audit log для bypass

Заметка сохраняет не каждую мысль, а инженерную картину. Строка Known failures / Risks — не признание провала, а признак зрелости: честное «кейс > 1000 пока не покрыт» лучше, чем дать читателю наткнуться на это через сорок минут. Прозрачная незавершённость лучше красивой недосказанности.

Пишите для другого читателя, а не для себя

Легко написать заметку, понятную вам и бесполезную остальным: автор достраивает текст собственной памятью, у читателя такой роскоши нет. Пишите для того, кто видит только файл, diff и проверки. Убирайте всё, что опирается только на контекст автора. «Сделал основное» для другого не означает ничего; «тесты ок», «почти закончил» — разговорный шум, а не инженерная информация.

Слабая формулировкаСильная формулировка
Тесты зелёныеЗапущен ./gradlew test --tests "*Refund*" — 8 tests passed
Остался один спорный кейсНе покрыт кейс refund > $1000 без approval
Почистил контроллерRefund decision logic вынесен из controller в RefundService
Ничего лишнего не менялScope сохранён: payment provider files не трогались

Сильная формулировка даёт следующему читателю то, что можно проверить. Слабая просит поверить автору на слово. А весь курс строится на привычке не верить на слово — даже если это слово сказал вчерашний вы.

git diff --stat main...refund-refactor
# 3 files changed, 48 insertions(+), 19 deletions(-)

./gradlew test --tests "*Refund*"
# BUILD SUCCESSFUL in 8s
# 8 tests completed, 8 passed

Две такие команды дают новому читателю гораздо больше, чем абзац «я тут немного поправил и вроде не сломал». В Next step не надо писать «продолжить работу» — это философское направление. Следующий шаг должен быть один и конкретный: «добавить тест на кейс > 1000», «сравнить diff с main и убедиться, что payment files не затронуты», «проверить, нужен ли audit log».

Fresh reviewer pattern: свежий контекст

Когда вы долго ведёте одну задачу, появляется авторская слепота. Вы помните, почему приняли решение, знаете, какой тупик уже пробовали, и автоматически «дочитываете» смысл там, где новый читатель увидит дыру. Здесь нужен fresh reviewer pattern.

Авторская сессия делает изменение. Потом другой контекст — новая сессия Claude или живой человек — получает компактный пакет: TASK_SPEC.md, HANDOFF_NOTE.md, актуальный diff и результаты проверок. И проверяет задачу не как автор, а как читатель, который ничего не должен угадывать.

Свежий reviewer часто ловит три типа вещей:

  • пропущенные edge cases;
  • выход за scope: автор «заодно» тронул файл, который не должен был трогать;
  • недоказанные утверждения: тесты локально зелёные, но нужный сценарий не запускался.
Прочитайте TASK_SPEC.md и HANDOFF_NOTE.md.
Посмотрите текущий diff относительно main.
Проверьте только refund-flow и не меняйте файлы.
Сфокусируйтесь на:
- выходе за scope,
- пропущенных тестах,
- кейсе refund > $1000,
- несоответствии между note и реальным diff.
Верните замечания с привязкой к доказательствам.

В этом запросе есть две сильные стороны. Reviewer получает scope и фокус, а не абстрактное «ну посмотри». И работает от evidence: note, diff, tests. Замечания можно проверить, а не спорить о них по интонации.

Сравните: автор пишет «всё зелёное, можно мержить», а reviewer читает handoff, открывает RefundService, смотрит тесты и замечает: теста на сумму больше 1000 долларов нет, хотя риск указан в заметке. Во второй ситуации процесс сработал: handoff не спрятал незавершённость, а reviewer не сделал вид, что её нет.

Fresh session нужен, чтобы продолжить работу. Fresh reviewer нужен, чтобы проверить. И ему не нужна вся переписка автора — иначе он заразится старыми гипотезами.

HANDOFF_NOTE.md vs PR description и changelog

Handoff легко спутать с соседними артефактами. Кажется, что PR description уже объясняет изменения, commit message уже есть, а changelog тоже что-то фиксирует. Но у этих документов разные роли. Если их смешать, каждый начинает работать хуже.

АртефактДля кого он написанНа какой вопрос отвечает
HANDOFF_NOTE.mdДля следующей session или человека, который продолжит/проверит задачуЧто сделано, что доказано, где риск и что делать дальше?
PR descriptionДля reviewer’а изменений как готового пакетаЧто изменилось и как это проверить перед merge?
Commit messageДля истории GitКакой логический шаг был зафиксирован этим commit?
ChangelogДля пользователя или команды релизаЧто изменилось в продукте на уровне версии/релиза?

HANDOFF_NOTE.md живёт внутри процесса, пока задача ещё движется. PR description обычно появляется на границе готового изменения. Changelog не должен объяснять, какой тест вы не успели написать для refund > 1000 — это другая плоскость разговора.

Полезно держать HANDOFF_NOTE.md чуть суше и точнее, чем PR description. В нём важнее инженерная картина. Не «мы хорошо поработали и сделали код чище», а «вынесли refund decision logic, затронули три файла, запускали такие-то тесты, вот известный риск, вот следующий шаг».

Сборка handoff в Commerce OS на практике

Допустим, вы ведёте задачу по AI Commerce Growth OS: нужно вынести decision logic возвратов из контроллера в сервис, не меняя API и не залезая в интеграцию с платёжным провайдером. Задача уже не помещается в один промпт, значит, без handoff она почти гарантированно начнёт разваливаться.

Сначала авторская сессия работает в своей ветке, делает первый milestone, запускает целевые тесты и фиксирует промежуточное состояние. Не нужно ждать «полной готовности». Как раз наоборот: handoff особенно полезен до полной готовности, когда уже есть сделанная часть, есть риск и понятен следующий шаг.

git add src/main/java/com/acme/commerce/refund/RefundController.java
git add src/main/java/com/acme/commerce/refund/RefundService.java
git add src/test/java/com/acme/commerce/refund/RefundControllerTest.java
git commit -m "Вынес refund decision logic в RefundService"

git status
# On branch refund-refactor
# working tree clean

После этого авторская сессия обновляет HANDOFF_NOTE.md, а fresh reviewer открывает задачу уже не по памяти автора, а по артефактам. Он видит scope из TASK_SPEC.md, видит, что затронут только refund-flow, видит тесты и строку про непокрытый кейс > 1000. Вместо расплывчатого «ну вроде мержим» появляется нормальный инженерный разговор: сначала добавим недостающий тест, потом ещё раз посмотрим на diff.

Handoff делает задачу независимой от одного носителя знания. Если автор уходит, задача не умирает.

Если вы сами открываете её завтра, вам не нужно «вспоминать, что я там имел в виду». Если хотите посмотреть свежими глазами, reviewer получает короткий и проверяемый пакет вместо десяти экранов переписки. Длинная AI-assisted задача перестаёт быть личной тайной автора и становится управляемой инженерной работой.

Практика (15–25 минут)

Цель: собрать handoff-пакет для незавершённой задачи и проверить его глазами fresh reviewer.

Что сделать

  1. Возьмите вымышленную задачу Commerce OS: вынести refund decision logic из RefundController в RefundService без изменения API. Создайте краткий TASK_SPEC.md и пару фейковых изменённых файлов.
  2. Напишите HANDOFF_NOTE.md с полями Goal, Task spec, Changed files, Decisions, Assumptions, Evidence, Tests/checks, Known failures / Risks и Next step. Используйте конкретные формулировки, а не «почти готово».
  3. Откройте fresh-контекст: новую сессию Claude, /clear или просто прочитайте пакет как посторонний человек. Дайте только TASK_SPEC.md, HANDOFF_NOTE.md, diff и результаты проверок. Не передавайте всю историю чата.
  4. Попросите reviewer проверить scope, пропущенные edge cases, недоказанные утверждения и соответствие note реальному diff. Файлы не менять.
  5. Запишите в HANDOFF_REVIEW.md 2–3 замечания с привязкой к evidence и обновите Next step. Если CLI недоступен, проведите review вручную по тем же вопросам.

Проверка

  • В handoff есть все ключевые поля и отдельный Known failures / Risks.
  • Goal и Next step конкретны; Next step — один следующий шаг.
  • Tests/checks содержат команду и результат, а не «тесты зелёные».
  • Fresh reviewer получил компактный пакет, а не всю переписку.
  • Замечания reviewer’а опираются на diff, note или результаты проверок.
  • После review обновлён следующий шаг, а не размытая формулировка «продолжить работу».
  • В практике только фейковые данные; файлы src/ не изменяются.
