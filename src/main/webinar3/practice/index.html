Практика вебинара 3

Справочник локалей

План без кода · M1 backend · M2 UI и handoff
Сквозная практика вебинара 3: собираем маленький справочник локалей и учимся вести длинную задачу как процесс — от плана и task spec до первого API, UI и честного handoff.

Что собираем

Маленький справочник локалей: список стран и языков с деталями.

ПолеПример
Код локалиen-AU — ISO 639 язык плюс ISO 3166 страна
Язык и странаEnglish, Australia
Валюта и TLDAUD, .au
Флагфлаг страны
Опциональнотаймзона и столица

Стек намеренно простой: Node на бэкенде, чистый HTML/CSS/JS на фронтенде, без фреймворков и npm-зависимостей. Данные лежат в готовом locales.json, без базы данных. Сначала собираем M1 — backend, затем M2 — UI. Поиск и фильтр (M3) остаются самостоятельным продолжением.

Этап 1 — план без кода

Первый шаг — не код, а контекст. Проекта ещё нет, читать нечего, поэтому опора — ваш SPEC.md: что строим, какой первый кусок делаем, какие границы у задачи.

Сначала придумайте промпт сами. Цель: получить план, а не файлы. Проверьте, что промпт:

  • не даёт Claude сразу писать код;
  • объясняет, какой контекст вы даёте вместо файлов;
  • задаёт технические рамки, чтобы не притащить лишний фреймворк;
  • просит разбить работу на проверяемые куски;
  • запрещает создавать файлы до согласования.

Рабочий вариант:

Я хочу сделать маленький справочник локалей для учебного проекта:
список локалей, у каждой - код (en-AU), язык, страна, валюта, TLD и флаг.
Проекта пока нет. Сначала составь план.
Стек простой: Node на бэке, чистый HTML/CSS/JS на фронте, без фреймворков и npm-зависимостей.

Сделай:
1. Сформулируй короткий TASK_SPEC прямо в ответе, файл пока не создавай.
2. Скажи, какой контекст тебе нужен от меня перед кодом.
3. Раздели работу на 3 milestones.
4. Для каждого milestone напиши проверяемый финиш.
5. В конце перечисли файлы, которые создал бы, но пока ничего не создавай.

Это не эталон, а один из рабочих вариантов. Если у вас только идея, попросите Claude сначала задать уточняющие вопросы и предложить 2–3 варианта scope: не нужно выдавливать полноценный task spec из тумана.

Этап 2 — M1: backend API

Теперь даём Claude построить один milestone — минимальный backend, который отдаёт список локалей из locales.json, и один тест на endpoint. Без UI, поиска и авторизации.

Теперь можно создать проект. Сначала инициализируй репозиторий: git init.

Работай только над M1:
- минимальный backend API, отдающий список локалей из готового locales.json;
- один тест, который проверяет ответ endpoint GET /locales;
- без UI, без поиска, без авторизации.

Перед правками:
1. покажи план файлов;
2. назови критерий остановки.

После работы, до коммита:
3. покажи git diff и команду проверки;
4. дождись моего "ок" и сделай маленький коммит M1.

Остановись после M1 и не переходи к M2 без моего подтверждения.

Если план M1 раздулся или полез в соседние темы, не запускайте реализацию: уменьшите M1 до одного проверяемого финиша, а остальное вынесите в следующий milestone.

Совет по реализации: держите данные в статичном locales.json, а сервер пусть просто читает файл и отдаёт его на GET /locales — без базы данных и лишних слоёв. Чем тоньше backend, тем меньше поверхность для багов и тем проще тест на форму ответа.

Этап 3 — M2: UI и handoff

Следующий milestone — UI со списком локалей из API M1. Контракт API менять нельзя. В конце нужен HANDOFF_NOTE.md.

Сначала план, файлы не трогать:

Продолжим к M2, но сначала составь план, файлы не трогай.

M2:
- UI со списком локалей из API M1;
- контракт API из M1 менять нельзя;
- в конце нужен HANDOFF_NOTE.md.

Назови файлы под правку, риск выхода за scope и как мне проверить diff.

План чистый — разрешаете M2 и просите записку. Лезет не туда — /rewind или переплан без правок.

Совет по окружению: чтобы fetch из браузера не упёрся в CORS, проще всего, когда Node отдаёт и статику фронта, и API на одном origin (localhost:3000). Фронт, открытый как file://, до API не достучится.

Затем handoff:

Составь HANDOFF_NOTE.md для свежего ревьюера.

Включи:
- goal;
- changed files и роль каждого файла;
- decisions;
- tests/checks с точными результатами;
- known risks;
- один next step.

Не включай всю историю чата.

Формулируйте сильно: не «тесты зелёные», а «npm test: 8 passed, 0 failed»; next step — один конкретный шаг, а не «продолжить работу». Свежий ревьюер — новая сессия Claude или человек — проверяет по этому пакету, не как автор, и часто ловит пропущенные edge cases, выход за scope и недоказанные утверждения. Не давайте ему всю переписку: иначе он заразится старыми гипотезами.

Рабочий цикл длинной задачи: план до кода, diff до доверия, summary до сжатия, handoff до передачи.

Архитектура и результат

Когда справочник собран, он складывается в простую картину:

locales.json → Node API → UI (HTML, CSS, JS)
                         ↑
                  GET /locales

Данные лежат в locales.json, Node отдаёт их по HTTP, фронт читает API и рисует список. Поиск и фильтр (M3) доделываются на том же каркасе. Вся архитектура — данные, один API и тонкий фронт; она держится на контракте между фронтом и Node, а не на фреймворке.

Проверка

  • TASK_SPEC.md содержит goal, scope, non-goals, constraints и три milestone с проверяемым финишем.
  • M1: API отдаёт список локалей, тест проходит, diff просмотрен, сделан маленький commit.
  • M2: UI показывает список из API, контракт M1 не изменён.
  • HANDOFF_NOTE.md содержит goal, changed files, decisions, точные tests/checks, known risks и один next step.
  • В проекте нет секретов, реальных персональных данных и полных боевых логов.
  • Если флаги через CDN недоступны, есть безопасный fallback.
