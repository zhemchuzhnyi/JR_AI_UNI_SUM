Стартовый ритуал и Git baseline

Claude Code

2 уровень · 1 лекция
Перед работой с Claude Code разберитесь с исходным состоянием проекта и задайте границы задачи. Git — страховка, которая помогает отделить новые изменения и проверить результат.

Git baseline — понятная точка старта

Git baseline — понятное и безопасное стартовое состояние проекта перед сессией с Claude: нужный репозиторий, известные локальные изменения, отдельная ветка, защищённые секреты и заранее очерченные границы задачи.

Рабочая директория не обязана быть идеально чистой. Важно понимать, какие изменения уже есть, и не смешивать их с новой задачей.

Clean working tree — Git не видит неожиданных локальных изменений относительно последнего коммита: git status отвечает nothing to commit, working tree clean. Тогда любой новый diff после старта относится именно к текущей задаче.

Рабочий ритм из вебинара: внёс → проверили → коммит. Каждый принятый набор правок сразу фиксируется коммитом; новый файл тоже коммитится после проверки. Можно попросить агента «верни как было», но он будет вспоминать состояние по памяти: что-то забудет, что-то перепишет по-своему, потратит время и токены. Git не вспоминает — он возвращает файл байт в байт, мгновенно и бесплатно.

Ориентир: если за тридцать секунд не получается объяснить, что за правки уже лежат в дереве, baseline ещё не готов.

Порядок такой: сначала понятное состояние проекта, потом AI-помощь — не наоборот.

Неясные изменения сначала нужно понять, а не отдавать Claude наугад.

Короткий ритуал перед сессией

  1. Убедитесь, что открыта папка нужного проекта: pwd. Это спасает от ошибки «я оказался не в том проекте», если рядом лежат похожие копии репозитория.
  2. Посмотрите состояние репозитория и разберитесь с изменениями: git status.
  3. Создайте отдельную ветку для задачи, например:
git switch -c fix/refund-inbox-order
  1. Проверьте, что секреты и лишние файлы исключены через .gitignore.
  2. Перед подтверждением project trust проверьте проект и его содержимое.
  3. Сформулируйте scope: что разрешено менять, а что должно остаться нетронутым.

Например: «Меняй только модуль возвратов и связанные тесты; не трогай API, миграции, .env* и настройки окружения».

Scope-черновик — это не полная спецификация, а короткая рамка сессии: что можно менять, а что нельзя. Его роль — снизить радиус случайных изменений и шанс получить «полезный, но лишний» diff.

Защитите секреты

Проверьте, что чувствительные файлы действительно игнорируются Git:

git check-ignore -v .env

Если команда ничего не отвечает, остановитесь и проверьте .gitignore до старта: Claude может прочитать файл, о существовании которого вы уже забыли, и невольно опереться на его содержимое в диалоге или изменениях.

В примере из лекции `.env` и `.env.*` исключаются, но `.env.example` остаётся в проекте как шаблон без секретов, а локальные настройки Claude тоже не попадают в репозиторий:

.env
.env.*
!.env.example
.claude/CLAUDE.local.md

Не подтверждайте project trust автоматически: убедитесь, что это нужный репозиторий и в нём нет данных, которые не следует открывать Claude Code. Полезно ответить себе на три вопроса: это точно тот репозиторий? понимаю ли я, что в этой папке могут запускаться команды и читаться файлы? нет ли здесь данных, которых не должно быть в сессии с AI?

Проверяйте изменения и отменяйте осознанно

После работы просмотрите построчные изменения и текущее состояние Git:

git diff
git status

Если git status показывает незнакомые правки ещё до старта, разберитесь с ними заранее — иначе старые и новые изменения смешаются в один diff:

git status
# On branch main
#   modified: src/support/refund/RefundInboxService.java
#   modified: src/orders/OrderSummary.java

git diff src/support/refund/RefundInboxService.java

Если правку нужно отменить, сначала проверьте diff. Например, команда ниже отменяет локальные изменения конкретного файла:

git restore src/support/refund/RefundInboxService.java

Не используйте git restore, пока не убедились, что изменения этого файла можно потерять.

Если вся попытка оказалась неудачной, вернитесь в main, а экспериментальную ветку оставьте для разбора или удалите позже, когда решение уже принято. Главное — не просить Claude «починить поверх» непонятного состояния: сначала diff, потом решение.

Главное — не идеальная чистота репозитория, а понятное исходное состояние, отдельная ветка, защищённые секреты и чёткий scope.

Практика (15–25 минут)

Цель: Собрать Git baseline в отдельном учебном репозитории с фейковыми данными.

Что сделать

  1. Создайте claude-practice/git-baseline, выполните git init, добавьте notes.txt с фейковыми строками и сделайте коммит baseline.
  2. Создайте ветку practice/baseline, измените notes.txt, посмотрите git status и git diff.
  3. Отмените изменения командой git restore notes.txt и убедитесь, что git status снова чистый.
  4. Снова измените файл, закоммитьте его и проверьте историю через git log --oneline.

Если Claude Code недоступен: выполните доступную часть шагов вручную в редакторе и терминале; недоступные команды разберите по официальной документации. Критерии проверки те же.

Проверка

  • До и после работы вы понимаете состояние git status.
  • Вы можете объяснить, что именно вернул git restore.
  • В репозитории только фейковые данные, без реальных секретов.
Git помогает увидеть фактические изменения; решение о том, принимать ли результат Claude, остаётся за человеком.
