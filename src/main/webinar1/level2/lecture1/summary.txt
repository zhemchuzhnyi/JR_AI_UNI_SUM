# Саммари лекции 1

## Стартовый ритуал и Git baseline — Claude Code, 2 уровень

Перед работой с Claude Code важно понять исходное состояние проекта и задать границы задачи. Git — не только способ подготовить pull request, но и страховка: он показывает, что изменилось, помогает отделить новую работу и при необходимости вернуть конкретный файл.

## Что такое Git baseline

**Git baseline** — понятное и безопасное стартовое состояние проекта перед сессией с Claude: вы знаете, в каком репозитории находитесь, видите локальные изменения, работаете в отдельной ветке, не тащите в репозиторий секреты и заранее очертили границы задачи.

Цель — не обязательно добиться полностью чистой рабочей директории. Если есть локальные изменения, сначала разберитесь, кому и к какой задаче они принадлежат. Не смешивайте их с новой работой Claude. Если нужно, завершите их, временно уберите или осознанно отмените.

**Clean working tree** — Git не видит неожиданных локальных изменений относительно последнего коммита в текущей ветке: `git status` отвечает `nothing to commit, working tree clean`. Тогда любой новый diff после старта относится именно к текущей задаче и читается легко.

Рабочий ритм из вебинара: **внёс → проверили → коммит**. Каждый принятый набор правок сразу фиксируется коммитом; новый файл тоже коммитится после проверки. Можно попросить агента «верни как было», но он будет вспоминать состояние по памяти: что-то забудет, что-то перепишет по-своему, потратит время и токены. Git не вспоминает — он возвращает файл байт в байт, мгновенно и бесплатно.

Ориентир «понятного» состояния: если за тридцать секунд не получается объяснить, что за правки уже лежат в рабочем дереве и зачем они нужны, baseline ещё не готов.

## Стартовый ритуал

Схема ритуала: нужная папка → `git status` → понятное состояние → отдельная ветка → `.gitignore` и секреты → осознанный project trust → короткий scope → старт Claude.

Порядок именно такой: сначала понятное состояние проекта, потом AI-помощь. Не наоборот.

1. Убедитесь, что находитесь в каталоге нужного проекта:

   ```bash
   pwd
   ```

   Проверка пути — не паранойя: она спасает от ошибки «я оказался не в том проекте», особенно когда рядом лежат `commerce-os`, `commerce-os-old`, `commerce-os-playground` и ещё одна «точно последняя» копия репозитория.

2. Проверьте состояние Git и разберите имеющиеся изменения:

   ```bash
   git status
   ```

3. Создайте отдельную ветку для новой задачи:

   ```bash
   git switch -c fix/refund-inbox-order
   ```

4. Проверьте `.gitignore` и убедитесь, что секреты и лишние файлы не попадут в изменения. Например:

   ```bash
   git check-ignore -v .env
   ```

   Ответ вида `.gitignore:12:.env    .env` означает, что `.env` игнорируется нужным правилом. Если ответа нет, проверьте `.gitignore` до старта работы: Claude может прочитать файл, о существовании которого вы уже забыли, и невольно опереться на его содержимое в диалоге, сводке или изменениях.

   Нормальный фрагмент `.gitignore` для такого проекта:

   ```gitignore
   .env
   .env.*
   !.env.example
   .claude/CLAUDE.local.md
   ```

5. Перед подтверждением project trust проверьте, что это нужный проект и в нём нет данных, к которым не следует давать доступ. Полезно задать себе три вопроса: это точно тот репозиторий? понимаю ли я, что в этой папке могут запускаться команды и читаться файлы? нет ли здесь чувствительных данных, которые вообще не должны участвовать в сессии с AI?

6. Кратко обозначьте scope — короткую рамку сессии, а не полную спецификацию: что можно менять, а что нельзя. Его роль — снизить радиус случайных изменений и шанс получить «полезный, но лишний» diff. Например: менять только модуль возвратов и связанные тесты; не трогать API, миграции, `.env*` и настройки окружения. В черновике из лекции (задача — проверить и поправить порядок refund-запросов в inbox) разрешённая зона выглядит как `src/support/refund/**` и связанные тесты. Даже одной фразы «трогаем только refund-модуль и его тесты» уже достаточно. Без границ Claude может заодно предложить переименовать соседние классы или «чуть улучшить» структуру модуля, и маленькая задача превратится в широкий diff, который долго ревьюить.

После правки просмотрите изменения и состояние репозитория:

```bash
git diff
git status
```

## Что делать с неожиданными изменениями

Если `git status` показывает изменённые или новые файлы, не передавайте Claude расплывчатое поручение «разберись с изменениями». Сначала выясните, что это за файлы и относятся ли они к текущей задаче. Иначе старые и новые правки могут смешаться, и станет сложнее понять, что именно изменил Claude.

Пример из лекции (проект Commerce OS): в ветке `main` уже лежат правки, которые не относятся к новой сессии.

```bash
git status
# On branch main
# Changes not staged for commit:
#   modified: src/support/refund/RefundInboxService.java
#   modified: src/orders/OrderSummary.java

git diff src/support/refund/RefundInboxService.java
# Git покажет построчно, что именно уже изменено
```

С такими правками нужно разобраться до старта: довести свою незавершённую работу до понятной точки, временно убрать её с дороги или осознанно выбросить случайный мусор. Не делайте вид, что «потом разберусь».

Если результат нужно отменить, сначала изучите diff. В лекции приведён пример отмены правок в одном файле:

```bash
git restore src/support/refund/RefundInboxService.java
```

`git restore` отменяет локальные изменения указанного файла. Не запускайте его, пока не убедились, что изменения можно потерять.

Не просите Claude «починить поверх» или «исправить всё», если состояние непонятно, — сначала разберитесь в diff. Если вся попытка оказалась неудачной, помогает отдельная ветка: можно вернуться в `main`, а экспериментальную ветку оставить на потом для разбора или удалить позже, когда решение уже принято. Смысл не в том, чтобы никогда не ошибаться, а в том, чтобы ошибка оставалась дешёвой.

## Главное

Безопасный старт — это не «идеально чистый Git», а понятное состояние проекта, отдельная ветка, защищённые секреты и чёткие границы задачи. После изменений проверяйте diff и сами решайте, принимать ли результат.

## Что запомнить

- Git baseline — понятное состояние проекта, а не обязательно идеально чистый tree.
- До старта проверьте `git status`, текущую ветку, `.gitignore` и отсутствие секретов.
- Незавершённую работу уберите с дороги осознанно: commit, отдельная ветка или stash.
- Перед отменой правок прочитайте diff и используйте `git restore` только для ненужных изменений.

## Практика (15–25 минут)

**Цель:** Собрать Git baseline в отдельном учебном репозитории с фейковыми данными.

**Что сделать:**
1. Создайте `claude-practice/git-baseline`, выполните `git init`, добавьте `notes.txt` с фейковыми строками и сделайте коммит `baseline`.
2. Создайте ветку `practice/baseline`, измените `notes.txt`, посмотрите `git status` и `git diff`.
3. Отмените изменения командой `git restore notes.txt` и убедитесь, что `git status` снова чистый.
4. Снова измените файл, закоммитьте его и проверьте историю через `git log --oneline`.

**Если Claude Code недоступен:** выполните доступную часть шагов вручную в редакторе и терминале; недоступные команды разберите по официальной документации. Критерии проверки те же.

**Проверка:**
- До и после работы вы понимаете состояние `git status`.
- Вы можете объяснить, что именно вернул `git restore`.
- В репозитории только фейковые данные, без реальных секретов.
