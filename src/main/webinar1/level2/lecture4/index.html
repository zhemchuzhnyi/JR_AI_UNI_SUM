CLAUDE.md, rules и auto memory

Claude Code

2 уровень · 4 лекция
Разделяйте инструкции по аудитории и сроку действия: общее и стабильное храните в CLAUDE.md, локальное — в CLAUDE.local.md, узкоспециализированное — в rules. Auto memory перепроверяйте.

Сначала — безопасный старт

Перед настройкой инструкций проверьте, что открыта нужная рабочая директория, состояние Git понятно (чистый working tree, отдельная ветка), а режим разрешений соответствует задаче. CLAUDE.md не заменяет понятный Git baseline и подходящие permissions.

Короткая памятка для проекта

CLAUDE.md — это инструкции Claude о том, как работать с репозиторием, а не документация и не замена README.md. Записывайте то, что неочевидно из кода и влияет на работу всей команды:

  • точные команды запуска, сборки и тестов;
  • важные соглашения и скрытые особенности проекта;
  • чувствительные зоны и границы изменений;
  • ожидаемый формат результата: изменённые файлы, проверки, риски.

Особенно полезны точные команды — Claude склонен угадывать, чем запускать проект, и иногда угадывает не туда. А скрытые особенности вроде сумм в копейках, soft delete вместо физического удаления или обязательного worker спасают от «логичных», но неверных правок.

Правила делайте конкретными: не «делай всё аккуратно и современно», а «не меняй сигнатуры публичных методов в src/api/** без явного подтверждения»; не «соблюдай стиль проекта», а «не предлагай форматирующие правки вне текущего scope задачи»; не «следи за безопасностью», а «не читай и не редактируй .env* без прямого запроса».

Пример для Commerce OS:

# CLAUDE.md

## Команды проекта
- run: `docker compose up`
- test: `./gradlew test`
- check: `./gradlew check`

## Договорённости
- не менять `/api/v1/**` без явного подтверждения
- не переписывать существующие файлы в `db/migration/`
- в ответе всегда перечислять изменённые файлы и запущенные проверки

Файл хорош тем, что короткий: как запускать проект, где опасные зоны и в каком виде отчитываться. Предпочитайте конкретные, проверяемые правила общим советам вроде «пиши хороший код» и держите файл небольшим и актуальным.

Не записывайте в файл и лишнее: инструкции под одну текущую задачу (вроде «сейчас работаем только с RefundService»), очевидные из кода факты и устаревшие сведения — иначе важные правила прячутся среди шума.

Слои CLAUDE.md

CLAUDE.md бывает не один: глобальный ~/.claude/CLAUDE.md подхватывается всегда; проектный ./CLAUDE.md или .claude/CLAUDE.md — при старте работы с проектом; файлы в подпапках (./subfolder/CLAUDE.md) — по необходимости, когда агент доходит до этой области; CLAUDE.local.md — личные заметки.

Если в репозитории есть AGENTS.md без CLAUDE.md, Claude прочитает AGENTS.md. Когда появляется CLAUDE.md, читается только он.

Куда поместить инструкцию

CLAUDE.md

Общие, стабильные правила, нужные команде и будущим сессиям. Обычно хранится в репозитории.

CLAUDE.local.md

Локальные порты, личные пути к данным и предпочтения. Не коммитится, если добавлен в .gitignore (сам по себе не игнорируется), но доступен Claude — не храните здесь секреты.

Rules

Правила для одной папки, типа файлов или отдельной области проекта. Не перегружайте ими общий файл.

Auto memory

Автоматически сохранённые наблюдения. Они могут быть временными или устаревшими, поэтому требуют проверки.

Правило для узкой области (например, только для db/migration/** или payments/) выносите в отдельное rule, а в CLAUDE.md оставляйте короткое напоминание, что такие чувствительные зоны существуют.

Если строка не нужна никому и понятна прямо из репозитория — не записывайте её вовсе. А формат самих rule-файлов и их синтаксис пока не важен: важна именно логика разделения.

Типичный CLAUDE.local.md для личных особенностей среды:

# CLAUDE.local.md

## Заметки о workspace
- локальная БД работает на порту 5454
- тестовые CSV для импорта лежат в `~/projects/data/subscriptions/`

## Личные предпочтения
- предлагай изменения небольшими diff-блоками
- если затронуто больше двух файлов, сначала коротко опиши план
Если нарушение факта было бы серьёзной проблемой, не полагайтесь только на auto memory.

Проверяйте автоматическую память

Например, Claude запомнил временный путь /api/v0/refunds; маршрут давно починили, а память не пересмотрели — и в новой сессии Claude уверенно тянется к устаревшему пути.

  1. Просматривайте, что Claude запомнил.
  2. Удаляйте устаревшие или ошибочные записи.
  3. Переносите важные и стабильные правила в CLAUDE.md или отдельное rule.

CLAUDE.md — это context, not enforcement: Markdown-инструкция задаёт контекст, но не является технической блокировкой. Для критичных ограничений используйте технические средства: Git baseline, permission mode, deny-правила в permissions (например, Read(./.env)) и hooks. .gitignore защищает от случайного коммита и скрывает файл из подсказок @, но не мешает Claude прочитать его.

Посмотреть и почистить auto memory можно командой /memory; точное название и синтаксис зависят от версии — сверьтесь с /help.

С чего начать

Создайте компактный baseline: команды проекта, несколько неочевидных договорённостей, чувствительные зоны и формат отчёта. Добавляйте правило при повторяющейся проблеме; удаляйте то, что утратило актуальность. У хорошего CLAUDE.md нет цели стать толще — есть цель стать точнее.

Пример baseline для маленького проекта:

# CLAUDE.md

## Команды
- run: `npm run dev`
- test: `npm test`

## Договорённости проекта
- все суммы храним в копейках
- не отключать TypeScript strict mode
- в ответе перечисляй изменённые файлы и запущенные проверки

## Не делать
- не трогать `.env*` без прямого запроса
- не делать массовый рефакторинг вне текущего запроса

Для Java-проекта на Gradle меняются только команды: run — ./gradlew bootRun, test — ./gradlew test.

Что запомнить

Общие и стабильные правила храните в CLAUDE.md, личные настройки — в CLAUDE.local.md, а правила для отдельных областей — в rules. Регулярно проверяйте auto memory: важные договорённости должны быть явно записаны, а ограничения, которые нельзя нарушить, нужно подкреплять техническими средствами.

Практика (15–25 минут)

Цель: Написать короткий CLAUDE.md и проверить, как работают слои памяти.

Что сделать

  1. В учебном git-репозитории создайте CLAUDE.md с командами проверки, одним правилом и форматом отчёта.
  2. Создайте CLAUDE.local.md с личной заметкой и добавьте его в .gitignore; проверьте через git check-ignore -v.
  3. Попросите Claude выполнить маленькую правку и отчитаться по формату из CLAUDE.md.
  4. Выполните /memory, посмотрите память и решите, что стоит перенести в CLAUDE.md, а что оставить локально.

Проверка

  • CLAUDE.md короткий и содержит только полезные правила.
  • CLAUDE.local.md не попадёт в Git.
  • Вы можете объяснить разницу между контекстом и технической блокировкой.
