# Саммари лекции 4

## `CLAUDE.md`, rules и auto memory — Claude Code, 2 уровень

`CLAUDE.md` полезен после безопасного старта: убедитесь, что открыта нужная рабочая директория, состояние Git понятно (чистый working tree, отдельная ветка), а выбранный режим разрешений соответствует задаче. Markdown сам по себе не компенсирует грязный или неясный baseline и слишком свободный доступ. Затем разделяйте инструкции по назначению: общие стабильные договорённости храните в `CLAUDE.md`, личные особенности среды — в `CLAUDE.local.md`, правила для отдельных областей — в rules, а автоматически сохранённые наблюдения проверяйте в auto memory.

`CLAUDE.md` — короткая рабочая памятка для Claude, а не документация проекта и не замена `README.md`. README объясняет проект человеку; `CLAUDE.md` сообщает Claude, как с ним работать.

## Что включать в `CLAUDE.md`

Добавляйте только то, что неочевидно из кода, но постоянно влияет на работу. Фильтр простой: нужна ли строка всей команде, актуальна ли она хотя бы на ближайшие недели, нельзя ли понять это прямо из репозитория.

- точные команды запуска, сборки и тестирования;
- важные соглашения по коду;
- скрытые особенности, от которых зависит корректность изменений (например, суммы хранятся в копейках, используется soft delete или нужен отдельный worker);
- чувствительные зоны и ограничения изменений (do-not-правила);
- ожидания к результату: перечислить изменённые файлы, проверки и оставшиеся риски.

Особенно полезны команды: Claude охотно угадывает, чем запускать проект, и иногда угадывает не туда. Если проект поднимается через `docker compose up`, а проверки гоняются через `./gradlew check`, запишите это явно — одна точная строка экономит много лишних попыток.

Правила формулируйте конкретно и проверяемо. Вместо «делай всё аккуратно и современно» — «не меняй сигнатуры публичных методов в `src/api/**` без явного подтверждения»; вместо «соблюдай стиль проекта» — «не предлагай форматирующие правки вне текущего scope задачи»; вместо «следи за безопасностью» — «не читай и не редактируй `.env*` без прямого запроса».

Пример короткого `CLAUDE.md` для Commerce OS из лекции:

```
# CLAUDE.md

## Команды проекта
- run: `docker compose up`
- test: `./gradlew test`
- check: `./gradlew check`

## Договорённости
- не менять `/api/v1/**` без явного подтверждения
- не переписывать существующие файлы в `db/migration/`
- в ответе всегда перечислять изменённые файлы и запущенные проверки
```

Файл хорош тем, что короткий: как запускать проект, где опасные зоны и в каком виде отчитываться. Живёт в репозитории и воспринимается как часть проекта.

## Слои `CLAUDE.md`

`CLAUDE.md` бывает не один: глобальный `~/.claude/CLAUDE.md` подхватывается всегда; проектный `./CLAUDE.md` или `.claude/CLAUDE.md` — при старте работы с проектом; файлы в подпапках (`./subfolder/CLAUDE.md`) — по необходимости, когда агент доходит до этой области; `CLAUDE.local.md` — личные заметки. Если в репозитории есть `AGENTS.md`, не считайте его автоматически активным: это fallback для проектов без `CLAUDE.md`. При наличии `CLAUDE.md` или `CLAUDE.local.md` фактический источник проверяйте через `/status` или `/memory`; не дублируйте правила в двух файлах.

## Чего не следует добавлять

Не записывайте в общий файл инструкции для одной текущей задачи (вроде «сейчас работаем только с RefundService»), очевидные из кода факты (что проект на Spring Boot и Next.js — видно из репозитория), общие лозунги вроде «пиши хороший код» и устаревшие сведения. Как только файл начинает напоминать семейный архив, важные правила прячутся среди шума, а Claude перестаёт получать чёткий сигнал: хороший файл читать скучно, и это комплимент. Не раздувайте его — цель файла в точности и практической пользе, а не в полноте описания проекта.

`CLAUDE.md` — это context, not enforcement: инструкции в Markdown задают контекст, но не являются технической блокировкой. Даже конкретное правило «не трогать `.env`» само по себе не запрещает действие. Для важных ограничений используйте технические средства: Git baseline, permission mode, deny-правила в permissions (например, `Read(./.env)`) и hooks. `.gitignore` защищает от случайного коммита и скрывает файл из подсказок `@`, но не мешает Claude прочитать его, поэтому как защита от чтения он не работает.

## Разделяйте уровни инструкций

| Место | Для чего подходит |
|---|---|
| `CLAUDE.md` | Общие стабильные соглашения проекта, нужные команде и будущим сессиям. Обычно хранится в репозитории. |
| `CLAUDE.local.md` | Локальные порты, личные пути к данным и индивидуальные предпочтения. Не коммитится, если добавлен в `.gitignore` (сам по себе не игнорируется). Claude всё равно может читать этот файл, поэтому секреты и пароли в нём хранить нельзя. |
| Rules | Правила, относящиеся только к определённой папке, типу файлов или узкой области. Не переносите все такие детали в общий файл. |
| Auto memory | Наблюдения, которые Claude автоматически запомнил во время работы; это вспомогательная память, а не источник гарантированно актуальных правил. |

Правило для узкой области (например, только для `db/migration/**` или `payments/`) не тащите в общий файл: вынесите его в отдельное rule, а в `CLAUDE.md` достаточно короткого напоминания, что такие чувствительные зоны существуют. Личные особенности среды держите в `CLAUDE.local.md`, чтобы они не выглядели как правила всей команды:

```
# CLAUDE.local.md

## Заметки о workspace
- локальная БД работает на порту 5454
- тестовые CSV для импорта лежат в `~/projects/data/subscriptions/`

## Личные предпочтения
- предлагай изменения небольшими diff-блоками
- если затронуто больше двух файлов, сначала коротко опиши план
```

Короткая схема выбора:

1. Нужно всей команде почти в каждой сессии — `CLAUDE.md`.
2. Нужно только вам в этом проекте — `CLAUDE.local.md`.
3. Относится к конкретной области или типу файлов — отдельное rule.
4. Это временный или недавно обнаруженный факт — auto memory, пока он не проверен.
5. Если факт не нужен или уже понятен из проекта — не записывайте его.

При этом сейчас важна сама логика разделения, а не формат rule-файлов и их синтаксис.

## Проверяйте auto memory

Автоматическая память может содержать случайные, временные или устаревшие выводы. Например, Claude запомнил временный путь `/api/v0/refunds`, маршрут давно починили, а память не пересмотрели — и в новой сессии Claude уверенно тянется к уже неактуальному пути. Периодически просматривайте память, удаляйте неверное и переносите действительно важные стабильные сведения в `CLAUDE.md` или отдельное rule. Если нарушение факта было бы серьёзной проблемой, не полагайтесь только на auto memory. Посмотреть и почистить auto memory можно командой `/memory`; точное название и синтаксис зависят от версии — сверьтесь с `/help`.

## С чего начать

Создайте небольшой baseline: команды проекта, несколько неочевидных договорённостей, одну-две чувствительные зоны и желаемый формат отчёта. Дополняйте его, когда повторяющаяся проблема показывает, что не хватает конкретного правила; удаляйте записи, которые перестали быть актуальными. У хорошего `CLAUDE.md` нет цели стать толще — у него есть цель стать точнее.

Пример baseline для маленького проекта по учёту подписок:

```
# CLAUDE.md

## Команды
- run: `npm run dev`
- test: `npm test`

## Договорённости проекта
- все суммы храним в копейках
- не отключать TypeScript strict mode
- в ответе перечисляй изменённые файлы и запущенные проверки

## Не делать
- не трогать `.env*` без прямого запроса
- не делать массовый рефакторинг вне текущего запроса
```

Для Java-проекта на Gradle смысл тот же, меняются только команды: run — `./gradlew bootRun`, test — `./gradlew test`. Короткий baseline почти всегда выигрывает у «умного», но раздутого файла.

## Что запомнить

Общие и стабильные правила храните в `CLAUDE.md`, личные настройки — в `CLAUDE.local.md`, а правила для отдельных областей — в rules. Регулярно проверяйте auto memory: важные договорённости должны быть явно записаны, а ограничения, которые нельзя нарушить, нужно подкреплять техническими средствами.

## Практика (15–25 минут)

**Цель:** Написать короткий `CLAUDE.md` и проверить, как работают слои памяти.

**Что сделать:**
1. В учебном git-репозитории создайте `CLAUDE.md` с командами проверки, одним правилом и форматом отчёта.
2. Создайте `CLAUDE.local.md` с личной заметкой и добавьте его в `.gitignore`; проверьте через `git check-ignore -v`.
3. Попросите Claude выполнить маленькую правку и отчитаться по формату из `CLAUDE.md`.
4. Выполните `/memory`, посмотрите память и решите, что стоит перенести в `CLAUDE.md`, а что оставить локально.

**Если Claude Code недоступен:** выполните доступную часть шагов вручную в редакторе и терминале; недоступные команды разберите по официальной документации. Критерии проверки те же.

**Проверка:**
- `CLAUDE.md` короткий и содержит только полезные правила.
- `CLAUDE.local.md` не попадёт в Git.
- Вы можете объяснить разницу между контекстом и технической блокировкой.
