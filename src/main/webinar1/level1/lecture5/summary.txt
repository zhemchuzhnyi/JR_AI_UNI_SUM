САММАРИ ЛЕКЦИИ 5
Интеграция с IDE: grounding и review — Claude Code, 1 уровень

Главная идея: терминал запускает Claude Code и управляет сессией, IDE помогает передать точный контекст и проверить diff в файле. Claude предлагает изменение, IDE показывает его в контексте, решение принимает человек.

1. Терминал и IDE дополняют друг друга
Терминал остаётся основной поверхностью для запуска Claude Code из корня проекта и управления сессией. IDE удобна для чтения кода, выделения нужного фрагмента и просмотра diff рядом с соседними методами. IDE не заменяет terminal-first workflow — она делает изменения проверяемыми.

Терминал — пульт: запуск, режимы, вывод команд, контроль сессии. IDE — место, где изменение видно: точный фрагмент, diff в контексте файла, сравнение «до/после». Разделение ролей из лекции:

- запустить Claude Code в проекте и управлять сессией — основная поверхность терминала; в IDE иногда доступно, но не главное;
- выделить точный фрагмент кода — неудобно в терминале, очень удобно в IDE;
- смотреть diff в контексте файла — можно и в терминале, но грубовато; самое удобное место — IDE;
- визуально сравнить «до/после» — слабо в терминале, сильная сторона IDE;
- быстро понять, что изменилось рядом, — ограниченно в терминале, очень удобно в IDE.

В терминале ответы Claude звучат убедительно, иногда слишком. Diff в IDE возвращает разговор в инженерную плоскость: вот файл, строка, соседний метод, фактическое изменение — и оно либо устраивает вас, либо нет.

2. IDE grounding: передавайте контекст явно
**IDE grounding** — это привязка запроса к конкретному коду: выделенному фрагменту, конкретному файлу, диапазону строк или соседним местам использования. Это не «глубокая интеграция из будущего», а точный контекст для Claude.
Открытый на экране файл не означает, что Claude получил его как контекст. Привязывайте запрос к выделению, пути файла, диапазону строк или примеру из соседнего кода. Уточняйте границы: что менять, что оставить нетронутым и какой результат нужен.

Пример из лекции — файл payments/RefundService.java:

  import java.math.BigDecimal;

  public class RefundService {
      public BigDecimal calculateRefund(BigDecimal total, BigDecimal discount) {
          return total.subtract(discount);
      }
  }

На запрос «исправь расчёт возврата» Claude гадает: о каком месте речь, искать ли другие файлы, менять ли сигнатуру, трогать ли соседей. С привязкой к выделенному методу догадок меньше — агент реже лезет «помогать» в соседние места без спроса.

Формула лекции: **IDE не делает Claude умнее — она делает конкретнее ваш запрос.**

Пример запроса:

  Проверь выделенный метод расчёта возврата.
  Нужна минимальная правка только в этом файле,
  без изменения сигнатуры. Сначала объясни риск,
  затем покажи diff.

Ещё примеры запросов из лекции:

  Объясни, что делает выделенный метод и какие у него граничные случаи.

  Исправь только выделенный фрагмент в файле payments/RefundService.java.
  Не меняй сигнатуру метода и не трогай соседние классы.

  Сравни строки 18–30 в support/TicketRow.tsx
  с существующим паттерном в orders/OrderBadge.tsx.

Упоминание файлов и диапазоны строк даются почти бесплатно: вместо «посмотри компонент со статусом» — «проверь support/TicketRow.tsx». Точнее привязка — меньше сюрпризов в diff.

Если задача спорная, сначала попросите объяснение риска и план без внесения правок. Узкие рамки уменьшают догадки и нежелательные изменения в соседних местах: вы не душите ИИ, а помогаете ему не расползаться за границы задачи.

3. Используйте привычную IDE
Подойдут VS Code или IDE JetBrains (IntelliJ IDEA, WebStorm, PyCharm и др.). Выбирайте ту, в которой уже удобно читать код и проверять изменения; интерфейсы различаются, но задача одна — передать контекст, открыть файл и увидеть diff.

По задачам лекции обе экосистемы делают одно и то же: открыть проект, выделить фрагмент и передать его как контекст, увидеть diff рядом с кодом, быстро перейти к файлу и посмотреть историю. Разница — в интерфейсе, горячих клавишах и том, что идёт «из коробки»: дополнительные инспекции в VS Code чаще зависят от расширений, в JetBrains — часто богаче из коробки. Лёгкий старт — там, где вы уже работаете: в JetBrains не переезжайте ради моды, с VS Code не переучивайте руки.

Панели, кнопки и вкладки меняются по версиям. Навык — не запоминать географию интерфейса, а понимать назначение поверхности: передать точный контекст, увидеть изменение, проверить его в файле.

4. Плагин — надстройка над CLI
Установите официальный плагин Claude Code в используемую IDE, но сначала установите и авторизуйте CLI. Плагин не заменяет CLI и не работает без него: не прошли установку и первый запуск CLI — сначала туда. Обычно плагин использует ту же авторизацию. Если он не видит CLI или просит войти повторно, проверьте, что CLI, IDE и проект работают в одной среде — особенно при сочетании Windows и WSL.

Два честных пути установки. VS Code:
- автоустановка через CLI: откройте проект в VS Code, откройте встроенный терминал (Ctrl+` или View → Terminal) и запустите claude — CLI обнаружит VS Code и предложит поставить расширение, согласитесь;
- вручную: Extensions (Cmd+Shift+X на macOS / Ctrl+Shift+X на Windows и Linux) → поиск Claude Code → официальное расширение от Anthropic → Install.
После установки в боковой панели (обычно слева) появится иконка Claude. Иконки не видно — смотрите в Activity Bar, она бывает свёрнута.

JetBrains (IntelliJ IDEA, WebStorm, PyCharm, GoLand и др.) — логика та же:
- автоустановка через CLI: откройте встроенный терминал (View → Tool Windows → Terminal или Alt+F12) и запустите claude — CLI определит IDE и предложит установить плагин; часто нужен перезапуск IDE;
- вручную: Settings/Preferences → Plugins (Cmd+, на macOS / Ctrl+Alt+S на Windows и Linux) → вкладка Marketplace → поиск Claude Code → официальный плагин от Anthropic → Install → перезапуск IDE по приглашению.
После перезапуска панель Claude — Tool Window, по умолчанию справа; точное место зависит от версии. Не видите — View → Tool Windows → Claude Code или через Find Action (Cmd+Shift+A / Ctrl+Shift+A).

Плагин ставится в каждую IDE отдельно: пользуетесь IntelliJ IDEA и WebStorm — ставьте в обе. Зато авторизация одна: прошли login в CLI (claude в терминале, через браузер) — плагин подхватит то же. Просит залогиниться отдельно — значит, не видит CLI-сессию: разные окружения, пути, shell. Запустите IDE из той же среды, где живёт CLI: на Linux и macOS обычно решается само, на Windows проверьте, откуда запущена IDE — Windows-native или WSL. Плагин ругается на отсутствие CLI — CLI не установлен или не в PATH той среды, из которой запущена IDE.

В JetBrains плагин даёт быстрый запуск по Cmd+Esc (Mac) / Ctrl+Esc (Windows/Linux), автоматически передаёт открытую вкладку и выделение, а по Cmd+Option+K / Alt+Ctrl+K вставляет ссылку вида `@src/auth.ts#L1-99`. Команда `/ide` проверяет связь CLI с редактором; файл можно указать через `@` или через Copy Reference.

Быстрая проверка интеграции: откройте любой файл проекта, выделите 5–10 строк, откройте панель Claude и попросите коротко: «Объясни выделенный фрагмент». Ответ с упоминанием реальных имён методов или переменных показывает, что выделение передалось. Общий ответ («обычно такой код делает X») может говорить, что контекст не прокинулся и плагин работает как обычный чат. Пункты меню и панели зависят от версии; источник правды — официальная документация по интеграции с IDE, а шаги выше — рабочий ориентир.

5. Проверяйте diff, а не описание
В diff убедитесь, что изменились только нужные файлы и строки, сигнатуры и соседний код не затронуты, а лишние импорты и массовое форматирование не появились. Сверьте фактическое изменение с обещанием Claude и стилем проекта. Изменение принимает или отклоняет человек, а не агент.

В IDE правки агента подсвечиваются прямо в файле: видно, что добавлено и что удалено, и вы принимаете или отклоняете изменение. Ошибку или лог из терминала тоже можно отправить в запрос, не копируя вручную.

Пример правки из лекции — Claude посмотрел метод расчёта возврата и предложил:

   public BigDecimal calculateRefund(BigDecimal total, BigDecimal discount) {
  -    return total.subtract(discount);
  +    BigDecimal safeDiscount = discount == null ? BigDecimal.ZERO : discount;
  +    return total.subtract(safeDiscount);
   }

На словах прекрасно: «обработал null, сохранил сигнатуру». Но важен сам diff: изменился только нужный метод или зацеплены соседи; не внесено ли форматирование в полфайла; не появились ли лишние импорты. Изменение читается не как абстрактный патч, а как часть живого файла: соседний код, стиль проекта, вписывается ли правка в окружение. Красный флаг: просили поправить строчку, а Claude полез в конфигурацию сборки. Смотрите только на текст — примете красивое объяснение за качество; смотрите на diff — принимаете решение по фактам.

6. Чат рядом с кодом: сверяйте обещание с фактом
Когда история, файл и diff рядом, проверка спокойнее: Claude пишет «изменю только RefundService.java, сигнатуру не трогаю», а вы убеждаетесь в этом по файлу — или видите, что в изменениях внезапно ещё один файл, которого в плане не было. Не нужно держать в голове, где был метод, что обещал Claude и какие строки вы выделяли: перед глазами и контекст, и предложение, и результат.

Несколько разговоров, вкладки и панели истории могут быть удобны, но не превращайте это в охоту за возможностями: разговор должен помогать читать код, а не отвлекать от него.

7. Сценарий Commerce OS
При сбое расчёта возврата из-за пустой скидки откройте payments/RefundService.java, выделите метод, обозначьте ограничение — минимальная правка без изменения сигнатуры — и попросите объяснить риск discount == null. Claude отвечает, что риск именно в этом, и предлагает тот самый маленький diff. Затем проверьте diff: затронут ли только нужный метод, не появились ли посторонние изменения. Только после проверки решайте, принимать ли правку.

Распределение ролей: запуск Claude в корне проекта — терминал; поиск и выделение точного метода, узкий запрос и просмотр diff — IDE; принимаете или отклоняете изменение вы, а не Claude. Здесь IDE становится местом, где вы принимаете инженерное решение.

Дальше в курсе — безопасность работы в реальном репозитории: понятное состояние Git, разумные разрешения и инструкции проекта.

Что запомнить: терминал запускает и контролирует; IDE заземляет запрос и показывает изменение в контексте; инженер проверяет факты и принимает решение.

## Практика (15–25 минут)

**Цель:** Сделать узкий запрос через IDE grounding и проверить фактический diff.

**Что сделать:**
1. Откройте небольшой проект в VS Code или JetBrains, убедитесь, что плагин Claude Code установлен, и выполните `/ide`.
2. Выделите небольшую функцию или блок кода и попросите: «Объясни только выделенный фрагмент, назови реальные имена методов и переменных».
3. Попросите изменить одну строку только в выделенном фрагменте, не меняя сигнатуру. При необходимости используйте `@file` или Copy Reference.
4. Посмотрите diff в IDE: изменилось ли только выделенное место, нет ли лишних импортов и форматирования.

**Проверка:**
- Ответ Claude содержит реальные имена из вашего файла, а не общие рассуждения.
- Diff не выходит за пределы выбранного фрагмента.
- Вы можете объяснить, что такое grounding и зачем проверять diff.

> Если плагин недоступен, сделайте то же через CLI с `@path` и диапазоном строк.
