Интеграция с IDE: grounding и review

Claude Code

1 уровень · 5 лекция
Терминал запускает Claude Code и управляет сессией; IDE помогает точно задать контекст и проверить изменение в настоящем файле. Claude предлагает — diff показывает факты — решение принимает человек.

Разные инструменты — разные роли

Терминал — управление

Запустите Claude Code из корня проекта, выбирайте команды и контролируйте сессию. Terminal-first workflow остаётся основой.

IDE — контекст и проверка

Откройте нужный файл, выделите точный фрагмент и просмотрите diff рядом с соседним кодом. Так проще заметить лишние изменения.

Терминал — пульт: запуск, режимы, вывод команд, контроль сессии. IDE — место, где изменение видно: точный фрагмент, diff в контексте файла, сравнение «до/после».

  • Запускать Claude Code в проекте и управлять сессией удобнее в терминале — в IDE это вспомогательная поверхность.
  • Выделять точный фрагмент кода неудобно в терминале и очень удобно в IDE.
  • Смотреть diff в контексте файла можно и в терминале, но грубовато; самое удобное место — IDE.
  • Визуально сравнить «до/после» и быстро понять, что изменилось рядом, — сильная сторона IDE.

IDE не заменяет терминал: она делает работу проверяемой и возвращает разговор к конкретному файлу, строкам и фактическому изменению.

Открытый на экране файл — ещё не переданный Claude контекст. Укажите его явно: выделением, путём, диапазоном строк или конкретным примером из проекта.

Grounding: сужайте рамки задачи

Grounding — привязка запроса к конкретному коду: выделенный фрагмент, конкретный файл, диапазон строк, соседние места использования. Чем точнее контекст и границы, тем меньше догадок и нежелательных правок в соседних местах.

Пример из лекции — файл payments/RefundService.java:

import java.math.BigDecimal;

public class RefundService {
    public BigDecimal calculateRefund(BigDecimal total, BigDecimal discount) {
        return total.subtract(discount);
    }
}

На запрос «исправь расчёт возврата» Claude гадает: о каком месте речь, искать ли другие файлы, менять ли сигнатуру, трогать ли соседей. С выделением в IDE он видит конкретный метод — поле догадок сужается, и агент реже лезет «помогать» в соседние места без спроса. Формула лекции: IDE не делает Claude умнее — она делает конкретнее ваш запрос.

Проверь выделенный метод расчёта возврата.
Нужна минимальная правка только в этом файле,
без изменения сигнатуры. Сначала объясни риск,
затем покажи diff.

Ещё примеры запросов с якорем вместо «посмотри вот это»:

Объясни, что делает выделенный метод и какие у него граничные случаи.
Исправь только выделенный фрагмент в файле payments/RefundService.java.
Не меняй сигнатуру метода и не трогай соседние классы.
Сравни строки 18–30 в support/TicketRow.tsx
с существующим паттерном в orders/OrderBadge.tsx.
  • Передавайте выделенный код или называйте файл и диапазон строк — упоминание файлов и диапазоны даются почти бесплатно.
  • Уточняйте ограничения: что менять нельзя и какого результата ждёте.
  • Для спорного изменения сначала попросите объяснение и план — без правок.

Лишнего нет — есть рамка. Вы не душите ИИ, а помогаете ему не расползаться за границы задачи.

IDE и плагин Claude Code

Используйте знакомую IDE — VS Code или JetBrains. Для задачи важнее уметь передать контекст и проверить diff, чем осваивать новый редактор.

VS Code

Проект, выделение как контекст, diff в файле, быстрый переход по файлам и символам — всё есть. Дополнительные инспекции чаще зависят от расширений. Отличный старт, если вы уже в VS Code.

JetBrains

IntelliJ IDEA, WebStorm, PyCharm и другие: те же базовые возможности, а инспекции часто богаче из коробки. Отличный старт, если вы уже в JetBrains — переезжать ради моды не нужно.

Панели, кнопки и вкладки меняются по версиям. Навык — не запоминать географию интерфейса, а понимать назначение поверхности: передать точный контекст, увидеть изменение, проверить его в файле.

Плагин — отдельная интеграция, а не просто «кнопка» над CLI. В JetBrains плагин обычно опирается на установленный CLI и его авторизацию. VS Code extension несёт собственную копию CLI для панели и может иметь отдельный вход; standalone CLI всё равно нужен для команды claude в терминале. Поэтому «плагин не работает без CLI» верно не для всех поверхностей: разделяйте JetBrains-плагин и VS Code extension.

Установка в VS Code. Два честных пути:

  1. Автоустановка через CLI: откройте проект в VS Code, откройте встроенный терминал (Ctrl+` или View → Terminal) и запустите claude. CLI обнаружит VS Code и предложит поставить расширение — согласитесь, установится автоматически.
  2. Через Extensions Marketplace: Extensions (Cmd+Shift+X на macOS / Ctrl+Shift+X на Windows и Linux) → в поиске Claude Code → официальное расширение от Anthropic → Install.

После установки в боковой панели появится иконка Claude — обычно слева. Иконки не видно — смотрите в Activity Bar, она бывает свёрнута в «...». Проверьте сразу: откройте панель Claude, выделите фрагмент кода и нажмите «обсудить с Claude» (название кнопки зависит от версии). Разговор начался — связка CLI + IDE работает.

Установка в JetBrains (IntelliJ IDEA, WebStorm, PyCharm, GoLand и др.) — логика та же:

  1. Автоустановка через CLI: откройте встроенный терминал (View → Tool Windows → Terminal или Alt+F12) и запустите claude. CLI определит IDE и предложит установить плагин; часто нужен перезапуск IDE — это нормально для JetBrains-плагинов.
  2. Через Plugins Marketplace: Settings/Preferences → Plugins (Cmd+, на macOS / Ctrl+Alt+S на Windows и Linux) → вкладка Marketplace → в поиске Claude Code → официальный плагин от Anthropic → Install → перезапуск IDE по приглашению.

После перезапуска панель Claude — Tool Window, по умолчанию справа; точное место зависит от версии. Не видите — View → Tool Windows → Claude Code или через Find Action (Cmd+Shift+A / Ctrl+Shift+A).

Плагин ставится в каждую IDE отдельно: IntelliJ IDEA и WebStorm — ставьте в обе, платформа общая, но плагины конфигурируются по продукту. Авторизация зависит от поверхности: в JetBrains плагин обычно подхватывает вход из CLI; VS Code extension может иметь собственный вход для панели. Если VS Code просит войти отдельно — это не обязательно ошибка. Если JetBrains не видит CLI-сессию, проверьте, что IDE, CLI и проект работают в одной среде — особенно при сочетании Windows и WSL.

Авторизация. Обычно плагин использует ту же авторизацию, что и CLI: прошли login в терминале через браузер — плагин её увидит и заработает, отдельного входа не нужно. Просит залогиниться отдельно — не видит CLI-сессию: разные окружения, пути, shell. Запустите IDE из той же среды, где живёт CLI; на Linux и macOS обычно решается само, на Windows проверьте, откуда запущена IDE — Windows-native или WSL. Плагин ругается на отсутствие CLI — значит, CLI не установлен или не в PATH той среды, из которой запущена IDE.

Горячие клавиши и ссылки на код: в JetBrains Cmd+Esc / Ctrl+Esc открывает Claude, открытая вкладка и выделение передаются автоматически, а Cmd+Option+K / Alt+Ctrl+K вставляет ссылку вида @src/auth.ts#L1-99. В VS Code проверьте Command Palette: команда вставки ссылки на выделенный код обычно доступна по Option+K / Alt+K; сочетание и название команды зависят от версии расширения. Команда /ide проверяет связь CLI с редактором; файл можно указать через @ или через Copy Reference.

Быстрая проверка: откройте любой файл проекта, выделите 5–10 строк, откройте панель Claude и попросите коротко: «Объясни выделенный фрагмент». Если ответ ссылается на реальные имена методов или переменных, выделение передалось. Общий ответ («обычно такой код делает X») может означать, что контекст не прокинулся и плагин работает как обычный чат.

Названия пунктов меню, расположение панелей и шаги установки меняются между версиями. Ориентируйтесь на назначение интеграции и официальную документацию по интеграции с IDE — это источник правды.

Проверяйте diff, а не обещание

Красивое описание не доказывает, что правка хорошая. Пример из лекции: Claude посмотрел метод расчёта возврата и предложил такую правку.

 public BigDecimal calculateRefund(BigDecimal total, BigDecimal discount) {
-    return total.subtract(discount);
+    BigDecimal safeDiscount = discount == null ? BigDecimal.ZERO : discount;
+    return total.subtract(safeDiscount);
 }

На словах прекрасно: «обработал null, сохранил сигнатуру». Но важен сам diff. В diff проверьте:

  • изменились ли только ожидаемые файлы и строки;
  • сохранилась ли сигнатура и не затронуты ли соседи;
  • нет ли лишних импортов, массового форматирования или посторонних изменений;
  • соответствует ли решение стилю и контексту проекта.

Изменение читается не как абстрактный патч, а как часть живого файла: соседний код, стиль проекта, вписывается ли правка в окружение. Сверяйте обещанный план с фактическими файлами и изменениями: Claude предлагает изменение, IDE показывает его в контексте, решение принимает человек.

В IDE правки агента подсвечиваются прямо в файле: видно, что добавлено и что удалено, и вы принимаете или отклоняете изменение. Ошибку или лог из терминала тоже можно отправить в запрос, не копируя вручную.

Красный флаг: просили поправить строчку, а Claude полез в конфигурацию сборки. Смотрите только на текст — примете красивое объяснение за качество; смотрите на diff — принимаете решение по фактам.

Чат рядом с кодом: сверяйте обещание с фактом

Когда история, файл и diff рядом, проверка спокойнее. Claude пишет: «Изменю только RefundService.java, сигнатуру не трогаю», — а вы убеждаетесь в этом по файлу. Или видите, что в изменениях внезапно ещё один файл, которого в плане не было.

Не нужно держать в голове, где был метод, что обещал Claude и какие строки вы выделяли: перед глазами и контекст, и предложение, и результат. IDE помогает не столько редактировать, сколько сверять обещание с фактом.

Несколько разговоров, вкладки и панели истории могут быть удобны, но не превращайте это в охоту за возможностями: разговор должен помогать читать код, а не отвлекать от него.

Сценарий Commerce OS

Оператор поддержки жалуется: при подготовке возврата интерфейс падает, если скидка в заказе не заполнена. Проект открыт в терминале, Claude Code запущен — но решение рождается в IDE. Откройте payments/RefundService.java и выделите только метод расчёта. Попросите объяснить риск discount == null и предложить минимальную правку без смены сигнатуры. Claude отвечает, что риск именно в этом, и предлагает тот самый маленький diff.

  1. Запустите Claude Code из корня проекта в терминале.
  2. Найдите и выделите точный метод в IDE, дайте узкий запрос с понятной границей.
  3. Изучите diff в контексте файла и убедитесь, что изменено только нужное.
  4. Примите решение сами; при лишних изменениях не принимайте предложение.

В IDE видно: сигнатура не изменилась, соседние методы не тронуты, файл не разъехался по форматированию, лишних правок нет. Здесь IDE перестаёт быть «редактором, куда встроили ИИ», и становится местом, где вы принимаете инженерное решение.

Запомните: терминал запускает и контролирует, IDE заземляет контекст и показывает изменение, инженер проверяет и решает.

Что запомнить

Терминал запускает и контролирует; IDE заземляет запрос и показывает изменение в контексте; инженер проверяет факты и принимает решение.

Практика (15–25 минут)

Цель: Сделать узкий запрос через IDE grounding и проверить фактический diff.

Что сделать

  1. Откройте небольшой проект в VS Code или JetBrains, убедитесь, что плагин Claude Code установлен, и выполните /ide.
  2. Выделите небольшую функцию или блок кода и попросите: «Объясни только выделенный фрагмент, назови реальные имена методов и переменных».
  3. Попросите изменить одну строку только в выделенном фрагменте, не меняя сигнатуру. При необходимости используйте @file или Copy Reference.
  4. Посмотрите diff в IDE: изменилось ли только выделенное место, нет ли лишних импортов и форматирования.

Проверка

  • Ответ Claude содержит реальные имена из вашего файла, а не общие рассуждения.
  • Diff не выходит за пределы выбранного фрагмента.
  • Вы можете объяснить, что такое grounding и зачем проверять diff.

Если плагин недоступен, сделайте то же через CLI с @path и диапазоном строк.

Главная привычка — не верить описанию на слово: задайте узкие рамки и проверьте фактический diff.
