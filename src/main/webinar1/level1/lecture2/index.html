Карта поверхностей и workflow курса

Claude Code

1 уровень · 2 лекция
У Claude Code несколько поверхностей — точек входа в работу. В начале курса достаточно устойчивой связки: запускать Claude Code из терминала в папке проекта, а файлы и изменения проверять в IDE.

Роли поверхностей

Терминал (CLI) — запускает работу

Claude стартует из конкретной директории, получает контекст живого проекта и работает с его реальными файлами. CLI — самая полнофункциональная поверхность: новые функции появляются сначала в нём. Поэтому курс начинает с подхода terminal-first: работа начинается и управляется из терминала, а IDE помогает проверить результат.

IDE — помогает проверять

VS Code или JetBrains показывают файлы, соседний код и diff. Терминал запускает процесс, IDE помогает увидеть, что изменилось и не затронуто ли лишнее.

Остальные поверхности

Desktop, web/cloud и remote/mobile дают другие способы доступа; Slack, GitHub и CI нужны для командных и автоматизированных процессов; browser/computer-use — для специальных сценариев.

Минимум на старте

Знать, что остальные варианты существуют, но пока не включать их в базовый процесс. Terminal-first не означает terminal-only.

Заучивать названия поверхностей не нужно — важна их роль: одна помогает работать внутри проекта, другая — проверять, третья — встраивать Claude в команду. Названия и кнопки со временем меняются, а эта идея держится. Claude Code ценен не числом кнопок, а ясностью пути от задачи до проверяемого результата. Остальные поверхности не второсортные — CI и командные сценарии реально ускоряют команду, но включать их стоит, когда цепочка «проект → diff → проверки → решение» уже устоялась.

В учебном репозитории Commerce OS начните в корне проекта:

cd commerce-os
claude

Запуск из проекта задаёт рабочий контекст и границы. Терминал держит рядом проект, Claude и проверки — так снимается вопрос «а этот ответ вообще про мой проект?». Веб-чат потребовал бы пересказывать структуру и искать файлы по описанию.

Claude даёт материал для инженерного решения, а не принимает решение за разработчика.

Базовый workflow курса

  1. Терминал: запустить Claude Code из папки проекта.
  2. Git: иметь понятное исходное состояние и историю изменений.
  3. IDE: прочитать реальные файлы и визуально просмотреть diff.
  4. Проверки: изучить diff, запустить тесты, сборку, lint или ключевой сценарий.
  5. Решение человека: принять или доработать результат.
  6. Проверяемый артефакт: подготовить изменения, которые можно объяснить и показать на ревью.

PR-ready artifact — это результат, готовый к чужим глазам: понятные изменения, diff, результаты проверок и краткое описание. Создавать pull request прямо сейчас не требуется. Цель — не «Claude сказал готово», а результат, который можно проверить и показать коллеге. Уберите из цепочки любое звено — процесс становится шатким; особенно опасно пропускать чтение diff.

Пример: сортировка заказов в Commerce OS

Структура учебного проекта:

commerce-os/
  orders/
  payments/
  support/
  dashboard/

Запустив Claude Code в корне проекта, попросите найти логику сортировки в модуле orders. Claude изучает реальную папку и находит связанные файлы. Затем откройте их в IDE, посмотрите соседний код и diff, проверьте поведение.

Краткий след результата может выглядеть так:

Изменено:
- orders/OrderService.java

Проверено:
- список заказов открывается
- новые заказы отображаются сверху

Только терминал усложняет визуальную проверку глазами; только IDE без запуска Claude теряет связку с контекстом проекта; только веб заставляет пересказывать кодовую базу; только Slack даёт активность без инженерной опоры. Поверхности работают лучше в своих ролях.

Java, Gradle и Python: когда устанавливать

В прошлой лекции Git и Node.js готовили заранее: они нужны до CLI. JDK и Gradle нужны для Java-экспериментов, Python — позже, в блоке про MVP-архетипы. Рекомендуемый вариант — после установки Claude Code поручить ему проверить, установить недостающее и показать версии: это станет первой практикой постановки задачи и проверки результата.

Можно установить инструменты и вручную заранее — примеры команд по ОС (сверяйтесь с актуальной официальной документацией, версии подбирайте под актуальную LTS):

# macOS — Homebrew
brew install openjdk
brew install gradle
brew install python
# Linux — Debian / Ubuntu
sudo apt install default-jdk gradle python3
# Linux — Fedora / RHEL
sudo dnf install java-latest-openjdk gradle python3
# Windows — winget
winget install --id EclipseAdoptium.Temurin.25.JDK
winget install --id Gradle.Gradle
winget install --id Python.Python.3.13

Проверка после установки (в новом окне терминала):

java -version
gradle -version
python3 --version

Вариант Б: попросить Claude Code. Пример формулировки задачи обычными словами:

Проверь, установлены ли на моей машине JDK, Gradle и Python 3.
Чего не хватает — поставь через мой пакетный менеджер (Homebrew),
после установки покажи версии: java -version, gradle -version, python3 --version.

Это не «волшебная команда», а нормальная инженерная постановка: что проверить, что сделать, чем подтвердить результат. Установка стека — безопасный полигон, чтобы почувствовать базовую схему курса: задача → действие агента → проверка результата.

Gradle Wrapper — версия сборки в проекте

В готовом Java-репозитории используйте ./gradlew (на Windows — gradlew.bat): Wrapper скачивает и запускает версию Gradle, заданную проектом. Так команда собирает проект одинаково, даже если глобально у участников стоят разные версии.

Глобальный gradle нужен главным образом, чтобы создать Wrapper в новом проекте командой gradle wrapper. После этого в повседневной работе используйте Wrapper, а не глобальную версию.

Практика (15–25 минут)

Цель: Пройти путь «терминал → diff → проверка → PR-ready artifact» и развести роли CLI и IDE.

Что сделать

  1. Создайте маленький учебный проект: папку, README.md и один текстовый файл. Откройте её в IDE.
  2. В терминале из корня проекта выполните pwd, claude --version, затем запустите claude.
  3. Попросите Claude изменить одну строку в текстовом файле. Посмотрите diff в IDE и проверьте, что лишние файлы не затронуты.
  4. Выполните простую проверку (например, cat или grep по файлу) и соберите короткий PR-ready artifact: что изменено, diff, проверки, оставшиеся риски.

Проверка

  • Вы можете назвать роль CLI и роль IDE в этой практике.
  • В artifact есть четыре части: изменение, diff, проверки, риски.
  • Правка не затронула файлы вне задачи.
Итоговая схема: терминал даёт контекст проекта, Git — состояние и историю, IDE — видимость изменений, проверки — доказательства, человек — финальное решение.
