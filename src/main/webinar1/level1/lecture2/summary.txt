# Саммари лекции 2

## Карта поверхностей и workflow курса — Claude Code, 1 уровень

## 1. Поверхности Claude Code и их роли
Поверхность — точка входа, через которую Claude Code включается в работу.

• Терминал (CLI) — основная поверхность курса и самая полнофункциональная: запускает Claude Code в конкретной папке проекта, задавая контекст и границы; новые функции появляются сначала в CLI.
• IDE (VS Code / JetBrains) — поверхность проверки: показывает реальные файлы, соседний код и diff.
• Desktop, web/cloud, remote/mobile — альтернативные способы доступа; на старте достаточно знать, что они существуют.
• Slack, GitHub и CI — командные и автоматизированные сценарии, важные позже.
• Browser/computer-use — специальные режимы, а не базовый способ работы в курсе.

**Terminal-first** означает: работа начинается и управляется из терминала — Claude Code запускается из корня проекта, а терминал держит рядом проект, Claude и проверки. Это не terminal-only: IDE помогает проверить результат. На старте основной набор — терминал плюс IDE; не нужно включать все поверхности сразу.

Заучивать названия не нужно — важна роль: одна поверхность помогает работать внутри проекта, другая — проверять, третья — встраивать Claude в команду. Названия и кнопки меняются, а эта идея держится. Claude Code ценен не числом кнопок, а ясностью пути от задачи до проверяемого результата. Поверхности не второсортные: CI и командные сценарии реально ускоряют команду, но включать их стоит, когда цепочка «проект → diff → проверки → решение» уже устоялась.

## 2. Запуск из проекта
Перейдите в корень репозитория и запустите Claude Code оттуда:

  cd commerce-os
  claude

Так Claude работает с реальной структурой Commerce OS, а не с пересказом проекта из веб-чата. Commerce OS — учебный пример интернет-магазина из материалов курса: модули orders (заказы), payments (платежи), support (поддержка) и dashboard (аналитика). Терминал держит рядом три вещи, которые должны жить вместе, — проект, Claude и проверки, поэтому привычка стартовать из проекта снимает вопрос «а этот ответ вообще про мой проект?».

## 3. Базовый workflow курса
Терминал → проект → Git → IDE и diff → проверки → решение человека → проверяемый результат.

• Git даёт понятное состояние репозитория и историю изменений.
• В IDE нужно прочитать изменённые файлы и посмотреть diff — фактический список правок.
• Проверьте поведение подходящими средствами: тестами, сборкой, lint и/или ключевым сценарием.
• Человек решает, принимать ли изменение и готов ли результат к показу.

Claude предоставляет материал для решения, а не принимает решение за разработчика. PR-ready artifact — это понятные изменения, diff, результаты проверок и краткое описание, которые можно отдать на ревью. Открывать pull request при этом не обязательно. Если убрать из цепочки любое звено, процесс шатается — особенно опасно пропускать чтение diff.

Пример для Commerce OS: запустить Claude из корня проекта, попросить найти сортировку в модуле orders, затем посмотреть найденные файлы и diff в IDE и проверить поведение списка заказов. Зафиксировать, что изменено и что проверено.

## 4. Java, Gradle и Python
Git и Node.js готовят до установки CLI. JDK и Gradle нужны для Java-экспериментов, Python — позже, в блоке про MVP-архетипы. Рекомендуется дождаться установки CLI и поручить Claude Code проверить, установить недостающее и вывести версии — это станет практикой постановки задачи и проверки результата. Можно установить вручную; команды и версии зависят от ОС, поэтому сверяйтесь с официальной документацией.

Пример установки вручную (версии подбирайте под актуальную LTS):

  # macOS — Homebrew
  brew install openjdk
  brew install gradle
  brew install python

  # Linux — Debian / Ubuntu
  sudo apt install default-jdk gradle python3
  # Linux — Fedora / RHEL
  sudo dnf install java-latest-openjdk gradle python3

  # Windows — winget
  winget install --id EclipseAdoptium.Temurin.25.JDK
  winget install --id Gradle.Gradle
  winget install --id Python.Python.3.13

Проверка после установки (в новом окне терминала):

  java -version
  gradle -version
  python3 --version

Вариант Б — попросить Claude Code. Пример постановки задачи:

  Проверь, установлены ли на моей машине JDK, Gradle и Python 3.
  Чего не хватает — поставь через мой пакетный менеджер (Homebrew),
  после установки покажи версии: java -version, gradle -version, python3 --version.

Это не «волшебная команда», а нормальная инженерная постановка: что проверить, что сделать, чем подтвердить результат. Так вы сразу применяете базовую схему курса: задача → действие агента → проверка результата. Установка стека — безопасный полигон, чтобы эту схему почувствовать. Какой бы вариант вы ни выбрали, итог один: к началу работы с кодом должны отвечать java -version, gradle -version и python3 --version.

## 5. Gradle Wrapper
В уже существующем Java-проекте сборку запускают через Wrapper: ./gradlew (Windows: gradlew.bat). Он скачивает версию Gradle, заданную репозиторием, поэтому сборка воспроизводится у всей команды независимо от глобальной установки.

Глобальный gradle в основном нужен, чтобы создать Wrapper в новом проекте: gradle wrapper. После этого используйте Wrapper проекта, а не глобальную версию.

Главная мысль: терминал задаёт контекст проекта, Git показывает состояние, IDE делает изменения видимыми, проверки дают доказательства, человек принимает итоговое решение.

## Практика (15–25 минут)

**Цель:** Пройти путь «терминал → diff → проверка → PR-ready artifact» и развести роли CLI и IDE.

**Что сделать:**
1. Создайте маленький учебный проект: папку, `README.md` и один текстовый файл. Откройте её в IDE.
2. В терминале из корня проекта выполните `pwd`, `claude --version`, затем запустите `claude`.
3. Попросите Claude изменить одну строку в текстовом файле. Посмотрите diff в IDE и проверьте, что лишние файлы не затронуты.
4. Выполните простую проверку (например, `cat` или `grep` по файлу) и соберите короткий PR-ready artifact: что изменено, diff, проверки, оставшиеся риски.

**Если Claude Code недоступен:** выполните доступную часть шагов вручную в редакторе и терминале; недоступные команды разберите по официальной документации. Критерии проверки те же.

**Проверка:**
- Вы можете назвать роль CLI и роль IDE в этой практике.
- В artifact есть четыре части: изменение, diff, проверки, риски.
- Правка не затронула файлы вне задачи.
