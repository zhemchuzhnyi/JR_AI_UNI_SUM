# Уровень 14 — контрольные вопросы

Контрольный блок по 5 лекциям уровня 14: 30 открытых вопросов с короткими ответами и ссылками на конспекты. 25 базовых вопросов проверяют понятийный каркас, 5 прикладных — применение в рабочих сценариях. Вопросы покрывают tool capability preflight, маршрут внешнего сигнала, hooks в settings.json, event/matcher/handler, exit-коды, лестницу раскатки, session hooks, дебаг и recovery.

## Лекция 1 — Tool capability preflight

1. **Чем подключённый tool отличается от workflow?**<br>
   Tool capability отвечает, что инструмент технически умеет. Workflow отвечает, как мы используем эту возможность в конкретной задаче, что запрещаем и чем проверяем результат. Подключённый сервер без границ, verification и kill switch — это новая кнопка, а не процесс.<br>
   → [Лекция 1](lecture1/index.html)

2. **Что такое tool capability preflight и какие вопросы он закрывает?**<br>
   Это короткая структурированная проверка применения capability в конкретном workflow. Десять вопросов: боль, нужные capabilities, запреты, режим доступа, credentials, объём контекста, approval, verification, правило при конфликте и kill switch. Самые важные — disallowed actions, verification и kill switch.<br>
   → [Лекция 1](lecture1/index.html)

3. **Почему read-only — безопасный старт и что должно быть в списке запретов?**<br>
   Read-only даёт внешний контекст при минимальном blast radius и не меняет внешнее состояние. Для issue tracker запрещают comment, close, reassign и change labels; для monitoring — silence, rollback и deploy; для БД — любые write/mutation. Session permissions шире workflow-границы: технически возможно не значит разрешено в задаче.<br>
   → [Лекция 1](lecture1/index.html)

4. **Что делать, если issue, docs, alert и код противоречат друг другу?**<br>
   Не выбирать «любимый» источник. Остановить edits, зафиксировать расхождение и превратить его в проверяемую гипотезу: какие claims подтверждаются кодом, какие — только внешним текстом, какая минимальная проверка снимет конфликт. Внешний сигнал подсказывает, куда смотреть, но не заменяет проверку.<br>
   → [Лекция 1](lecture1/index.html)

5. **Зачем нужен kill switch и когда tool получает project scope?**<br>
   Если интеграцию нельзя быстро отключить, она не готова к реальной жизни: нужен короткий путь назад — отключить config, убрать подключение, отозвать токен. Project scope — общая ответственность, туда идут только интеграции с понятным сценарием, verification path и owner. Preflight фиксируется в README/ONBOARDING_GUIDE и рядом с конфигом tool.<br>
   → [Лекция 1](lecture1/index.html)

## Лекция 2 — маршрут внешнего сигнала

6. **Какой маршрут проходит внешний сигнал до результата?**<br>
   Внешний сигнал → гипотеза → маленькое изменение → проверка кодом и tests → артефакт в репозитории. Середина маршрута защищает от соблазна принять гору контекста из сервиса за готовый диагноз. Tool сокращает путь к проверке, но не заменяет её.<br>
   → [Лекция 2](lecture2/index.html)

7. **Почему комментарий в issue — данные, а не инструкция?**<br>
   Комментарий — чья-то догадка, а не доказанный диагноз. Текст issue может содержать prompt injection или просто ошибочную гипотезу. Claude извлекает симптомы, ограничения и шаги, но не исполняет команды из текста; проверка замыкается на код и tests.<br>
   → [Лекция 2](lecture2/index.html)

8. **Что общего у шести сценариев tool integration?**<br>
   Один каркас: сигнал → гипотеза → план → небольшое изменение → проверка → артефакт. Меняется источник сигнала и тип проверки: issue, monitoring, read-only DB, design, docs, browser. Ни один сценарий не перепрыгивает понимание кода и verification.<br>
   → [Лекция 2](lecture2/index.html)

9. **Чем отличается verification для monitoring, docs lookup и read-only DB?**<br>
   Monitoring: воспроизведение, логи, regression test. Docs lookup: сверка версии проекта, build, tests, affected files. Read-only DB: поиск кодового пути, integration tests, query review. Во всех случаях проверка замыкается на проект, а не на сам tool.<br>
   → [Лекция 2](lecture2/index.html)

10. **Какие артефакты остаются после tool-workflow и почему внешний tool не source of truth?**<br>
   `TASK_SPEC.md` с scope и проверкой, `EVIDENCE_LOG.md` с фактами и гипотезами, заметки в `API_MAP.md`, browser-сценарий и скриншот, обновлённые tests. Issue, alert, docs, код и tests показывают разные стороны; ни один не доказывает всё сразу. Source of truth — проверенная комбинация кода, tests и review.<br>
   → [Лекция 2](lecture2/index.html)

## Лекция 3 — event, matcher и handler

11. **Что такое hook и почему он срабатывает независимо от решения модели?**<br>
   MCP — дверь наружу: откуда взять данные или куда сходить. Hook — автоматика внутри Claude Code: что сделать, когда внутри произошло событие. Он не думает и не планирует: совпало условие — выполнил команду. Инструкцию в `CLAUDE.md` модель может забыть, hook срабатывает по событию и matcher, поэтому ошибка в нём тоже срабатывает независимо.<br>
   → [Лекция 3](lecture3/index.html)

12. **Где живут hooks, чем отличаются scope-файлы и как они приезжают из plugin?**<br>
   Hooks регистрируются в settings-файлах, в объекте `hooks`; скрипты удобно держать в `.claude/hooks/`. `~/.claude/settings.json` — личные хуки, `.claude/settings.json` — проектные, `.claude/settings.local.json` — личные хуки проекта, не для команды. Проектный hook виден в diff. Hooks также могут приезжать с plugin, skill или agent; `once: true` снимает хук из skill после первого срабатывания.<br>
   → [Лекция 3](lecture3/index.html)

13. **Из каких трёх частей состоит контракт hook?**<br>
   Event — когда реагировать; matcher — при каком условии; command/handler — что сделать. В settings.json это `hooks → event → matcher → hooks → type/command`. Читается как фраза: когда произошло это, и только если совпало условие, выполни это действие.<br>
   → [Лекция 3](lecture3/index.html)

14. **Какие три группы событий и какие типы хуков нужно держать в голове?**<br>
   До действия — `PreToolUse`, единственная точка, где действие можно остановить до выполнения. После действия — `PostToolUse`: формат, проверка, лог. Жизнь сессии — `SessionStart`, `UserPromptSubmit`, `Stop`, `Notification`. Типы: `command`, `http`, `mcp_tool`, `prompt`, экспериментальный `agent`; начинать стоит с командных.<br>
   → [Лекция 3](lecture3/index.html)

15. **Как matcher и exit-код определяют поведение hook?**<br>
   Matcher — фильтр по инструменту или ситуации: `Edit|Write`, `Bash`, `mcp__github__.*`; он чувствителен к регистру. Можно сузить через `if`, например `Bash(rm *)`. На вход handler получает JSON через stdin. `exit 0` пропускает, `exit 2` блокирует `PreToolUse` и передаёт stderr Claude, другой код — ошибка хука. У `SessionStart` и `UserPromptSubmit` stdout при `exit 0` попадает в контекст сессии.<br>
   → [Лекция 3](lecture3/index.html)

## Лекция 4 — лестница раскатки

16. **Какие признаки делают задачу хорошим кандидатом для hook и с чего начинать?**<br>
   Повторяемая ситуация, предсказуемый результат, отсутствие тонкого вкуса и лёгкий откат. Начинать стоит с узких безопасных сценариев: форматирование, мягкий lint/report, напоминание про чувствительный модуль, узкая защита пути, контекст на старте сессии.<br>
   → [Лекция 4](lecture4/index.html)

17. **Чем non-blocking отличается от blocking и как заблокировать `rm`?**<br>
   Non-blocking пишет лог, форматирует или подсказывает, но не отменяет действие. Blocking запрещает действие; технически это `exit 2`. Для `rm` ставят `PreToolUse` с matcher `Bash` и `if: "Bash(rm *)"`, скрипт печатает причину в stderr и возвращает 2. Это guardrail от частого случая, а не гарантия: жёсткий запрет — deny-правило в permissions.<br>
   → [Лекция 4](lecture4/index.html)

18. **Как выглядит базовая лестница раскатки и где место format-on-edit?**<br>
   Log-only → non-blocking → narrow blocking. На log-only видно, не слишком ли широк matcher; на non-blocking проверяется польза; только затем появляется право сказать «стоп» в узком случае. Project settings — отдельная верхняя ступень. format-on-edit обычно остаётся на non-blocking: он не должен блокировать действие.<br>
   → [Лекция 4](lecture4/index.html)

19. **Почему validation и testing hooks — быстрый сигнал, а не CI?**<br>
   Ранний сигнал должен быть дешевле ошибки, которую он помогает заметить. Тяжёлая, редкая или шумная проверка на каждом edit съедает темп. Hook первого уровня либо гоняет короткую локальную проверку, либо напоминает, какие targeted checks не забыть; полный CI остаётся в pipeline.<br>
   → [Лекция 4](lecture4/index.html)

20. **Что делают session hooks?**<br>
   `SessionStart` может вывести последние коммиты или памятку в контекст. `UserPromptSubmit` ведёт журнал промптов в репозитории. `Stop` сигналит, что Claude закончил отвечать. `Notification` сообщает, что Claude ждёт решения. Журнал не должен содержать env-переменные, токены и куски `.env`.<br>
   → [Лекция 4](lecture4/index.html)

## Лекция 5 — debugging, side effects и recovery

21. **Какие пять вопросов задавать hook, который ведёт себя странно?**<br>
   Загружен ли hook (`/hooks`, scope, битый JSON, `claude doctor`)? То ли событие (`PreToolUse` против `PostToolUse`)? Совпал ли matcher (регистр, инструмент)? Отработал ли handler (exit code, stderr, ручной запуск)? Нет ли side effects (шум, loops, лишний diff, секреты в логе)? Идти по порядку, а не править скрипт наугад.<br>
   → [Лекция 5](lecture5/index.html)

22. **Почему первая проверка — регистрация, а не handler?**<br>
   Иначе можно полчаса чинить команду, которой в сессии нет. `/hooks` показывает активные хуки и источник; битый JSON, неверный scope и неперечитанный конфиг — частые причины «тишины». Claude Code может показать Settings Error, а `claude doctor` показывает, что отброшено.<br>
   → [Лекция 5](lecture5/index.html)

23. **Как читать handler как обычную команду?**<br>
   `exit 0` — успех, `exit 2` — блокирующий ответ для `PreToolUse`, другой код — ошибка handler. stdout/stderr должны быть аккуратными: шум загрязняет лог и контекст. Частые механические причины: quoting, неисполняемый файл, timeout, отсутствующий `jq`, неверный путь. Ручной запуск с тестовым JSON быстро снимает мистику.<br>
   → [Лекция 5](lecture5/index.html)

24. **Какие side effects делают формально работающий hook вредным?**<br>
   Шум, который перестают замечать; лишние изменения файлов и огромный diff; loops, когда after-edit снова вызывает edit; скрытие исходной ошибки; утечка env-переменных, токенов или кусков файлов в лог. От loops спасают узкий matcher и ранний guard в handler.<br>
   → [Лекция 5](lecture5/index.html)

25. **Как устроен recovery path и что показал разбор format-on-edit?**<br>
   Сначала quick disable: убрать блок из settings, `"disableAllHooks": true` или `claude --settings '{"disableAllHooks": true}'`. Затем staged rollback: откат на ступень ниже, сужение matcher, guard, запись в CHANGELOG. В разборе format-on-edit matcher расползся до `frontend/src/**/*`, hook трогал generated-файлы; фикс — вернуть `ts/tsx`, добавить ранний выход для `*.generated.*` и проверить оба случая.<br>
   → [Лекция 5](lecture5/index.html)

## Прикладные сценарии

26. **Какой артефакт фиксирует инженерную постановку задачи в issue-to-PR workflow и что в нём?**<br>
   `TASK_SPEC.md`: цель и ожидаемое поведение, scope и non-goals, ограничения, затронутые области, план проверки (tests, ручные сценарии, критерии готовности), правило при конфликте и fallback. Issue остаётся сырым внешним сигналом, а `TASK_SPEC.md` превращает его в проверяемую задачу в контексте проекта.<br>
   → [Лекция 2](lecture2/index.html)

27. **Опишите корректный workflow monitoring triage.**<br>
   Alert — сигнал, а не диагноз. Зафиксировать факты в `EVIDENCE_LOG.md`, сформулировать гипотезу, проверить её по коду и логам, воспроизвести локально, сделать минимальное изменение, прогнать regression test и повторно проверить. Начинать с silence, rollback или deploy нельзя; чинить по тексту alert — тоже.<br>
   → [Лекция 2](lecture2/index.html)

28. **Почему read-only DB analysis замыкается на код и tests, а не на ручные правки данных?**<br>
   База показывает состояние, но не причину. Ручные правки уничтожают улики, обходят код, миграции и review и не воспроизводятся на других средах. Нужно найти кодовый путь через `API_MAP.md` и inventory, исправить код или миграцию, покрыть tests и проверить данные снова. Read-only остаётся источником фактов, а изменение проходит через код.<br>
   → [Лекция 2](lecture2/index.html)

29. **Как правильно использовать дизайн-макет в design-to-code workflow?**<br>
   Макет — контекст и целевое поведение, а не приказ генерировать всё заново. Сопоставить его с существующими компонентами, токенами и design system, зафиксировать разрыв, уточнить конфликты, внести минимальные изменения и проверить в браузере: responsive-состояния, клавиатурная доступность, консоль. Результат — UI-задача и скриншоты «до/после».<br>
   → [Лекция 2](lecture2/index.html)

30. **Как browser check дополняет docs lookup?**<br>
   Docs lookup даёт version-specific ожидание, browser check — фактическое поведение. Workflow: docs сужает вопрос → гипотеза → минимальное изменение → browser check сценария, консоли, network и скриншота → вывод замыкается на код и tests. Docs без браузера остаются теорией, browser без docs — случайными кликами.<br>
   → [Лекция 2](lecture2/index.html)
