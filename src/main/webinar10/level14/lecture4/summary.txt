# Саммари лекции 4

## Automation hooks: лестница раскатки — Claude Code, 14 уровень

## 1. Признаки действительно полезного hook

После знакомства с event, matcher и handler очень хочется сразу нажать внутреннюю красную кнопку «автоматизировать всё». Это нормальное желание: раз инструмент умеет реагировать на события, значит, на него можно повесить что угодно. Но здесь важно вовремя притормозить — одни задачи hook решает хорошо, другие только добавляют шума.

У полезного hook почти всегда четыре признака:

1. он срабатывает в повторяемой ситуации;
2. даёт предсказуемый результат;
3. не требует тонкого человеческого вкуса;
4. легко откатывается.

Форматирование после редактирования — хороший кандидат. Подсказка «вы задели чувствительный путь, запустите проверку» — тоже. А «оценить, насколько архитектурно красив мой код» — уже не hook-задача: ни детерминизма, ни дешёвого отката, ни гарантии, что автоматизация не пойдёт философствовать вместо помощи.

Для Workflow Kit команды Commerce OS полезнее всего начинать с земных сценариев:

- formatter приводит код к одному стилю;
- linter ищет подозрительные конструкции до ручной проверки;
- узкий защитный hook не даёт полезть в чувствительный путь;
- report-hook напоминает, какие проверки важны после конкретного модуля.

Сначала маленький сигнал, потом осознанное действие — а не «я повесил automation, дальше сама разберётся».

Точные имена событий, полей matcher и флагов блокировки могут отличаться в вашей версии Claude Code. Ориентируйтесь на `/hooks` и актуальную документацию. Важна логика, а не конкретный JSON-синтаксис.

## 2. Безопасные сценарии для первых hooks

Первый hook — не время геройствовать. Это как нож на кухне: сначала вы режете хлеб, а не жонглируете тремя клинками. Берите узкие сценарии, где побочный эффект легко заметить и убрать.

| Сценарий | Что делает hook | Почему это хороший старт |
|---|---|---|
| Форматирование после редактирования | прогоняет форматтер по одному изменённому файлу | изменение локальное, понятное, обычно легко откатить |
| Мягкий lint/report | показывает предупреждение или запускает короткую проверку | даёт быстрый сигнал, но не блокирует работу |
| Напоминание про чувствительный модуль | сообщает, что после изменения стоит запустить дополнительные проверки | не лезет в код, но снижает шанс забыть важный шаг |
| Узкая защита пути | блокирует запись в конкретную опасную зону | полезно, но только после аккуратной раскатки |
| Контекст на старте сессии | печатает краткую памятку или команды проекта | не вмешивается в код, зато уменьшает бытовые ошибки |

Форматирование — почти идеальная первая автоматизация. Если у команды уже выбран formatter, hook не «думает», а просто применяет заранее согласованное правило. Не замена review, а способ не тратить ревью на споры о пробелах и кавычках.

Мягкий lint или report-hook хорош именно потому, что не строит из себя начальника. Он не говорит «стоять, не пущу», а говорит «я заметил полезный сигнал». Особенно в Commerce OS, где фронтенд на Next.js и бэкенд на Java живут рядом: у разных частей проекта проверки разные — hook здесь лучше сначала использовать как ранний радар, а не как мини-охрану на проходной.

С напоминаниями для чувствительных модулей получается очень человеческий сценарий. Вы редактировали путь про возвраты или платежи; hook не обязан гонять тяжёлые тесты, но может напомнить: «Вы задели модуль refunds, не забудьте targeted checks». Новичку такой сигнал особенно полезен: инженерная мышечная память формируется повторением маленьких ритуалов.

## 3. Non-blocking и blocking: разный характер

Снаружи два hook могут выглядеть почти как близнецы: тот же event, похожий matcher, почти тот же handler. Но по реальному эффекту это два разных зверя. Non-blocking — вежливый коллега, заглянул через плечо: «Тут, кажется, стоит проверить ещё кое-что». Blocking — турникет, который не пустит дальше, пока условие не выполнено. Ошибка в первом раздражает, во втором — останавливает работу.

| Режим | Что происходит при срабатывании | Где использовать первым |
|---|---|---|
| Non-blocking | hook пишет лог, форматирует, показывает сигнал, но не отменяет действие | почти всегда лучший старт |
| Blocking | hook может запретить действие или потребовать дополнительного шага | только в очень узких и проверенных сценариях |

Технически блокировка выражается exit-кодом. Hook получает JSON события через stdin и завершается:

- `exit 0` — не возражает, действие идёт дальше;
- `exit 2` — блокирующий ответ: `PreToolUse` отменяет действие, а текст в stderr уходит Claude как объяснение;
- любой другой код — ошибка самого хука, но не блокировка.

Минимальный non-blocking hook для стадии наблюдения:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "scripts/log-format-candidate.sh"
          }
        ]
      }
    ]
  }
}
```

Узкий blocking-пример для `rm`:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "if": "Bash(rm *)",
        "hooks": [
          {
            "type": "command",
            "command": "\"${CLAUDE_PROJECT_DIR}\"/.claude/hooks/block-rm.sh"
          }
        ]
      }
    ]
  }
}
```

Скрипт читает JSON, достаёт команду, проверяет наличие `rm`, пишет причину в stderr и возвращает `exit 2`. Смысл не в синтаксисе, а в характере вмешательства. Ошибся non-blocking — лишний шум в логах, переживаемо. Ошибся blocking — начнёте спорить со своим же automation-слоем, как с упрямым шлагбаумом на парковке: и машина ваша, и двор ваш, а шлагбаум всё равно уверен, что вы здесь посторонний.

Важная граница: учебный guard на `rm` — это страховка от самого частого случая, а не гарантия. Он ловит буквальное `rm` в команде, но удалить файл можно и другими способами. Жёсткий запрет — это deny-правило в permissions; hook остаётся дополнительным контуром.

При этом блокировка хуком работает даже в `bypassPermissions`: это политика проекта, которую не обойти сменой режима. Именно поэтому before-hook — не просто подсказка, а реальный предохранитель.

Поэтому на раннем этапе почти всё должно быть non-blocking. Blocking включайте только там, где matcher очень узкий, сценарий стабилен, а цена ложного срабатывания команде понятна заранее. Иначе вы строите не safety rail, а случайный генератор фрустрации.

## 4. Лестница раскатки: hook по шагам

Хороший hook редко рождается сразу «боевым». Он взрослеет по стадиям: сначала вы смотрите, срабатывает ли он правильно, потом — не шумит ли часто, и только затем даёте право на жёсткое вмешательство.

Базовая лестница:

```text
Log-only
  → Non-blocking
  → Narrow blocking
```

1. **Log-only.** Hook ничего не меняет, только пишет: «Я сработал на таком-то файле». Скучно, но бесценно: сразу видно, не слишком ли широк matcher.
2. **Non-blocking.** Hook делает мягкое действие: подсказка, небольшой report, дешёвая проверка, форматирование. Всё ещё наблюдение, но прикладное: видно, помогает automation или просто украшает терминал новыми строками.
3. **Narrow blocking.** Automation может сказать «стоп», но очень локально: запись в чувствительный путь без подтверждения, опасная команда в защищённой зоне. Расползётся широко — команда начнёт ненавидеть не риск, а сам инструмент.

Дальше — командная зрелость. Хук, обкатанный лично и описанный в README, можно поднять в project settings. Это отдельная верхняя ступень: туда попадают не эксперименты, а артефакты с понятным сценарием, owner и путём отключения.

Две оговорки к лестнице:

- каждая ступень живёт хотя бы пару рабочих сессий; хук ловит лишнее на log-only, и это идеальный момент чинить matcher, пока он никому не мешает;
- строгая лестница обязательна там, где хук умеет мешать, — blocking и всё, что уходит команде. Личный баннер на старте сессии можно включить сразу: цена ошибки — лишняя строка в терминале.

Форматирование и validation-report — это варианты non-blocking ступени, а не отдельные «разрешения» на blocking. Не надо превращать лестницу в шесть обязательных бюрократических пролётов; важно не перепрыгивать с log-only сразу в blocking.

## 5. format-on-edit для Workflow Kit на практике

Соберём сквозной пример и зафиксируем рабочий baseline для format-on-edit: узкий matcher, non-blocking handler и guard для крайних случаев. Цель — вырастить живучий артефакт в `.claude/settings.json`, который команда Commerce OS раскатит без ежедневных молитв о стабильности.

Сначала мы вообще не форматируем код — проверяем только, что hook ловит нужные файлы фронтенда и не лезет в бэкенд, generated-файлы и случайные артефакты. Hook идёт в log-only:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "scripts/log-format-candidate.sh"
          }
        ]
      }
    ]
  }
}
```

Сам скрипт может быть совсем маленьким: прочитать JSON из stdin, достать `tool_input.file_path` через `jq` и напечатать путь в stderr. Никакой магии. Несколько рабочих сессий я просто наблюдаю, действительно ли hook срабатывает там, где нужно. Поймал лишние файлы — идеальный момент поправить matcher или добавить проверку пути в скрипте, пока он никому ничего не ломает.

Когда стало ясно, что matcher ведёт себя прилично, можно дать hook право на реальное форматирование:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}
```

Если проекту нужна дополнительная защита от лишних файлов, лучше завернуть команду в свой скрипт и сделать ранний выход для исключений:

```bash
#!/usr/bin/env bash
FILE=$(jq -r '.tool_input.file_path')
case "$FILE" in
  src/*.ts|src/*.tsx) ;;
  *) exit 0 ;;
esac
case "$FILE" in
  *.generated.ts|*.snap) exit 0 ;;
esac
npx prettier --write "$FILE"
```

Именно такая связка — узкий matcher плюс guard в handler — обычно и становится живучим baseline для проекта.

На этом месте многие воодушевляются и хотят сразу добавить ещё ESLint, тесты, проверку импортов и напоминание пить воду. Лучше остановиться. Один hook на пять дел превращается в комбайн, который сложнее понять, чем отключить. Хороший Workflow Kit живёт наоборот: один артефакт — одна внятная ответственность. Зрелый format-on-edit выглядит скучно — и это комплимент.

## 6. Hooks для проверки и тестов: быстрый сигнал, не CI

После форматирования следующий соблазн — проверки. Кажется: раз hook умеет запускать команду, значит после каждого редактирования надо гонять тесты, линтер, сборку и весь проект через статический анализ. Практически одно редактирование превращается в маленькую очередь на посадку в аэропорту.

Для validation и testing hooks действует правило: **ранний сигнал должен быть дешевле, чем ошибка, которую он помогает заметить**. Проверка тяжёлая, редкая или шумная — ей не место в hook первого уровня, выносите на поздний этап workflow. Hook здесь — быстрый сенсор, а не переносной дата-центр.

Для фронтенд-файлов можно начать с мягкого lint на изменённый файл:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "scripts/lint-changed-file.sh"
          }
        ]
      }
    ]
  }
}
```

Для чувствительных зон бэкенда чаще полезнее не запускать дорогие тесты автоматически, а выдать точную подсказку: «Изменён файл в refund-модуле, проверьте targeted tests». Hook не притворяется умнее разработчика. Он просто вовремя напоминает: «Вы задели модуль, где цена забывчивости выше обычной». Новичку мягкий сигнал часто полезнее автоматического запуска тяжёлой suite — он приучает думать о риске изменения.

Хороший testing hook — не тот, что запускает всё. Это hook, который приносит нужный сигнал в нужный момент и не съедает темп. Боретесь после его включения не с багами, а со временем ожидания — значит, автоматизация ушла дальше своей реальной ценности.

## 7. Хуки жизни сессии

Третью группу событий обычно недооценивают: она ничего не блокирует и не форматирует. Зато делает сессии дисциплинированными — и оставляет память о работе.

**SessionStart** — особое событие: всё, что скрипт напечатает в stdout при `exit 0`, попадает прямо в контекст сессии. Так умеют всего несколько событий — из тех, что мы разбираем, ещё `UserPromptSubmit`. Баннер «на чём остановились»:

```json
{
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          { "type": "command", "command": "git log --oneline -5" }
        ]
      }
    ]
  }
}
```

Claude начинает сессию, уже видя последние пять коммитов — не надо пересказывать, где вы остановились.

Дальше журнал и сигнал:

- **UserPromptSubmit** — журнал сессии: каждый ваш промпт дописывается в файл в репозитории. Через неделю видно, что и почему вы делали;
- **Stop** — Claude закончил отвечать: длинная задача работает, вы занимаетесь своими делами, а сигнал или звук возвращает вас к терминалу;
- **Notification** — отдельное событие «Claude ждёт вас»: подтверждение прав или простой. Разница со Stop — «закончил» против «ждёт вашего решения».

Эти три сценария — баннер, журнал, сигнал — ровно то, что вы соберёте в практике вебинара. Важно помнить про безопасность: журнальный hook не должен писать env-переменные, токены и куски `.env`. Журнал — самодостаточный артефакт проекта, а не свалка секретов.

У Stop-хука есть защита от зацикливания: если он каждый раз отвечает «продолжай работать», после 8 блокировок подряд Claude Code перекрывает его. Остальные побочные эффекты автоматизации выключать придётся вам.

## 8. Если hook молчит или мешает

Hook с опечаткой в matcher или событии ломается молча: нет красного баннера «hook failed, изучите проблему». Просто перестал форматироваться код — и всё. Поэтому диагностика — не интуиция, а путь по шагам: загружен ли hook, то ли событие, совпал ли matcher, отработал ли handler, нет ли side effects.

Если hook уже мешает работать, сначала быстро верните себе управляемость: уберите блок из settings, включите `"disableAllHooks": true` или запустите `claude --settings '{"disableAllHooks": true}'`. После этого — спокойный откат на ступень ниже, сужение matcher и короткая запись о причине.

Подробный разбор пяти вопросов, типичных поломок, побочных эффектов и recovery — тема следующей лекции.

## 9. Признаки того, что hook помогает, а не мешает


У автоматизации простой экзамен: после недели использования команда должна работать спокойнее, а не напряжённее. Если hook срабатывает не там, пишет слишком много, неожиданно меняет файлы, маскирует исходную ошибку своей собственной или требует отдельного ритуала отключения — он не созрел. Не трагедия — сигнал откатиться на предыдущую ступень лестницы.

Полезно задавать hook три вопроса:

1. Можно ли объяснить его смысл одним абзацем без шаманства?
2. Можно ли отключить его одним понятным действием?
3. Делает ли он проблему меньше, чем сам добавляет шума?

Хоть один мутный ответ — сузьте matcher, ослабьте вмешательство или верните hook в log-only.

В Workflow Kit, который со временем становится общим артефактом команды, это особенно важно. Личный эксперимент можно молча пережить. Общий hook, который капризничает, быстро подрывает доверие ко всему automation-слою. А доверие в инженерном workflow хрупкое: теряется за один странный вечер, возвращается неделями.

Поэтому зрелость hook почти всегда выглядит скромно. Он решает маленькую повторяемую боль. Его легко понять и легко выключить. Он не пытается быть умнее всего процесса. Лучший комплимент для automation: она настолько к месту, что о ней почти перестают думать.

## Что запомнить

- Хороший hook: повторяемая ситуация, предсказуемый результат, отсутствие тонкого вкуса, лёгкий откат.
- Первые hooks — узкие и безопасные: форматирование, мягкий lint/report, напоминание, узкая защита пути, баннер сессии.
- Non-blocking — лучший старт; blocking — только в узких проверенных сценариях.
- Блокирует `exit 2`; `exit 0` пропускает; другие коды — ошибка хука, а не блокировка.
- Базовая лестница: log-only → non-blocking → narrow blocking; project settings — отдельная ступень зрелости.
- Ступени нельзя перепрыгивать: сначала наблюдаем, потом даём действие.
- format-on-edit начинается с log-only и узкого matcher, затем получает право на форматирование.
- Узкий matcher + guard в handler — живучий baseline.
- Один hook — одна внятная ответственность; не превращайте его в комбайн.
- Validation/testing hook — быстрый сигнал, а не CI на каждый edit.
- Session hooks: `SessionStart` даёт контекст, `UserPromptSubmit` ведёт журнал, `Stop` сигналит о завершении, `Notification` — об ожидании.
- Диагностика молчащего хука идёт по шагам: загрузка, событие, matcher, handler, side effects.
- Recovery: quick disable, откат на ступень ниже, сузить matcher, записать причину; подробно — в лекции 5.
- Hook должен быть понятен, легко отключаться и уменьшать проблему больше, чем добавлять шума.
- Зрелая automation выглядит скучно и не требует ежедневных молитв.

## Практика (15–25 минут)

**Цель:** спроектировать лестницу раскатки для automation hook и проверить, что он остаётся узким, non-blocking и легко откатывается.

**Что сделать:**
1. В вымышленном Workflow Kit создайте `HOOK_ROLLOUT.md`. Выберите один сценарий: format-on-edit для `frontend/src/**/*.ts(x)` или guard на `rm` для PreToolUse. Для format-on-edit blocking не нужен; для guard лестница идёт до narrow blocking.
2. Распишите базовую лестницу: log-only → non-blocking → narrow blocking (если применимо). Для каждой ступени укажите event, matcher, command, ожидаемый эффект и условие перехода дальше. Отдельно отметьте, когда hook готов к project settings.
3. Для первой ступени напишите log-only фрагмент settings и короткий скрипт, который печатает путь или команду-кандидат. Для следующей — non-blocking handler, который не меняет код.
4. Для guard опишите exit-контракт и проверьте скрипт на фейковом JSON: `echo '{"tool_name":"Bash","tool_input":{"command":"rm notes-old.md"}}' | ./block-rm.sh`. Ожидайте `exit 2`; команда внутри JSON не должна выполняться. Добавьте guard: какие пути или команды hook не трогает.
5. Заполните `HOOK_HEALTH.md`: три вопроса о понятности, отключении и соотношении пользы/шума, плюс quick disable и откат на ступень ниже. Полный дебаг по пяти вопросам — в следующей лекции. Не используйте реальные опасные команды и секреты.

**Проверка:**
- В `HOOK_ROLLOUT.md` есть ступени log-only → non-blocking → narrow blocking или обоснование, почему blocking не нужен.
- Первая ступень не меняет файлы, только логирует.
- Matcher узкий, guard исключает лишние зоны.
- Blocking появляется только на поздней ступени и в узком сценарии.
- Guard возвращает `exit 2` на фейковом JSON и объясняет причину в stderr.
- Для hook указан способ быстрого отключения.
- В `HOOK_HEALTH.md` есть три вопроса о здоровье hook и критерии отката.
- Нет реальных опасных команд и секретов.
- Если Claude Code недоступен, лестница и проверка выполнены вручную по тем же критериям.
