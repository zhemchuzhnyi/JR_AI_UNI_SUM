Tool integration

Claude Code

14 уровень · лекция 2
Внешний tool ценен не потому, что подключён, а потому, что сокращает путь от сигнала до проверенного инженерного действия. Один каркас — шесть разных сигналов.

1. Tool полезен, когда сокращает путь к проверке

Когда внешний tool уже прошёл preflight — разрешения сужены, лишние write actions закрыты, verification и kill switch понятны, — вопрос уже не в самом подключении. Внешний инструмент ценен не потому, что подключён, а потому, что сокращает путь от внешнего сигнала до проверенного инженерного действия.

Issue, monitoring alert, данные из read-only базы, дизайн, документация и browser check кажутся шестью разными мирами. На деле каркас один: tool остаётся capability, workflow начинается там, где signal превращается в гипотезу, план и проверку. Иначе выходит знакомая офисная картина: вам переслали письмо, вы переслали его Claude, Claude переслал вам уверенное мнение, а код как был не проверен, так и остался.

Внешний сигнал
  → гипотеза
  → план
  → небольшое изменение
  → проверка
  → артефакт в репозитории

Гипотеза и план между «получили сигнал» и «сделали diff» — защита от момента, когда сервис подкинул гору контекста, а вы приняли его за готовый диагноз. Ни один источник не даёт права перепрыгнуть шаг «понять, что происходит в коде».

Workflow-заметка возле TASK_SPEC.md:

## Внешний сигнал
Issue COM-142: дубли в списке возвратов
## Гипотеза
Проблема в сортировке на уровне сервиса, а не в SQL-запросе
## Проверка
Тест сортировки + ручная проверка inbox
## Артефакт
TASK_SPEC.md + PR_DESCRIPTION.md

Скромно, но связывает внешний источник и рабочий цикл. Не «MCP подключён», а «сигнал превращён в задачу, план и проверку».

2. Issue-to-PR: трекер помогает думать

Самый понятный сценарий — issue tracker. Preflight уже зафиксировал границы: tracker — read-only источник задачи, а claims из комментариев остаются данными, пока их не подтвердили код и tests. Ценность интеграции в том, что жалоба быстрее превращается в TASK_SPEC.md.

В Workflow Kit есть read-only интеграция вроде .claude/mcp/issue-tracker.json — доступ к карточке, комментариям, меткам, скриншотам, ссылкам на обсуждения. Дальше обычная инженерия: issue → TASK_SPEC.md, discovery по коду, маленький план, и только тогда diff.

Ситуация в Commerce OS: в inbox поддержки возвратные заявки идут в неправильном порядке. Из трекера приходит issue с жалобой оператора, скриншотом и фразой «критично, мешает работе». Это хороший вход, но ещё не решение. Следующий шаг — превратить жалобу в техническую задачу:

# TASK_SPEC.md
Задача: исправить порядок заявок на возврат в inbox поддержки
Источник: issue COM-142
Scope: модуль support inbox и связанный тест сортировки
Не менять: API списка заявок и схему БД
Проверка: тест сортировки + ручная проверка в UI
Риск: не затронуть обычные тикеты без возврата

Теперь Claude работает по структуре, а не по эмоции «критично». Полезно задавать узкую рамку: не «разберись с issue», а «прочитай issue, свяжи его с кодом, предложи affected files, подготовь черновик TASK_SPEC.md и укажи, каких фактов не хватает».

Хороший issue-to-PR workflow держится на цепочке: discovery, diff, tests, PR_DESCRIPTION.md. Выпадет хоть один шаг — интеграция снова превращается в красивую пересылку контекста.

3. Monitoring triage: алерт — сирена, не диагноз

С monitoring работает тот же каркас, только сигнал живёт в runtime. Preflight фиксирует read-only posture: tool покажет alert и ограниченное окно логов. Alert нужен не как fix plan, а как старт triage.

Если перескочить через reproduce step, получится классический patch loop: Claude чинит симптом, вылезает новый, потом ещё один, и через двадцать минут у вас три изменения в unrelated-файлах и ни одного ответа на «что было корневой причиной».

EVIDENCE_LOG.md превращает alert из эмоционального раздражителя в инженерный журнал наблюдений:

# EVIDENCE_LOG.md
Сигнал: рост ошибок 500 на /api/orders/{id}/refund
Окно логов: 10:12–10:18
Гипотеза: таймаут при повторной проверке статуса возврата
Проверка: воспроизвести локально запрос с тем же сценарием
Подтверждение: падает регрессионный тест RefundTimeoutTest

Alert не сказал «исправь сервис возвратов» — он задал направление. Важно удерживать границу автономности: tool не глушит alert, не откатывает релиз, не выполняет произвольные команды на проде и не объявляет баг закрытым потому, что график «вроде стал лучше». Это автопилот в зоне, где цена ошибки слишком велика.

Monitoring workflow: alert → hypothesis → reproduce → fix → regression check. Пока нет reproduce и regression check, интеграция не замкнута.

4. Read-only БД: смотрим смело, лечим через код

С read-only БД preflight сделал главный выбор: смотреть можно, лечить руками нельзя. База показывает форму проблемы, но не объясняет её причину.

В Commerce OS видны странные дубли заявок на возврат. Read-only запрос подтвердит, что дубли есть и в каком объёме, — и спор «нам показалось» сменяется разговором по фактам.

SELECT order_id, COUNT(*) AS cnt
FROM refund_requests
GROUP BY order_id
HAVING COUNT(*) > 1;

Если один order_id встречается три раза, это не повод бежать и править данные руками. Следующий вопрос: какой кодовый путь породил это состояние? Повторная отправка формы? Некорректная обработка таймаута? Тестовые данные, легшие в таблицу во время проверки? База честно показывает «что есть», но не знает «почему так получилось».

Read-only DB analysis замыкается на код и проверку. Удобно связать результат с API_MAP.md или найденным endpoint: увидели дубли — через карту API и discovery нашли путь /api/orders/{id}/refund — проверили сервис — добавили regression test.

Держаться за read-only как default стоит и потому, что база любит правду, но не любит импульсивные UPDATE и DELETE, особенно «просто чтобы быстро проверить гипотезу». Изменения данных идут через код, миграции, тестовые сценарии и human approval.

5. Design-to-code: макет — это контекст, а не приказ

До сих пор внешние tools разбирали то, что уже случилось в проекте: жалобу, runtime-сигнал, состояние данных. Теперь другой тип сигнала — reference, который задаёт целевое поведение интерфейса.

Дизайн-интеграции и скриншоты вызывают смесь восторга и паники. Восторг — «Claude увидит макет и всё сверстает». Паника — макет аккуратнее текущего экрана, и рука тянется «заодно немного переделать всё». Это «заодно» превращает маленькую UI-задачу в ремонт половины интерфейса.

Правильный design-to-code workflow начинается не с генерации компонентов, а с сопоставления дизайна с реальным кодом. Макет, скриншот, комментарий дизайнера — внешний сигнал: интерфейс должен выглядеть иначе.

В админ-панели Commerce OS нужно сделать кнопку «Возврат» заметнее в карточке тикета. Дизайнер прислал обновлённый экран. Это не повод просить «переделай блок как на макете» — сначала маленькая задача:

## UI-задача
Экран: карточка тикета в support inbox
Изменить: сделать кнопку "Возврат" визуально заметнее
Не менять: поведение формы, API и логику отправки
Проверка: скриншот до/после + ручной проход в браузере

После этого Claude поможет найти компонент и предложить минимальное изменение. Дизайн — reference, а не автогенератор архитектуры. Ваших компонентов, ограничений вёрстки, правил темы и истории багов он не знает — это знает кодовая база и TASK_SPEC.md.

Относитесь к design-to-code как к переводу: макет говорит языком интерфейса, репозиторий — языком компонентов и ограничений. Claude может быть переводчиком, но не диктатором, объявляющим войну коду из-за отступа 12 → 16 пикселей. Иногда изменение действительно важное — но понять это можно внутри workflow, а не по красоте макета.

6. Docs lookup и browser checks вместе

Документация и browser tools хорошо работают в паре. Документация отвечает, как правильно делать в текущей версии технологии, браузер — что на самом деле произошло после изменения. Только docs — формально правильный, но неработающий в вашем проекте код. Только браузер — долго тыкаете экран и не понимаете, почему он так себя ведёт.

Docs lookup полезен там, где не хочется полагаться на память Claude: на фиксированном стеке нужен точный синтаксис конфигурации. Вместо гаданий по прошлому проекту Claude достаёт узкий факт, а вы применяете его к файлу и проверяете локальной сборкой.

Но документация сама задачу не закрывает. Browser workflow — финальное заземление: не «верю, что компонент выглядит правильно», а воспроизвожу сценарий, делаю скриншот и проверяю, что интерфейс не сломал соседние элементы.

## Проверка в браузере
Страница: /admin/support
Сценарий: открыть тикет и нажать "Возврат"
Ожидание: кнопка заметна, форма открывается, верстка не прыгает
Факт: сценарий проходит, смещение layout не наблюдается

Цикл замыкается, и только тогда вы говорите «изменение принято». Без browser check design-to-code и docs lookup остаются умными предположениями.

7. Один каркас для шести сценариев

Issue tracker, monitoring, база, дизайн, документация и browser кажутся шестью разными мирами. На деле каркас один — меняется внешний сигнал и тип проверки на конце.

Внешний tool не делает работу за вас, он делает ваш следующий шаг точнее. А вы вместе с Claude Code превращаете эту точность в инженерный цикл: понять, спланировать, изменить, проверить и зафиксировать в артефакте репозитория.

Не нужно держать в голове шесть разных «интеграций». Достаточно узнавать один каркас: issue, alert, строки из базы, макет, страница документации, поведение в браузере — на входе разные, а маршрут до артефакта в репозитории один. Освоили его на трекере — почти бесплатно получаете monitoring, базу, дизайн, docs и браузер.

Что запомнить

  • Tool ценен, когда сокращает путь от сигнала до проверенного действия.
  • Каркас: сигнал → гипотеза → план → небольшое изменение → проверка → артефакт.
  • Issue tracker помогает собрать TASK_SPEC.md, но не заменяет discovery и tests.
  • Alert — сирена, а не диагноз; нужен reproduce и regression check.
  • Read-only БД показывает факт состояния, но причину ищут в коде.
  • Макет — reference, а не приказ переделать весь интерфейс.
  • Docs lookup даёт версионный факт, browser check подтверждает фактическое поведение.
  • Verification всегда замыкается на проект: код, тесты, build, browser, review.
  • Шесть сценариев используют один workflow-каркас, меняется только сигнал и проверка.
  • Артефакты (TASK_SPEC.md, EVIDENCE_LOG.md, PR_DESCRIPTION.md) фиксируют результат в репозитории.

Практика (15–25 минут)

Цель: разложить шесть tool-сценариев по одному workflow-каркасу и собрать артефакты для двух из них без реальных внешних подключений.

Что сделать

  1. В вымышленном Workflow Kit создайте TOOL_WORKFLOW_MAP.md с таблицей шести сценариев: issue-to-PR, monitoring, read-only DB, design-to-code, docs lookup, browser check.
  2. Для каждого сценария заполните: внешний сигнал, что даёт tool, что остаётся человеку, чем проверяется результат, какой артефакт создаётся.
  3. Возьмите issue-to-PR и monitoring: создайте фейковый TASK_SPEC.md для issue COM-142 и EVIDENCE_LOG.md для alert по /api/orders/{id}/refund.
  4. Для design-to-code и docs+browser опишите минимальную проверку: что не меняем, какой browser-сценарий и скриншот нужны, какой version-specific факт проверяем.
  5. Проверьте карту: ни один сценарий не перепрыгивает гипотезу, reproduce/проверку и артефакт. Если Claude Code доступен, сымитируйте один сценарий; если нет — выполните вручную. Не подключайте реальные сервисы.

Если Claude Code или внешние tools недоступны: выполните карту и артефакты вручную в редакторе, без реальных подключений; критерии проверки те же.

Проверка

  • В TOOL_WORKFLOW_MAP.md есть все шесть сценариев и пять колонок.
  • Для issue-to-PR создан TASK_SPEC.md с scope, non-goals и проверкой.
  • Для monitoring создан EVIDENCE_LOG.md с сигналом, гипотезой, reproduce и подтверждением.
  • Для design-to-code указано, что не меняется, и browser check.
  • Для docs lookup указан version-specific факт и build/test проверка.
  • Ни один сценарий не заканчивается «tool сказал — приняли».
  • В практике только фейковые данные, без реальных подключений и секретов.
  • Если Claude Code недоступен, карта и артефакты выполнены вручную по тем же критериям.
