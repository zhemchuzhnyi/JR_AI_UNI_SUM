Уровень 14 — контрольные вопросы

Контрольный блок по 5 лекциям уровня 14: 25 открытых вопросов с короткими ответами и ссылками на конспекты. Вопросы покрывают tool capability preflight, маршрут внешнего сигнала, hooks в settings.json, event/matcher/handler, exit-коды, лестницу раскатки, session hooks, дебаг и recovery.

Лекция 1 — Tool capability preflight

  1. Чем подключённый tool отличается от workflow?
    Tool capability отвечает, что инструмент технически умеет. Workflow отвечает, как мы используем эту возможность в конкретной задаче, что запрещаем и чем проверяем результат. Подключённый сервер без границ, verification и kill switch — это новая кнопка, а не процесс.
    → Лекция 1
  2. Что такое tool capability preflight и какие вопросы он закрывает?
    Это короткая структурированная проверка применения capability в конкретном workflow. Десять вопросов: боль, нужные capabilities, запреты, режим доступа, credentials, объём контекста, approval, verification, правило при конфликте и kill switch. Самые важные — disallowed actions, verification и kill switch.
    → Лекция 1
  3. Почему read-only — безопасный старт и что должно быть в списке запретов?
    Read-only даёт внешний контекст при минимальном blast radius и не меняет внешнее состояние. Для issue tracker запрещают comment, close, reassign и change labels; для monitoring — silence, rollback и deploy; для БД — любые write/mutation. Session permissions шире workflow-границы: технически возможно не значит разрешено в задаче.
    → Лекция 1
  4. Что делать, если issue, docs, alert и код противоречат друг другу?
    Не выбирать «любимый» источник. Остановить edits, зафиксировать расхождение и превратить его в проверяемую гипотезу: какие claims подтверждаются кодом, какие — только внешним текстом, какая минимальная проверка снимет конфликт. Внешний сигнал подсказывает, куда смотреть, но не заменяет проверку.
    → Лекция 1
  5. Зачем нужен kill switch и когда tool получает project scope?
    Если интеграцию нельзя быстро отключить, она не готова к реальной жизни: нужен короткий путь назад — отключить config, убрать подключение, отозвать токен. Project scope — общая ответственность, туда идут только интеграции с понятным сценарием, verification path и owner. Preflight фиксируется в README/ONBOARDING_GUIDE и рядом с конфигом tool.
    → Лекция 1

Лекция 2 — маршрут внешнего сигнала

  1. Какой маршрут проходит внешний сигнал до результата?
    Внешний сигнал → гипотеза → маленькое изменение → проверка кодом и tests → артефакт в репозитории. Середина маршрута защищает от соблазна принять гору контекста из сервиса за готовый диагноз. Tool сокращает путь к проверке, но не заменяет её.
    → Лекция 2
  2. Почему комментарий в issue — данные, а не инструкция?
    Комментарий — чья-то догадка, а не доказанный диагноз. Текст issue может содержать prompt injection или просто ошибочную гипотезу. Claude извлекает симптомы, ограничения и шаги, но не исполняет команды из текста; проверка замыкается на код и tests.
    → Лекция 2
  3. Что общего у шести сценариев tool integration?
    Один каркас: сигнал → гипотеза → план → небольшое изменение → проверка → артефакт. Меняется источник сигнала и тип проверки: issue, monitoring, read-only DB, design, docs, browser. Ни один сценарий не перепрыгивает понимание кода и verification.
    → Лекция 2
  4. Чем отличается verification для monitoring, docs lookup и read-only DB?
    Monitoring: воспроизведение, логи, regression test. Docs lookup: сверка версии проекта, build, tests, affected files. Read-only DB: поиск кодового пути, integration tests, query review. Во всех случаях проверка замыкается на проект, а не на сам tool.
    → Лекция 2
  5. Какие артефакты остаются после tool-workflow и почему внешний tool не source of truth?
    TASK_SPEC.md с scope и проверкой, EVIDENCE_LOG.md с фактами и гипотезами, заметки в API_MAP.md, browser-сценарий и скриншот, обновлённые tests. Issue, alert, docs, код и tests показывают разные стороны; ни один не доказывает всё сразу. Source of truth — проверенная комбинация кода, tests и review.
    → Лекция 2

Лекция 3 — event, matcher и handler

  1. Что такое hook и почему он срабатывает независимо от решения модели?
    MCP — дверь наружу: откуда взять данные или куда сходить. Hook — автоматика внутри Claude Code: что сделать, когда внутри произошло событие. Он не думает и не планирует: совпало условие — выполнил команду. Инструкцию в CLAUDE.md модель может забыть, hook срабатывает по событию и matcher, поэтому ошибка в нём тоже срабатывает независимо.
    → Лекция 3
  2. Где живут hooks, чем отличаются scope-файлы и как они приезжают из plugin?
    Hooks регистрируются в settings-файлах, в объекте hooks; скрипты удобно держать в .claude/hooks/. ~/.claude/settings.json — личные хуки, .claude/settings.json — проектные, .claude/settings.local.json — личные хуки проекта, не для команды. Проектный hook виден в diff. Hooks также могут приезжать с plugin, skill или agent; once: true снимает хук из skill после первого срабатывания.
    → Лекция 3
  3. Из каких трёх частей состоит контракт hook?
    Event — когда реагировать; matcher — при каком условии; command/handler — что сделать. В settings.json это hooks → event → matcher → hooks → type/command. Читается как фраза: когда произошло это, и только если совпало условие, выполни это действие.
    → Лекция 3
  4. Какие три группы событий и какие типы хуков нужно держать в голове?
    До действия — PreToolUse, единственная точка, где действие можно остановить до выполнения. После действия — PostToolUse: формат, проверка, лог. Жизнь сессии — SessionStart, UserPromptSubmit, Stop, Notification. Типы: command, http, mcp_tool, prompt, экспериментальный agent; начинать стоит с командных.
    → Лекция 3
  5. Как matcher и exit-код определяют поведение hook?
    Matcher — фильтр по инструменту или ситуации: Edit|Write, Bash, mcp__github__.*; он чувствителен к регистру. Можно сузить через if, например Bash(rm *). На вход handler получает JSON через stdin. exit 0 пропускает, exit 2 блокирует PreToolUse и передаёт stderr Claude, другой код — ошибка хука. У SessionStart и UserPromptSubmit stdout при exit 0 попадает в контекст сессии.
    → Лекция 3

Лекция 4 — лестница раскатки

  1. Какие признаки делают задачу хорошим кандидатом для hook и с чего начинать?
    Повторяемая ситуация, предсказуемый результат, отсутствие тонкого вкуса и лёгкий откат. Начинать стоит с узких безопасных сценариев: форматирование, мягкий lint/report, напоминание про чувствительный модуль, узкая защита пути, контекст на старте сессии.
    → Лекция 4
  2. Чем non-blocking отличается от blocking и как заблокировать rm?
    Non-blocking пишет лог, форматирует или подсказывает, но не отменяет действие. Blocking запрещает действие; технически это exit 2. Для rm ставят PreToolUse с matcher Bash и if: "Bash(rm *)", скрипт печатает причину в stderr и возвращает 2. Это guardrail от частого случая, а не гарантия: жёсткий запрет — deny-правило в permissions.
    → Лекция 4
  3. Как выглядит базовая лестница раскатки и где место format-on-edit?
    Log-only → non-blocking → narrow blocking. На log-only видно, не слишком ли широк matcher; на non-blocking проверяется польза; только затем появляется право сказать «стоп» в узком случае. Project settings — отдельная верхняя ступень. format-on-edit обычно остаётся на non-blocking: он не должен блокировать действие.
    → Лекция 4
  4. Почему validation и testing hooks — быстрый сигнал, а не CI?
    Ранний сигнал должен быть дешевле ошибки, которую он помогает заметить. Тяжёлая, редкая или шумная проверка на каждом edit съедает темп. Hook первого уровня либо гоняет короткую локальную проверку, либо напоминает, какие targeted checks не забыть; полный CI остаётся в pipeline.
    → Лекция 4
  5. Что делают session hooks?
    SessionStart может вывести последние коммиты или памятку в контекст. UserPromptSubmit ведёт журнал промптов в репозитории. Stop сигналит, что Claude закончил отвечать. Notification сообщает, что Claude ждёт решения. Журнал не должен содержать env-переменные, токены и куски .env.
    → Лекция 4

Лекция 5 — debugging, side effects и recovery

  1. Какие пять вопросов задавать hook, который ведёт себя странно?
    Загружен ли hook (/hooks, scope, битый JSON, claude doctor)? То ли событие (PreToolUse против PostToolUse)? Совпал ли matcher (регистр, инструмент)? Отработал ли handler (exit code, stderr, ручной запуск)? Нет ли side effects (шум, loops, лишний diff, секреты в логе)? Идти по порядку, а не править скрипт наугад.
    → Лекция 5
  2. Почему первая проверка — регистрация, а не handler?
    Иначе можно полчаса чинить команду, которой в сессии нет. /hooks показывает активные хуки и источник; битый JSON, неверный scope и неперечитанный конфиг — частые причины «тишины». Claude Code может показать Settings Error, а claude doctor показывает, что отброшено.
    → Лекция 5
  3. Как читать handler как обычную команду?
    exit 0 — успех, exit 2 — блокирующий ответ для PreToolUse, другой код — ошибка handler. stdout/stderr должны быть аккуратными: шум загрязняет лог и контекст. Частые механические причины: quoting, неисполняемый файл, timeout, отсутствующий jq, неверный путь. Ручной запуск с тестовым JSON быстро снимает мистику.
    → Лекция 5
  4. Какие side effects делают формально работающий hook вредным?
    Шум, который перестают замечать; лишние изменения файлов и огромный diff; loops, когда after-edit снова вызывает edit; скрытие исходной ошибки; утечка env-переменных, токенов или кусков файлов в лог. От loops спасают узкий matcher и ранний guard в handler.
    → Лекция 5
  5. Как устроен recovery path и что показал разбор format-on-edit?
    Сначала quick disable: убрать блок из settings, "disableAllHooks": true или claude --settings '{"disableAllHooks": true}'. Затем staged rollback: откат на ступень ниже, сужение matcher, guard, запись в CHANGELOG. В разборе format-on-edit matcher расползся до frontend/src/**/*, hook трогал generated-файлы; фикс — вернуть ts/tsx, добавить ранний выход для *.generated.* и проверить оба случая.
    → Лекция 5
