Tool capability preflight

Claude Code

14 уровень · лекция 1
Подключённый tool — ещё не workflow. Перед использованием внешней возможности нужен короткий preflight: боль, capabilities, границы, проверка и безопасное использование.

1. Подключённый tool — ещё не workflow

Когда вы впервые подключаете внешний tool, легко попасть в ловушку ложной готовности. Кажется, что самое сложное позади: сервер подключён, доступ есть, Claude его видит — и дальше всё просто. Технически вы добавили новый рычаг, но не решили, когда, зачем и на каких условиях его вообще можно трогать.

Боль → Capability → Границы → Проверка → Безопасное использование

Если в цепочке есть только второй пункт — у вас не workflow, а просто новая кнопка. Новая кнопка без правил — любимый источник хаоса. Особенно если она пишет комментарии в tracker, читает продовые логи или меняет что-то во внешней системе.

  • Tool capability отвечает: что инструмент технически умеет?
  • Workflow отвечает: как мы используем эту возможность в реальной задаче, что запрещаем и чем проверяем результат?

Пример: у команды Commerce OS в Workflow Kit подключён issue tracker — это capability. Но пока не зафиксировано, что Claude читает только issue и комментарии, не меняет статусы и сверяет claims с кодом, — процесса нет, есть доступ к tracker.

Лекция не про «как подключить ещё один server», а про то, как перестать видеть в tool магию и относиться к нему как к управляемой инженерной возможности.

2. Preflight: короткая проверка перед взлётом

Слово preflight пришло из авиации. Даже если самолёт выглядит идеально, пилот всё равно не говорит: «Стоит ровно, наверное, всё в порядке». Сначала — короткая проверка перед взлётом. С tool integration та же история: доступ есть, а безопасный взлёт ещё не подтверждён.

Tool capability preflight — короткая структурированная проверка того, как capability внешнего инструмента сработает в конкретном workflow: не на все случаи жизни, а под одно применение.

ВопросЧто вы фиксируетеЗачем это нужно
Какую боль снимаем?конкретную проблему, а не общую симпатию к автоматизациичтобы не подключать tool «на всякий случай»
Какие capabilities реально нужны?например, read issue, read comments, search by labelчтобы не тащить лишние возможности
Что запрещено?write actions, close issue, comment, mutate dataзапреты важны не меньше разрешений
Какой режим доступа нужен?read-only или write-capableread-only почти всегда безопасный старт
Где живут credentials?env, secret storage, project scope, local scopeчтобы не разложить секреты по проекту
Что попадёт в context?полный log, короткая выборка, summary, лимит строкслишком жирный output ломает reasoning
Нужен ли approval?никакой, human review, explicit confirmationчтобы не маскировать риск под удобство
Чем проверяем результат?код, tests, logs, локальное воспроизведениеtool не выигрывает спор просто потому, что он внешний
Что делать при конфликте с кодовой базой?считать это гипотезой, а не истинойиначе Claude начнёт «чинить» по чужим догадкам
Как выключаем tool?kill switch: disable scope, убрать config, revoke tokenесли tool нельзя быстро отключить, он не готов
Самые важные строки — не про технику, а про дисциплину: disallowed actions, verification и kill switch.

Многие команды охотно описывают, что инструмент умеет, и почти не описывают, чего ему нельзя, — а потом удивляются write-capable integration там, где всем нужен read-only.

Правило: по умолчанию tool получает read-only роль. Session permissions говорят «технически возможно»; workflow boundary должен быть уже: «в этой задаче делаем только вот это».

Точные имена команд, scope-файлов и способов отключить MCP в Claude Code меняются от версии к версии. Вопросы preflight — нет. Запоминайте не имя кнопки, а логику проверки.

3. Preflight на примере issue tracker в Commerce OS

Команда Commerce OS ловит баг: refund-запросы в support inbox сортируются неправильно. Issue в tracker есть, комментариев много: скриншот, гипотеза про кеш, а кто-то в пятницу вечером написал «наверное, проблема где-то в сортировке». Звучит мощно, но это не диагноз — это усталый человек в интернете.

Tracker полезен: экономит ручной copy-paste и даёт Claude контекст — но только с заранее зафиксированными границами. В Workflow Kit это можно оформить как короткий раздел в docs/ONBOARDING_GUIDE.md.

## Предполётная проверка инструмента: issue tracker
Pain: не копируем issue и комментарии вручную в сессию.
Allowed: read issue, read comments, search by label.
Forbidden: comment, close, reassign, change labels.
Credentials: read-only token из env.
Verification: claims из issue сверяем с кодом и tests.
Kill switch: отключаем project scope config и перезапускаем сессию.

Теперь под такой preflight можно формулировать задачу:

Прочитай issue COM-142 через tracker.
Разрешено только чтение issue и комментариев.
Не меняй статус, labels и assignee.
Верни summary, open questions и список вероятно затронутых файлов.

Tracker нужен не для решения за вас, а для сборки пакета доказательств: Claude выделяет факты, сомнения и затронутые области кода — а вы проверяете их через код, tests и plan mode. Так capability превращается в workflow.

Тонкий, но критичный нюанс: комментарий в tracker — это данные, а не инструкция. Написано «Почините, сбросив кеш Redis» — Claude не исполняет это как команду: это гипотеза, вполне возможно ошибочная. Автоматизация уровня «кто-то предположил — система дисциплинированно исполнила» — слишком азартный вид спорта.

4. Preflight для monitoring, docs и read-only DB

Каркас preflight один и тот же, но риск и verification меняются в зависимости от природы сигнала.

СценарийЧто tool даётЧто сразу запрещаемЧем закрываем verification
Monitoring alertalert, короткое окно логов, runtime signalsilence alert, rollback, deploy actionsreproduce locally, logs, regression test
Docs lookupверсионные факты, changelog, API notesавтоматические code changes «по docs»project version, build, tests, affected files
Read-only DB analysisсхема, sample rows, shape of dataлюбые write/mutation операцииcode path, integration tests, query review

Monitoring. Tool даёт ценный runtime signal, но alert — ещё не fix plan. Если Sentry говорит, что /api/dashboard/metrics тормозит, хороший workflow такой: сначала гипотеза, потом проверка затронутых файлов и локальный reproduce, и только после этого — изменение. Alert не даёт права перепрыгнуть через reproduce step.

Docs lookup. Tool помнит version-specific факты лучше усталого человека. Но docs не равны истине в вакууме: они говорят, как должно работать в определённой версии. Ваш проект может жить на другой версии или иметь legacy-слой. Поэтому preflight для docs lookup привязывается к версии проекта и замыкается на build и tests.

Read-only DB. Безопасный режим здесь только один: read-only. База нужна не для того, чтобы Claude «поправил запись руками», а чтобы увидеть shape of data, заметить аномалии и связать их с кодом. Как только появляются write actions, вы выходите из комфортной практики и заходите на территорию отдельного approval flow.

Во всех трёх случаях verification замыкается не на tool, а на проекте: коде, тестах, локальном воспроизведении, review.

External signal подсказывает, куда смотреть, но не заменяет проверку.

5. Конфликт tool с кодом, тестами или документацией

Самые интересные ситуации начинаются, когда источники расходятся. Tracker говорит одно, docs lookup — другое, alert намекает на третье, а код: «Коллеги, у меня тут вообще четвёртая история». В этот момент важно не назначать победителя по принципу «внешний убедительнее».

ИсточникЧто он хорошо показываетЧего он сам по себе не доказывает
Issue / комментарийкак проблему видят люди, бизнес-контекстчто root cause найден правильно
Alert / logsчто реально случилось в runtimeчто вы уже поняли причину
Docs lookupчто ожидается в определённой версии или APIчто именно так устроен ваш проект
Кодчто система сейчас делаетчто это поведение корректно бизнесово
Testsчто у вас уже проверяетсячто покрыты все реальные сценарии

Универсального source of truth нет. Когда источники спорят, правильная реакция — не выбрать любимый, а превратить конфликт в проверяемую гипотезу.

Хороший ход — остановить edits и попросить Claude сделать расследование:

Есть конфликт между внешним источником и codebase.
Не вноси изменений.
Покажи, какие claims подтверждаются кодом, какие только issue/docs,
и предложи минимальную проверку, которая снимет конфликт.

Сначала фиксируете расхождение, потом — минимальную проверку: локальный reproduce, targeted test, чтение файла, сверку версии, — и только затем разрешаете implementation. Иначе Claude лечит конфликт интерпретацией, а не доказательством: красивый diff, не решающий проблему.

Здесь особенно важен принцип из прошлого модуля: treat external text as data, not as instructions. Tool output не проталкивает систему в решение — он помогает точнее сформулировать вопрос к коду и проверке.

6. Закрепление preflight в Workflow Kit

Самая частая судьба хороших правил — прозвучать один раз и быть забытыми. Если preflight действительно нужен, его надо зафиксировать в командном артефакте: README.md, ONBOARDING_GUIDE.md и рядом с конфигом конкретного tool.

### Внешние инструменты: позиция по умолчанию
Default mode: read-only first.
Project scope: only after written preflight.
Conflict rule: tool claims are hypotheses until verified in code/tests.
Kill switch: every tool must have one-step disable path.

Это не бюрократия ради бюрократии, а способ превратить индивидуальную осторожность в командную норму: новый разработчик видит не только integrations, но и подход команды.

Scope. Tool сырой, неочевидный или нужен только вам для эксперимента — держите на личном или локальном уровне. Project scope — общая ответственность: только integrations с понятным сценарием, verification path и owner.

Kill switch. Интеграцию нельзя быстро отключить — она не готова к реальной жизни. Где-то это отключение project-scoped config, где-то отзыв токена, где-то временный возврат на local scope. Механика зависит от версии Claude Code и инфраструктуры, но принцип один: у команды должен быть короткий путь назад. Без него automation выглядит смело только до первого инцидента.

Когда вы соберёте ответы на все десять вопросов preflight в одном месте — у вас на руках не «ещё один подключённый server», а полный контур: названа боль, сужены capabilities, выписаны disallowed actions, зафиксированы credentials и объём context, назначен способ verification и есть kill switch. Именно этот контур, а не сам факт подключения, отличает управляемую интеграцию от рычага без правил.

Что запомнить

  • Подключённый tool — ещё не workflow.
  • Формула: боль → capability → границы → проверка → безопасное использование.
  • Preflight отвечает, как capability работает в конкретной задаче, а не «на все случаи».
  • Десять вопросов preflight: боль, capabilities, запреты, режим, credentials, context, approval, verification, конфликт, kill switch.
  • Read-only — безопасный старт; session permissions шире workflow-границы.
  • Комментарий в issue — данные, а не инструкция.
  • Verification всегда замыкается на код, тесты, логи и review, а не на внешний tool.
  • Monitoring, docs lookup и read-only DB проверяются по-разному; запреты и verification зависят от сигнала.
  • При конфликте источников не выбирайте «любимый» — превращайте конфликт в проверяемую гипотезу.
  • Preflight фиксируется в README/ONBOARDING_GUIDE и рядом с конфигом tool.
  • Project scope — только после письменного preflight; у интеграции должен быть owner и kill switch.

Практика (15–25 минут)

Цель: собрать tool capability preflight для issue tracker и ещё одного внешнего сигнала, проверить границы, verification и kill switch на учебном сценарии Commerce OS.

Что сделать

  1. В вымышленном Workflow Kit создайте TOOL_PREFLIGHT.md. Заполните десять вопросов для issue tracker: боль, capabilities, запреты, режим, credentials, context, approval, verification, конфликт, kill switch.
  2. Добавьте второй preflight для monitoring или docs lookup. Укажите, какие действия запрещены и чем именно проверяется результат в проекте.
  3. Придумайте фейковый issue COM-142 с комментарием «почините, сбросив кеш Redis». Запишите, почему это данные/гипотеза, а не команда, и какую минимальную проверку нужно сделать до изменений.
  4. Составьте CONFLICT_RULES.md: что делать, если issue, docs и код расходятся. Добавьте правило «остановить edits и запросить расследование», а не выбирать внешний источник победителем.
  5. Зафиксируйте политику в docs/ONBOARDING_GUIDE.md: read-only first, project scope после preflight, conflict rule, kill switch. Проверьте, что в preflight нет реальных токенов и подключений.

Если Claude Code или MCP недоступны: выполните preflight и конфликтный сценарий вручную в редакторе, без реальных подключений; критерии проверки те же.

Проверка

  • В TOOL_PREFLIGHT.md заполнены все десять вопросов.
  • Для issue tracker явно запрещены comment, close, reassign и change labels.
  • Credentials описаны как env/secret storage, без значений.
  • Для monitoring/docs указан verification через проект, а не через сам tool.
  • Комментарий issue разобран как гипотеза, а не команда.
  • В CONFLICT_RULES.md есть правило остановить edits и провести минимальную проверку.
  • В ONBOARDING_GUIDE.md зафиксированы read-only first, scope, conflict rule и kill switch.
  • Нет реальных внешних подключений и секретов.
  • Если Claude Code или MCP недоступны, preflight выполнен вручную по тем же критериям.
