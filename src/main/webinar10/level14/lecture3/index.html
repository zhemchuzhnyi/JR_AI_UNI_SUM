Hooks

Claude Code

14 уровень · лекция 3
Hook — не ещё один tool, а автоматика внутри Claude Code: когда произошло событие и совпало условие, выполнить одну понятную команду. Формула: event + matcher + handler. И срабатывает это независимо от решения модели.

1. Hooks — отдельный слой, а не «ещё один tool»

Когда внешний tool уже прошёл preflight, а его claims всё равно замыкаются на код, tests и review, появляется следующий вопрос: что внутри самого Claude Code повторяется так часто, что пора автоматизировать? Отсюда и растут hooks.

Когда вы впервые слышите про hooks, легко принять их за ещё одну интеграцию. Но hook отвечает на другой вопрос. Tool, MCP или plugin capability — это про «откуда взять данные или куда сходить». Hook — про «что автоматически сделать, когда внутри Claude Code произошло определённое событие».

  • MCP — дверь наружу: issue tracker, мониторинг, документация, база, браузер.
  • Hook — автоматика внутри дома.

Дверь не решает, когда включить свет в коридоре, — решает датчик движения. Hook не нужен, чтобы «получить данные из Jira». Он нужен, чтобы после редактирования файла прогнать форматтер, перед записью в защищённый путь остановить действие или в начале сессии напомнить правила проекта.

У hooks есть важное свойство, которого нет у обычной инструкции: hook срабатывает независимо от решения модели. Инструкцию в CLAUDE.md модель может забыть, проигнорировать или понять слишком широко. Hook — это автоматика поверх модели, а не пожелание ей. Поэтому у hook и цена соответствующая: ошибка в нём срабатывает так же независимо.

Hooks почти никогда не стоят в центре архитектуры. Они не заменяют task spec, human review и tests — убирают рутинные микро-действия, которые вы и так делаете снова и снова. Пытается «думать вместо вас» — тревожный сигнал. Помогает не забыть простое, повторяемое, проверяемое действие — его территория.

В Workflow Kit это хорошо видно. Hook формата не знает бизнес-логики Commerce OS — что такое заказ, возврат или MRR. Он автоматизирует одну привычку: изменил Claude код в нужной зоне — сразу прогони formatter. Скромно, полезно, без драматургии.

2. Событие → условие → действие

Термин event-driven automation звучит строго, а суть простая: вы не запускаете команду вручную каждый раз, а система сама реагирует на событие. Не «я вспомнил и запустил formatter», а «произошло событие — formatter вызвался сам». Не «шаг 1, потом шаг 2», а «случилось X — проверь Y и выполни Z».

Бытовая аналогия — датчик движения в подъезде. Шаги — event. Условие «только когда темно» — matcher. Включить лампу — handler. Движения нет — лампа молчит. Движение днём — фильтр не пропустил, лампа молчит. Движение ночью — фильтр подошёл, лампа зажглась. Hook устроен так же, только вместо коридора — lifecycle инструментов, файлов и сессий.

Внутри Claude Code произошло событие
  → matcher подходит?
      → нет: hook молчит
      → да: запускается handler
          → полезное действие: форматирование, блокировка, запись в журнал

Hook не существует сам по себе. Пока событие не случилось, он спит — не «периодически умничает», а ждёт момента. Поэтому hooks хороши для событийной механики вокруг workflow: перед инструментом, после редактирования, в начале или конце сессии. Для длинных рассуждений, анализа кодовой базы и сложных решений нужны другие механизмы.

Hook = событие + условие + действие.

3. Состав hook: event, matcher, handler

Важно научиться читать hook как маленький контракт из трёх частей, а не «JSON, который иногда запускается».

ЧастьГлавный вопросЧто означает
eventКогда?в какой момент lifecycle Claude Code стоит реагировать
matcherПри каком условии?как сузить срабатывание до нужных инструментов, путей или ситуаций
handler / commandЧто сделать?какую команду или скрипт реально выполнить

Hook регистрируется не в отдельном «файле хука», а в settings-файлах Claude Code, в знакомом объекте hooks. Скрипты-обработчики при этом удобно держать рядом, в .claude/hooks/.

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}

Читается как предложение: после инструмента правки файлов — выполни команду. jq достаёт из JSON путь изменённого файла и передаёт его prettier.

Scope работает так же, как у других settings:

  • ~/.claude/settings.json — ваши хуки;
  • .claude/settings.json — хуки проекта;
  • .claude/settings.local.json — личные хуки этого проекта, не для команды.

То есть hook — командный артефакт: чужой блокирующий хук виден в diff до того, как начнёт мешать.

Хуки умеют приезжать и с plugin, и в frontmatter конкретного skill или агента. У агента они работают, пока он работает, а хук из skill после первого вызова остаётся до конца сессии (once: true снимает его после первого срабатывания). Это та же логика доставки, что у плагинов.

Не путайте hook с уже знакомыми сущностями. Skill вы вызываете как повторяемую процедуру — вручную или по trigger. Agent получает роль и отдельный контекст. Hook ничего не исследует и не планирует — срабатывает, когда совпал шаблон. Это его сила и его предел. Тянет засунуть в hook пол-оркестра сложных шагов — инструмент выбран не тот.

Точные имена событий, синтаксис matcher и структура конфига могут немного меняться между версиями Claude Code. Держимся модели из трёх частей, а не «этот ключ называется только так». Актуальный синтаксис сверяете через /hooks и текущую справку.

4. Карта событий: три группы

Событий больше трёх десятков, заучивать список не нужно. Держите карту из трёх групп — почти все полезные хуки попадают в одну из них.

ГруппаСобытияЗачем
до действияPreToolUseединственная точка, где действие можно остановить до выполнения: защита путей, блок опасных команд
после действияPostToolUseреакция на уже случившееся: формат, быстрая проверка, запись в лог
жизнь сессииSessionStart, UserPromptSubmit, Stop, Notificationстарт сессии, ваш промпт, Claude закончил отвечать, Claude ждёт вас

PreToolUse — «вахтёр на входе». Полезен там, где важно не забыть про границы. Вы не хотите, чтобы Claude автоматически удалял файлы или редактировал .env или что-то под payments/. Тогда before-hook может увидеть попытку и вовремя остановить. Это не про удобство, а про защитный контур.

PostToolUse — реакция после действия. Если Claude уже изменил файл, здесь уместны форматирование, запуск лёгкой проверки или короткое сообщение в лог. Сюда обычно попадает базовый format-on-edit hook. Он никого не останавливает и не спорит о смысле жизни — просто делает маленькую рутинную вещь сразу после правки.

Session lifecycle часто недооценивается. Иногда полезнее не блокировать и не форматировать, а в начале сессии показать последние коммиты, записать промпт в журнал или вернуть вас к терминалу звуком, когда Claude закончил. Мелочь, но из таких мелочей складывается командная дисциплина.

Все эти группы описывают внутреннюю жизнь Claude Code, а не внешний мир. Hook не про «в Jira появился новый тикет». Hook про «внутри текущей работы наступил момент, на который стоит автоматически отреагировать».

Кроме командных хуков бывают "type": "http" (отправить событие POST-запросом на URL) и "type": "mcp_tool" (вызвать инструмент уже подключённого MCP-сервера), а также "type": "prompt" и экспериментальный "type": "agent" — в последних двух решение принимает не скрипт, а модель. Это продвинутый слой: сначала научитесь жить с обычными командными.

5. matcher: точность вместо навязчивости

Event отвечает за момент, matcher — за точность. Именно здесь чаще всего начинаются педагогические приключения. Новички любят написать «на все инструменты» или «на все файлы», а потом удивляться, что автоматизация срабатывает чаще, чем уведомления от банковского приложения. Проблема не в hook, а в слишком широком matcher.

Matcher — фильтр. Для событий-инструментов это имя инструмента; можно несколько имён и регулярное выражение:

  • Edit|Write — только правки файлов;
  • Bash — только команды терминала;
  • mcp__github__.* — все инструменты MCP-сервера github;
  • пустая строка — на каждое срабатывание события. Иногда нужно, чаще — шум.

Matcher чувствителен к регистру: edit не совпадёт с Edit — вторая по популярности причина «хук молчит».

У событий жизни сессии matcher свой: SessionStart матчится по тому, как сессия началась — startup, resume, clear, compact, fork, а Notification — по типу уведомления.

Можно сузить ещё сильнее — полем if у самого хука, в синтаксисе permission-правил:

{ "matcher": "Bash", "if": "Bash(rm *)" }

Тогда скрипт стартует только на rm, а на остальные Bash-команды даже не запускается.

Сравните:

  • «После любого изменения любого файла запускай formatter».
  • «После изменения файлов в src/, если это ts или tsx, запускай formatter».

Вторая мысль скучнее. Скучные мысли в автоматизации, как правило, безопаснее. Даже если matcher выбирает инструмент, путь можно проверить внутри handler или через if, но не стоит ставить одну гигантскую ловушку на всё подряд.

Правило: matcher узкий настолько, насколько разумно. Шумный hook быстро приучает команду его игнорировать.

Hook, которому перестали доверять, фактически уже мёртв — просто ещё лежит в репозитории.

6. handler: exit-код и граница между конфигом и действием

После event и matcher остаётся самая земная часть — handler. Он отвечает: что конкретно выполнить, когда всё совпало. Handler — не тайный интеллект, не скрытый subagent и не маленький оркестр. Чаще всего это просто команда или скрипт.

Hook и Claude Code разговаривают на языке терминала. На вход скрипт получает JSON события через stdin:

{
  "hook_event_name": "PreToolUse",
  "tool_name": "Bash",
  "tool_input": { "command": "npm test" },
  "cwd": "/home/dev/project"
}

На выход — код завершения:

  • exit 0 — хук не возражает, действие идёт дальше;
  • exit 2 — блокирующий ответ: PreToolUse отменяет действие, а всё, что скрипт написал в stderr, уходит Claude как объяснение;
  • любой другой код — ошибка самого хука: покажется в transcript, но ничего не заблокирует.
Блокирует именно 2, не «любой ненулевой». Это частый источник хуков, которые «вроде блокируют, но нет».

Иногда handler совсем небольшой: вызвать formatter на файле. Иногда — shell-скрипт, который печатает напоминание. Иногда — guard-скрипт, который проверяет путь и завершается с нужным статусом. Смысл один: hook нашёл ситуацию, handler сделал одну понятную вещь.

Особенность session-событий: всё, что SessionStart или UserPromptSubmit печатают в stdout при exit 0, попадает прямо в контекст сессии. Так можно передать Claude последние коммиты или памятку проекта. Для остальных событий stdout — это в основном лог.

Две практические границы:

  • handler должен быть предсказуемым; гигантская цепочка команд на двадцать секунд после каждого edit быстро надоест;
  • handler должен быть узко полезным; если он похож на мини-платформу с пятью ветками поведения, логами и эвристиками, это уже не hook-задача, а отдельный script/tool/skill.

7. Первый hook в Workflow Kit

В Claude Workflow Kit for Team hooks — обычные записи в .claude/settings.json, а скрипты — в .claude/hooks/. Команда поддерживает их так же, как CLAUDE.md, skills и agents. Hook — процессный артефакт, а не «магия внутри Commerce OS».

Первый пример — format-on-edit:

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}

Читается как предложение: после редактирования файла запусти formatter по конкретному пути. Если jq в системе нет — поставьте: его отсутствие — частая причина молчащих хуков.

Второй — защита чувствительных зон:

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "\"${CLAUDE_PROJECT_DIR}\"/.claude/hooks/guard-protected-paths.sh"
          }
        ]
      }
    ]
  }
}

Скрипт получает JSON события, проверяет путь и при попытке записи в payments/ или .env* пишет причину в stderr и завершается с exit 2. Event — «перед изменением файла». Matcher — «только инструменты Edit и Write». Handler — «вызови защитный скрипт». Hook не делает проект умнее, он делает проект спокойнее.

Третий — баннер в начале сессии:

{
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          { "type": "command", "command": "git log --oneline -5" }
        ]
      }
    ]
  }
}

Claude начинает сессию, уже видя последние пять коммитов. Не надо пересказывать, где вы остановились.

Один hook помогает с чистотой кода. Второй — с безопасностью. Третий — с дисциплиной начала работы. Все три устроены одинаково и читаются как договорённость команды:

Когда произошло это, и только если совпало вот это условие, нужно автоматически сделать вот это действие.

Event отвечает «когда», matcher — «при каком условии», handler — «что сделать». Собранные вместе, они дают первый осмысленный hook в Workflow Kit. А какие задачи доверять hook, а какие он только испортит, и как раскатывать его по шагам — тема следующей лекции.

Что запомнить

  • Hook — отдельный слой автоматики внутри Claude Code, а не ещё один tool/MCP.
  • MCP — дверь наружу, hook — автоматика внутри дома.
  • Hook срабатывает независимо от решения модели; CLAUDE.md модель может забыть, hook — нет.
  • Формула: hook = событие + условие + действие.
  • Три части контракта: event — когда, matcher — при каком условии, command/handler — что сделать.
  • Hooks живут в settings-файлах, а скрипты удобно держать в .claude/hooks/.
  • Три группы событий: PreToolUse, PostToolUse, session lifecycle (SessionStart, UserPromptSubmit, Stop, Notification).
  • PreToolUse — защитный контур; PostToolUse — реакция после действия; session hooks — дисциплина, память и сигналы.
  • Matcher чувствителен к регистру; Edit|Write, Bash, mcp__github__.* — примеры узких фильтров.
  • Блокирует exit 2; exit 0 пропускает, другие коды — ошибка хука.
  • SessionStart и UserPromptSubmit могут передать stdout в контекст сессии.
  • Handler — команда или скрипт, а не скрытый интеллект и не мини-платформа.
  • Hook не заменяет task spec, human review и tests.
  • Если hook стал сложным оркестром или ему перестали доверять — инструмент выбран не тот.

Практика (15–25 минут)

Цель: спроектировать два hook-контракта для Workflow Kit в реальном формате settings.json, проверить узость matcher, поведение handler и безопасный путь отключения.

Что сделать

  1. В вымышленном Workflow Kit создайте HOOK_CONTRACTS.md и settings.fragment.json. Опишите два hook: format-on-edit для src/**/*.ts(x) и guard для payments/ и .env*.
  2. Для каждого заполните три части: event, matcher, command. Используйте реальные события PostToolUse и PreToolUse, а не выдуманные имена.
  3. Зарегистрируйте оба hook в settings.fragment.json по схеме hooks → event → matcher → hooks → type/command. Скрипты не создавайте боевыми: достаточно путей и комментария, что они делают.
  4. Для guard опишите exit-контракт: что печатается в stderr, когда возвращается exit 2, и почему exit 1 не блокирует. Для format-on-edit проверьте команду на тестовом JSON через jq.
  5. Добавьте в HOOK_CONTRACTS.md путь отключения: как убрать блок из settings и как временно выключить все hooks. Проверьте, что нет реальных опасных команд и секретов.

Если Claude Code недоступен: выполните контракты и проверку вручную в редакторе; критерии проверки те же.

Проверка

  • В HOOK_CONTRACTS.md есть два hook-контракта.
  • У каждого явно указаны event, matcher, command.
  • Использованы реальные события PostToolUse и PreToolUse.
  • Format-on-edit ограничен src/ и нужными расширениями, а не всеми файлами.
  • Guard ограничен чувствительными путями.
  • В settings.fragment.json корректная вложенность hooks → event → matcher → hooks.
  • Описано, что блокирует именно exit 2, а причина уходит в stderr.
  • Есть путь быстрого отключения.
  • Нет реальных опасных команд и секретов.
  • Если Claude Code недоступен, контракты и проверка выполнены вручную по тем же критериям.
