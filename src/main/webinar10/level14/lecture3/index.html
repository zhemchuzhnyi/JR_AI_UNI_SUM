Hooks

Claude Code

14 уровень · лекция 3
Hook — не ещё один tool, а автоматика внутри Claude Code: когда произошло событие и совпало условие, выполнить одно понятное действие. Формула: event + matcher + handler.

1. Hooks — отдельный слой, а не «ещё один tool»

Когда внешний tool уже прошёл preflight, а его claims всё равно замыкаются на код, tests и review, появляется следующий вопрос: что внутри самого Claude Code повторяется так часто, что пора автоматизировать? Отсюда и растут hooks.

Когда вы впервые слышите про hooks, легко принять их за ещё одну интеграцию. Но hook отвечает на другой вопрос. Tool, MCP или plugin capability — это про «откуда взять данные или куда сходить». Hook — про «что автоматически сделать, когда внутри Claude Code произошло определённое событие».

  • MCP — дверь наружу: issue tracker, мониторинг, документация, база, браузер.
  • Hook — датчик и автоматика внутри дома.

Дверь не решает, когда включить свет в коридоре, — решает датчик движения. Hook не нужен, чтобы «получить данные из Jira». Он нужен, чтобы после редактирования файла прогнать форматтер, перед записью в защищённый путь остановить действие или в начале сессии напомнить правила проекта.

Hooks почти никогда не стоят в центре архитектуры. Они не заменяют task spec, human review и tests — убирают рутинные микро-действия, которые вы и так делаете снова и снова. Пытается «думать вместо вас» — тревожный сигнал. Помогает не забыть простое, повторяемое, проверяемое действие — его территория.

В Workflow Kit это хорошо видно. Файл вроде .claude/hooks/format-on-edit.json не знает бизнес-логики Commerce OS — что такое заказ, возврат или MRR. Он автоматизирует одну привычку: изменил Claude код в нужной зоне — сразу прогони formatter. Скромно, полезно, без драматургии.

2. Событие → условие → действие

Термин event-driven automation звучит строго, а суть простая: вы не запускаете команду вручную каждый раз, а система сама реагирует на событие. Не «я вспомнил и запустил formatter», а «произошло событие — formatter вызвался сам». Не «шаг 1, потом шаг 2», а «случилось X — проверь Y и выполни Z».

Бытовая аналогия — датчик движения в коридоре. Движение — event. Условие «только ночью» — matcher. Включить лампу — handler. Движения нет — лампа молчит. Движение днём — фильтр не пропустил, лампа молчит. Движение ночью — фильтр подошёл, лампа зажглась. Hook устроен так же, только вместо коридора — lifecycle инструментов, файлов и сессий.

Внутри Claude Code произошло событие
  → matcher подходит?
      → нет: hook молчит
      → да: запускается handler
          → полезное действие: форматирование, блокировка, напоминание

Hook не существует сам по себе. Пока событие не случилось, он спит — не «периодически умничает», а ждёт момента. Поэтому hooks хороши для событийной механики вокруг workflow: перед инструментом, после редактирования, в начале или конце сессии. Для длинных рассуждений, анализа кодовой базы и сложных решений нужны другие механизмы.

Hook = событие + условие + действие.

3. Состав hook: event, matcher, handler

Важно научиться читать hook как маленький контракт из трёх частей, а не «JSON, который иногда запускается».

ЧастьГлавный вопросЧто означает
eventКогда?в какой момент lifecycle Claude Code стоит реагировать
matcherПри каком условии?как сузить срабатывание до нужных путей, инструментов или ситуаций
handlerЧто сделать?какую команду или скрипт реально выполнить

Не путайте hook с уже знакомыми сущностями. Skill вы вызываете как повторяемую процедуру — вручную или по trigger. Agent получает роль и отдельный контекст. Hook ничего не исследует и не планирует — срабатывает, когда совпал шаблон. Это его сила и его предел. Тянет засунуть в hook пол-оркестра сложных шагов — инструмент выбран не тот.

Точные имена событий, синтаксис matcher и структура конфига могут немного меняться между версиями Claude Code. Держимся модели из трёх частей, а не «этот ключ называется только так». Актуальный синтаксис сверяете через /hooks и текущую справку.

4. Три группы event

Полный список событий конкретной версии смотрится в инструменте, а заучивать его наизусть — романтика уровня ручной правки XML в пятницу вечером. Но карту в голове держать стоит: почти все полезные hooks укладываются в три группы.

Группа событийЧто означает по-человеческиТипичные сценарии
Before tool useсработать до опасного или важного действиязаблокировать запись в защищённый путь, попросить подтверждение, не дать выполнить рискованную команду
After tool use / file changesсработать после действия или изменения файлаформатирование, короткий отчёт, запуск локальной проверки, напоминание
Session lifecycleсработать на этапах жизни сессиипоказать баннер в начале, сохранить состояние, отправить уведомление, загрузить полезный контекст

Before tool use — «вахтёр на входе». Полезен там, где важно не забыть про границы. Например, вы не хотите, чтобы Claude автоматически редактировал .env или что-то под payments/. Тогда before-hook может увидеть попытку записи и вовремя остановить. Это не про удобство, а про защитный контур.

After tool use — реакция после действия. Если Claude уже изменил файл, здесь уместны форматирование, запуск лёгкой проверки или короткое сообщение в лог. Сюда обычно попадает базовый format-on-edit hook. Он никого не останавливает и не спорит о смысле жизни — просто делает маленькую рутинную вещь сразу после правки.

Session lifecycle часто недооценивается. Иногда полезнее не блокировать и не форматировать, а в начале сессии напомнить правила проекта: «Проверьте git status», «Не трогайте payments/ без отдельного плана», «Используйте только approved commands». Мелочь, но из таких мелочей складывается командная дисциплина.

Все эти группы описывают внутреннюю жизнь Claude Code, а не внешний мир. Hook не про «в Jira появился новый тикет». Hook про «внутри текущей работы наступил момент, на который стоит автоматически отреагировать».

5. matcher: точность вместо навязчивости

Event отвечает за момент, matcher — за точность. Именно здесь чаще всего начинаются педагогические приключения. Новички любят написать «на все файлы» или «на все команды», а потом удивляться, что автоматизация срабатывает чаще, чем уведомления от банковского приложения. Проблема не в hook, а в слишком широком matcher.

Matcher — фильтр. Он отвечает: в каких именно обстоятельствах после события нужно запускать обработчик. Фильтр может смотреть на путь к файлу, тип инструмента, шаблон команды, иногда — на дополнительные признаки контекста. Важнее не список возможностей, а принцип: matcher должен быть узким настолько, насколько разумно.

Сравните:

  • «После любого изменения любого файла запускай formatter».
  • «После изменения файлов в src/, если это ts или tsx, запускай formatter».

Вторая мысль скучнее. Скучные мысли в автоматизации, как правило, безопаснее.

Схематический пример matcher для форматирования:

{
  "event": "afterFileEdit",
  "matcher": { "paths": ["src/**/*.ts", "src/**/*.tsx"] },
  "handler": { "command": "prettier --write {{file}}" }
}

Hook не трогает конфиги, markdown, shell-скрипты и чужие директории. Он реагирует только на зону, ради которой был задуман.

Защита чувствительных путей:

{
  "event": "beforeToolUse",
  "matcher": { "tool": "Write", "paths": ["**/payments/**", "**/.env*"] },
  "handler": { "command": "scripts/block-protected-write.sh" }
}

Такой фильтр работает как охранник на нужной двери. Не мешает редактировать обычный код, но не даёт бездумно лезть в опасные зоны. Хорошая привычка для Workflow Kit: не ставить одну гигантскую ловушку на всё подряд, а делать точечные рамки там, где blast radius действительно велик.

Если сомневаетесь, делайте matcher уже, а не шире. Шумный hook быстро приучает команду его игнорировать.

Hook, которому перестали доверять, фактически уже мёртв — просто ещё лежит в репозитории.

6. handler: граница между конфигом и действием

После event и matcher остаётся самая земная часть — handler. Он отвечает: что конкретно выполнить, когда всё совпало. Handler — не тайный интеллект, не скрытый subagent и не маленький оркестр. Чаще всего это просто команда или скрипт.

Иногда handler совсем небольшой: вызвать formatter на файле. Иногда — shell-скрипт, который печатает напоминание. Иногда — guard-скрипт, который проверяет путь и завершает выполнение с нужным статусом. Смысл один: hook нашёл ситуацию, handler сделал одну понятную вещь.

Например, handler на уровне сессии:

#!/usr/bin/env bash
echo "Проверьте git status и scope задачи"
echo "Не трогайте payments/ без отдельного плана"

Да, это полноценный handler. Никакого волшебства. Просто маленький скрипт, который помогает не забыть контекст в начале работы.

Две практические границы:

  • handler должен быть предсказуемым; гигантская цепочка команд на двадцать секунд после каждого edit быстро надоест;
  • handler должен быть узко полезным; если он похож на мини-платформу с пятью ветками поведения, логами и эвристиками, это уже не hook-задача, а отдельный script/tool/skill.

Handler обычно получает часть контекста события: путь к файлу, имя инструмента или другой payload. Глубоко в технические детали передачи значений не уходим; на уровне модели достаточно понимать: hook знает, что произошло, и может передать обработчику данные, чтобы тот сработал на конкретном файле или действии.

7. Первый hook в Workflow Kit

В Claude Workflow Kit for Team hooks — обычные файлы репозитория внутри .claude/hooks/. Команда поддерживает их так же, как CLAUDE.md, skills и agents. Hook — процессный артефакт, а не «магия внутри Commerce OS».

Первый пример — format-on-edit:

// .claude/hooks/format-on-edit.json
{
  "event": "afterFileEdit",
  "matcher": { "paths": ["src/**/*.ts", "src/**/*.tsx"] },
  "handler": { "command": "prettier --write {{file}}" }
}

Читается как предложение: после редактирования файла, если путь попадает в src/**/*.ts(x), запусти formatter.

Второй — защита чувствительных зон:

// .claude/hooks/block-protected-paths.json
{
  "event": "beforeToolUse",
  "matcher": { "tool": "Write", "paths": ["**/payments/**", "**/.env*"] },
  "handler": { "command": "scripts/block-protected-write.sh" }
}

Event — «перед использованием инструмента записи». Matcher — «только если запись идёт в payments/ или .env*». Handler — «вызови защитный скрипт». Hook не делает проект умнее, он делает проект спокойнее.

Третий — баннер в начале сессии:

// .claude/hooks/session-banner.json
{
  "event": "sessionStart",
  "handler": { "command": "scripts/session-banner.sh" }
}
#!/usr/bin/env bash
echo "Проверьте git status и scope задачи"
echo "Если задача нетривиальная — начните с плана"

Один hook помогает с чистотой кода. Второй — с безопасностью. Третий — с дисциплиной начала работы. Все три устроены одинаково. Если научились читать один, умеете читать остальные.

Самый полезный навык: когда открываете hook-конфиг, не смотрите на него как на «ещё один JSON». Читайте как договорённость команды:

Когда произошло это, и только если совпало вот это условие, нужно автоматически сделать вот это действие.

Event отвечает «когда», matcher — «при каком условии», handler — «что сделать». Собранные вместе, они дают первый осмысленный hook в Workflow Kit. А какие задачи доверять hook, а какие он только испортит, и как раскатывать его по шагам — тема следующей лекции.

Что запомнить

  • Hook — отдельный слой автоматики внутри Claude Code, а не ещё один tool/MCP.
  • MCP — дверь наружу, hook — датчик и автоматика внутри дома.
  • Формула: hook = событие + условие + действие.
  • Три части контракта: event — когда, matcher — при каком условии, handler — что сделать.
  • Три группы событий: before tool use, after tool use/file changes, session lifecycle.
  • Before-hook — защитный контур; after-hook — реакция после действия; session hook — дисциплина и напоминания.
  • Matcher должен быть узким; широкий фильтр превращает hook в шум.
  • Handler — команда или скрипт, а не скрытый интеллект и не мини-платформа.
  • Hook не заменяет task spec, human review и tests.
  • В Workflow Kit hooks живут в .claude/hooks/ и читаются как процессные артефакты.
  • Если hook стал сложным оркестром или ему перестали доверять — инструмент выбран не тот.

Практика (15–25 минут)

Цель: спроектировать два hook-контракта для Workflow Kit, проверить узость matcher, предсказуемость handler и безопасный путь отключения.

Что сделать

  1. В вымышленном Workflow Kit создайте HOOK_CONTRACTS.md. Опишите два hook: format-on-edit для src/**/*.ts(x) и before-write guard для payments/ и .env*.
  2. Для каждого заполните три части: event, matcher, handler. Сформулируйте контракт одной фразой: «когда…, если…, сделать…».
  3. Для format-on-edit придумайте matcher уже, чем «все файлы»: укажите пути и типы, которые hook не трогает. Для guard опишите, что handler делает при попытке записи и как сообщает причину.
  4. Проверьте handler на предсказуемость и узкую пользу: нет ли цепочки на двадцать секунд, нет ли пяти ветвей и «мини-платформы». Запишите, когда hook лучше заменить отдельным script/tool/skill.
  5. Добавьте в HOOK_CONTRACTS.md путь отключения: как быстро выключить hook, если он шумит или блокирует лишнее. Проверьте, что нет реальных опасных команд и секретов.

Если Claude Code недоступен: выполните контракты и проверку вручную в редакторе; критерии проверки те же.

Проверка

  • В HOOK_CONTRACTS.md есть два hook-контракта.
  • У каждого явно указаны event, matcher, handler.
  • Format-on-edit ограничен src/ и нужными расширениями, а не всеми файлами.
  • Before-write guard ограничен чувствительными путями.
  • Handler описан как команда/скрипт с понятным результатом.
  • Указано, почему hook не должен становиться мини-платформой.
  • Есть путь быстрого отключения.
  • Нет реальных опасных команд и секретов.
  • Если Claude Code недоступен, контракты и проверка выполнены вручную по тем же критериям.
